1. **[P1] A failed saved-device bind recursively retries on the player queue.**

   [AudioPlayer+Devices.m:143](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:143), introduced by `d5016865`.

   The new synchronous snapshot path calls `selectSavedOutputDeviceOnQueue:` without setting `_pendingSavedDeviceLookupInFlight`. If the HAL refuses the bind, `rebindOutputOnQueueToDevice:` calls `resetToStoppedStateOnQueue`, which calls the resolver again before the original selection has returned or cleared its pending intent. The same published device is selected again, recursively. A persistent refusal can overflow the stack; even a transient refusal can produce repeated nested graph rebuilds. The asynchronous branch already holds the guard specifically to prevent this.

   The probe injected a refused output-unit bind and observed four nested attempts from one resolution. It cleared the pending intent on the fourth attempt to keep the test bounded. Expected: one attempt, then wait for a later recovery edge. Hold the same resolution guard across the synchronous selection, including failure cleanup.

2. **[P2] A later system-default notification can erase the device preserved by the unplug fix.**

   [AudioPlayer+Devices.m:89](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:89), introduced by `d5016865`; subsequent caller at [line 65](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:65).

   An unplug preserves the device for the first fallback announcement, then clears `_involuntaryFallbackUID` and `_involuntaryFallbackName`. A subsequent default-output notification calls `setOutputDeviceOnQueue:-1` again, even if the hardware binding is unchanged. That announcement has no fallback marker. `MainPlayerController` interprets it as a deliberate System Output choice and clears the persisted UID, name and model UID. The in-memory pending device may still exist, so the player and saved settings disagree; quitting before the DAC returns loses the preference again.

   The probe delivered device removal followed by a system-default change. The first announcement carried the missing UID; the second carried an empty marker. Preserve the fallback reason for the whole fallback period, until an explicit selection or successful re-adoption changes it.

3. **[P2] A model-matched return can override the destination's saved exclusive setting.**

   [AudioPlayer+Devices.m:116](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:116), introduced by `d5016865`.

   Every model match under a different UID unconditionally reads the old UID's modes. Persistence follows a different rule: `carryOutputModesFromDeviceUID:toDeviceUID:` keeps an existing destination entry. For example, port A has bit-perfect and exclusive on; port B already has bit-perfect on and exclusive off. Returning on B applies A's exclusive-on intent to the player, while the store and Settings retain B's exclusive-off preference. The delegate deliberately does not send modes back after a selection, so that disagreement is not automatically corrected.

   The corrected probe modeled those two mode records and observed `_exclusiveOutputWanted == YES` on B. Use one effective-mode decision for both the bind and persistence: an existing destination record must win before hardware is prepared or hogged.

4. **[P2] A saved bit-perfect device absent at launch cannot return automatically in that session.**

   [AudioPlayer+Devices.m:190](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:190). This is an incomplete edge of the re-adoption fix, retaining an older behavior rather than a wholly new regression.

   When launch resolution finds no device and bit-perfect is wanted, it clears all three pending identity fields before falling back. The new code preserves the on-disk choice, but later device-list notifications have no in-memory intent to resolve. Launch with the DAC powered off, then power it on: re-adoption requires another launch or a manual selection. This differs from an unplug after a successful bind, which retains pending intent.

   The probe resolved an absent saved device with bit-perfect enabled and confirmed the pending UID became nil. Retain the identity while disabling the unavailable mode; avoid immediate repeated lookups with the existing resolution guard and notification boundaries, rather than deleting the identity.

5. **[P2] Asynchronous quit allows an engine-stop completion to act as natural track end.**

   [AppDelegate.m:303](/Users/cmicali/projects/vibe/Vibe/Mac/App/AppDelegate.m:303), exposed by `bca6e9fa`; cleanup at [AudioPlayer+Devices.m:1516](/Users/cmicali/projects/vibe/Vibe/Audio/Mac/Devices/AudioPlayer+Devices.m:1516).

   `prepareForTermination` stops the engine without retiring `_segmentGeneration`, clearing an armed successor, or disabling later transport/recovery work. The new `NSTerminateLater` path keeps the application alive while cleanup and conversion cancellation finish. A segment completion caused by the engine stop therefore remains current and can reach `didFinishPlaying:`. The shell's handler has no termination check and advances to the next track when allowed. This can change the restored playlist selection or begin another play after output cleanup.

   The probe played only 4,096 frames of a two-second fixture, then invoked termination cleanup with a prepared-device obligation. It received one natural-end delegate callback before the test's simulated quit wait ended. This demonstrates the callback hazard in the real offline engine; it does not claim a physical A300 re-hog was observed. Retire transport work before stopping the engine and keep it retired throughout asynchronous termination, including outstanding opens and recovery callbacks.

**What the evidence does and does not establish about the remaining delay**

The beta7 attachment contains 26 first-render lines, all 47–58 ms after node play, and zero `USER MARK` lines. It contains one 252 ms player-queue stall at startup and three later main-thread stalls of 345, 655 and 284 ms. Darkside's preflight rejection is explicit. This supports fast measured starts in that recording, but does not establish that a reported lag coincided with any particular start, or that the DAC audibly emitted the samples at those times.

The `first audio out` probe derives a time from the player node's render clock; its audible-start estimate adds a separately decoded file's initial silence. It is not a loopback or an acoustic measurement. The silence probe also opens the URL directly on a global queue, outside the bounded file-loading path. That is an additional code-inspection concern for slow/provider-backed files: instrumentation should not introduce uncontrolled background opens. It was not exercised against a stalled provider here.

The next useful evidence is a symptom-correlated recording: exclusive on/off using the same files and device, marked lag times, and the matching stall stacks/render lines. If those remain fast during a confirmed audible lag, a loopback or acoustic recording would distinguish rendered progress from audible delivery. The available files do not justify declaring the remaining problem fixed or assigning it to the A300 firmware.
