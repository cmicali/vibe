# iOS channel and touch-driver verbs

The `debug-ios.sh` verbs iOS adds or answers differently, with their reply schemas — the shared verbs in `references/mac-verbs.md` (`play_index`, `check_consistency`, `dump_stats`, `dump_metadata_progress`, the cloud and loading verbs, `work_tally`) answer here too — the `drive-ios.sh` gesture verbs and their costs, the iPad path, and how per-session simulators and the build lock work. Read when driving the simulator beyond `dump_state`; `SKILL.md`'s "iOS: the simulator loop" carries the rules and traps.

## The channel

Same file protocol and one-JSON-object contract as the mac's, with **no CLI client**: the simulator app's container tmp is a plain host directory, so `debug-ios.sh` writes the command file and reads the reply, and the app's tmp watcher answers. Exit codes match the mac client (0 ok, 1 no response, 2 command error). Replies to action verbs are read synchronously and can lag pipeline work — follow with `dump_state`. App side: `Vibe/Debug/iOS/DebugCommands.m` over `Vibe/Debug/DebugChannel.m`; the cross-platform verbs live once in `Vibe/Debug/DebugCommonVerbs.m`.

```bash
S=.claude/skills/vibe-debug/scripts/debug-ios.sh

"$S" dump_equalizer      # references/equalizer-counters.md; set_equalizer_mode likewise
"$S" dump_audio_path     # a common verb: the render chain stage by stage, as on the mac minus the device stage (references/mac-verbs.md)
"$S" dump_now_playing    # {hasInfo, title, artist, duration, elapsed, rate, hasArtwork} — the mac verb minus playbackState
"$S" dump_view_tree      # {windows: [{class, frame, keyWindow, rootViewController, contentView: {…, subviews}}]} — UILabel text and button labels included
"$S" dump_art            # {currentIndex, window, held, pages: [{index, title, metadata, art, needsLoad, loading, inWindow, cellUp, waveformProgress}]} — the pager's art window; waveformProgress is a live page's scrubber position (null with no cell), which every page but the current one rests at 0; waveformFilled is the fraction loaded the page's latest waveform delivery carried (null before any delivery; a streaming decode tracks the download), waveformComplete whether it finished, and the top-level waveformTarget the page being decoded. The ONLY way to tell "not decoded yet" from "no art": both draw the vinyl placeholder. held past the budget, or a page landing with art:false, is the prefetch failing to keep up
"$S" dump_screenshot     # {ok, path, pointWidth, pointHeight, scale} — in-process render into the container; the HOST reads the path directly, no TCC. UIVisualEffectView blurs only approximate; `simctl io screenshot` is the ground truth
"$S" play_pause          # compact {ok, state, index, count, position, parked, playerPresentation}; also next, previous, and seek answers the same
"$S" seek 90             # seconds, through the scrubber's didSeek path, so the seek-in-flight guard behaves as a real release
"$S" set_pause_at_track_end on  # a common verb: {ok, pauseAtTrackEnd} — writes Settings > Playback > On track end and applies it at once (re-parks or drops the prefetched successor). Read back in dump_state.settings, beside crossfadeMilliseconds (the stored choice; player.crossfadeMilliseconds is what the player holds)
"$S" open <path>         # a file INSIDE the container (seed via launch-ios.sh); the FolderSession open-in-place path. Replaces the playlist, plays, AND expands the card
"$S" append <path>       # a common verb: the same file or directory ADDED to the end of the playlist instead of replacing it, through FolderSession.addURLs:. Nothing plays, the tab and the card stay put, and files already in the playlist are skipped. An Add onto an empty playlist is promoted to an open
# TRAP: BOTH of these take a path INSIDE the container, which is not security-scoped — the scope round trip goes unexercised — and the data container's UUID ROTATES on every install, so a path cached from an earlier run fails their existence check. Re-resolve it (simctl get_app_container … data) before each call
"$S" expand_player       # the card without a gesture; also minimize_player. The shell presents it only on an open, so this is the other way in
"$S" check_waveform_preparation refresh  # live regressions: refresh|transition|artwork|widget|interaction|work|work_inputs; {ok, measured checks}. Requires an expanded, paused local playlist with a prepared neighbor. Transition needs that neighbor offscreen; artwork also needs colored art. Refresh runs the bake refresh and the neighbor fetch and asserts zero filesystem probes (resets dataless diagnostics); transition checks that the arriving page shows the stored bake on one main turn, using an unobserved temporary playlist, then restores the live playlist without changing shuffle or FX; artwork discards and reloads the neighbor's display art and checks its prepared palette after one second; run it under the `album_art` waveform theme, the only one whose palette reads the art. Widget checks that a neighbor cannot overwrite the current offer; interaction checks track-change gesture cancellation, zoom publication and the final bake while keeping pixels; Work reports milliseconds for 1,000 partial deliveries and 10,000 transparent-image color reads, plus placeholder-color and nil-memo checks; it requires a complete current waveform. Work_inputs verifies that missing and partial current waveforms are rejected without changing their state. Run each on a freshly opened folder after file_cache has primed its waveforms.
"$S" set_waveform_zoom 0.12  # the DJ zoom, 0-1 = fraction of the track visible, through the delegate callback a released pinch takes, so it fans out across pages and persists. Replies {waveformZoomRequested, waveformZoomEffective}; they DIFFER when the layout cannot draw the depth asked — the only way to check the clamp
"$S" set_waveform_style wiggle_centered  # {ok, waveformStyle} — the persisted identifier, never the display name; an unknown one lists the valid set. Reads back as dump_state.settings.waveformStyle. TRAP: `wiggle` displays "Wiggle MC" and `wiggle_centered` displays "Wiggle"; both draw wiggles, so the wrong one looks right
"$S" set_fx_pad 0.8 0.5     # the FX pad's position through the model's funnel (x 0-1 left→right: reverb, then delay past 0.5; y 0-1 bottom→top: the low cut's cutoff), or `set_fx_pad off` for the lift. The pad itself does not draw for it — a real finger is drive-ios.sh's drag from the FX circle. Replies {ok, fx}; dump_state.fx is the FX intent, read without the player queue so it answers while that queue is held: stages.<lowKill|reverb|delay|shortDelay>.{intent, enabled, active, gateTarget} (intent is the low cut's cutoff in Hz or a send's level), delayTapBPM (the current track's tag or detected tempo, 0 = the 120 default) and unitRenders, which advances only while an effect is engaged or a tail rings; what the hosting says (connected, hostedUnits, sampleRate, tailSeconds) is dump_audio_path's fx stage. ui.fxPadShown follows Settings > Playback > Enable audio effects (dump_state.settings.audioFXEnabled), ui.fxPadEngaged a finger on a pad, on whichever page
"$S" set_output_route airplay "Living Room"  # draws the card's route indicator as any kind (none|speaker|receiver|wired|bluetooth|airplay|carplay|other), model untouched — the simulator reports the built-in speaker and nothing else. A page reconfigure or real route event overwrites it, so set it immediately before the check
"$S" select_tab playlist # or favorites, files, search (the UISearchTab circle)
"$S" dump_favorites      # {favorites: [{name, location, path}]} — the starred folders as the Favorites tab draws them; nothing is resolved, so a favorite on a dead path still lists
"$S" tap_favorite_star   # what tapping the star on the Playlist tab's bar does: toggles the open folder in and out of favorites. TRAP: the ADD is asynchronous (the bookmark is minted off main), so ok:true means the handler ran — poll dump_favorites for the row. Errors with no folder open
"$S" open_favorite 0     # index into dump_favorites.favorites; drives the row's own didSelectRow:, so the resolve, the open and the unreachable-folder alert are the tap's. Needs select_tab favorites first — the tab's provider is lazy
"$S" append_favorite 0   # the same row ADDED instead of opened: the screen's own openFavorite:appending:YES, so resolve and alert are the row action's. Same lazy-provider caveat
"$S" search zebra        # {ok, query, materiallyVisible, filesWalkRunning, sections:[{header, rows:[{text, secondaryText}]}]} — runs a query and replies once the table settles (the files half answers off a walk; materiallyVisible tells "no matches" from "the files half never ran"). The field takes KEYSTROKES neither this channel nor the touch driver synthesizes, so this is the only way to query. Needs select_tab search first
"$S" open_search_hit 0   # index into search.sections[1].rows (the Local section) — taps a FILE hit: it plays alone, a one-track playlist with the card up and the tab unchanged, as every file tap does; Play in Folder is its long press
"$S" dump_dropbox        # {linked, fake, accountID, accountName, accountPath, playlistTracks:[{dropboxPath, placeholder, stream}]} — the Dropbox account and which playlist tracks are still placeholders (iOS/Dropbox/AGENTS.md). stream is the transfer writing the file now, null when none: {size, writtenBytes, windowBytes (the tail window held, 0 once the download reaches it), readers (handles open on the part file)}. A REAL sign-in is Dropbox's own web sheet, which only a human can fill; the mirror itself is under accountPath in the app container
"$S" set_fake_dropbox <directory>|off [<transfer-seconds>]   # a directory on the HOST answers as the Dropbox account (VibeFakeDropbox.h: its folders are Dropbox folders, its files Dropbox files, each with a rev every answer's Dropbox-API-Result names, over the client's own HTTP boundary), linked at once with no sign-in and no network. A whole download takes about transfer-seconds (0 = at once) in 64 KB pieces, a resend from a Range is paced the same from its offset, and a closed range (a tag read, the tail window) answers at once; every answer, a 206 included, carries Dropbox-API-Result. Installing again over an installed fake swaps the tree and clears the faults and log WITHOUT rebuilding the client's sessions (VibeFakeDropbox.m's TRAP: the client keys downloads by task id, which restarts per session). The mirror is lazy: to open a folder no listing has made, mkdir its directory under accountPath and `open` it — FolderSession lists it from Dropbox first
"$S" fake_dropbox_fault <kind> [file=<basename>] [after=<bytes>] [seconds=<s>] [rate=<bytes/s>]   # one streaming road each, for that file or every file; bytes take K and M; replies {ok, faults}. stall (deliver up to after, then nothing until `fake_dropbox_fault resume`), drop (once: a lost connection at after → the client's Range resend), rev-change (once: as drop, and the resend names a new rev → FileChanged), throttle (once: 429 Retry-After seconds), expired-token (once: 401 → one /oauth2/token refresh), tail-fail (every tail read — the closed range of the file's last VibeAudioFileTailWindowBytes — 500s), slow-tail (every tail read answers after seconds), slow-tags (every other closed-range read — the tag parse's — answers after seconds, so it lands after the stream turned readable), rate (downloads paced at rate bytes/s: a WAV slower than its 176 KB/s bitrate, deterministically), latency (every files/download answers seconds late, a server's time to first byte, so a tail read sent after the download's first response would land a second first byte later). after defaults to 512K, past the readable mark. `clear` drops them all; set_fake_dropbox clears them too
"$S" dump_fake_dropbox   # {fake, requests:{endpoint: count}, downloads:{whole, resume, ranged, tail}, faults, transfers (the downloads delivering now), log:[{seq, t, file, kind, range, rev, status, delivered, outcome: running|stalled|complete|dropped|cancelled|answered}]} — the last 200 files/download requests, so "one tail read", "resumed at byte N with the same rev" and "the skipped track's transfer was cancelled" are numbers
"$S" dump_layout_anchors # {navigationBar, firstRow, tabBar, strip (each [x,y,w,h] in window points), contentOffsetY, adjustedContentInset, tabsSafeAreaInsets, topSafeAreaInsets (each [top,left,bottom,right]), tabsHidden, backdropScale, cardOffset} — where the selected tab's LIVE chrome sits. Under a moving card every one must hold still: what scales is a snapshot (iOS/AGENTS.md's backdrop TRAP)
"$S" sample_layout_anchors <seconds>   # records dump_layout_anchors on every display-link frame; then run a gesture through drive-ios.sh and read the series with dump_layout_samples {sampling, samples:[…]}. scripts/check-layout-stability.sh wraps the three and fails on any anchor that took two values — the layout-jump oracle
"$S" sample_frame_rate <seconds>   # a display link riding whatever rate the app's own work earns; dump_frame_rate answers {averageHz, frames, hitches (a frame that took two periods or more), worstIntervalMs, maximumHz}. The simulator caps at 60; on a PHONE launch with --frame-rate-probe and the same report lands in the log every five seconds, which --log-stderr relays — the only way to ask a device whether an animation got 120 Hz or hitched
"$S" dump_search         # {roots, folders} — the search scope. roots: the open BASE folder and every folder an append added, the folders added in Settings, the app's Documents, plus the STARRED folders once the search screen has been visited (FavoritesStore resolves their grants on that appearance); it is the composition before FileSearchIndex prunes nested and duplicate roots, so a folder can legitimately appear twice — re-appending the base folder is one ordinary way to see that. folders: just the added ones, the rows Settings shows
"$S" add_search_folder <dir>  # {ok, added, roots, folders} — widens the scope as picking a folder in Settings would; remove_search_folder <index into dump_search.folders>. The channel cannot drive the system document picker (another process's UI), so these are the only way to set a scope up. added:false = a persistent root already covers it, not a failure. NOT security-scoped — SKILL.md's trap
"$S" set_fake_cloud 4 100   # a common verb: references/test-audio.md
"$S" clear_caches        # blocks until both PINCaches are empty; waits its own 20 s window
```

The search screen's index lives in its view controller, so what a query matched is read from `dump_view_tree`: the playlist section's rows draw `displayTitle` (no extension), the files section's the filename over the containing folder.

## What the simulator cannot show

Interruptions (calls, Siri), route changes (headphone unplug), background audio past lock, and the lock-screen card need a real device; the `AVAudioSession` code runs but is not exercised faithfully. The card's route indicator draws and its picker opens on a tap — `dump_state`'s `ui.routePickerUp` flips — but the simulator offers no second route, so the sheet shows nothing and AVKit never sends the did-end edge; only `set_output_route` shows the off-device renderings there. Per `SKILL.md`'s simulator-only rule, report these as unverified rather than driving a phone.

## The touch driver

`drive-ios.sh` executes gestures through the resident `VibeiOSDriver` XCUITest (`Tests/iOSDriver/`, not part of `VibeTests`) over the same file protocol — the only sanctioned touch-synthesis path on iOS. Its header comment lists every gesture verb and its arguments.

- **Latency**: ~0.7 s per gesture, the first included; `start` is ~10 s once the driver is built. XCTest reads only an app it launched or activated, so the driver activates the player on its first gesture and on `attach`, which `launch-ios.sh` sends after every relaunch while a driver is up. TRAP: without that, a gesture against an app launched outside the driver retries snapshots for 60 s and then relaunches the app itself, playlist gone and without the silencing flags; after a relaunch by anything other than `launch-ios.sh`, send `drive-ios.sh attach`. The runner disables XCTest's per-event quiescence waits (a playing app never idles under Vibe's display link; without this every gesture costs ~2 minutes); that reaches XCTest internals, harness-only, and degrades to slow-but-working if an Xcode update renames them (`Tests/iOSDriver/VibeiOSDriverTests.m`).
- `springboard tap|press|drag|type|tap_label|tree …` targets the Home screen and widget gallery using the same gesture arguments; ordinary gestures return to Vibe. `tree` reads the accessibility hierarchy; `tap_label` activates an exact label or identifier (quote labels containing spaces). Start with `VIBE_SIGN_SIM=1` for widget captures so the driver build preserves the app-group entitlements.
- Run `start` before `launch-ios.sh` so the app it launches is the one the driver attached to; either order installs correctly, this one skips a relaunch. If the app is dead, the next gesture relaunches it with the silencing flags.
- One session per DEVICE: `start` kills only this device's previous driver.
- `pinch scale velocity` is the one element-targeted verb — XCUITest has no coordinate multi-touch, so it finds the scrubber by accessibilityIdentifier and needs the card expanded.
- `type "key"` is how the keyboard is driven: it sits in a window of its own, so a tap aimed at a key hits the app BEHIND it.
- `input.swift` clicks on the Simulator window are obsolete for this.

## Staleness: `install-ios.sh`

`install-ios.sh` is the single home of "the installed app matches the built one"; `launch-ios.sh` and `drive-ios.sh start` both call it, and it installs only when the bundles differ, which is what makes it safe with a driver session live. `xcodebuild test` leaves the app-under-test on disk without installing it, so `start` installs after the build finishes, never before. `drive-ios.sh status` reports `appStale` as the backstop, since a driver session outlives any number of rebuilds. Staleness is decided by hashing every file of both bundles (~80ms), never by mtime: a `make strings` run counts, a relink that changed nothing does not — every xcodebuild run relinks the executable even when it compiles nothing, so an mtime rule fired for every other session in the checkout whenever one built.

**TRAP: `drive-ios.sh start` launches nothing.** It installs the built app when it differs, which kills a running one, and returns with no app up, so a channel poll right after it waits out its timeout on every call. Follow it with `launch-ios.sh`, whose `attach` hands the driver the app it just launched: the first gesture then lands in about a second on that same process, and state set before it — a selected tab, a fake Dropbox, a pushed screen — survives. No warm-up tap.

## Per-session simulators and the build lock

`sim-udid.sh` names the device `Vibe-<dir>-<hash>` from the checkout path plus `CLAUDE_CODE_SESSION_ID` (one stable device per checkout outside Claude Code). Each session therefore has its own app container, debug channel and touch driver (command dir `build/ios-driver/<UDID>`, session kills scoped to that device). Stale devices from ended sessions are GC'd on every `sim-udid.sh` call (Shutdown and untouched for 12 hours). `VIBE_SIM_UDID` pins a device; `VIBE_SIM_NAME` renames.

What same-checkout sessions share is `build/DerivedData`, `Vibe.xcodeproj` and the one built `.app`, so builds and installs are serialized by `scripts/build-lock.sh`: `drive-ios.sh start` holds it across `xcodegen generate`, the `xcodebuild test` build and the install, and drops it once the runner is up. Unlocked, `xcodegen` rewrites the project under another session's live `xcodebuild`, two builds clobber one products directory, and `simctl install` copies a bundle another session's linker is midway through writing. A stuck lock is `build/.build-lock`; it names its holder's pid and is broken automatically once that process is gone. A caller left waiting says so once on stderr, with that pid, so the wait is not mistaken for a hang.

## iPad

The target is device family `1,2`; the app is a resizable iPadOS 26 window (min 320×200, `VibeiOSSceneDelegate`, though iPadOS holds windows at least about 486pt tall): wider-than-tall shows the landscape layout, taller-than-wide the portrait one, and a window under 600pt tall the card's compact layouts — the strip once it is twice as wide as tall (`Player/AGENTS.md`). `sim-udid.sh` models iPhones only, so `xcrun simctl create` an iPad and export `VIBE_SIM_UDID`; all three scripts honor it. `drive-ios.sh rotate left|right|portrait` flips orientation (there is no simctl rotation); assert from `dump_screenshot`'s `pointWidth`/`pointHeight` and check the current track index survived. iPadOS windowed mode (floating windows, corner-drag resize) is enabled per device in Settings → Multitasking & Gestures; a fresh iOS 27 iPad simulator starts in it. The iOS Simulator control tool's `touch_path` drags the resize corner (hold ~0.6 s first), in the framebuffer's portrait device points even when rotated; read the result from `dump_screenshot`'s `pointWidth`/`pointHeight`, since the screen draws a window scaled down. TRAP: in a rotated, windowed scene `drive-ios.sh tap` reports ok and lands nowhere — tap with the same tool, aimed from its screenshot.

## Streaming scenarios

`scripts/dropbox-streaming.sh [-o <out-dir>] [-j <simulators>] [scenario ...]` drives the Dropbox streaming feature end to end over the fake: every format streaming (`stream-wav`, `stream-flac`, `stream-m4a`, `stream-m4a-moovlast`, `stream-mp3`: plays before a quarter of the transfer, the loading bar moving and ending complete, a placeholder until complete, one tail read with its format's window held (`VibeAudioFileTailWindowBytes`), the playing track's tag read making at most one request, the waveform filling with the download and none for the neighbouring page), `seek` (back at once, ahead waiting for the download), `skip` (the old transfer cancelled), `pause-replay`, `buffering` (a `rate` slower than the bitrate: holds, one resume each, the position still), `stall` (Connection lost at a shortened deadline, then resume; a stall lifted in time releases), `small-mp3` (3 MB, over the small window's 256 KB floor, so it streams), the format that cannot stream (`stream-adts`), `seek-ahead-mp3`/`-flac`/`-m4a` (the position reads the target at once and holds, buffering, until the download reaches it), `quick-skip` (a skip 0.3 s after the open still cancels the transfer), `gapless` (a streaming successor armed and promoted with one download), `pause-buffering`, `scrub-buffering`, `sign-out` (the account change clears the playlist, the same `clearPlaylist` as Clear Playlist), `reupload` (the host file changed between listing and play: the fake's rev follows size and mtime, and the new version installs), and one scenario per fault (`drop`, `throttle`, `expired-token`, `rev-change`, `tail-fail`, `slow-tail`, and `latency`: every answer 1.5 s late, the tail asked with the download and the MP3 open about one first byte in). `stream-mp3-noxing` is an MP3 with no Xing/Info frame, which streams on a length estimated from its head's frames (`Audio/AGENTS.md`). Each opens a fresh fixture folder of APFS clones transcoded once from `tone-long.wav` into `build/streaming-fixtures`, writes every poll to `<out-dir>/<scenario>.jsonl` and the measured numbers and failed checks to `summary.json`, and exits nonzero on any failed check. A poll is one `debug-ios.sh --all` round trip every quarter second, so a buffering hold of half a second is seen rather than missed. The default run spreads the scenarios over three simulators, this session's and two it boots, launches and shuts down after (`-j N`; `-j 1` for this one alone; `VIBE_STREAMING_KEEP=1` leaves them up), each taking the next unclaimed scenario, longest first: about two and a half minutes for all, six on one simulator; run it after `launch-ios.sh`. It replaces the playlist and leaves `set_audio_loading` at its defaults.
