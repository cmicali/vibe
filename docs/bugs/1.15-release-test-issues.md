## 3. R1 — incorrect PCM after a Mac bit-perfect rate switch

### Observation and impact

The corrected full acceptance run passed **31 captures**, then failed `after-rate-switch` after a playlist crossed from a 44.1 kHz track to a 48 kHz track.

This is a **fresh capture of a replay after the switch settled**. It is not a claim of uninterrupted capture across the hardware rate change. A hardware transition can interrupt a capture; the verifier deliberately starts another replay/capture to test the destination format independently.

The nominal, physical, and virtual device formats reported 48 kHz. Instrumentation later read both AudioUnit stream formats as 48 kHz too. Playback state reported bit-perfect active, exact rate, matching channels, acceptable depth, pitch zero, playback rate 1, volume 1, declick off, and no FX. The source consumed its 96,000 frames in roughly 1.84 seconds.

The length and correlation are consistent with unintended rate conversion somewhere across the application/AudioUnit/virtual-driver boundary. **They do not identify which layer caused it.** There is no basis yet to claim every physical DAC fails, but the repeated PCM mismatch must not be dismissed as a successful bit-perfect path merely because its status says active.

The offline JSON also contains an original-reference correlation of `NaN` with an invalid wraparound lag. That field is not useful evidence. The resampled-reference correlation is a diagnostic comparison, not an exact-PCM acceptance result.

### Reduced test method

The reduced verifier is copied from the normal verifier, retaining its capture and comparison machinery. Its focused loop at `OUT/verify-rate-switch.swift:718–745`:

1. Enables bit-perfect output.
2. Opens a two-track playlist: `noise-44100-16-2.wav`, then `noise-48000-24-2.wav`.
3. Requires the first track to start active.
4. Waits up to six seconds for the second URL, a positive position, and reported 48 kHz.
5. Fails if a gapless splice is armed across the hardware rate change.
6. Requires the actual nominal device rate to be 48 kHz.
7. Captures a fresh playback of the 48 kHz file and applies exact comparison.
8. Repeats ten times, or fifty in the longer derivative, and performs cleanup.

Core excerpt:

~~~swift
let first = fixture("noise-44100-16-2.wav")
let second = fixture("noise-48000-24-2.wav")
_ = debug(binary, ["set_bit_perfect", "on"])
for iteration in 1...10 {
    report(["rateSwitchIteration": iteration])
    _ = debug(binary, ["open", playlistPath([first, second])])
    started(first, active: true)
    let deadline = Date().addingTimeInterval(6)
    var switched = false
    repeat {
        let state = debug(binary, ["dump_state"])
        let live = state["player"] as? [String: Any] ?? [:]
        if (state["currentTrack"] as? [String: Any])?["url"] as? String == second,
           (live["position"] as? Double ?? 0) > 0,
           (live["bitPerfect"] as? [String: Any])?["sampleRate"] as? Double == 48000 {
            switched = true
            report(["case": "rate-switch-boundary", "player": live])
            break
        }
        guard live["gaplessArmed"] as? Bool == false else {
            fail("a hardware rate switch armed a gapless splice")
        }
        pause(0.02)
    } while Date() < deadline
    guard switched, nominalRate(device) == 48000 else {
        fail("track boundary did not switch to 48 kHz")
    }
    captureCase("rate-switch-\(iteration)", "noise-48000-24-2.wav")
}
~~~

### What the stacks establish

The output queue was in Apple's RemoteIO stop RPC when it aborted. The player queue was waiting for the output queue's stop to finish. The main thread's debug consistency snapshot was waiting on the player queue. Other audio threads were waiting during host-device startup/default-device aggregation and format reconnect.

This establishes a blocked dependency chain, **not a demonstrated circular lock dependency entirely within Vibe**. The main-thread debug wait explains the unresponsive channel; it does not by itself explain the RemoteIO failure.

An abort in Apple code is not enough to conclude “Apple bug, safe to ship.” An application lifecycle sequence can trigger a framework failure, and the shared host environment can also matter.

Relevant current source:

- `Vibe/Audio/iOS/AudioPlayer+Recovery.m:43–44`: `releaseIdleOutputUnitOnQueue` waits for the output stop.
- The adjacent `TRAP` explains why: deactivating the audio session while RemoteIO is still running cuts the output. Removing the wait without preserving that order would break an existing guarantee.
- `Vibe/Audio/AudioPlayer+Pipeline.m:1232–1267`: idle-stop scheduling and callback.
- `Vibe/Audio/AudioPlayer.m:213–218`: `runSyncOnQueue:`.
- `Vibe/Audio/AudioOutputUnit.m:330–352` and `525–528`: queueing/waiting/actual stop.

### Comparator methodology

The verifier compares finite float32 bit patterns without error tolerance, including the sign of zero. It checks the source channels in order, rejects missing/repeated markers, short recordings, overflow, unexpected pre-source/tail samples, and non-silent unused output channels. Approximate alignment is diagnostic only and cannot earn `exact:true`. Native reference precision exceeding the decoder's float32 precision is rejected rather than comparing two equally truncated decodes.

The documented **first 50 ms startup/resume fade is excluded** from the bit-perfect claim. Nonperiodic markers and the full remaining reference are mandatory. Self-tests cover alignment corruption, gapless seams, one-bit changes near inclusion/EOF boundaries, channel delay/crosstalk, sample extremes, invalid inputs, multichannel arrays, and contamination of output channel sixteen.

Neither this fade exclusion nor a successful fresh capture establishes uninterrupted exact PCM across a hardware rate switch.

### Isolated baseline and narrower cause

### Rejected follow-up experiments

1. **Reset after initialization.** A Mac-only `AudioUnitReset(..., kAudioUnitScope_Global, 0)` after successful `AudioUnitInitialize` passed a ten-iteration run. The longer run failed on iteration 6, with **88,229 audible frames**. It still created the wrong-rate converter. The reset is removed. 2. **Poll the unit's output format before initialization.** Waiting until AUHAL's output-scope bus-0 sample rate matched the requested input rate passed **50/50** exact captures and eliminated the wrong-rate converter in the sampled logs. Its observed waits were roughly 50–75 ms early in the run. The polling interval was **5,000 microseconds = 5 ms**, with a 1.5-second deadline, on the output unit's queue. This was rejected as a production design and removed, despite passing PCM. Its evidence remains useful for locating the race: `candidate-wait-format-*` and `rejected-wait-format.diff`. **Do not reintroduce this wait as an accepted fix.**

### Current candidate: replace the HAL component during format configuration

`AudioOutputUnit.m` now has one shared component-construction function, `VibeCreateOutputUnit`, used for initial creation and Mac reconfiguration. It installs output/input enablement and the render callback, and handles a failed setup by disposing the partially made component. In `halConfigureFormat:renderProc:refCon:`, the Mac creates a fresh HALOutput component and binds it to the already selected device before configuring the client format and initializing. The old component is disposed after the replacement is successfully created and bound. The iOS RemoteIO component is not replaced by a format change.

This keeps the existing `AudioOutputUnit` object, its serialized HAL queue, render state, counters, channel-map publication, failure handler, and run generations. That distinction matters: the earlier overnight experiment replaced the whole wrapper and failed its active-playback check; this candidate replaces only the underlying AudioUnit. Its purpose is to start with the device's current format instead of reusing a component whose asynchronous format notification has not arrived.

There is **no new polling loop, notification waiter, retry timer, or delayed-start state**. Configuration still happens in the existing ordered HAL work, and a failed creation, bind, format write or initialization follows the existing configure/start refusal path. Stop closes the render gate immediately; a queued start checks its run generation before opening that gate. A later configuration follows the earlier one on the same queue.

**Timeout scope remains explicit:** AudioComponent creation, binding, disposal and initialization are synchronous CoreAudio calls. This candidate does not make a hung CoreAudio call cancellable or solve R3. Do not claim that every output operation is now bounded. Any future design that adds a notification wait must separately handle its deadline, stop/replacement/device/shutdown invalidation, and late delivery; the discarded polling experiment did not supply that design.

### Cancellation and regression coverage

`Tests/OutputFormatRulesTests.m` adds `testAConfigurationFinishingAfterStopReplacementOrShutdownCannotStartObsoletePlayback`. It holds the configuration boundary with a controlled semaphore while exercising the production queue and generation handling, then releases it after:

- Stop: no hardware start is permitted and the gate remains closed.
- Replacement configuration: only the latest 48 kHz start is permitted; the superseded 44.1 kHz start never reaches the hardware boundary.
- Shutdown (`markDead`): no hardware start is permitted and the gate remains closed.

The controlled waits use the suite's hang/gate timeout constants. The hardware boundary is replaced for this deterministic test; it does not pretend to prove the CoreAudio converter itself. The real loopback is the PCM oracle. Existing tests also cover a stale queued start, late start refusal attribution, a refused device bind, dead-unit start suppression, failed output startup, stopped/restarted playback, and a source rebuild with a render held in flight.

## 16. R3 follow-up: synchronous HAL notifications deadlock Vibe's event logger

### Conclusion and scope

The isolated reproduction establishes a Vibe-side callback-ordering bug in the macOS beta diagnostic logger. A running-state notification reaches the listener synchronously on CoreAudio's IO thread. Vibe then reads a HAL property inside that listener, waiting on a HAL lock while another HAL thread holds the command gate and waits for the IO thread to stop. The same first volume-read fault from R3 produces repeated 13–28 second output-stop/UI stalls. Returning from the callback before doing the property read removes those stalls in the controlled comparison.

**This fixes the demonstrated listener lock cycle; it does not prove the original six-minute `AudioUnitInitialize` RPC hang had that same cause.** That original sample shows a server RPC wait, not this IO-thread/property-read cycle. The original host had already experienced repeated audio failures before PID 38581 launched. Do not erase the historical incident, mark R2 solved, or describe every synchronous CoreAudio call as bounded because this reproduction now passes.

The affected logger is behind `VIBE_VERBOSE_LOGGING`, not `DEBUG`. Both comparison apps explicitly enabled it. The mechanism was introduced by `b47042e3bfe06f7d936c4e72fbd2a3f5104c7019` (2026-09-21), and the same inline-read listener is present in the `v1.14` tag. Thus this demonstrated bug predates 1.15; that source history is not a runtime reproduction of 1.14 and says nothing about builds with the logger disabled.

### Fix, lifetime, and interruption behavior

`AudioDeviceManager.m:353` now registers and unregisters event-log listeners with a NULL delivery queue. `CoreAudioUtil.m:673` owns the single callback factory used by system, device and stream logging. Each callback copies each `AudioObjectPropertyAddress` by value, queues its read/log on the existing serial `_eventLogQueue`, and returns. Merely adding an async block while still registering `_eventLogQueue` would be insufficient: a later synchronous IO notification could wait behind a previously blocked read on that queue.

No player, track, output unit or mutable watch record is captured by the deferred work. It captures the numeric object ID, name, address, queue and utility class; it emits a diagnostic only. Removal or a new track can leave an old diagnostic queued, but that diagnostic cannot restart playback, change the current device, install a result or release an output unit. A disappeared object can yield an unreadable property in the log. Logging values are observed when the queued read runs, not snapshots of the property at notification time.

There is no new waiting state, timeout, poll loop, timer, cancellation flag or teardown drain. Neither the listener nor playback waits for the logging queue. An OS property call can still block that queue; this change does not cancel it or bound all HAL API calls. Playback's existing request/generation and timeout behavior is unchanged. No sleep or delayed initialization was added.

The change consolidates three duplicated listener bodies into one existing utility class. It adds no files, types, fields or timers. Production code has **5 net added lines**; the review's total including tests and the handoff is recorded in the PR.
