# Dropbox (iOS)

Dropbox through its HTTP API, not its Files provider. The provider lists a folder only once Dropbox has, so search and browsing came back empty or stalled. There is no SDK: a handful of endpoints over `NSURLSession`, all Objective-C. This directory has no UI. The shell that draws the account is `Vibe/iOS/AGENTS.md`. The mirror is a remote fetch backend (`Loading/AGENTS.md`), which `VibeiOSAppDelegate` installs at launch with `installAsRemoteBackend`, beside the Links store.

| File | Owns |
| --- | --- |
| `DropboxClient` | The account: PKCE sign-in in `ASWebAuthenticationSession`, the refresh token in the Keychain, the access token in memory, and the JSON call. It subclasses `HTTPTransferClient` (`Loading/Net/AGENTS.md`), which runs the streamed download and the ranged read. This class makes their requests and reads Dropbox's answers. All three share one failure ladder (`handleFailureStatus:…`): an expired token refreshes once, any other 401 unlinks, and a throttle waits and resends. |
| `DropboxMirror` | The account as local files: listing reconciliation, the sidecars, search and the path mapping. It subclasses `RemotePlaceholderStore` (`Loading/Net/AGENTS.md`), which owns the placeholders, the directory index's storage, the streaming fetch, the ranged read and the download budget. This class names each placeholder's Dropbox `id` and reads Dropbox's answers. |
| `DropboxRules.h` | The decisions with no network or disk: PKCE, the wire encodings, entry reading, the version check, the index key. Tested. |

Both classes are Foundation-only and compiled into the macOS `VibeTests`, which drive them over a stubbed `NSURLProtocol` and a temp root (`DropboxMirrorTestCase` and its subclasses).

## The account

**The app key is `VibeDropboxAppKey` in the generated Info.plist** (`project.yml`). It is not a secret: PKCE needs none, and Dropbox grants every app the `db-<key>://2/token` redirect without registration. Scopes: `account_info.read files.metadata.read files.content.read`. The app must be a **Full Dropbox** app, since an App folder one sees nothing.

**The App Console app is in development status.** Dropbox accepts a production request only once an app has 50 linked users, and development status links users up to that count. So production is never a release blocker. Apply in the App Console as linked users approach 50.

**The refresh token is one Keychain item, `AfterFirstUnlockThisDeviceOnly`.** A refresh must work under the lock screen while background playback downloads the next track. A backup restored on another phone signs in again. **TRAP: before first unlock the item reads as locked (`errSecInteractionNotAllowed`), not absent.** Read as absent, the whole session would run signed out. The client remembers the lock and reads again at the next use (`isLinked`, `accountID`, any call), at most once every `kAccountLoadRetryInterval`, and posts the account change when it lands. Nothing is deleted at launch, only on a real account change.

**TRAP: the default simulator build cannot reach the Keychain.** It is unsigned, so every `SecItem` call answers `-34018` (`errSecMissingEntitlement`). Sign-in works for the session, but the refresh token is never saved, and the next launch is signed out. Build with `VIBE_SIGN_SIM=1` to test anything across a relaunch (the `vibe-debug` skill). A device build is always signed.

**A scope the app lacks answers 400 with plain text, not JSON**, naming the scope. The client logs that body, and a sign-in logs the scopes it was granted. A scope enabled in the App Console reaches only grants made after it, so sign in again.

**One refresh is in flight at a time.** It is the refresh claim, and every caller arriving during it is a waiter on it. `_accountGeneration` moves on every sign-in and sign-out, so a refresh or a 401 from the previous account can neither restore nor unlink the current one. **TRAP: a Keychain save checks its generation inside the Keychain lock**, which a delete also takes. Delete-then-add is two calls, and a sign-out between them left the signed-out account linked at the next launch. A late answer to the account-name call cannot stamp its name and id on the next account (`refreshAccountNameWithCompletion:`), and the mirror's directory is the id. A 401 `expired_access_token` refreshes once and retries. Any other 401, and a refresh answered 400 (`invalid_grant`, revoked on dropbox.com), unlinks. Unlinking posts `VibeDropboxAccountDidChangeNotification`. The mirror then prunes every other account's directory, and `PlaybackController` clears a playlist reaching into the mirror, whole, as Clear Playlist does. Signing out revokes with a live access token, refreshing an expired one first, so the grant ends on Dropbox's side too. A cancel's rules are the base's (`Loading/Net/AGENTS.md`).

**The launch warms the account once** (`warmUp`, off main). With an account it refreshes the access token, which lives in memory, so a launch's first request would otherwise refresh. It also sends each session one `files/download` naming no file, refused at once, to open the connection to `content.dropboxapi.com`. A session's connections are its own, and the download and its tail ride different sessions. This takes the refresh and two TLS handshakes off the first play. It never runs on a foreground, or before first unlock.

## The mirror

`Library/Application Support/Dropbox/<account id>/`, excluded from backup and outside Documents, so the Files app never shows it. **It is lazy: a Dropbox folder exists here only once something listed it.** The browser lists on every visit, a search hit lists its parent before it opens, and an open lists a folder nothing has listed yet (`FolderSession`'s `listFromDropboxIfMirrored:`, which asks `hasListedDirectory:`). A folder its parent's listing made carries only its path in its index. One listed itself carries its files. There is no full sync, and search is Dropbox's. **TRAP: a directory a reconcile deletes takes the cached indexes with it** (`reconcileDirectory:`). Kept, a folder that leaves Dropbox and comes back is made empty, still reads as listed, and its open plays nothing. **A folder made on the way to a search hit takes the hit's `path_display`**, never `path_lower`, or the browser and the playlist title name it in lowercase.

- **A placeholder is a sparse file of the remote size and `server_modified` with no permissions.** How it is written is the store's (`Loading/Net/AGENTS.md`). **Size plus mtime is the version.** Dropbox moves `server_modified` on every upload, and downloaded bytes take the mtime from their own response's `Dropbox-API-Result`, so the next listing sees them as current. A version that differs goes back to a placeholder, and a departed entry is deleted.
- **Only playable audio and playlist files (`.cue`, `.m3u`, `.m3u8`) are mirrored.** The playlists download with the listing, off the disk queue, since `rowsForWalk:` reads a sheet while the folder opens and a tap on an M3U reads it at once. **TRAP: one download per sheet** (`_sidecarWaiters`, the claim). Two refreshes of one folder both find the sheet missing and share its part file. The first to finish would rename the other's half-written bytes into place, so a refresh that finds the sheet claimed waits on that download.
- **TRAP: a name read back from disk is never sent as a Dropbox path.** A file URL's path comes back decomposed (NFD), while Dropbox keeps names as uploaded, usually composed, so a derived path misses every accented file. Each directory's index (the store's xattr) holds its own Dropbox path and each file's Dropbox `id`, keyed by `VibeDropboxIndexKey`. A download goes by `id:…`, which also survives a rename (`remoteTargetForURL:error:`). A relisting goes by the directory's recorded path.
- **TRAP: only the last component of a `path_display` is guaranteed its case.** So a component is matched case-insensitively against what is on disk (`VibeDropboxLocalName`) before one is made, and two spellings of one folder land in one directory. The match lists the directory rather than probing. On a case-insensitive volume an `lstat` of another spelling succeeds, and the URL would carry that spelling.
- **The fetch streams into a hidden part file**, and the progress poll reads the transfer's own written count. A Dropbox row's loading bar is therefore a real percentage. The fetch, its stream and its tail window are the store's.
- **The part file's rules are `HTTPTransferClient`'s** (`Loading/Net/AGENTS.md`): made once, only appended to, resent from its last byte, pinned to its first response's version, and kept when the link ended the transfer. For Dropbox the version is the `Dropbox-API-Result` `rev`, and the size is its `size`. A download by `id` answers whatever version is current, so the pin stops two revs splicing into one file. A mismatch fails the transfer with `VibeDropboxErrorFileChanged`, and a length other than `size` with `VibeDropboxErrorAPI`. `keepsPartAfterError:` keeps the part for a cancel (how a stall lets a stream go) and for a connection lost past the resend bound. The stale sweep takes a kept part after a day. **TRAP: the stale-part sweep goes by ctime, never mtime.** The install dates a finished part to its version just before the rename, and a relisting between the two would delete it.
- **A Dropbox stream's tail is read by id, like its download.** The store installs the tail window only when both answers name the same rev (`Loading/Net/AGENTS.md`). The tail read starts with the download, not after its first response. So a file that needs its tail to open (an MP3's last 128 bytes, an M4A with `moov` last, a FLAC with no length, an AIFF or WAV with a tag after its audio) opens from the head. A longer index-last M4A, or a tag larger than the window, waits for its download.
- **Tags are read by range, never by download.** The rule and a streaming file's shortcut are the store's. The metadata scan parses a placeholder through TagLib reading `files/download` with a `Range` header, about three requests a file with its artwork. Only playing and the prefetch of what plays next download a whole file. So does the scan's read of a format TagLib cannot parse (`PlayableExtensions.tagParsed` excludes w64 and caf), whose CoreAudio facts need the whole file. A row that lost its art rendition reads it by the same rule (`PlaceholderFiles readsRemotePlaceholderByRange:`). One known gap: a FLAC whose STREAMINFO has no length parses with no duration, since the fallback that measures it opens the file.
- **Past the download budget the oldest downloads go back to placeholders** (the store's eviction). The budget counts the linked account's directory. The user chooses it in Settings › Files and Dropbox › Maximum Size (`kVibeDropboxDownloadBudgets` in `DropboxRules.h`). Settings saves it under `VibeDropboxDownloadBudgetKey`, which the mirror starts from, then sets `downloadBudget`. A smaller budget applies at once and posts the new total as a download's landing does. Size and mtime are kept, so the cached tags and waveform still match, and the card draws an evicted track's cached waveform while parked (`Vibe/iOS/Player/AGENTS.md`). A player still reading an evicted file keeps its open descriptor. Remove Downloads does the same to all of them.

**The simulator needs no account.** `set_fake_dropbox <directory>` (`Vibe/Debug/iOS/VibeFakeDropbox`) puts that directory under the client as the account, over the same HTTP boundary the tests stub. Every case this doc's traps describe is a scripted tree there. `fake_dropbox_fault` scripts the streaming cases, and `vibe-debug`'s `dropbox-streaming.sh` runs them as scenarios. `dump_dropbox` reads the account and which playlist tracks are placeholders. The real sign-in is Dropbox's web sheet, which only a human fills.

Opens are the shell's ordinary roads. A mirror directory is an app-container URL with no security scope, which `FolderSession` treats as a root every open covers. A file opened alone becomes its folder with it selected, bookmarks persist, and a relaunch restores from the placeholders offline.
