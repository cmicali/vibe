# Loading: from a path to a readable file

Everything between a path and a usable `AudioFileHandle`, which the audio core owns. Both apps compile this directory.

| File | Owns |
| --- | --- |
| `AudioFileMaterializationCoordinator` | the claim |
| `AudioWorkScheduler`, `AudioWorkAdmissionRules.h` | admission |
| `AudioLoadingConfiguration` | the immutable limits and the open-timeout seam |
| `AudioFileOpenRules.h`, `AudioFileOpenTimeoutMath.h` | the decisions, among them the tail window a stream fetches for an open that reads a file's end, and `VibeMountReadsAhead`, the rule for which files read ahead |
| `CloudTransferRegistry` | which files are on the wire |
| `DownloadProgressMonitor` | how far one transfer has come, for the registry |
| `CloudFileMaterializer` | the abortable download of a placeholder, a provider's or a remote one |
| `Net/` | files the app fetches itself over HTTP. Its doc is `Net/AGENTS.md` |

The player's side of an open is `Audio/AGENTS.md`'s. That is the deadline, progress identity and prefetch. The sweep's retries against the foreground hold are `Audio/Metadata/AGENTS.md`'s. Three root `AGENTS.md` guarantees are implemented here: the foreground open outranks background downloads, the six-run handle ceiling, and a row shows the loading bar only while a transfer is running.

## One claim, two stages

**A file's journey from dataless placeholder to handle is one path-keyed claim in two stages.** Stage 1 is the one operation that can make a standardized path local; Playback, Prefetch and the two metadata roles affect admission, never identity. Stage 2 is the purpose-keyed handle runs riding it: one current handle waiter per `(purpose, path)`, so playback and prefetch keep independent handles and delivery while sharing the path's transfer. Only a stage-1 Ready or readable claim dispatches a handle open; Yielded, AdmissionExhausted and Failed become terminal outer errors without touching CoreAudio. `AudioFileOpenRules.h` holds the decisions: `VibeAudioFileOpenBeginDelivery` and `VibeAudioFileOpenDetachDelivery` are the two sides of the race for the one Waiting transition, whichever changes it first owns the outcome, and `VibeStandardizedAudioOpenPath` is the one spelling every claim is keyed by, using `VibeComparablePath` without filesystem I/O. **TRAP: `URLByStandardizingPath` stats the target**, so it can stall the player or state queue before the bounded probe begins; compare spelling alone.

**The stage-1 state queue owns in-memory claim state and performs no filesystem or provider I/O.** A first waiter synchronously installs a `Probing` claim, then one private `AudioWorkScheduler` classifies the path off-queue; same-path waiters join and share the probe. A fresh answer starts an immediately admitted claim; a dataless claim that had to wait or be readmitted enters `Refreshing` after reserving its lane, re-probes in that admitted worker, and becomes `Running` only when state accepts the fresh answer. The successful paths are therefore `Probing → Running` and `Probing → Pending → Refreshing → Running`, and dataless readmission routes through `Pending` or `Refreshing` likewise. **A fresh local answer is the run's answer**: an initial probe's settles the claim Ready in the next state turn with no operation, lane or worker, and a start refresh's settles it from that worker without running the operation it made; a local verdict carried from an earlier run is not fresh, and runs an operation that probes again, since the file may have been evicted since. Object identity drops a result from a cancelled or replaced probe, and a ready operation records the path local before any cancellation or rebind restart decision.

The accepted dataless verdict is reported through `onDataless` at most once per open token, on its completion queue and only while delivery is still waiting. Joining an already-classified claim or rebinding a handle run reports it too. Rebinding cancels the superseded token, dropping its queued callback.

**A remote transfer is readable before it is complete, and readable is a field of `Running`, not a state.** The operation's `onReadable` comes from a placeholder store's fetch (`Net/AGENTS.md`). A provider never calls it. It runs on the client's shared delivery queue. From there it only hops to the state queue (its `TRAP:`). There `claimBecameReadable:` matches the run by generation. It drops a readable whose transfer already finished, which the lookup answers nil for. Otherwise it keeps the run's `CloudFileAvailability`, which marks the claim readable. It serves every playback and prefetch waiter as a Ready would. A handle run's open is dispatched in that same turn, never through its token. The claim stays `Running`, and its metadata waiters wait for complete. A playback or prefetch waiter joining a readable claim is served on the next state turn, once its run holds its token. Complete then settles the claim Ready as before, delivering to nobody new; a failure settles its remaining waiters Failed and the availability fails the delivered handles' reads with the transfer's error. **A readable stream is held by what it served, counted in one place, the availability's holders** (`addReader`): each open dispatched while readable holds it from its dispatch until its result has been delivered on the state queue, and each handle it returned from its open until its dealloc (`holdStream`, sent on the open's worker before the open lets go), so the count never dips to zero across the handoff; `onLastReaderGone` asks again, reaching the state queue behind the turn that delivered, so a rebound run's waiter is installed first. Only served handles hold: any other reader of the part file, the waveform's, rides the stream and fails with it (`Audio/Waveform/AGENTS.md`). That count stands in for the served waiters wherever a playback or prefetch waiter counted (`claimServesForeground:`): the foreground hold stays raised, so the sweep's ranged reads stay off the wire while the user's stream downloads, and a metadata waiter may still join. A run with no waiter and no reader is cancelled (`cancelRunIfAbandoned:`, the one place a last waiter leaving cancels too), so a skip away from a stream stops its download and frees its lane; a metadata waiter still on the claim keeps it running.

**The eight initial-probe slots are process-wide, and their exhaustion is a bounded failure by design.** Production can present about eleven distinct claims at once (playback, prefetch, the scan and priority metadata slots, seven artwork requests), so eight wedged probes can make a later healthy path expire after the five-second grace. That settles as `AdmissionExhausted`, spends one of metadata's three per-path attempts, and can drop the path from the current scan; it replaces an unbounded tail of uncancellable system calls. Refresh probes do not use the slots: a never-returning refresh stays state-isolated but holds its reserved transfer lane, including the one-wide background lane.

## Admission has two lifetimes

**A transfer lane ends when its materialization run settles, which for a stream is when the download completes or fails, not when its handles open; the handle-run ceiling is a separate lifetime.** A readable claim keeps its lane and its registry entry while the handles it served read the part file, so a lane can be held for the whole download under a playing track, exactly as long as before streaming: what changed is that the open and the start overlap it. The lane counts still bound transfers, not opens, and the abandoned-stream cancel is what keeps a rapid skipper from filling the interactive lane with downloads nobody hears. Each coordinator permits at most six live handle runs, process-wide in the app since production shares one: the root guarantee's two-source bound plus room for four stranded opens. A run ends when its open returns. A streaming run leaves the ceiling at delivery, and its transfer runs on. A streaming open never strands, since a cancel ends its waits. A read-ahead open never strands either. Its syscalls run on its handle's own thread, and every wait it makes can be interrupted (`Audio/AGENTS.md`). What can still strand a run is a whole-file open on a local volume, a provider's file included, and the QuickTime reader's URL open. A symlinked path, and any path the mount table cannot place, takes the direct road and can strand a run. The six therefore stand unchanged. A read-ahead thread a dead mount strands is bounded apart from the runs. At eight orphans, a new read-ahead open waits until one exits. That wait can be interrupted too. An existing `(purpose, path)` run is looked up and rebound before the ceiling is checked, so saturation never duplicates or rejects work in flight; a seventh key is refused at once with `VibeAudioFileOpenErrorAdmissionExhausted`, counted in `requestsAdmissionExhausted`, before materialization starts. The ceiling is a private, purpose-blind safety bound over `_handleRuns.count`, not loading policy: no queue, grace, configuration value or per-handle counter, and prefetch can exhaust it and get a later playback key refused. Waveform work keeps its own two fixed-slot schedulers.

**Transfer-lane admission is the coordinator's own** (`admitClaim:…`): running claims against the lane's maximum, then pending claims against the pending bound with a deadline at the grace, and a file already local starts at once outside the lanes, so only dataless claims are bounded. **Only a dataless run holds a lane slot** (`holdsLane`), and a start refresh that finds its file local hands the reserved one back: nothing times a running read out, so a local read stalled on a network share or a sleeping disk, counted, held the one-wide background lane for as long as it blocked, and every cloud row's metadata expired behind it. `AudioWorkAdmissionRules.h`, tested, is the scheduler's: `VibeAudioWorkAdmission` and `VibeAudioWorkAdmissionExpired` are what `AudioWorkScheduler` reads, here for the dataless probe. Transfer exhaustion and the handle-run refusal both map to `VibeAudioFileOpenErrorAdmissionExhausted`: the file never began, which is not that file's playback timeout.

**A run stays registered until its handle open really returns.** A timeout or superseding request detaches the outer delivery and the materialization waiter; a handle open already begun keeps its run until it returns, and a cancellation before stage 2 removes it. **A whole-file open is uncancellable, since it does no waits. A streaming open and a read-ahead open are cancellable at every wait.** The cancel sets the run's `openInterrupted`, and the open's `interrupted:` block answers it. For a stream the cancel also calls the transfer's `wakeWaiters`. Its wait then asks the block at once. A read-ahead's wait needs no wake: it asks the block again every 0.25 s. Either open, parked waiting for bytes, then returns with an interruption. That reaches no one. The waiter was detached, or a rebound one gets a fresh run. That is what makes the player's open deadline stop a stalled stream or a stalled read-ahead. Rebind and the abandoned-then-rebound restart preserve the same dictionary membership, so repeated retries cannot multiply stranded workers. A never-returning whole-file call stays one of the six until process restart, but it holds no transfer slot.

**Cancelling is the only way to stop waiting, and it is deliberately not separable from marking an admitted handle-open run abandoned.** `finishHandleRun:…` tells "this run produced nothing because nobody was waiting" from "this file would not open" by the run's cancelled mark alone; a waiter cleared without it would let the first be delivered to a later same-purpose/path waiter as a nil file with no error, which every caller reads as the file failing. Before the handle open is dispatched, cancellation simply detaches the central request and removes the outer claim. A completion therefore always carries a file or a reason there is none.

**A run that installs another version than its placeholder stood for re-keys every track.** The production operation compares the file's `cacheKey` before and after the run. A remote file downloads as it is now: a Dropbox file re-uploaded since its folder was listed, or a link changed since its open. When the key moved, the operation sends `AudioTrack.invalidateMemoizedCacheKeys`. No waveform or metadata is then filed under, or served from, the old version's entry. A stream's waveform keyed while it streamed is filed under the old key and orphaned, never served for the new version.

**Stage 1 has two kinds of backend behind one `CloudFileMaterializer`.** A provider's placeholder goes through `NSFileCoordinator`. A remote placeholder goes to the remote fetch installed for its root (`CloudFileMaterializer`, below). The Links store is one on both platforms. The Dropbox mirror is one on iOS. The coordinator cannot tell them apart and must not: both are a dataless verdict and a blocking, cancellable operation, and readable is a callback either may make; only the remote one does.

## The transfer registry

**`CloudTransferRegistry` is the coordinator's publication surface for "which files are on the wire", and only a dataless verdict publishes.** A fresh initial answer governs an immediately admitted run; a delayed or readmitted dataless claim publishes from its `Refreshing` worker's fresh answer. `Running` plus `dataless` means begin was published, so `finishClaim:` pairs the end without a second flag, readable or not: a stream's row shows the bar until the download ends. A local run, and a claim merely queued behind lane capacity, publish nothing, which is what bounds the row indicators exactly as the lanes bound the transfers. **It is the one home of "this file is loading, this far", and it watches each transferring path once.** It is main-thread. Each entry has one `DownloadProgressMonitor`, whose fraction is the best source for the backend (below). That is a remote transfer's own written count, or a provider's publication or poll. Its observers are weak and many: each shell's row list and its player model. `cloudTransferRegistryDidChange:` is coalesced per main turn and fires on begin, end and a shown fraction's change; the optional `didMoveTransferForPath:` is the monitor's uncoalesced movement feed, keyed by the transfer's standardized path, which each shell matches against its loading open's path, standardized once at `didBeginLoading:`, and forwards to `noteOpenProgressForOpenRequestIdentifier:` by its loading open's identifier (`Audio/AGENTS.md`). **TRAP: no consumer runs a monitor of its own.** A second monitor on the playing file means the registry standing aside for it, and a stream starts at its readable edge, long before its download ends, so whatever ends that monitor at `didStartPlaying:` leaves the playing row's fraction frozen, or never set, for the rest of the download. Row wiring is `Playlist/Mac/AGENTS.md`'s and `iOS/AGENTS.md`'s.

## DownloadProgressMonitor

Best-effort download progress for a cloud file being materialized, feeding `CloudTransferRegistry`, which every loading indicator on both platforms reads: shimmer while indeterminate, determinate fill when a fraction is known. Main thread only. **It observes and must never trigger a download** — the player's open is what actually fetches.

**The registry starts the only one, per transferring path, through `+monitorForURL:movement:handler:`** (the transfer registry, above), and cancels it at the transfer's end; nothing else watches a file. The two-step init/start it wraps is private to the class.

Three sources, best wins. Everywhere: a poll of the dataless file's allocated size against its logical size, plus an iCloud `NSMetadataQuery` when the item is in iCloud's index. **A remote placeholder's poll reads its transfer instead** — `CloudFileAvailability.writtenBytes` against the size being downloaded, which a re-upload since the listing makes differ from the placeholder's — since its bytes reach it only in the install's one rename. macOS also has the File Provider `NSProgress` publication, exact when the provider publishes and superseding the poll. iOS has no consumer-side progress API for third-party providers, so those files have only the poll — the header records why, so nobody re-researches it.

`DownloadProgressMonitor` owns only source precedence, movement and whole-percent coalescing. The private classes in `DownloadProgressSourceAdapters` each own one system lifecycle — timer, metadata query or File Provider subscription/KVO — including its complete cancellation path. A new observation mechanism belongs behind the same fraction callback instead of adding another lifecycle to the monitor.

`DownloadProgressSourceAdaptersInternal.h` narrows the host-less boundary to iCloud query construction/ubiquity lookup and File Provider subscriber registration. The tests still drive the production notification, filtering, KVO, replacement, unpublish and cancellation paths; only the OS finding a cross-process publication remains a live-app check.

An `NSProgress` unpublish is not completion: it also covers an abandoned operation or a disappearing provider. It detaches that exact source and lets the poll verify the file; only a reported 100% or materialized filesystem state publishes completion.

The UI fraction remains whole-percent coalesced, but transfer liveness is not. Only a finite, strictly positive raw increase is movement; initial zero, repeated, backward, negative and NaN samples never extend the player's deadline. The fake source passes zero through the same rule rather than silently hiding the provider's initial-value shape.

Both of those decisions are `DownloadProgressRules.h`, header-only and tested: `VibeDownloadProgressIsMovement` is the liveness half, and `VibeDownloadPollShouldPublish` is the poll's — the two-part dataless-and-blocks test below.

**A clear `SF_DATALESS` and the allocated blocks must both say the file is here.** Every measured provider flags its placeholders (Dropbox on both platforms, iCloud Drive); the second half guards one that would not, which would otherwise read a download not yet begun as a motionless 100%. With no positive fraction the monitor reports nothing at all rather than a zero.

**TRAP: `NSURLIsUbiquitousItemKey` is not an iCloud test.** Every File Provider item answers YES to it — a Dropbox file included — so it only gets as far as "some cloud". The `NSMetadataQuery` is what settles it, and it stops on an item iCloud does not index rather than idling for the length of the download.

`Vibe/Debug/VibeFakeCloud` stands in for the provider's reporting too, and its seam **replaces** the sources above rather than joining them: under a fake transfer the file on disk is genuinely local, so the poll would answer a final 100% on its first tick. `DownloadProgressMonitor+Debug.h` carries the whole rule.

## CloudFileMaterializer

Pulls a file provider's placeholder down to disk as an explicit, **abortable** step, for background work that needs a cloud file's bytes and must be able to stop wanting them. Background only — it blocks for a transfer, and coordinating on main is how an app deadlocks against its own presenters.

It exists because an ordinary read cannot be interrupted. Opening a dataless file — TagLib's read, `AudioFileHandle`'s open — blocks in the kernel until the provider finishes, whatever the app decides meanwhile. `NSFileCoordinator`'s `-cancel` is the one documented way out ("any current invocation will stop waiting and return immediately", from any thread), which is why the download is coordinated here rather than left implicit inside whatever opens the file next.

Its sole production caller is `AudioFileMaterializationCoordinator`. That coordinator wraps each admitted path-wide run in a fresh materializer, while playback, prefetch and metadata attach role-bearing waiters to the one standardized-path claim. Consumers cancel their own request tokens; only the last waiter leaving, or a central metadata yield, reaches this primitive's cancel path. Neither the coordinator's handle-open stage nor `AudioTrackMetadataLoader` mints a materializer directly.

**Cancellation has exactly one spelling here**, `VibeMaterializationCancelledError` (`NSCocoaErrorDomain` / `NSUserCancelledError`, which is also what `NSFileCoordinator` returns for its own `-cancel`). Above this primitive, the central coordinator's result enum — Ready, Yielded, AdmissionExhausted or Failed — is the policy surface; callers do not infer retry behavior from this underlying error.

**Every transfer — the coordinator's, the remote fetch's, the debug fake's — hands `-cancel` one block** (`installCancelTransfer:token:`), installed only while its token is current; a cancel that came first is run by the caller at once.

**A fresh `NSFileCoordinator` per download** — cancelling poisons one for good, so reusing it would turn the first abort into a permanent refusal to download anything. `materializeURL:` builds one per call, and `AudioFileMaterializationCoordinator` a fresh `CloudFileMaterializer` per admitted run.

**TRAP: cancelling stops *us* waiting.** Whether the provider abandons the transfer is its own business — a replicated extension's `fetchContents` gets an `NSProgress` the system *may* cancel once nothing waits on it, but nothing promises that. It frees the lane and the thread at once; it does not promise to free the bandwidth.

`Vibe/Debug/VibeFakeCloud` drives it with a fake transfer provider, so the cloud paths can be exercised without a real provider.

**A second backend: the remote fetch.** A store that keeps its own placeholders installs a backend for its root with `setRemoteRoot:fetch:read:availability:`. Its fetch and read blocks come all or none. Installing a root replaces that root's backend. A root with no blocks removes it. A nil root removes them all. Several roots may be installed. A file goes to the backend of the longest root holding it. A placeholder store installs itself with `installAsRemoteBackend` (`Net/AGENTS.md`), at launch, before any open. The mac installs the Links store. iOS installs the Dropbox mirror and the Links store (`iOS/Dropbox/AGENTS.md`). Every change also sets `NSURLUtil`'s remote placeholder roots. The dataless verdict and the backend that answers it then cannot disagree. An unreadable file under no root is never sent to a backend. It is merely unreadable.

`materializeURL:` sends a remote placeholder to its backend instead of to `NSFileCoordinator`. The fetch block blocks the worker until the bytes have replaced the placeholder. It hands back a cancel block through `onCancel`. `-cancel` runs that block from any thread, at once if the cancel came first. **Unlike the provider path, this cancel stops the transfer**, not just the wait. A fetch that can be read before it completes also calls `onReadable`. It does so at most once, when the lookup below answers for the file and its head is written. It calls from its own thread, so it must return at once. `materializeURL:token:onReadable:error:` hands the caller's block straight through. The provider path never calls it. A file that completes first never does either. The coordinator opens the playback and prefetch handles on it. The claim, its lane, the foreground hold, and the loading bar run on until the fetch completes (One claim, two stages, above).

**The second block reads a placeholder's bytes by range** for the tag parse (`Audio/Metadata/AGENTS.md`). Opening a folder then costs its tags, not its files. `remoteReadForURL:` answers the read of the file's backend, nil under no root.

**The optional third block, `availability`, is the streaming lookup.** It answers a `CloudFileAvailability` for a file whose transfer is writing its part file now, and nil otherwise. A file it answers nil for opens whole in `AudioFileHandle` (`Audio/AGENTS.md`). The lookup may answer nil only once the object it handed out has finished, since a reader that looked it up may be waiting on it. Every placeholder store installs one (`Net/AGENTS.md`).

**A `CloudFileAvailability` says how much of a file is readable while a writer fetches it, and it takes either of two writers.** A transfer writes a part file from byte 0. Its final size is known before the first byte, and it notes bytes only after writing them. A writer with no part file fetches the file by range into blocks held in memory (`initWithoutPartFile`). The one such writer is `AudioFileHandle`'s read-ahead on a network mount (`Audio/AGENTS.md`). The size is unknown until that writer calls `noteSize:` once. `noteShortenedEnd:` lowers the size when a read finds the file shorter, and never raises it. Each writer finishes once. Complete readies every range on the disk. An error fails every wait, bytes already read included. **TRAP: a writer with no part file always finishes with an error.** Complete would send readers to a disk it never wrote, and `finishWithError:` asserts it.

A reader waits for a range, clipped to the size. A range at or past the size is the end, never a wait. The reader's own `interrupted` block ends a wait. It is asked whenever the wait would block. An optional deadline ends a wait too. A wait sleeps until woken, whichever the writer. `wakeWaiters` makes every wait ask again. Waits run on worker threads only. Nothing the render reaches touches it.

**Bytes held in memory change what answers a range, not who asks.** Blocks are offset-ordered and never overlap. A range held by contiguous blocks is Ready. A reader passing a buffer gets the bytes copied out across block boundaries, under the same lock. A transfer holds at most one block, its **tail window**. That is bytes past the download's edge that the writer read ahead and installed (`installWindow:atOffset:`). While held, the window lies wholly past the bytes written, so no read mixes the two. A range straddling the window's start waits for the disk. The note that reaches the window's start drops it. A writer with no part file installs blocks at any offset below the size (`installBlock:atOffset:`). A block already wholly held is ignored, and any other replaces the blocks it overlaps. That writer drops the blocks it no longer wants (`dropBlocksOutsideRangeAt:length:`). The drop always keeps the block at byte 0, the block that ends at the size, and any block a blocked wait wants. **TRAP: every block is dropped under the lock a reader copies under.** A wait a block answered has then copied before the block goes. `progressBytes` is the bytes written plus every block byte ever installed. It only grows.

**The writer's wait for work** (`waitForWorkUntil:wanted:length:readerPosition:`) is for a writer with no part file. It returns at once when a wait blocks, when the reader enters another block, when `readAheadPaused` is cleared, or when the availability finishes. Otherwise it returns at its deadline. It reports the range a blocked wait wants and the reader's position, which is the offset of the most recent wait. While `readAheadPaused` is set, the writer fetches only a range a wait wants. The reader's handle sets it while its reads are interrupted. **The writer asks `heldEndAt:` what is already held, never a wait.** It answers where the bytes held contiguously from an offset end, and records nothing. A wait would move the reader's position to the writer's offset. A transfer ignores all of this.

`readyBytesAt:length:` never waits. It answers the longest prefix of a range held now, from the blocks or from the part file below the bytes noted. It never reads half a write, and answers nothing once finished. A placeholder store's tag reads take a streaming file's bytes this way. Each `AudioFileHandle` the coordinator serves from the part counts as a reader, from its open to its dealloc (`holdStream`). An open about to become one may hold it too (the coordinator's, above). A read-ahead's availability has no readers to count. `onLastReaderGone` tells whoever runs the transfer that nobody wants it. That is how the coordinator cancels a stream skipped away from.

## Why the monitor and the materializer are not merged

They look like one thing and are opposites in the two ways that matter: the monitor **observes and must never trigger** a download and is main-thread only, while the materializer **causes** one, can abort it, and must never run on main. Merging them would put "never triggers" and "triggers" behind one name. The overlap that is real — *is this file here yet* — already lives in one place, `NSURLUtil.isDatalessFile:`.

## Configuration

**`AudioLoadingConfiguration` is immutable once built, and its diagnostic surface is for tests and the debug channel only.** The safe tuning surface is the background lane width, the local parse concurrency and the prefetch depth; the interactive lanes, pending bounds, grace, retry count and `openTimeouts` are diagnostic, replaced by `Vibe/Debug/`'s category and the test suite, never by production code.
