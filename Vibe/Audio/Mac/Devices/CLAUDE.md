# Output devices (macOS only)

The CoreAudio HAL output-device layer: `AudioDevice`, `AudioDeviceManager`, `CoreAudioUtil`, and `AudioPlayer+Devices`. The iOS counterpart is `Audio/iOS/`, which is an `AVAudioSession` and nothing like this.

## AudioDeviceManager

A singleton that owns device-change listening. At init it registers CoreAudio listeners for the default output device and the device list, kept for the life of the process, then performs a post-registration sweep. `outputDevices` serves the latest immutable snapshot and waits at most 250ms for the first one on every calling thread; an unavailable `coreaudiod` therefore cannot strand a caller's serial queue.

**A snapshot is normally published only after every read agrees** — the device list, the system default, and each device's output-channel, name and UID properties, plus the default appearing in the resulting list. A partial result keeps the prior snapshot and takes the retry path rather than looking like device removal, so legitimate empty results stay representable while a transient HAL failure cannot persist a false System Output fallback.

**But strictness is bounded, because a persistent failure is not a transient one.** A virtual or aggregate driver that always fails a property read, a device with an empty name, or a default device that enumerates with no output channels would otherwise keep *every* device unpublished for the life of the process: the two-second retry never stops, the Output menu never populates, and `resolveOutputDeviceForUID:` never completes, so the saved device can never bind. After `kMaxIncompleteSweeps` (3) consecutive refusals one sweep publishes what it could read, omitting the devices that failed, and logs that it did. The three inputs with no partial form — the list, its size, and the system default — still return nil however many sweeps have failed.

**TRAP: absence in `outputDevices` is not removal.** It answers `@[]` both for "no output devices exist" and for "no sweep has been published yet", which is what the 250ms ceiling returns during setup or while a failure is retrying. Every decision that treats absence as removal — and so falls back to System Output *and persists it* — asks `knowsOutputDeviceIsAbsent:` instead, which answers NO until there is a real snapshot to be absent from. Both callers are in `AudioPlayer+Devices`: the device-list observer and `handleEngineConfigurationChange`, the latter mattering most because it is driven by `AVAudioEngine` rather than by this class and can therefore arrive before any snapshot exists.

Saved-device discovery does not use that synchronous getter. `resolveOutputDeviceForUID:name:completion:` waits asynchronously for the first successful snapshot, UID first and name as compatibility fallback. `AudioPlayer` starts honestly on System Output and retains an unmatched saved preference. A match is applied only where `VibeCanBindSavedOutputDevice` allows — the rule is stated once, under `AudioPlayer+Devices` below — and only committed after the HAL bind succeeds; if playback wins the lookup race, the intent stays pending for the next eligible transition or device/default refresh. Discovery never occupies the player's sole queue while CoreAudio is unavailable.

**TRAP: never call `outputDevices` from `_refreshQueue`.** Setup runs there, so a call from that queue before setup completes pointlessly consumes the getter's full 250ms wait ceiling on work that cannot advance until the call returns.

`refreshOutputDevicesCache` runs only on that serial refresh queue, which orders the stores, so a newer sweep can never be overwritten by an older one.

**Observers are fanned out on the main thread in the common run-loop modes**, not with a plain `dispatch_async` — GCD main-queue blocks do not run during menu tracking, and this way the devices menu refreshes while it is open. Observers (`AudioDeviceManagerObserver`) are held weakly: `AudioPlayer` and `OutputDevicesMenuController`.

## AudioPlayer+Devices

All device management on this platform: resolution, switching, config-change recovery, and parking or falling back when a device vanishes. It is a category on `AudioPlayerInternal.h`'s shared private surface, exactly as the iOS `AudioPlayer+Recovery` is, and is declared in `AudioPlayer.h` beside `(State)`.

The player's async init asks the manager to resolve the saved output device — **by UID first and name as fallback** — without blocking the player queue. Until a successful bind, `currentlyRequestedAudioDeviceId` stays `-1` and the saved preference remains pending rather than reporting an explicit device that was never selected.

**Where that deferred bind may land is `VibeCanBindSavedOutputDevice`: Stopped, or Loading while the engine is not running.** Stopped alone was not enough — launching by double-clicking a file starts an open within milliseconds of the async init, so the *first* track would play through the system default and only move to the saved device at the next track boundary. At launch nothing is rendering, so the rebind is inaudible and the in-flight open starts itself on the new device. **TRAP: an ordinary mid-session track change is also Loading**, with the outgoing node still fading out on a running engine, and rebinding there would stop the engine under that fade and click — which is why the engine check is part of the rule rather than a comment about launch. Playing and Paused are excluded outright: a failed bind there tears down live playback.

`didChangeOutputDevice:` is sent on **every** settled mutation, not only when the id moved. The delegate both persists the choice and drives the menu checkmark and is idempotent, so re-announcing an unchanged value is free; suppressing it left "Settings names the last committed device" a guarantee nothing enforced, and any path that left the two disagreeing could never resynchronize them, because the one call that writes Settings was skipped exactly when they already looked equal.

An explicitly bound device that later disappears, whether mid-playback or while idle, falls back to System Output, and the fallback is persisted. AVAudioEngine can follow a changed system default even between devices at the same rate, after the default notification and without a configuration notification. A listener on the output unit’s actual device feeds the same configuration recovery, which treats a running graph on the wrong device as unhealthy. An unreadable binding is unknown, never inferred from the system default. An absent launch preference instead remains pending. A failed explicit concrete-device bind preserves that pending preference because Settings still names it; a successful explicit bind supersedes it. Explicit System Output always clears it, even when `currentlyRequestedAudioDeviceId` is already `-1`, because `-1` is the durable policy to follow whatever system default exists now or later. A failed system-default property read does not park playback as though no output existed; one coalesced retry follows, then a real device/default notification must provide the next attempt. The menu's checkmark tracks `currentlyRequestedAudioDeviceId`; the menu itself is `Mac/Menu/`.

Selecting the already-active device still rebuilds when bit-perfect output is wanted but that device has not been prepared: a saved device missing at launch can leave the mode waiting on System Output until this selection makes it eligible. A device switch stops the node, so it must clear the armed gapless splice first and re-arm after its reschedule — see `Audio/CLAUDE.md`.

## Bit-perfect output

`AudioPlayer.setBitPerfectOutput:exclusiveOutput:` (Settings > General > Audio) delivers each file's decoded samples to the chosen device unchanged. The decisions are `OutputFormatRules.h`, header-only and tested; the mechanism shares `AudioPlayer+Devices.m`'s existing internal category with device switching; the raw property reads and writes are `CoreAudioUtil`'s. What it holds true, measured with the loopback oracle (`verify-bit-perfect.swift` in the `vibe-debug` skill, against BlackHole): 44.1, 48, 88.2 and 96 kHz WAVs and a 96/24 FLAC arrive sample-exact.

**Exclusive output is a separate opt-in**, off by default, below Bit-perfect output. Both preferences land on the player queue in one setter and use the existing same-device rebuild to preserve the current track and position. Changed settings stop the engine before changing ownership. Reapplying identical settings returns without rebuilding; an exclusive preference changed while bit-perfect is off is saved without touching the graph. Disabling exclusivity releases the device without restoring its format or adding a varispeed; disabling bit-perfect output restores the format and releases it through `leaveOutputDeviceOnQueue`, inside the rebuild after the engine stopped. If the saved device is absent at launch, the switch still permits turning bit-perfect off: the same rebuild restores varispeed on the active System Output without changing that device policy. Restoring a hogged device while the engine was still running stranded the next start in CoreAudio with error 35. An in-flight open also stops/rebinds the warm engine without consuming the request, so its settlement starts with the latest exclusive preference. Termination stops the engine before restoring and releasing too. The saved exclusive preference survives a bit-perfect toggle, but can act only while bit-perfect output is on. `hogWanted` folds that preference with device eligibility, so choosing shared output is never reported as a failed exclusive take.

**Compile-time removal:** `VIBE_ENABLE_EXCLUSIVE_OUTPUT` defaults to `1` in `project.yml`. Set it to `0` there, regenerate the project, and every build path omits the exclusive row, its action and writable preference, the player's ownership state and acquire/release methods, and the HAL hog reader/writer. The getter answers NO even over a saved YES. Bit-perfect rate/depth matching, graph pruning and reports remain. For a single build, pass `VIBE_ENABLE_EXCLUSIVE_OUTPUT=0` to `xcodebuild`; both Debug and Release use the flag.

**The format rides the play settlement; the hog rides the running engine.** `prepareOutputOnQueueForFile:` runs in `finishPlayOnQueueWithFile:…` after the request is consumed and before the node is attached, and in `configureOutputDeviceOnQueue:`'s restore branch. It reads the bound device's first output stream once, applies the rate rule (exact, else the smallest integer multiple, else untouched; scans discrete offers and continuous ranges, including 3x, 6x and ratios above 16x) and the as-is depth rule (the integer depth equal to the source's, else the smallest above, else float32 — every Apple built-in and virtual device is float32-only), and when the device's format or the master bus's rate differs it stops the engine itself — both callers guarantee nothing is audible — writes one `kAudioStreamPropertyPhysicalFormat`, polls the nominal rate back for up to 1.5 s, and **rewires `mainMixer → outputNode` at the device's rate** through `wireMasterBusOnQueueAtRate:`, the same helper `installMasterBusOnQueue` wires the FX-less bus with. `acquireExclusiveOutputOnQueue` runs in `startEngineAndPlayNode:` before the engine starts; `releaseExclusiveOutputOnQueue` after both idle-stop engine stops, before a rebind, on mode off and at quit. A virtual transport is never hogged, which is what lets the loopback record it.

**TRAP: the mixer's default output rate is 44.1 kHz whatever the device, and the output unit resamples the difference silently** — measured at 1.4e-3 against a 48 kHz device. That is why the FX-less master bus is wired at the output node's rate on every engine (`Audio/CLAUDE.md`), and why `outputNeedsSwitchOnQueueForFile:` counts a mixer rate that differs from the chosen rate as a switch: a device whose rate moved under a running engine leaves the connection stale until the next settlement rewires it. The FX graph's connections are still made at the mixer's default rate, which is one of the two reasons the mode is inert in a run with the graph.

**TRAP: setting `kAudioDevicePropertyHogMode` ignores the value and toggles ownership**, so `setHogOwnedByThisProcess:` reads first and writes only when the owner has to change; "owned by this process" is the whole state, and a release while another process holds it is already true. The sandboxed build takes and releases it without any entitlement.

**TRAP: the system default output device is never hogged** (`VibeBitPerfectShouldHog`, `isSystemDefault`). Hogging it makes coreaudiod move the default to another device, and AVAudioEngine's output unit — a default output unit, whatever `kAudioOutputUnitProperty_CurrentDevice` was set to — follows the default off the device it was just bound to, at a moment of its own choosing; the measurements, and why re-binding did not close the race, are Q8 of `docs/future/bit-perfect-output.md` (`hogfollow.swift` in the `vibe-debug` skill). On the default device the samples still arrive unchanged, the caption says "shared, because it is the system output device", and a user who wants exclusivity picks another system output in Sound settings. Whether the device is the default is read live, by the take and by the report alike, since it moves under a paused track; and `configureOutputDeviceOnQueue:` keeps the hog (with the format slot and the prepared device) on a rebuild of the device already held rather than paying the write twice.

**A switching settlement parks until the outgoing audio is silent.** The settlement rejects an obsolete open identifier before any device query or park, so a late result cannot replace the current request's parked block. A format switch stops the engine, which would cut a still-fading node mid-waveform, so `finishPlayOnQueueWithFile:…` parks itself in `_parkedSettlement` when a switch is needed while `_activeRetiredOutputCount > 0`, preempts the fades to the declick length, and `completeRetiredFadePair:` re-enters it verbatim at count zero; `consumeRequest:` then drops a re-entry a newer play or a stop superseded, so no generation is needed.

**The chain is pruned by the switch, not the device.** With the mode on and no FX graph, `ensureVarispeedOnQueue` (in `AudioPlayer.m`, the one writer of `_varispeed`) mints nothing and `connectNode:throughVarispeedWithFormat:` connects node → mixer directly; the settlement calls it right before the incoming node is connected — not the submission, so a toggle during an in-flight open lands on the chain the mode wants — and the device restore calls it on the current track, which is how both mode toggles rebuild the current track in place. Measured: a varispeed at ratio 1.0 is not a pass-through (last-bit differences of about 5e-6), which is why it is removed rather than trusted.

**Restore is one slot.** The first change to a device's format in a run remembers the device, its stream and the format it had; mode off, a switch to another device and `prepareForTermination` (from `applicationWillTerminate:`) write it back and clear the slot — `leaveOutputDeviceOnQueue` is the restore, the prepared device forgotten and the hog released, in that order. A vanished device takes the off path verbatim: `abandonBitPerfectForVanishedDeviceOnQueue` drops the mode, restores (a write to a device already gone fails and is forgotten) and releases before the two fallback sites bind System Output, and the shell reads the report's `enabled` going false on the `-1` announcement to persist the setting off — the launch-time `-1`, announced while the saved device is still binding, leaves the mode wanted and is not a fallback.

**Eligibility is an allowlist of transports** (`VibeBitPerfectDeviceEligible`): built-in, PCI, USB, FireWire, Thunderbolt, HDMI, DisplayPort, AVB and virtual; Bluetooth, AirPlay, Continuity, the Remote types, aggregates and Unknown are out, and so is anything Apple adds until argued in. The System Output policy is the absence of a chosen device, not a transport — the device that happens to be the current default is judged like any other. The switch, the Output menu and the report all read the one rule. **Which device the mechanism drives is the requested id, or the destination while a switch is in flight** (`_rebindDeviceID`, set for the duration of `configureOutputDeviceOnQueue:`): the switch prepares and hogs its destination before `setOutputDeviceOnQueue:` commits the id — a failed switch must not commit — so resolving the requested id there switched the device just left. It is never the output unit's own device, which follows the system default whenever that moves (the hog trap above), so reading it names a device the engine is about to leave. `AudioDevice.transportType` is read by the sweep as an optional refinement that never discards a device.

**The report** (`VibeBitPerfectReport`, `bitPerfectReport`) carries the status and every fold input, and **nothing in it is cached**: each publication computes it from its owners — the mode, the graph, the chosen device, the hog, the current file's source format (so a gapless promote reports the promoted file), and the prepared device's physical format, software volume, mute and default-ness read from the HAL. The prepare records only what those reads need: the device, its stream and the format asked of it (`_prepared*`), which `formatConfirmed` compares the live format against, also requiring the output unit to be bound to that device and successful format, volume and mute reads. An unconfirmed output reports SwitchFailed before any rate mismatch can report RateUnsupported; a successfully prepared fallback rate still reports RateUnsupported. `channelsMatch` checks the source, decoder, mixer, both sides of the output unit and physical stream: any changed channel count reports ChannelConversion. Mute has its own status even at full volume. `depthOK` asks whether the file's processing format carries the source as well as the device's physical format does: AVAudioFile decodes to float32, whose significand is 24 bits, so a 32-bit integer source is never Active whatever the device offers (measured: 24,641,537 came out 24,641,536). The paused recovery in `handleEngineConfigurationChange` accepts the paused graph only while `outputNeedsSwitchOnQueueForFile:` is NO — a format another process moved during the pause is what that notification often is, and the rebuild's prepare sets it back before the resume. The publication rides the edges that already exist — `refreshOutputAudioActiveOnQueue` (every state publication and fade completion), the end of a device switch (held during the rebuild), the two hog edges and the mode toggle — plus an output-unit device listener (same-rate default changes can move the engine without its configuration notification), one HAL listener on the prepared device's output properties, filtering volume and mute changes on the player queue, and the manager's system-default change, since the user moves both mid-track. A publication that changed the report is announced through `audioPlayerDidChangeBitPerfectReport:` on main, the only edge the header's lock and the Settings caption redraw from; reading the report right after a setter sees the previous one. **The gapless splice is gated on the mode too**: a queued segment keeps the device's format, so `maybeArmGaplessOnQueue` asks `outputNeedsSwitchOnQueueForFile:` and a boundary whose next file wants another format takes the settlement, which switches. The idle stop waits 6 s while a device is hogged and 10 s otherwise.
