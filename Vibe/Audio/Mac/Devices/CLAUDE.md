# Output devices (macOS only)

The CoreAudio HAL output-device layer: `AudioDevice`, `AudioDeviceManager`, `CoreAudioUtil`, and `AudioPlayer+Devices`. The iOS counterpart is `Audio/iOS/`, which is an `AVAudioSession` and nothing like this.

`CoreAudioUtil.diagnosticDescriptionOfDeviceID:` is the one read-everything call — formats, declared latency, clock, exclusive owner — and exists for Save Debug Info (`Mac/App/CLAUDE.md`); nothing that changes a device reads it. The player's side of that report is `bitPerfectReportDictionary` and `outputDeviceDiagnosticSnapshot`, which the debug channel's `dump_state` reads too.

## AudioDeviceManager

A singleton that owns device-change listening. At init it registers CoreAudio listeners for the default output device and the device list, kept for the life of the process, then performs a post-registration sweep. `outputDevices` serves the latest immutable snapshot and waits at most 250ms for the first one on every calling thread; an unavailable `coreaudiod` therefore cannot strand a caller's serial queue.

With `VIBE_VERBOSE_LOGGING=1`, the `HAL:` event log follows published output devices, records watched device/output-stream property changes and arrivals/removals, and identifies default/alert output changes and `coreaudiod` restarts.

**A snapshot is normally published only after every read agrees** — the device list, the system default, and each device's output-channel, name and UID properties, plus the default appearing in the resulting list. A partial result keeps the prior snapshot and takes the retry path rather than looking like device removal, so legitimate empty results stay representable while a transient HAL failure cannot persist a false System Output fallback.

**But strictness is bounded, because a persistent failure is not a transient one.** A virtual or aggregate driver that always fails a property read, a device with an empty name, or a default device that enumerates with no output channels would otherwise keep *every* device unpublished for the life of the process: the two-second retry never stops, the Output menu never populates, and `resolveOutputDeviceForUID:` never completes, so the saved device can never bind. After `kMaxIncompleteSweeps` (3) consecutive refusals one sweep publishes what it could read, omitting the devices that failed, and logs that it did. The three inputs with no partial form — the list, its size, and the system default — still return nil however many sweeps have failed.

**TRAP: absence in `outputDevices` is not removal.** It answers `@[]` both for "no output devices exist" and for "no sweep has been published yet", which is what the 250ms ceiling returns during setup or while a failure is retrying. Every decision that treats absence as removal — and so falls back to System Output *and persists it* — asks `knowsOutputDeviceIsAbsent:` instead, which answers NO until there is a real snapshot to be absent from. Its caller is `AudioPlayer+Devices`' device-list observer. The rate edge below cannot wait for a snapshot — a listener fires before the list catches up — so it asks the device itself (`deviceIsConfirmedDead:`) instead.

Saved-device discovery does not use that synchronous getter. `resolveOutputDeviceForUID:modelUID:name:completion:` waits asynchronously for the first successful snapshot and matches most specific first: device UID, then model UID, then name as the compatibility fallback for settings saved before either existed. `AudioPlayer` starts on System Output. An unmatched saved preference remains pending during ordinary playback; with bit-perfect armed, a published absence disables the mode and commits System Output. A match is applied only where `VibeCanBindSavedOutputDevice` allows — the rule is stated once, under `AudioPlayer+Devices` below — and only committed after the HAL bind succeeds; if playback wins the lookup race, the intent stays pending for the next eligible transition or device/default refresh. Discovery never occupies the player's sole queue while CoreAudio is unavailable.

**TRAP: never call `outputDevices` from `_refreshQueue`.** Setup runs there, so a call from that queue before setup completes pointlessly consumes the getter's full 250ms wait ceiling on work that cannot advance until the call returns.

`refreshOutputDevicesCache` runs only on that serial refresh queue, which orders the stores, so a newer sweep can never be overwritten by an older one. The enumerator result is copied before publication. `initWithEnumerator:retryScheduler:` lets the host-less suite control the HAL and timer boundaries without registering hardware listeners; `refreshOutputDevicesWithCompletion:` is the shared refresh entry used by device notifications and the tests.

**Observers are fanned out on the main thread in the common run-loop modes**, not with a plain `dispatch_async` — GCD main-queue blocks do not run during menu tracking, and this way the devices menu refreshes while it is open. Observers (`AudioDeviceManagerObserver`) are held weakly: `AudioPlayer` and `OutputDevicesMenuController`.

## AudioPlayer+Devices

All device management on this platform: resolution, switching, the rate the graph runs at, and parking or falling back when a device vanishes. It is policy over the hosted output unit, which `AudioPlayer+Graph` owns. It is a category on `AudioPlayerInternal.h`'s shared private surface, exactly as the iOS `AudioPlayer+Recovery` is; its public half, `(Devices)`, is declared in its own header, which the macOS shell imports beside `AudioPlayer.h`.

The player's async init asks the manager to resolve the saved output device — **by device UID, then model UID, then name** — without blocking the player queue. The hosted output unit (`AudioOutputUnit`) is bound to the system default at creation, at that device's rate, and moves only when a rebind moves it: nothing follows the system default on its own.

**TRAP: a class-compliant USB interface's device UID is its USB location, not the unit.** `AppleUSBAudioEngine` builds it from manufacturer, product and `locationID`, so the same Audient iD4 is `…:2100000:1,2` in one port and `…:1100000:1,2` in the next (measured). Such a device exposes no serial number anywhere — `kAudioObjectPropertySerialNumber` is unsupported and its USB descriptor carries none — so nothing distinguishes two of them but the port. `kAudioDevicePropertyModelUID` is the documented, port-independent identifier for the *model*, and is what finds the device on its new port. It is compared as an opaque token and never parsed; parsing the device UID would depend on an undocumented layout. Vendor drivers often key the device UID on a serial instead (an RME Fireface's is `RMEUSBDevice-205-<serial>`), and Bluetooth devices on the MAC address, so for them the device UID is already per unit. Until a successful bind, `currentlyRequestedAudioDeviceId` stays `-1` and the saved preference remains pending rather than reporting an explicit device that was never selected.

**Where that deferred bind may land is `VibeCanBindSavedOutputDevice`: whenever nothing is audible — Stopped, Loading while the engine is not running, or a Paused track.** Stopped alone was not enough — launching by double-clicking a file starts an open within milliseconds of the async init, so the *first* track would play through the system default and only move to the saved device at the next track boundary. At launch nothing is rendering, so the rebind is inaudible and the in-flight open starts itself on the new device. **TRAP: an ordinary mid-session track change is also Loading**, with the outgoing voice still fading out on a running engine, and rebinding there would stop the engine under that fade and click — which is why the engine check is part of the rule rather than a comment about launch. Playing is excluded outright: a failed bind there tears down live playback. **A pause is not excluded**, though it was until a vanished device needed it: an unplug parks playback as Paused, so excluding Paused left a device that came back unadoptable until the next stop. The rebuild restores a paused track as Paused rather than resuming it; the pause verb calls the resolver because a pause is silent the moment it is published.

`didChangeOutputDevice:` is sent on **every** settled mutation, not only when the id moved. A refused selection reannounces the retained choice before its completion, repairing a UID cleared by Settings reset; a still-pending saved launch preference is preserved instead of being overwritten with the temporary binding. The delegate both persists the choice and drives the menu checkmark and is idempotent, so re-announcing an unchanged value is free; suppressing it left "Settings names the last committed device" a guarantee nothing enforced, and any path that left the two disagreeing could never resynchronize them, because the one call that writes Settings was skipped exactly when they already looked equal.

A vanished device and an absent launch preference share the pending identity slot. Falling back disables unavailable modes and follows System Output without forgetting that identity, so a later device/default notification or silent transport transition can re-adopt it. Every `-1` announcement derives its involuntary reason from the pending slot, including repeated default notifications, and carries it to the delegate as explicit arguments, captured by value before the hop to main, since a successful bind or user selection may clear the slot before the delegate runs. Only an explicit System Output selection or successful concrete selection clears pending intent; a failed concrete selection retains it.

**TRAP: returning devices resolve synchronously against `cachedOutputDevices`.** An asynchronous answer can lose to a local open that moves Loading to Playing and makes the bind ineligible. Only initial discovery waits asynchronously; its callback re-reads the current preference and snapshot so it cannot revive an older choice. **TRAP: hold `_pendingSavedDeviceLookupInFlight` across every bind, including a cached resolution.** A refused HAL bind publishes Stopped; its reset must not schedule another attempt while that guard is held. Other resets defer resolution to the next queue turn, after the enclosing mutation has finished its rollback. An absent snapshot result with bit-perfect already off does nothing, keeping intent without resubmitting lookups.

A failed system-default property read is unknown, not absence: retain playback, try one coalesced delayed bind, then wait for a real notification. Confirmed absence parks playback. The menu checkmark follows `currentlyRequestedAudioDeviceId` (`Mac/Menu/`).

**The edges are the manager's two observers and, while a bit-perfect device is prepared, that device's one HAL listener.** The system default moving reaches `setOutputDeviceOnQueue:-1` when System Output is the policy, whose rebind moves the unit; the device list changing asks `knowsOutputDeviceIsAbsent:` and falls back; and the prepared device's listener carries its nominal rate beside its controls — a rate other than the graph's, on a device not confirmed dead, is another process moving the device, and `configureOutputDeviceOnQueue:` on it has the prepare set the mode's format back. Vibe's own format writes arrive at that listener with the graph already at the rate, a no-op. There is no `AVAudioEngineConfigurationChangeNotification` on macOS and no listener on the unit: the hosted unit never moves or stops on its own, so the states recovery existed for — the unit left the device, the unit at the wrong rate — cannot occur.

Selecting the already-active device still rebuilds when bit-perfect output is wanted but that device has not been prepared, so a newly eligible selection prepares the current track too. **A rebind stops the engine and keeps the current voice**: the engine stop kills every fading voice, the current voice keeps its ring and gain, and a restart continues it in place. Only when the source segment must be rebuilt — the mode or the bus format the file wants changed — does the voice die with it, and the rebind starts a new one at the retained intent; either way the successor is re-queued after (`Audio/CLAUDE.md`).

## Bit-perfect output

`AudioPlayer.setBitPerfectOutput:exclusiveOutput:enableFX:` (Settings > Audio) delivers each file's decoded samples to the chosen device unchanged.

**Declick** (Settings > Audio, below Exclusive output; `AppSettings.declick`, default on, one choice for every device) decides what the mode does at a transport edge: on, the ≤10 ms declick ramp ordinary playback applies at a play, seek, pause, resume, stop or track change, so the edge cannot click and every other frame — the whole of a gapless boundary included — is still delivered unchanged; off, a cut that leaves every sample untouched. It reaches the player as `AudioPlayer.declick` through `VibeSettingsLiveEffectDeclick`, with no rebuild, and `leavesSamplesUntouchedOnQueue`, the one gain rule, is "bit-perfect wanted and Declick off". The crossfade never enters the mode either way: `effectiveCrossfadeMilliseconds` clamps it to the declick minimum. Ordinary playback always ramps, so the pane disables the switch while the mode is off. The loopback verifier turns it off around its captures, which compare from the first frame.

**Both modes belong to the destination UID.** `AppSettings` remembers only enabled modes, retaining entries while devices are unplugged. The shell supplies them through `audioPlayer:outputModesForDeviceUID:bitPerfectOutput:exclusiveOutput:`, a read-only delegate query supporting main and the player queue. Explicit selection and saved-device resolution share `selectOutputDeviceOnQueue:`, which reads the destination's modes before the one rebuild and restores the previous flags if the switch commits nothing. **TRAP: a failed rebuild may already have rewired or prepared the destination.** After restoring the flags, a Stopped player stops the engine and takes the existing `leaveOutputDeviceOnQueue` cleanup, reconciling the master bus and retiring the failed destination's format, listeners and hog obligations. A failed pin that left live playback intact does not tear it down. **TRAP: a name fallback can resolve a different UID; read its own modes before preparing or hogging it, never the missing device's flags.** Pushing modes after a bind would first rewrite the format of, and possibly hog, a device whose mode is off. **The one exception is a model-UID match under a new device UID** — the same model on another USB port, not a stranger sharing a name. Only when the destination has no saved enabled modes does `selectSavedOutputDeviceOnQueue:` use `_modesUIDForNextSelection` to read the old UID. An existing destination entry wins before any hardware mutation. `carriedOutputModesDeviceUID` carries that actual decision by value into the delegate callback; the shell persists only that carry on main through `AppSettings.carryOutputModesFromDeviceUID:toDeviceUID:`. A manual selection never infers a carry from matching models. The carry copies rather than moves, so the old port keeps its entry, and never overwrites modes already chosen for the destination. The residual: two identical units of one model share modes, because the OS cannot tell them apart. Queued mode/FX edits reread the queue's current UID (or the still-pending saved UID), so a snapshot submitted behind a switch cannot overwrite the destination's preferences. System Output has no UID and reads off. If its default-device read fails or reports no output, its committed mode change still rebuilds the current binding: an unknown read preserves playback, while confirmed absence parks it. The public selection completion runs on main after the device callback, including failed switches, so the shell can release its mode-edit guard. `setOutputDeviceOnQueue:` also rebuilds when only the standing graph disagrees with the flags: switching a bit-perfect device to System Output may leave the unit on the same hardware but must restore its format and FX route. The decisions are `OutputFormatRules.h`; raw HAL reads and writes are `CoreAudioUtil`'s. The loopback oracle (`verify-bit-perfect.swift`) measures 44.1, 48, 88.2 and 96 kHz WAVs and a 96/24 FLAC sample-exact.

**Exclusive output is a separate opt-in**, off by default, below Bit-perfect output. Bit-perfect, exclusive output and the saved FX preference land on the player queue in one setter and use the existing same-device rebuild to preserve the current track, position and pause state. The rebuild reads `getPlaybackIntent:forTrack:` before stopping the engine. Changed settings stop the engine before changing ownership. Reapplying identical settings returns without rebuilding; an exclusive preference changed while bit-perfect is off is saved without touching the graph. Disabling exclusivity releases the device without restoring its format or adding a varispeed; disabling bit-perfect output restores the format and releases it through `leaveOutputDeviceOnQueue`, inside the rebuild after the engine stopped. While saved-device discovery is pending, the switch still permits turning bit-perfect off: the same rebuild restores varispeed while keeping the current binding, without depending on a device read or changing that policy. Restoring a hogged device while the engine was still running stranded the next start in CoreAudio with error 35. An in-flight open also stops/rebinds the warm engine without consuming the request, so its settlement starts with the latest exclusive preference. Termination stops the engine before restoring and releasing too. The saved exclusive preference survives a bit-perfect toggle, but can act only while bit-perfect output is on; with an eligible device prepared, it *is* `hogWanted`. **The device that happens to be the system output is taken like any other** — the trap below is what that costs and how it is paid — so the only device the mode refuses is one whose transport is ineligible or whose HAL hog property is not writable.

**Compile-time removal:** `VIBE_ENABLE_EXCLUSIVE_OUTPUT` defaults to `1` in `project.yml`. Set it to `0` there, regenerate the project, and every build path omits the exclusive row, its action and writable preference, the player's ownership state and acquire/release methods, and the HAL hog reader/writer. The getter answers NO even over a saved YES. Bit-perfect rate/depth matching, graph pruning and reports remain. For a single build, pass `VIBE_ENABLE_EXCLUSIVE_OUTPUT=0` to `xcodebuild`; both Debug and Release use the flag.

**Off is dormant.** Every bit-perfect entry point gates itself on `_bitPerfectWanted` — the report's publication on that and the Off report already being out — so ordinary playback, gapless checks, state changes, engine starts and device recovery call them without repeating the check. Disabling publishes one zeroed Off report and removes the device listener after restoring the device. No report recomputation, format negotiation, volume read or hog attempt runs during disabled playback. Cleanup of a failed restore, listener removal or release is retained and retried at the next cleanup edge, never by polling. Listener removal retries once and keeps its exact handle on failure, refusing to register a second device until it succeeds. The device listener exists only for a prepared bit-perfect device. Disabled playback keeps the one bus at the mixer's format with its varispeed, at the device's rate, and the original six-second idle stop.

**The format rides the play settlement; the hog rides the running engine.** `prepareOutputOnQueueForFile:` runs in `finishPlayOnQueueWithFile:…` after the request is consumed and before the source segment is reconciled, and in `configureOutputDeviceOnQueue:`'s restore branch. It reads the bound device's first output stream once, applies the rate rule (exact, else the smallest integer multiple, else untouched; scans PCM offers carrying every source channel and continuous ranges, including 3x, 6x and ratios above 16x; encoded-only rates cannot hide a usable PCM multiple) and the depth rule (the source's integer depth for lossless files or a 16-bit preference for lossy files, else the smallest integer depth above, else float32 — every Apple built-in and virtual device is float32-only), rejects physical formats with fewer channels than the source, and when the device's format or the master bus's rate differs it stops the engine itself — both callers guarantee nothing is audible — writes one `kAudioStreamPropertyPhysicalFormat`, confirms the physical format and the nominal rate for up to 1.5 s, and **brings the graph to the device's rate** through `applyOutputRateOnQueue:` (`AudioPlayer+Graph`). `acquireExclusiveOutputOnQueue` runs in `startEngineOnQueue:` before the engine starts; `releaseExclusiveOutputOnQueue` after both idle-stop engine stops, before a rebind, on mode off and at quit. Physical and virtual devices use the same `CoreAudioUtil.supportsHogModeForDeviceID:` check: the HAL hog property must exist and be writable before an acquisition is attempted. This is a capability check, not an ownership guarantee; the existing owner read-back still decides success. Loopback recording requires Exclusive output off. **A lossy source on a device prepared at 16-bit integer is decoded straight to 16-bit** (`VibeBitPerfectDecodesAsInteger16`): `decodeFormatOnQueueForFile:` gives the voice an Int16 interleaved decode format, the bus's converter does the one rounding, and the decoder expands the integers back to float exactly, so the mixer and output unit carry 16-bit-grid values unchanged. Every voice start prepares first, so the first track after launch qualifies too. Apple's MP3 decoder produces 16-bit samples natively (`ACMP3Decoder` logs its output as Int16 interleaved, and every MP3 measured decodes onto the 16-bit grid), so for MP3 and MP2 no sample changes; AAC rounds in the decoder instead of the HAL. Lossless sources keep float32, which carries them exactly. A gapless successor is decoded in its own decode format, resolved when it is queued.

**The graph runs at the bound device's rate, in every mode.** The mixer, the FX segment and the hosted unit all run at the rate `applyOutputRateOnQueue:` last applied: `followOutputDeviceRateOnQueue` reads the device's nominal rate after every bind, and the prepare applies the rate its format write settled on, so nothing in the chain resamples and the report has one rate to check. **TRAP: `applyOutputRateOnQueue:` never calls `disableManualRenderingMode`, which opens the default output device; it enables manual rendering again at the new format, which keeps every node and connection.** `outputNeedsSwitchOnQueueForFile:` still counts a mixer rate that differs from the chosen one as a switch: a rate moved under the graph by another process before its listener landed. The retained FX segment is disconnected before preparation; leaving bit-perfect restores its connections when FX is enabled, and a rate change rewires a connected segment whole (`AudioFX.setConnected:inEngine:format:`), because an effect cannot convert between its input and output.

**TRAP: an accepted format write precedes the nominal rate.** `setOutputFormatOnQueue:stream:device:` confirms every physical-format field except the reserved word and the nominal rate within 1.5 s before the graph follows the rate. Matching rate, depth and channel count alone cannot confirm a restore with different packing or byte order. Preparation and restoration share it; clearing a restore obligation early can lose the original format across live mode toggles.

**TRAP: setting `kAudioDevicePropertyHogMode` ignores the value and toggles ownership**, so `setHogOwnedByThisProcess:` reads first and writes only when the owner has to change; "owned by this process" is the whole state, and a release while another process holds it is already true. The sandboxed build takes and releases it without any entitlement. `_hoggedDeviceID` records a possible ownership obligation before the take, since a successful write followed by a failed read-back may own the device. Release retries once, then retains that slot until a later release succeeds or the manager confirms the device is gone. A second device cannot overwrite it. The report reads the actual owner of the prepared device, so an outstanding release on a previous device cannot claim exclusivity on the new one.

**Taking the system default output device moves the default; the hosted unit stays.** coreaudiod answers the hog by moving the default to another device. AVAudioEngine's default output unit used to follow that move off the device it had just been pinned to, about 50 ms after the take, which cost a settle, a re-pin, an AU listener and a recovery edge, and `-[AVAudioEngine prepare]` inside that window deadlocked the app (the system-output experiment in `docs/future/bit-perfect-output.md` keeps the measurements). A hosted HALOutput unit bound to the device stays put through the take, running or stopped, and starts under the hog in 10 ms (`hogfollow.swift hal`), so `acquireExclusiveOutputOnQueue` returns as soon as the hog is confirmed and the caller's engine start follows. `configureOutputDeviceOnQueue:` keeps the hog (with the format slot and the prepared device) on a rebuild of the device already held rather than paying the write twice.

**A switching settlement stops the engine, and nothing waits for it.** An unreadable format is unknown compatibility: it refuses to queue a gapless successor. The settlement rejects an obsolete open identifier before any device query. A format switch stops the engine, which kills every fading voice; bit-perfect output fades nothing but its declicks (`Audio/CLAUDE.md`), so the only voice that can be cut is a declick, and a declick is what a cut in this mode costs anyway.

**The chain is pruned by the switch, not the device.** With the mode on, `ensureSourceSegmentOnQueueForFile:rebuilt:` (`AudioPlayer+Graph`) builds the bus at the file's own format straight into the mixer, with no varispeed; every settlement reconciles the segment right before the voice starts, so a toggle during an in-flight open lands on the chain the mode wants — and the device rebind reconciles it on the current track, re-voicing it at the retained intent when the segment was rebuilt, which is how both mode toggles rebuild the current track in place. Measured: a varispeed at ratio 1.0 is not a pass-through (last-bit differences of about 5e-6), which is why it is removed rather than trusted.

`CoreAudioUtil.releaseDeviceObligation:attempt:isAbsent:` is the shared retry and slot-retirement loop for format restoration and exclusive release. Its tests exercise failures, retry success and confirmed removal with controlled property operations; unknown discovery keeps the obligation.

**Restore is one slot.** The first change to a device's format in a run remembers the device, its stream and the format it had; mode off, a switch to another device and `prepareForTermination` (during `applicationShouldTerminate:`) retry the write once and clear the slot only after success or a confirmed device removal — `leaveOutputDeviceOnQueue` is the restore, the prepared device forgotten and the hog released, in that order. A failed restore stays in the slot for the next leave, prepare or quit; another device may play at its existing format but cannot change format until that restore succeeds. A vanished device takes the off path verbatim: `abandonBitPerfectForVanishedDeviceOnQueue` drops the mode, restores (a confirmed removal retires the obligation) and releases before the two fallback sites bind System Output. A pending open gets the ordinary segment at its settlement, whichever device is bound by then, and the shell retains the missing device on every involuntary `-1` announcement; its stored modes survive.

**Eligibility is an allowlist of transports** (`VibeBitPerfectDeviceEligible`): built-in, PCI, USB, FireWire, Thunderbolt, HDMI, DisplayPort, AVB and virtual; Bluetooth, AirPlay, Continuity, the Remote types, aggregates and Unknown are out, and so is anything Apple adds until argued in. The System Output policy is the absence of a chosen device, not a transport — the device that happens to be the current default is judged like any other. The switch, the Output menu and the report all read the one rule. **Which device the mechanism drives is the requested id, or the destination while a switch is in flight** (`_rebindDeviceID`, set for the duration of `configureOutputDeviceOnQueue:`): the switch prepares and hogs its destination before `setOutputDeviceOnQueue:` commits the id — a failed switch must not commit — so resolving the requested id there switched the device just left. It is never the unit's own device, which names the one a switch is leaving. `AudioDevice.transportType` is read by the sweep as an optional refinement that never discards a device.

**The report** (`VibeBitPerfectReport`, `bitPerfectReport`) carries the status and every fold input, and **only the output controls are cached**: each publication computes it from its owners — the mode, the graph, the chosen device, the hog, the current file's source format (so a gapless promote reports the promoted file), and the prepared device's physical format, software volume, balance, mute and default-ness read from the HAL. The prepare records only what those reads need: the device, its stream and the format asked of it (`_prepared*`), which `formatConfirmed` compares the live format against, also requiring the hosted unit to be bound to that device, the mixer and the unit to run at the physical sample rate, successful format and output-control reads, and the installed device listener. A device at the right rate cannot confirm a graph that still resamples. Failed listener registration retries once immediately and again at the next prepare; the same-device path preserves the prepared format during that retry. An unconfirmed output reports SwitchFailed before any rate mismatch can report RateUnsupported; a successfully prepared fallback rate still reports RateUnsupported. `channelsMatch` requires the source, decoder, mixer and output-unit input to retain the source channel count. The output unit’s live `ChannelMap` must route those channels in order into the prepared physical stream, with every other hardware output silent; its one-based starting channel and physical width are read from the HAL. Wider interfaces therefore qualify without accepting a downmix, swapped pair, duplicate output or unknown map. The map is read at every publication. Rate changes preserve the mixer’s channel layout, including layouts wider than stereo. Mute has its own status even at full volume. Off-center virtual balance or driver stereo pan is VolumeScaled, with a balance-specific caption, even when the main volume is 100%; both controls are read and observed. The reader also checks the driver's main volume/mute and every source channel in the prepared stream; virtual controls may cover a different preferred layout. The listener covers every output element, including channel-only volume/mute changes. Missing optional controls mean unity/center/unmuted; unreadable or invalid controls cannot confirm the output. `depthOK` rejects non-PCM physical formats and asks whether the file's processing format carries the source as well as the device's physical format does: AVAudioFile decodes to float32, whose significand is 24 bits, so a 32-bit integer source is never Active whatever the device offers (measured: 24,641,537 came out 24,641,536). A format another process moves under the prepared device reaches its listener as a nominal-rate change, and the rebind's prepare sets the mode's format back. The publication rides the edges that already exist — `refreshOutputAudioActiveOnQueue` (every state publication and fade completion), the end of a device switch (held during the rebuild), the two hog edges and the mode toggle — plus one HAL listener on the prepared device — its output properties and its nominal rate, filtered on the player queue — and the manager's system-default change, since the user moves both mid-track. A publication that changed the report is announced through `audioPlayerDidChangeBitPerfectReport:` on main, the only edge the header's lock and the Settings caption redraw from; reading the report right after a setter sees the previous one. **The gapless splice is gated on the mode too**: a queued segment keeps the device's format, so `maybeArmGaplessOnQueue` asks `outputNeedsSwitchOnQueueForFile:` and a boundary whose next file wants another format, its channel order included, takes the settlement, which switches the device or rebuilds the bus. The idle stop waits 6 s in both modes. **The volume, balance and mute reads are the exception**: `refreshOutputAudioActiveOnQueue` republishes on every state publication and fade completion, several times per track change on the player queue, and those ten-odd reads (each behind an `AudioObjectHasProperty`) are where a USB interface can be slow — #47's A300 took ~20 ms longer per bit-perfect track change than a DisplayPort device here. They are kept per prepared device and stream while `_outputLevelListener` is registered, because that listener watches every output-scope property and clears the cache before it republishes; a fresh registration clears it too, and a failed read is never kept. A Loading publication has no file and asks for no channels, so it reuses the last track's reading. Beta builds log each fresh read and any publication whose device reads took 2 ms or more.

`AppDelegate` detaches the delegate on main; `prepareForTermination` closes admission, and uses `stopOnQueue` to retire the voice and cancel the open, the park and the successor before stopping the engine and restoring/releasing device obligations. Pending discovery, device notifications, playback and prefetch cannot restart it during `NSTerminateLater`. `outputDeviceDiagnosticSnapshot` shares the pending identity, modes, obligations and graph rates between Save Debug Info and the debug channel; it reads on the player queue, so shipping callers invoke it off main.

A model-match mode carry remains readable through `_unpersistedOutputModeSources` until the main-thread device callback has saved it. This small map is protected by `_stateLock`; queued FX edits resolve it transitively, including consecutive port changes. The callback clears only its matching entry after persistence, so later destination edits use that destination's own record. Never synchronously call main from the player queue to persist a carry.

**Losing an output parks the current voice where it is.** `parkPlaybackForMissingOutputDeviceOnQueue` stops the engine — killing every fading voice, since nothing can be heard — and pauses the current voice with a cut that lands at the first render after any restart, so no schedule survives to fire a false track end. A failed re-adoption at natural end cannot clear the already-captured finish settlement.
