# Output devices (macOS only)

The CoreAudio HAL output-device layer: `AudioDevice`, `AudioDeviceManager`, `CoreAudioUtil`, and `AudioPlayer+Devices`. The iOS counterpart is `Audio/iOS/`, which is an `AVAudioSession` and nothing like this.

`CoreAudioUtil.diagnosticDescriptionOfDeviceID:` is the one read-everything call — formats, declared latency, clock, exclusive owner — and exists for Save Debug Info (`Mac/App/CLAUDE.md`); nothing that changes a device reads it. The player's side of that report is `bitPerfectReportDictionary` and `outputDeviceDiagnosticSnapshot`, which the debug channel's `dump_state` reads too.

## AudioDeviceManager

A singleton that owns device-change listening. At init it registers CoreAudio listeners for the default output device and the device list, kept for the life of the process, then performs a post-registration sweep. `outputDevices` serves the latest immutable snapshot and waits at most 250ms for the first one on every calling thread; an unavailable `coreaudiod` therefore cannot strand a caller's serial queue.

**A snapshot is normally published only after every read agrees** — the device list, the system default, and each device's output-channel, name and UID properties, plus the default appearing in the resulting list. A partial result keeps the prior snapshot and takes the retry path rather than looking like device removal, so legitimate empty results stay representable while a transient HAL failure cannot persist a false System Output fallback.

**But strictness is bounded, because a persistent failure is not a transient one.** A virtual or aggregate driver that always fails a property read, a device with an empty name, or a default device that enumerates with no output channels would otherwise keep *every* device unpublished for the life of the process: the two-second retry never stops, the Output menu never populates, and `resolveOutputDeviceForUID:` never completes, so the saved device can never bind. After `kMaxIncompleteSweeps` (3) consecutive refusals one sweep publishes what it could read, omitting the devices that failed, and logs that it did. The three inputs with no partial form — the list, its size, and the system default — still return nil however many sweeps have failed.

**TRAP: absence in `outputDevices` is not removal.** It answers `@[]` both for "no output devices exist" and for "no sweep has been published yet", which is what the 250ms ceiling returns during setup or while a failure is retrying. Every decision that treats absence as removal — and so falls back to System Output *and persists it* — asks `knowsOutputDeviceIsAbsent:` instead, which answers NO until there is a real snapshot to be absent from. Both callers are in `AudioPlayer+Devices`: the device-list observer and `handleEngineConfigurationChange`, the latter mattering most because it is driven by `AVAudioEngine` rather than by this class and can therefore arrive before any snapshot exists.

Saved-device discovery does not use that synchronous getter. `resolveOutputDeviceForUID:modelUID:name:completion:` waits asynchronously for the first successful snapshot and matches most specific first: device UID, then model UID, then name as the compatibility fallback for settings saved before either existed. `AudioPlayer` starts on System Output. An unmatched saved preference remains pending during ordinary playback; with bit-perfect armed, a published absence disables the mode and commits System Output. A match is applied only where `VibeCanBindSavedOutputDevice` allows — the rule is stated once, under `AudioPlayer+Devices` below — and only committed after the HAL bind succeeds; if playback wins the lookup race, the intent stays pending for the next eligible transition or device/default refresh. Discovery never occupies the player's sole queue while CoreAudio is unavailable.

**TRAP: never call `outputDevices` from `_refreshQueue`.** Setup runs there, so a call from that queue before setup completes pointlessly consumes the getter's full 250ms wait ceiling on work that cannot advance until the call returns.

`refreshOutputDevicesCache` runs only on that serial refresh queue, which orders the stores, so a newer sweep can never be overwritten by an older one. The enumerator result is copied before publication. `initWithEnumerator:retryScheduler:` lets the host-less suite control the HAL and timer boundaries without registering hardware listeners; `refreshOutputDevicesWithCompletion:` is the shared refresh entry used by device notifications and the tests.

**Observers are fanned out on the main thread in the common run-loop modes**, not with a plain `dispatch_async` — GCD main-queue blocks do not run during menu tracking, and this way the devices menu refreshes while it is open. Observers (`AudioDeviceManagerObserver`) are held weakly: `AudioPlayer` and `OutputDevicesMenuController`.

## AudioPlayer+Devices

All device management on this platform: resolution, switching, config-change recovery, and parking or falling back when a device vanishes. It is a category on `AudioPlayerInternal.h`'s shared private surface, exactly as the iOS `AudioPlayer+Recovery` is, and is declared in `AudioPlayer.h` beside `(State)`.

The player's async init asks the manager to resolve the saved output device — **by device UID, then model UID, then name** — without blocking the player queue.

**TRAP: a class-compliant USB interface's device UID is its USB location, not the unit.** `AppleUSBAudioEngine` builds it from manufacturer, product and `locationID`, so the same Audient iD4 is `…:2100000:1,2` in one port and `…:1100000:1,2` in the next (measured). Such a device exposes no serial number anywhere — `kAudioObjectPropertySerialNumber` is unsupported and its USB descriptor carries none — so nothing distinguishes two of them but the port. `kAudioDevicePropertyModelUID` is the documented, port-independent identifier for the *model*, and is what finds the device on its new port. It is compared as an opaque token and never parsed; parsing the device UID would depend on an undocumented layout. Vendor drivers often key the device UID on a serial instead (an RME Fireface's is `RMEUSBDevice-205-<serial>`), and Bluetooth devices on the MAC address, so for them the device UID is already per unit. Until a successful bind, `currentlyRequestedAudioDeviceId` stays `-1` and the saved preference remains pending rather than reporting an explicit device that was never selected.

**Where that deferred bind may land is `VibeCanBindSavedOutputDevice`: whenever nothing is audible — Stopped, Loading while the engine is not running, or a Paused track whose fade has settled.** Stopped alone was not enough — launching by double-clicking a file starts an open within milliseconds of the async init, so the *first* track would play through the system default and only move to the saved device at the next track boundary. At launch nothing is rendering, so the rebind is inaudible and the in-flight open starts itself on the new device. **TRAP: an ordinary mid-session track change is also Loading**, with the outgoing node still fading out on a running engine, and rebinding there would stop the engine under that fade and click — which is why the engine check is part of the rule rather than a comment about launch. Playing is excluded outright: a failed bind there tears down live playback. **A settled pause is not excluded**, though it was until a vanished device needed it: an unplug parks playback as Paused, so excluding Paused left a device that came back unadoptable until the next stop. The rebuild restores a paused track as Paused rather than resuming it, and `_outputAudioActive` is what separates a settled pause from one whose fade is still sounding. `completePauseOfNode:` calls the resolver for exactly that reason — it is the first silent moment.

`didChangeOutputDevice:` is sent on **every** settled mutation, not only when the id moved. A refused selection reannounces the retained choice before its completion, repairing a UID cleared by Settings reset; a still-pending saved launch preference is preserved instead of being overwritten with the temporary binding. The delegate both persists the choice and drives the menu checkmark and is idempotent, so re-announcing an unchanged value is free; suppressing it left "Settings names the last committed device" a guarantee nothing enforced, and any path that left the two disagreeing could never resynchronize them, because the one call that writes Settings was skipped exactly when they already looked equal.

A vanished device and an absent launch preference share the pending identity slot. Falling back disables unavailable modes and follows System Output without forgetting that identity, so a later device/default notification or silent transport transition can re-adopt it. Every `-1` announcement derives its involuntary reason from the pending slot, including repeated default notifications. **TRAP: copy that reason by value before dispatching to main**; a successful bind or user selection may clear it before the delegate runs. Only an explicit System Output selection or successful concrete selection clears pending intent; a failed concrete selection retains it.

**TRAP: returning devices resolve synchronously against `cachedOutputDevices`.** An asynchronous answer can lose to a local open that moves Loading to Playing and makes the bind ineligible. Only initial discovery waits asynchronously; its callback re-reads the current preference and snapshot so it cannot revive an older choice. **TRAP: hold `_pendingSavedDeviceLookupInFlight` across every bind, including a cached resolution.** A refused HAL bind publishes Stopped and re-enters the resolver; without that guard it recursively rebuilds forever. An absent snapshot result with bit-perfect already off does nothing, keeping intent without resubmitting lookups.

A failed system-default property read is unknown, not absence: retain playback, try one coalesced delayed bind, then wait for a real notification. Confirmed absence parks playback. AVAudioEngine can silently follow a changed default even at the same rate; the prepared device's output-unit listener feeds configuration recovery, where a wrong binding or output rate makes the graph unhealthy. The menu checkmark follows `currentlyRequestedAudioDeviceId` (`Mac/Menu/`).

Both engine-configuration and output-unit device events enqueue the same recovery block. Recovery never rebuilds inside the AU listener's event drain: a bind emits another event, and rebuilding there while Loading could keep the drain running forever, starving the pending file's settlement and the UI's queue reads. With bit-perfect enabled, Loading on the intended device, like Stopped, needs no recovery merely because the engine is stopped; settlement starts it. A real binding mismatch still rebuilds without consuming the open. With the mode off, recovery keeps the original health check and Stopped return, and reads the output binding only for the original paused-graph check. Whichever branch runs, the recovery publishes the report once at its end, so neither caller does.

Selecting the already-active device still rebuilds when bit-perfect output is wanted but that device has not been prepared, so a newly eligible selection prepares the current track too. A device switch stops the node, so it must clear the armed gapless splice first and re-arm after its reschedule — see `Audio/CLAUDE.md`.

## Bit-perfect output

`AudioPlayer.setBitPerfectOutput:exclusiveOutput:enableFX:` (Settings > Audio) delivers each file's decoded samples to the chosen device unchanged.

**Both modes belong to the destination UID.** `AppSettings` remembers only enabled modes, retaining entries while devices are unplugged. The shell supplies them through `audioPlayer:outputModesForDeviceUID:bitPerfectOutput:exclusiveOutput:`, a read-only delegate query supporting main and the player queue. Explicit selection and saved-device resolution share `selectOutputDeviceOnQueue:`, which reads the destination's modes before the one rebuild and restores the previous flags if the switch commits nothing. **TRAP: a failed rebuild may already have rewired or prepared the destination.** After restoring the flags, a Stopped player stops the engine and takes the existing `leaveOutputDeviceOnQueue` cleanup, reconciling the master bus and retiring the failed destination's format, listeners and hog obligations. A failed pin that left live playback intact does not tear it down. **TRAP: a name fallback can resolve a different UID; read its own modes before preparing or hogging it, never the missing device's flags.** Pushing modes after a bind would first rewrite the format of, and possibly hog, a device whose mode is off. **The one exception is a model-UID match under a new device UID** — the same model on another USB port, not a stranger sharing a name. Only when the destination has no saved enabled modes does `selectSavedOutputDeviceOnQueue:` use `_modesUIDForNextSelection` to read the old UID. An existing destination entry wins before any hardware mutation. `carriedOutputModesDeviceUID` carries that actual decision by value into the delegate callback; the shell persists only that carry on main through `AppSettings.carryOutputModesFromDeviceUID:toDeviceUID:`. A manual selection never infers a carry from matching models. The carry copies rather than moves, so the old port keeps its entry, and never overwrites modes already chosen for the destination. The residual: two identical units of one model share modes, because the OS cannot tell them apart. Queued mode/FX edits reread the queue's current UID (or the still-pending saved UID), so a snapshot submitted behind a switch cannot overwrite the destination's preferences. System Output has no UID and reads off. If its default-device read fails or reports no output, its committed mode change still rebuilds the current binding: an unknown read preserves playback, while confirmed absence parks it. The public selection completion runs on main after the device callback, including failed switches, so the shell can release its mode-edit guard. `setOutputDeviceOnQueue:` also rebuilds when only the standing graph disagrees with the flags: switching a bit-perfect device to System Output may leave the unit on the same hardware but must restore its format and FX route. The decisions are `OutputFormatRules.h`; raw HAL reads and writes are `CoreAudioUtil`'s. The loopback oracle (`verify-bit-perfect.swift`) measures 44.1, 48, 88.2 and 96 kHz WAVs and a 96/24 FLAC sample-exact.

**Exclusive output is a separate opt-in**, off by default, below Bit-perfect output. Bit-perfect, exclusive output and the saved FX preference land on the player queue in one setter and use the existing same-device rebuild to preserve the current track, position and pending pause intent. The rebuild reads `getPlaybackIntent:forTrack:` before preempting ramps and settles a consumed pause through the usual delegate callback. Changed settings stop the engine before changing ownership. Reapplying identical settings returns without rebuilding; an exclusive preference changed while bit-perfect is off is saved without touching the graph. Disabling exclusivity releases the device without restoring its format or adding a varispeed; disabling bit-perfect output restores the format and releases it through `leaveOutputDeviceOnQueue`, inside the rebuild after the engine stopped. While saved-device discovery is pending, the switch still permits turning bit-perfect off: the same rebuild restores varispeed while keeping the current binding, without depending on a device read or changing that policy. Restoring a hogged device while the engine was still running stranded the next start in CoreAudio with error 35. An in-flight open also stops/rebinds the warm engine without consuming the request, so its settlement starts with the latest exclusive preference. Termination stops the engine before restoring and releasing too. The saved exclusive preference survives a bit-perfect toggle, but can act only while bit-perfect output is on; with an eligible device prepared, it *is* `hogWanted`. **The device that happens to be the system output is taken like any other** — the trap below is what that costs and how it is paid — so the only device the mode refuses is one whose transport is ineligible or whose HAL hog property is not writable.

**Compile-time removal:** `VIBE_ENABLE_EXCLUSIVE_OUTPUT` defaults to `1` in `project.yml`. Set it to `0` there, regenerate the project, and every build path omits the exclusive row, its action and writable preference, the player's ownership state and acquire/release methods, and the HAL hog reader/writer. The getter answers NO even over a saved YES. Bit-perfect rate/depth matching, graph pruning and reports remain. For a single build, pass `VIBE_ENABLE_EXCLUSIVE_OUTPUT=0` to `xcodebuild`; both Debug and Release use the flag.

**Off is dormant.** Every bit-perfect entry point gates itself on `_bitPerfectWanted` — the report's publication on that and the Off report already being out — so ordinary playback, gapless checks, state changes, engine starts and device recovery call them without repeating the check. Disabling publishes one zeroed Off report and removes both device listeners after restoring the device. No report recomputation, format negotiation, volume read or hog attempt runs during disabled playback. Cleanup of a failed restore, listener removal or release is retained and retried at the next cleanup edge, never by polling. Listener removal retries once and keeps its exact handle on failure, refusing to register a second device until it succeeds. Both the output-control listener and the output-unit binding listener exist only for a prepared bit-perfect device. Disabled playback keeps the original mixer format, creates its varispeed at submission, and uses the original six-second idle stop. A mode toggle restores the saved mixer connection before returning to this path.

**The format rides the play settlement; the hog rides the running engine.** `prepareOutputOnQueueForFile:` runs in `finishPlayOnQueueWithFile:…` after the request is consumed and before the node is attached, and in `configureOutputDeviceOnQueue:`'s restore branch. It reads the bound device's first output stream once, applies the rate rule (exact, else the smallest integer multiple, else untouched; scans PCM offers carrying every source channel and continuous ranges, including 3x, 6x and ratios above 16x; encoded-only rates cannot hide a usable PCM multiple) and the as-is depth rule (the integer depth equal to the source's, else the smallest above, else float32 — every Apple built-in and virtual device is float32-only), rejects physical formats with fewer channels than the source, and when the device's format or the master bus's rate differs it stops the engine itself — both callers guarantee nothing is audible — writes one `kAudioStreamPropertyPhysicalFormat`, polls the nominal and output-unit rates back for up to 1.5 s, and **rewires `mainMixer → outputNode` at the device's rate** through `reconnectMasterBusOnQueueWithFormat:`, retaining the original mixer connection until the device is left. `acquireExclusiveOutputOnQueue` runs in `startEngineAndPlayNode:` before the engine starts; `releaseExclusiveOutputOnQueue` after both idle-stop engine stops, before a rebind, on mode off and at quit. Physical and virtual devices use the same `CoreAudioUtil.supportsHogModeForDeviceID:` check: the HAL hog property must exist and be writable before an acquisition is attempted. This is a capability check, not an ownership guarantee; the existing owner read-back still decides success. Loopback recording requires Exclusive output off.

**TRAP: the mixer's default output rate is 44.1 kHz whatever the device, and the output unit resamples the difference silently** — measured at 1.4e-3 against a 48 kHz device. That is why bit-perfect preparation rewires the FX-less master bus at the chosen device rate, and why `outputNeedsSwitchOnQueueForFile:unknownNeedsSwitch:` counts a mixer rate that differs from the chosen rate as a switch: a device whose rate moved under a running engine leaves the connection stale until the next settlement rewires it. The retained FX segment is disconnected before preparation; leaving bit-perfect restores its original connections when FX is enabled.

**TRAP: an accepted format write and even the nominal rate can precede the output unit.** `setOutputFormatOnQueue:stream:device:` confirms every physical-format field except the reserved word, the nominal rate and, for the bound device, the output-unit rate within 1.5 s. Matching rate, depth and channel count alone cannot confirm a restore with different packing or byte order. Preparation and restoration share it: starting early leaves stale render-buffer sizing and `node.play` waiting for IO that fails with `TooManyFramesToProcess`; clearing a restore obligation early can lose the original format across live mode toggles.

**TRAP: setting `kAudioDevicePropertyHogMode` ignores the value and toggles ownership**, so `setHogOwnedByThisProcess:` reads first and writes only when the owner has to change; "owned by this process" is the whole state, and a release while another process holds it is already true. The sandboxed build takes and releases it without any entitlement. `_hoggedDeviceID` records a possible ownership obligation before the take, since a successful write followed by a failed read-back may own the device. Release retries once, then retains that slot until a later release succeeds or the manager confirms the device is gone. A second device cannot overwrite it. The report reads the actual owner of the prepared device, so an outstanding release on a previous device cannot claim exclusivity on the new one.

**TRAP: taking the system default output device moves it, and the output unit follows.** coreaudiod answers the hog by moving the default to another device, and AVAudioEngine's output unit — a default output unit whatever `kAudioOutputUnitProperty_CurrentDevice` was set to — follows the default off the device it was just bound to. Measured (`hogfollow.swift` in the `vibe-debug` skill, and the system-output experiment in `docs/future/bit-perfect-output.md`): the default has already moved when the hog write returns, but **the unit follows about 50 ms LATER**, so reading the unit straight after the take still names the right device and proves nothing. `settleOutputUnitAfterHoggingSystemDefaultOnQueue:` therefore waits for the follow to land before pinning the unit back, and pins until a read agrees. Pinning inside that window is simply followed again, and an engine started inside it never gets an IO cycle: `[AVAudioPlayerNode play]` blocks five seconds in `awaitIOCycle` and the recovery rebuilds the graph underneath it — the whole visible cost of getting this wrong. **Even after the unit has left, the pin can collide with the follow's own `SelectDevice` still finishing** (#47's AirPulse A300, at launch): AUHAL answers `'nope'` having created the device's IO proc but not updated the unit's stream formats, so the unit reads as bound to the right device at the old device's rate. A same-device pin is then a no-op, so retrying cannot repair it; `recoverEngineConfigurationOnQueue` does, because in bit-perfect mode it also requires the unit's hardware format at the device's rate, and AVAudioEngine posts a configuration change right after. Before that check the graph read as healthy and the report said "switch failed" for the whole session. **TRAP: `-[AVAudioEngine prepare]` must not be used to absorb the re-bind.** It `dispatch_sync`s onto the AVAudioIOUnit queue, which is draining the property listener for that very re-bind and is blocked in CoreAudio while the HAL reorganizes around the take; the player queue deadlocks against it and the app hangs. The settle runs only when a follow is actually coming — the device was the default *and* the unit was bound to it, both read before the take, an unreadable default counting as "it was" — so an ordinary non-default take pays nothing. `configureOutputDeviceOnQueue:` keeps the hog (with the format slot and the prepared device) on a rebuild of the device already held rather than paying the write twice.

**A switching settlement parks until the outgoing audio is silent.** An unreadable format is unknown compatibility: it refuses gapless arming and waits for outgoing silence before preparation can retry the read. Paused recovery passes NO for that unknown case, so a persistent read failure cannot rebuild repeatedly from its own configuration events. The settlement rejects an obsolete open identifier before any device query or park, so a late result cannot replace the current request's parked block. A format switch stops the engine, which would cut a still-fading node mid-waveform, so `finishPlayOnQueueWithFile:…` parks itself in `_settlementWaiter` when a switch is needed while `_activeRetiredOutputCount > 0`, preempts the fades to the declick length, and `completeRetiredFadePair:` re-enters it verbatim at count zero; `consumeRequest:` then drops a re-entry a newer play or a stop superseded, so no generation is needed.

**The chain is pruned by the switch, not the device.** With the mode on, `ensureVarispeedOnQueue` (in `AudioPlayer.m`) mints nothing and `connectNode:throughVarispeedWithFormat:` connects node → mixer directly; the enabled settlement reconciles it right before the incoming node is connected, so a toggle during an in-flight open lands on the chain the mode wants — and the device restore calls it on the current track, which is how both mode toggles rebuild the current track in place. Measured: a varispeed at ratio 1.0 is not a pass-through (last-bit differences of about 5e-6), which is why it is removed rather than trusted.

`CoreAudioUtil.releaseDeviceObligation:attempt:isAbsent:` is the shared retry and slot-retirement loop for format restoration and exclusive release. Its tests exercise failures, retry success and confirmed removal with controlled property operations; unknown discovery keeps the obligation.

**Restore is one slot.** The first change to a device's format in a run remembers the device, its stream and the format it had; mode off, a switch to another device and `prepareForTermination` (during `applicationShouldTerminate:`) retry the write once and clear the slot only after success or a confirmed device removal — `leaveOutputDeviceOnQueue` is the restore, the prepared device forgotten and the hog released, in that order. A failed restore stays in the slot for the next leave, prepare or quit; another device may play at its existing format but cannot change format until that restore succeeds. A vanished device takes the off path verbatim: `abandonBitPerfectForVanishedDeviceOnQueue` drops the mode, restores (a confirmed removal retires the obligation) and releases before the two fallback sites bind System Output. A pending open regains its normal varispeed immediately, even if the fallback is already bound or unavailable, and the shell retains the missing device on every involuntary `-1` announcement; its stored modes survive.

**Eligibility is an allowlist of transports** (`VibeBitPerfectDeviceEligible`): built-in, PCI, USB, FireWire, Thunderbolt, HDMI, DisplayPort, AVB and virtual; Bluetooth, AirPlay, Continuity, the Remote types, aggregates and Unknown are out, and so is anything Apple adds until argued in. The System Output policy is the absence of a chosen device, not a transport — the device that happens to be the current default is judged like any other. The switch, the Output menu and the report all read the one rule. **Which device the mechanism drives is the requested id, or the destination while a switch is in flight** (`_rebindDeviceID`, set for the duration of `configureOutputDeviceOnQueue:`): the switch prepares and hogs its destination before `setOutputDeviceOnQueue:` commits the id — a failed switch must not commit — so resolving the requested id there switched the device just left. It is never the output unit's own device, which follows the system default whenever that moves — a take of the default makes it do exactly that (the hog trap above) — so reading it names a device the engine is about to leave. `AudioDevice.transportType` is read by the sweep as an optional refinement that never discards a device.

**The report** (`VibeBitPerfectReport`, `bitPerfectReport`) carries the status and every fold input, and **nothing in it is cached**: each publication computes it from its owners — the mode, the graph, the chosen device, the hog, the current file's source format (so a gapless promote reports the promoted file), and the prepared device's physical format, software volume, balance, mute and default-ness read from the HAL. The prepare records only what those reads need: the device, its stream and the format asked of it (`_prepared*`), which `formatConfirmed` compares the live format against, also requiring the output unit to be bound to that device, the mixer output and both sides of the output unit to match the physical sample rate, successful format and output-control reads, and an installed output-control listener. A device at the right rate cannot confirm a graph that still resamples. Failed listener registration retries once immediately and again at the next prepare; the same-device path preserves the prepared format during that retry. An unconfirmed output reports SwitchFailed before any rate mismatch can report RateUnsupported; a successfully prepared fallback rate still reports RateUnsupported. `channelsMatch` requires the source, decoder, mixer and output-unit input to retain the source channel count. The output unit’s live `ChannelMap` must route those channels in order into the prepared physical stream, with every other hardware output silent; its one-based starting channel and physical width are read from the HAL. Wider interfaces therefore qualify without accepting a downmix, swapped pair, duplicate output or unknown map. The existing AU listener also watches the channel map, and both listeners must be installed before confirmation. Rate changes preserve the mixer’s channel layout, including layouts wider than stereo. Mute has its own status even at full volume. Off-center virtual balance or driver stereo pan is VolumeScaled, with a balance-specific caption, even when the main volume is 100%; both controls are read and observed. The reader also checks the driver's main volume/mute and every source channel in the prepared stream; virtual controls may cover a different preferred layout. The listener covers every output element, including channel-only volume/mute changes. Missing optional controls mean unity/center/unmuted; unreadable or invalid controls cannot confirm the output. `depthOK` rejects non-PCM physical formats and asks whether the file's processing format carries the source as well as the device's physical format does: AVAudioFile decodes to float32, whose significand is 24 bits, so a 32-bit integer source is never Active whatever the device offers (measured: 24,641,537 came out 24,641,536). The paused recovery in `handleEngineConfigurationChange` accepts the paused graph only while `outputNeedsSwitchOnQueueForFile:unknownNeedsSwitch:` is NO — a format another process moved during the pause is what that notification often is, and the rebuild's prepare sets it back before the resume. The publication rides the edges that already exist — `refreshOutputAudioActiveOnQueue` (every state publication and fade completion), the end of a device switch (held during the rebuild), the two hog edges and the mode toggle — plus an output-unit device listener (same-rate default changes can move the engine without its configuration notification), one HAL listener on the prepared device's output properties, filtering volume, balance and mute changes on the player queue, and the manager's system-default change, since the user moves both mid-track. A publication that changed the report is announced through `audioPlayerDidChangeBitPerfectReport:` on main, the only edge the header's lock and the Settings caption redraw from; reading the report right after a setter sees the previous one. **The gapless splice is gated on the mode too**: a queued segment keeps the device's format, so `maybeArmGaplessOnQueue` asks `outputNeedsSwitchOnQueueForFile:unknownNeedsSwitch:` and a boundary whose next file wants another format takes the settlement, which switches. The idle stop waits 6 s in both modes.

`prepareForTermination` detaches the delegate, closes admission, and uses `stopOnQueue` to cancel segments, fades, opens and gapless work before stopping the engine and restoring/releasing device obligations. Pending discovery, device notifications, playback and prefetch cannot restart it during `NSTerminateLater`. `outputDeviceDiagnosticSnapshot` shares the pending identity, modes, obligations and graph rates between Save Debug Info and the debug channel; it reads on the player queue, so shipping callers invoke it off main.
