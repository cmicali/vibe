# Audio: playback engine, FX, metadata, devices, waveform data, BPM, conversion

## Playback engine

`AudioPlayer` drives an `AVAudioEngine` with a fresh `AVAudioPlayerNode` per track. State machine `{Stopped, Playing, Paused, Loading}`; `Loading` covers the in-flight file open, reports `isPlaying`, and gives position and duration of zero.

**Threading.** Every engine mutation runs on a serial `dispatch_queue` (`com.vibe.audioplayer`, default QoS). The UI-facing getters — `position`, `duration`, `isPlaying` — read under an `os_unfair_lock` and never block. Two generation counters sort out async work: `_generation` discards stale `scheduleSegment` completions, and `_rampGeneration` cancels in-flight volume fades, which stop, seek, skip and device switches all bump first. Every fade is asynchronous, so the queue never sleeps. `run_on_main_thread()` dispatches UI updates back.

**Crossfades and seeks.** The track-change crossfade's length is `crossfadeMilliseconds` (default the 10ms declick minimum; Settings > Playback offers 500 and 2000). It applies only when a play replaces an *audibly playing* track — first plays and the pause, seek and stop declicks always run at the minimum, so transport stays instant, and `play:atPosition:startPaused:` (the convert swap) forces the minimum too: it replaces a track with its own audio, which a crossfade would only dip. Both sides ride the queue-confined `_incomingFadeMilliseconds`: the outgoing retire set in `playOnQueue:` and the fade-in when the open lands in `finishPlayOnQueue:`. Longer fades keep ~10ms per step (`VibeFadeStepsForMilliseconds`), so the curve stays smooth rather than ten audible stairs. Crossfade-length fades ride the equal-power curve — complementary out/in sides sum to ~unity power, so a 2s crossfade holds level instead of dipping to near-silence at the midpoint — while declick-length fades keep the log curve; `VibeFadeVolumeForFadeLength` picks per fade length (`VibeFadeCurve.h`). A track change crossfades on two independent chains: each track gets its own `AVAudioUnitVarispeed`, minted in `playOnQueue:`, with `_varispeed` always pointing at the current or incoming track's. The outgoing node's live connection is never rerouted — it fades out on its own varispeed and is detached, varispeed and all, once silent, while the incoming node fades in from silence on the new one (`finishPlayOnQueue:`, same ramp generation). Reconnecting a live node reconfigures the graph and clicks — exactly what per-track varispeeds avoid; they also remove the mono-to-stereo output-unit restart, since each varispeed is connected once, for one format. The fade-in also declicks the incoming first frame, rarely a zero crossing.

A seek while playing declicks *without reconnecting the graph at all* — reconnecting a live node is itself a click on a running engine. `seekToPosition:` fades the current node down, reschedules it in place at the new frame inside the fade-out completion, then fades back up, so both the `[node stop]` and the new segment's start land at silence. A paused seek simply reschedules the silent node.

**Robustness.** A last-valid-position cache preserves the playhead when the engine stops itself (device unplug, format change) before recovery can read it. Files open off-queue with a timeout, so an undownloaded iCloud or Dropbox placeholder cannot wedge playback; a slow open surfaces Loading instead. `stop` (File > Close) unloads outright: it supersedes any in-flight open so a Loading track never starts, fades a playing node to silence before teardown, and deliberately fires no delegate callback — not a track-end event, so it must not drive auto-advance, and the caller owns the UI reset.

**Prefetch and idle.** The controller calls `prefetchTrack:` on every track start to pre-open the likely next track; the next `play:` of that path consumes the parked `AVAudioFile`, so auto-advance and skip pay no file open. The engine stops when playback goes idle — Stopped or Paused — releasing the output device, and restarts lazily; the stop is deferred about six seconds and cancelled by generation in `startEngineAndPlayNode:`, so consecutive tracks reuse the running engine and resume-from-pause pays only the engine restart.

**Gapless auto-advance.** With the crossfade off (the declick minimum) and the prefetched next file matching the current connection format — sample rate and channel count, `GaplessSpliceMath.h` — the prefetch also opens a *private second handle* and schedules it as a second segment on the current node (`maybeArmGaplessOnQueue`), which `AVAudioPlayerNode` renders back-to-back sample-accurately. The private handle matters: `AVAudioFile` has one stateful read position and the node pre-reads scheduled files, so the armed segment must never share the parked instance a `play:` would consume. The current segment's completion then means "boundary passed", not "playback stopped": `promoteGaplessOnQueue` republishes the queued file as current *in place* — no node stop, no fade, no graph mutation, `_generation` deliberately not bumped — with a zero-or-negative `_segmentStartFrame` (`playerTime.sampleTime` is monotonic across queued segments; the position getter's math is signed), and fires `didAutoAdvanceFromTrack:toTrack:` so the controller advances the playlist *without* calling `play:`. A track's end fires exactly one of `didFinishPlaying:` or the auto-advance callback, never both. INVARIANT: every `[node stop]` of the current node drops its queued segment, so every such site — seek, idle-stop repark, device switch, the retire in `playOnQueue:`, stop and the failure resets — clears the armed flag first (`setGaplessQueuedOnQueue:`), and the sites that reschedule the same file re-arm after their reschedule. When the playlist's *next* changes under an armed splice (convert swap), `prefetchOnQueue:` unqueues by rescheduling the current remainder through the seek path, the only click-free way to drop a queued segment — and raising the crossfade setting mid-track unqueues the same way (`setCrossfadeMilliseconds:`), while lowering it re-arms. Because a promote can land between a main-thread action and its queue block, intent is snapshotted: `seekToPosition:` and `finishCurrentTrack` capture the current track at dispatch and drop the request if the boundary advanced it, and the promote's own delivery is snapshot-guarded like `finishPlaybackOnQueue`'s, so a play racing the boundary can never leave the playlist a row ahead of the audio. Format-mismatched or crossfading transitions keep the classic teardown path. CoreAudio honors LAME/iTunes gapless metadata, so tagged MP3/AAC and all lossless files splice seamlessly; an untagged MP3's own baked-in encoder padding is the one gap this cannot remove. `isGaplessArmed` (lock-free) surfaces the armed state to the debug channel's `dump_state`.

**Devices.** The async init resolves the saved output device on the player queue, by UID first and name as fallback, keeping device enumeration off the launch path's main thread. All device management — resolution, switching, config-change recovery, parking or falling back when a device vanishes — lives in the `AudioPlayer+Devices` category.

## Convert to FLAC (`Convert/`)

Convert > Convert to FLAC and the window body's right-click item re-encode the *current track* as FLAC beside it — the app's only write path. Current-track-only is deliberate: a background row's conversion has no progress surface, and its swap has no playback state to preserve.

**The encoder is CoreAudio's** (`AVAudioFile` with `kAudioFormatFLAC`): no new dependency, nothing for `THIRD-PARTY-NOTICES.md`. ffmpeg was never an option — the app is sandboxed and ships in the App Store.

TRAP: **the buffer's `commonFormat` is the only thing that sets the FLAC's declared source bit depth.** `AVEncoderBitDepthHintKey` and `AVLinearPCMBitDepthKey` are both silently ignored by this encoder. Int16 buffers give a 16-bit FLAC; anything wider gives 24-bit, the format's ceiling — so `encodeSource:` picks the buffer format from the source's own depth, or a 16-bit recording is written as a 24-bit file that is bit-exact but misdescribes itself and is larger.

**Getting the output past the sandbox is the hard part.** `ENABLE_USER_SELECTED_FILES: readwrite` covers files the user actually opened, not a *new sibling* of one. The converter encodes into the container's tmp, then tries three rungs, cheapest first (unless `AppSettings.convertAsksWhereToSave` — Settings > Convert — is on and a window exists, which skips straight to the panel rung; snapshotted at accept like the delete toggle. Ask-mode also lifts the destination-exists refusal and its menu disable — the panel saves under another name or replaces atomically after its own prompt): a plain move (works when the grant was a folder); a coordinated move against an `NSFilePresenter` whose `primaryPresentedItemURL` is the source (works for a single-file grant); and an `NSSavePanel` pre-filled with the folder and name (its own grant always works). The first two run on the converter queue, not main: file coordination blocks until every other presenter of the URL relinquishes it — other processes and the file-provider daemon included, unbounded on an iCloud or network folder. Only the panel hops to main.

TRAP: **the related-item rung's sandbox extension lives exactly as long as the presenter registration.** Unregistering after the move leaves a file the app has just written and can no longer *read* — the player fails with `avfaudio error -54` — so presenters stay registered for the session, which the app needs anyway: the file is now in the playlist. The rung also needs the flac extension declared in `CFBundleDocumentTypes` with `NSIsRelatedItemType`, separate from the real "Audio Files" entry; `DocumentTypes.declaredTypes` skips related-item entries so the type is not claimed twice.

`FLACTagCopier` carries the source's ID3v2 tag over with TagLib: `setProperties` for the scalars (its `PropertyMap` normalizes ID3 spellings to Vorbis ones, `TBPM` → `BPM`) plus the front-cover picture. Failure is non-fatal — an untagged FLAC is still the user's audio, and every display path falls back to the filename.

`FLACConvertRules.h` holds the eligibility and naming rules as static inlines, so the unit tests reach them without compiling the converter or TagLib. Eligibility is WAV and AIFF only: the sniffed `metadata.fileType` decides once it exists; the extension covers the window before the background scan reaches a freshly dropped row.

`progressHandler` reports the encode on the main thread at about one-percent steps, with the converting track so the owner can tell whether it is on screen. It drives the waveform's brush-through sweep; see `Waveform/CLAUDE.md`.

**Disposing of the source.** `trashSourceIfEnabled:convertedTo:` acts on Convert > Delete Original, off by default and snapshotted when the conversion is accepted — a toggle flipped mid-encode applies to the next conversion, as the menu items say, never the one in flight. Trash rather than unlink: undoable, and recoverable from the Finder. It refuses when the output resolves to the source itself — no rung can produce that, but the loss would be the audio. Failure is logged and otherwise ignored; the conversion succeeded either way. The single-file grant covers the trashing — the source is exactly the file the user opened. The completion reports where the Trash put the file, which the controller folds into the undo record. **Who calls it, and when, is the controller's** — the player holds the source open until the swap; see `Main Window/CLAUDE.md`.

**Undoing the conversion** is the controller's too, through `NSUndoManager` (`Main Window/CLAUDE.md`); the converter contributes only the file primitives `trashItemAtURL:completion:` and `restoreTrashedItemAtURL:toURL:completion:`. All three disposal calls run on their own serial dispose queue, not the converter queue — an undo never waits out an encode, and a move a cloud folder makes unbounded stays off the main thread; completions land on main. Both moves run inside coordinated writes, because a FLAC only the related-item rung could place lives at a path whose sandbox extension rides the presenter's file coordination — a bare move there is denied. The restore's move refuses to overwrite, so something new at the original path blocks it rather than being clobbered.

TRAP: **menu validation must never stat the file system.** It runs on the main thread on every menu open, and a stat on an unreachable network mount blocks until the mount times out. The FLAC-already-exists answer is a cache each validation re-warms off-main — stale by at most one menu open, safe stale: the conversion re-checks before writing. The Edit menu's undo items likewise read `NSUndoManager`'s stack alone; an emptied Trash surfaces only when the restore runs — log, beep, Trash revealed.

## Performance effects

`AudioPlayer` owns `AudioFX` (readonly `fx`): the low-kill high-pass, with its Q key and W double-cutoff boost, and the send-returns — E a long reverb wash, R and T BPM-synced ping-pong delays on 1/8- and 1/16-note taps, fed by the controller through `delayTapBPM`.

`AudioFX` stores plain on-off state per effect; telling a tap from a hold is `TransportKeyMonitor`'s job. One coupling is enforced here so every path — key, menu, debug — gets it: clearing `lowKillEnabled` also clears `lowKillBoostActive`. The boost modifies that filter, so a latched W must not outlive the low kill and hold the cutoff up while the low kill reads off.

The class owns the whole master-bus graph segment between `mainMixerNode` and `outputNode`: low-kill EQ, then a dry path plus gated parallel returns, then the master mix. `installInEngine:` wires it once on the player queue during the async init; the `AudioFX` object is created synchronously, so intent set before the engine exists is applied at install. Every toggle is click-free — cutoff sweeps and gate fades on the player queue with generation-counter preemption like the player's volume ramps. Its .m comments record the hard-won AVFAudio traps: MatrixReverb's stale header ranges assert in the render thread, mixer volume and pan writes before attach are dropped, and EQ bypass flips click.

## Metadata (`Metadata/`)

`AudioTrackMetadata` uses TagLib to extract title, artist, album art and codec information. `AudioTrackMetadataCache` persists through PINCache with `NSSecureCoding`; `parsedOK` marks failed parses, which are shown but never cached.

The playlist scan runs in two stages on one four-worker queue. High-priority cache checks — a stat and a small disk read, never the audio data, so a dataless cloud placeholder cannot block them — sweep first and publish every previously seen track at disk speed. Misses re-enqueue as parses, dataless placeholders demoted below local files so a cloud-heavy folder cannot pin all four workers.

The current track skips the scan: `loadMetadataNow:` from `didBeginLoading:` and `didStartPlaying:`, in a persistent user-initiated lane, so the header's tags and art never queue behind the sweep. On a miss it skips the parse while the file is still dataless — the player's own open is materializing it — and the `didStartPlaying:` call retries once local.

Album art: the disk cache stores only a 128px thumbnail JPEG; full-resolution art decodes on demand, capped at 1024px through ImageIO, for the current track alone, and `discardDecodedAlbumArt` demotes it on track change. No lock is ever held across file I/O or an image decode — a cloud file can block a read indefinitely.

## Devices

`AudioDeviceManager`, a singleton, owns device-change listening. At init it registers CoreAudio listeners for the default output device and the device list, kept for the life of the process. It fans out to weakly held `AudioDeviceManagerObserver`s — `AudioPlayer` and `OutputDevicesMenuController` — on the main thread in the **common run-loop modes**: GCD main-queue blocks do not run during menu tracking, and this way the devices menu refreshes while open.

## Waveform data (`Waveform/`) and BPM/key detection (`Analysis/`)

Rendering lives in `Vibe/Waveform/` (see its `CLAUDE.md`); this directory owns the data.

`AudioWaveform` is a C++ structure storing one min/max float pair per chunk. `AVFAudioWaveformLoader`, backed by `AVAudioFile`, generates waveform data asynchronously and hands immutable snapshots to the main thread for progressive rendering. The pass is decode-bound — CoreAudio's MP3 and FLAC codecs cost 3-5x everything downstream combined, and the read block size does not move that floor — so the loader pipelines the decode against the processing: block N+1 decodes while block N runs through the mono mix, the analyzers and the chunker on a serial queue one block behind, ping-ponging two buffers whose reuse the per-slot semaphores gate. That takes the wall time down to roughly the decode alone, and the output is exact, because the serial queue preserves the stream order the analyzers' framing depends on. All processing-side state, the progress throttle and its snapshots included, lives on that queue and is read only after the final drain. Cache lookups run on `AudioWaveformCache`'s serial loader queue, but the open and decode run on a global utility queue: the `AVAudioFile` open has no cancellation point and can block for minutes on a cloud placeholder — off-queue it strands one worker rather than wedging every later track's waveform. Persistence via PINCache.

`AudioBPMAnalyzer` (ObjC++ and Accelerate) detects tempo on the waveform loader's decode pass, so it costs no second file read. `AppSettings.analyzeBPM` (Settings > Playback, default on) gates that ride-along: off, the waveform caches with no BPM, so a file scanned while off is not re-analyzed on re-enable until its cache entry goes; tagged BPM and the explicit `scan_bpm` debug path are unaffected. While streaming it builds a power-spectrum spectral-flux onset envelope. At end of file: autocorrelation and a harmonic comb over 60–200 BPM; a time-domain phase comb rescores the top candidates — refining each candidate's fractional period against the envelope over a window of ≤40 seconds — to resolve 2:1 and 3:2 metrical errors; then a tolerance-free interpolated fine pass polishes the winner's period. The coarse comb's jitter window flattens its score into a plateau about ±0.1 BPM wide; the fine pass lands within roughly ±0.01 BPM on a steady tempo. Below a confidence gate it returns 0 — noise, speech, rubato. Measure with the vibe-debug skill's `scan-bpm.sh` against the generated `bpm-*.wav` loops; no app launch needed.

**Cost.** Both analyzers together run at roughly 6,000x realtime in Release, about a fifth of the decode they ride along with — and since the loader pipelines that decode against them (see Waveform data above), they add nothing to the load's wall time, only CPU; `scan_bpm`/`scan_key` report the `streamSeconds`/`finishSeconds` split, though in Debug, where -O0 inflates whatever is not a vDSP call. What is left in each is almost entirely its FFT — 172 1024-point ones a second for the tempo, 2.7 32768-point ones for the key — so making them cheaper again means fewer or smaller frames, not tighter code around them. **Decimating for the key analyzer is not one of those ways**, tempting as its 3520 Hz ceiling makes it look: even a short decimating FIR runs on every sample and would cost more than the whole analyzer, which pays for its big FFT only 2.7 times a second.

Four rules hold the current floor, each measured rather than assumed:

- **Every per-bin or per-sample reduction goes through vDSP**, never a written-out loop: a per-sample branch does not predict, a single accumulator serializes on float-add latency, and a written-out spectral-flux loop cost several times the FFT ahead of it.
- **Touch only the band that votes.** The key analyzer's chroma band is a sixth of its spectrum; the magnitude and fold passes run over the band alone.
- **A scatter becomes a run.** Within the band each semitone's voting bins are contiguous, so the chroma fold is one reduction per semitone instead of a scatter-add per bin, and the harmonic spreading is 12 operations on the folded result rather than two per bin. The same reshaping settles the phase comb, which is swept **a beat at a time rather than a phase at a time**: a grid's phase offset is an integer, so every phase reads the same beat offsets and one vDSP add per beat scores all of them at once.
- **`vDSP_DFT` is not a drop-in win over `vDSP_fft_zrip`.** It takes a third off the key analyzer's 32768-point frames and *loses* on the tempo analyzer's 1024-point ones, which is why the two differ. Nor is fusing the window into the de-interleave: a strided multiply straight into split-complex beat `vDSP_vmul` plus `vDSP_ctoz` in a microbenchmark and lost in both analyzers in situ. Microbenchmarks mislead here — measure a real decode.

The tempo analyzer's summation order and double accumulators are accuracy-bearing — changing them changes results. `Tests/AudioBPMAnalyzerTests.mm` and `Tests/AudioKeyAnalyzerTests.mm` pin the framing invariant both analyzers rely on — the buffer sizes the decoder happens to hand an analyzer never reach its result — because both frame in place out of the caller's buffer and copy only what straddles a boundary.

**Accuracy is validated against GiantSteps**, not just the synthetic loops: `scripts/validate-tempo.py` scores `scan_bpm` over the [GiantSteps tempo dataset](https://github.com/GiantSteps/giantsteps-tempo-dataset) (664 Beatport previews, annotations v2) with the MIREX metrics — Accuracy1 within 4%, Accuracy2 forgiving 1/3, 1/2, 2 and 3x. The dataset is not vendored; point `--dataset` at a local clone with audio downloaded. The full set runs in about 35 seconds (`--jobs 6`) — re-run it after any analyzer change; `--sample N` gives a quick signal.

Current: **Accuracy1 85.1%, Accuracy2 92.6%** over 652 files. `kTempoPriorCenterBPM` (swept on that set; the optimum is flat between 138 and 142) is the single most consequential constant in the analyzer, and **it buys fast material at the cost of slow**: fast genres score near-perfectly while most tracks under 100 BPM read as their double. Deliberate for a DJ tool, but it is why a hip-hop or downtempo track can show 174 instead of 87 — and no prior can fix that, since 87 and 174 are the same octave pair and only the phase comb's grid evidence can separate them, so **improving the comb is the real fix and the prior is a compromise** standing in for it. `docs/future/tempo-accuracy.md` has the plan, the per-genre failure breakdown and the approaches already tried and ruled out, so they are not tried again.

`AudioKeyAnalyzer` (same shape: ObjC++, Accelerate, streaming, gated by `AppSettings.analyzeKey` — **defaults off** because exact-match accuracy on real dance music is around half and that is not worth showing unasked; a *tagged* key is unaffected and always displays — with the same caching caveat, exercised by `scan_key`/`scan-key.sh` against the generated `key-*.wav` loops with the `bpm-*.wav` loops as the atonal negative case) detects the musical key on the same pass: a chromagram over ~0.75s FFT frames — each bin's magnitude folded onto its nearest semitone's pitch class within 55–3520 Hz, then the frame normalized to one vote — correlated at end of file against the 24 rotations of Sha'ath's EDM-tuned major/minor profiles.

Three constants carry the accuracy, all swept on GiantSteps. **`kHarmonicWeight`** (0.5) is worth 8 points of MIREX score on its own; **`kBassTonicWeight`** (0.15) and **`kModeThirdWeight`** (0.45) add 1.4 more together. The latter two exist because profile correlation identifies a *scale*, not a tonal center — the relative, dominant and subdominant keys share that scale, and those confusions dominated the errors. So a second chroma over the bass band (`kBassMaxHz`) votes on which note the bassline treats as the root — supplementing the full-range chroma, never replacing it, since band-limiting the whole thing measured far worse — and the balance between the minor and major third is scored explicitly, because in a bare 12-bin correlation the one interval that defines the mode is one bin among twelve. The scoring is deliberately additive over a correlation in [-1, 1], and **the confidence gate stays on the correlation alone**: it answers "is this tonal at all", which the other two terms, conditioned on a key already being chosen, cannot. `kHarmonicWeight` credits each peak to the fundamentals it could be a *harmonic of* — the note a fifth below (its 3rd harmonic) and a major third below (its 5th harmonic); without it every note manufactures its own major third and the chroma drifts major, wrecking mode detection on a mostly minor corpus. Frames are normalized to one vote and never log-compressed: compressing raw magnitudes squashes loud passages harder than quiet ones — the opposite of the intent — and any log compression at all measured worse than none. Below a correlation gate it returns `VibeMusicalKeyNone` — percussion, noise, speech. The key representation, Camelot/musical-name formatting and tag parsing live in `Common/MusicalKey.h`, header-only static inlines. TRAP: a `VibeMusicalKey` of 0 is C major, so freshly inited holders (`CodableAudioWaveform.key`, `AudioTrackMetadata.key`, `AudioTrack.detectedKey`) must be set to -1 explicitly — a zero-filled ivar or a nil-message fabricates C major.

**Key accuracy runs the same harness**: `scripts/validate-key.py` scores `scan_key` against the [GiantSteps key dataset](https://github.com/GiantSteps/giantsteps-key-dataset) with the MIREX key weighting (1.0 exact, 0.5 fifth, 0.3 relative, 0.2 parallel). Current: **61.3% weighted, 54.7% exact** over 602 files. Four things were swept and measured *worse*, so they are not worth retrying blind: narrowing the chroma band; restricting to spectral peaks (reviving it means first undoing the run-at-a-time fold under Cost, which cannot express a per-bin test); log-compressing the chroma at any strength; and the Krumhansl-Kessler, Temperley and flat-diatonic profile pairs (Sha'ath's win). **Tuning correction is not worth building**: the mean cent offset from equal temperament (`AudioKeyAnalyzer.tuningCents`, also in the `scan_key` reply) is −0.2 cents median over the corpus and never exceeds ±1.8 — this material is digitally produced at A=440. (That measurement cannot see gross detuning: a track more than `kMaxCentsFromSemitone` off has every bin rejected and surfaces as no key.)

What remains is tonal-center errors — outright-wrong tonics, then parallel and relative confusions: the chroma identifies the scale, and picking the tonic within it is the unsolved half. The published ceiling for profile-correlation methods is near; edmkey's ~70% comes from profiles fitted to EDM, which would need k-fold cross-validation here to mean anything.

The results travel in `CodableAudioWaveform.bpm`/`.key`, arrive through `audioWaveformCache:didDetectBPM:forURL:` and `didDetectKey:forURL:`, and land in the transient `AudioTrack.detectedBPM`/`.detectedKey`. Deliveries can race a track change, so receivers must match the URL against the current track. A file's own tag beats analysis for both: `AudioTrackMetadata.bpm` reads TagLib's PropertyMap "BPM" (ID3 TBPM, MP4 tmpo, Vorbis BPM), and `AudioTrackMetadata.key` reads "INITIALKEY" (ID3 TKEY, Vorbis/FLAC INITIALKEY) falling back to the MP4 freeform atom's verbatim "initialkey", parsed through `VibeMusicalKeyFromString` (musical names, Camelot, Open Key). The BPM label shows the winner, scaled live by the pitch fader; the key shares that label line in the notation `AppSettings.keyNotation` selects, deliberately not pitch-shifted.

The C++ waveform types stay out of ObjC headers: `AudioWaveformCache.h` forward-declares `CodableAudioWaveform` rather than importing `AudioWaveform.h`, so the UI layer compiles as plain ObjC.
