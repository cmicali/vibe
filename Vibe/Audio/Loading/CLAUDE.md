# Loading: materialization, admission and the transfer registry

Everything between a path and a usable `AudioFileHandle` (owned by the audio core): `AudioFileMaterializationCoordinator` (the claim), `AudioWorkScheduler` and `AudioWorkAdmissionRules.h` (admission), `AudioLoadingConfiguration` (the immutable limits and the open-timeout seam), `AudioFileOpenRules.h` and `AudioFileOpenTimeoutMath.h` (the decisions), and `CloudTransferRegistry` (which files are on the wire). The player's side of an open, the deadline, progress identity and prefetch, is `Audio/CLAUDE.md`'s; the sweep's retries against the foreground hold are `Metadata/CLAUDE.md`'s; the progress monitor is `System/CLAUDE.md`'s. Three root `CLAUDE.md` guarantees are implemented here: the foreground open outranks background downloads, the six-run handle ceiling, and a row shows the loading bar only while a transfer is running.

## One claim, two stages

**A file's journey from dataless placeholder to handle is one path-keyed claim in two stages.** Stage 1 is the one operation that can make a standardized path local; Playback, Prefetch and the two metadata roles affect admission, never identity. Stage 2 is the purpose-keyed handle runs riding it: one current handle waiter per `(purpose, path)`, so playback and prefetch keep independent handles and delivery while sharing the path's transfer. Only a stage-1 Ready dispatches a handle open; Yielded, AdmissionExhausted and Failed become terminal outer errors without touching CoreAudio. `AudioFileOpenRules.h` holds the decisions: `VibeAudioFileOpenBeginDelivery` and `VibeAudioFileOpenDetachDelivery` are the two sides of the race for the one Waiting transition, whichever changes it first owns the outcome, and `VibeStandardizedAudioOpenPath` is the one spelling every claim is keyed by.

**The stage-1 state queue owns in-memory claim state and performs no filesystem or provider I/O.** A first waiter synchronously installs a `Probing` claim, then one private `AudioWorkScheduler` classifies the path off-queue; same-path waiters join and share the probe. A fresh answer starts an immediately admitted claim; a dataless claim that had to wait or be readmitted enters `Refreshing` after reserving its lane, re-probes in that admitted worker, and becomes `Running` only when state accepts the fresh answer. The successful paths are therefore `Probing → Running` and `Probing → Pending → Refreshing → Running`, and dataless readmission routes through `Pending` or `Refreshing` likewise. Object identity drops a result from a cancelled or replaced probe, and a ready operation records the path local before any cancellation or rebind restart decision.

**The eight initial-probe slots are process-wide, and their exhaustion is a bounded failure by design.** Production can present about eleven distinct claims at once (playback, prefetch, the scan and priority metadata slots, seven artwork requests), so eight wedged probes can make a later healthy path expire after the five-second grace. That settles as `AdmissionExhausted`, spends one of metadata's three per-path attempts, and can drop the path from the current scan; it replaces an unbounded tail of uncancellable system calls. Refresh probes do not use the slots: a never-returning refresh stays state-isolated but holds its reserved transfer lane, including the one-wide background lane.

## Admission has two lifetimes

**A transfer lane ends when its materialization run settles and is never carried into a handle open; the handle-run ceiling is a separate lifetime.** Each coordinator permits at most six live handle runs, process-wide in the app since production shares one: the root guarantee's two-source bound plus room for four stranded calls. An existing `(purpose, path)` run is looked up and rebound before the ceiling is checked, so saturation never duplicates or rejects work in flight; a seventh key is refused at once with `VibeAudioFileOpenErrorAdmissionExhausted`, counted in `requestsAdmissionExhausted`, before materialization starts. The ceiling is a private, purpose-blind safety bound over `_handleRuns.count`, not loading policy: no queue, grace, configuration value or per-handle counter, and prefetch can exhaust it and get a later playback key refused. Waveform work keeps its own two fixed-slot schedulers.

**Transfer-lane admission is the coordinator's own** (`admitClaim:…`): running claims against the lane's maximum, then pending claims against the pending bound with a deadline at the grace, and a file already local starts at once outside the lanes, so only dataless claims are bounded. `AudioWorkAdmissionRules.h`, tested, is the scheduler's: `VibeAudioWorkAdmission` and `VibeAudioWorkAdmissionExpired` are what `AudioWorkScheduler` reads, here for the dataless probe. Transfer exhaustion and the handle-run refusal both map to `VibeAudioFileOpenErrorAdmissionExhausted`: the file never began, which is not that file's playback timeout.

**A run stays registered until its uncancellable handle open really returns.** A timeout or superseding request detaches the outer delivery and the materialization waiter; a handle open already begun keeps its run until it returns, and a cancellation before stage 2 removes it. Rebind and the abandoned-then-rebound restart preserve the same dictionary membership, so repeated retries cannot multiply stranded workers. A never-returning stage-2 call stays one of the six until process restart, but it holds no transfer slot.

**Cancelling is the only way to stop waiting, and it is deliberately not separable from marking an admitted handle-open run abandoned.** `finishHandleRun:…` tells "this run produced nothing because nobody was waiting" from "this file would not open" by the run's cancelled mark alone; a waiter cleared without it would let the first be delivered to a later same-purpose/path waiter as a nil file with no error, which every caller reads as the file failing. Before the handle open is dispatched, cancellation simply detaches the central request and removes the outer claim. A completion therefore always carries a file or a reason there is none.

## The transfer registry

**`CloudTransferRegistry` is the coordinator's publication surface for "which files are on the wire", and only a dataless verdict publishes.** A fresh initial answer governs an immediately admitted run; a delayed or readmitted dataless claim publishes from its `Refreshing` worker's fresh answer. `Running` plus `dataless` means begin was published, so `finishClaim:` pairs the end without a second flag. A local run, and a claim merely queued behind lane capacity, publish nothing, which is what bounds the row indicators exactly as the lanes bound the transfers. Main-thread, one weak observer per shell, one `DownloadProgressMonitor` per transferring path unless the shell's own monitor already feeds that path through `noteProgress:forURL:`. Row wiring is `Playlist/Mac/CLAUDE.md`'s and `iOS/CLAUDE.md`'s.

## Configuration

**`AudioLoadingConfiguration` is immutable once built, and its diagnostic surface is for tests and the debug channel only.** The safe tuning surface is the background lane width, the local parse concurrency and the prefetch depth; the interactive lanes, pending bounds, grace, retry count and `openTimeouts` are diagnostic, replaced by `Vibe/Debug/`'s category and the test suite, never by production code.
