# Now Playing

The `MPRemoteCommandCenter` / `MPNowPlayingInfoCenter` bridge. It publishes what is playing and receives transport commands back. It owns no playback state. Its driver hands it track and timing updates, and takes the commands back through the delegate. The driver routes them to the same transport entry points the on-screen buttons use. `MainPlayerController+NowPlaying` is the driver on macOS, `PlaybackController+NowPlaying` on iOS.

**The driver pushes the track's values, never the row.** `updateWithSourceKey:title:artist:artwork:…` takes the row's `sourceKey`, `displayTitle`, `displayArtist`, and one image. The source key is the dirty check's identity, so a cue row of the same file is a change. A nil source key means no track.

**Nothing is published until the first track plays.** The update withholds every publish before its first Playing one: no track, a parked start and a paused start alike. A launch into a restored session therefore cannot claim the system slot. Next and previous availability is applied before that return regardless. After the first play, a nil source key clears the slot once.

**Shuffle and repeat are commands, not Now Playing info.** `changeShuffleModeCommand` and `changeRepeatModeCommand` take the system's controls (Siri, the Watch, accessories) to the delegate's `setShuffleEnabled:` and `setRepeatMode:`. Those write the setting and apply it exactly as the app's own control does. The state the system shows is `currentShuffleType` and `currentRepeatType` on the commands. `updateShuffleEnabled:repeatMode:available:` writes them wherever a shell applies the modes, so a change from anywhere reaches it. A shuffle request of Items or Collections is on, since there is no album-level shuffle. `available` sets both commands' `enabled`. The mac always passes YES. iOS passes the card's Show shuffle and repeat, so CarPlay hides its buttons with the card's. iOS writes any request that still arrives back as off (`iOS/Settings/AGENTS.md`).

**TRAP: the command center is process-global, and the system picks which enabled commands fill the compact transport.** The lock screen, Control Center, CarPlay, AirPods and the mac's media keys share it. The shuffle and repeat pair leaves next and previous in place. The iPhone lock screen and both platforms' Control Center draw no shuffle or repeat at all. The mac's media keys and AirPods taps still skip, and Siri reaches the pair. The skip-interval pair that `docs/future/carplay.md` weighs would take their place. Check any further command on a device first.

`MPNowPlayingInfoCenter.playbackState` is written on macOS only, under `TARGET_OS_OSX`. iOS derives the state from the audio session and the published rate.

**TRAP: the published artwork must be rasterized privately on the main thread, and that result must be the only thing the `MPMediaItemArtwork` request handler returns.** The handler runs on MediaPlayer's threads. The source is the live `NSImage` the UI is drawing, and `NSImage` is not safe to draw from two threads at once. `VibeArtworkForPublishing` always redraws, even a small thumbnail. It caps art at 512px and hands over a private copy. iOS passes the image through.

**The image is the track's `cachedArt`, else its `cachedThumbnail`, else the shell's placeholder.** Each is read without blocking. The thumbnail covers the gap until the full art decodes. On macOS the placeholder is the current theme's `defaultArtworkImageForAppearance:` for the main window's effective appearance, nil when the theme's default artwork is clear, window, a glyph or a color. The shell resolves the side before rasterization. This honors Vibe's appearance setting, Settings preview and single-mode theme pin. On iOS it is `record-bg`, passed through without rasterization. The dirty check compares image identity. A theme or appearance change republishes when it changes the placeholder image. Reusing the same image avoids an artwork-driven publish on every tick.

**The republish rules are `NowPlayingRules.h`**, header-only and tested. Both platforms publish through them, and the iOS widget publisher shares its string comparison. `initWithClock:publish:commandAvailability:` runs the same publication path without registering remote commands. The host-less tests use it. Actual system registration is a live-app check.

**TRAP: the debug-only `--no-audio-hw` and `--no-now-playing` flags suppress all of it**: no publish and no command registration. Publishing can pull AirPods from another device even when rendering to a virtual output. `--no-now-playing` keeps hardware rendering for loopback tests. The `vibe-debug` launcher passes it unless `VIBE_NOW_PLAYING=1`. Verifying this class needs a launch without either flag. Under either one, `dump_now_playing` reports `hasInfo: 0`.
