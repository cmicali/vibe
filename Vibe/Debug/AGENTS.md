# The debug command channel

How a running app is driven and read from outside, on both platforms. **The verbs are deliberately not listed here.** The unknown-command reply derives from the command tables. The `vibe-debug` skill documents their usage. This file is the structure: what the pieces are, which are shared, and where a new verb goes. Read the `vibe-debug` skill first to use the channel, and this file to change it.

## Layout

Each shared subdirectory matches a section below. The transport is vibe-libs' `dev/DebugChannel`, whose doc is its authority.

- **`Verbs/`** holds the verbs both platforms answer, one file per topic, and the protocol they are written against.
- **`Oracles/`** holds the oracles.
- **No shared `Seams/` remains.** A shared class's `+Debug` category moved to vibe-libs with the class, and sits beside it there. The next section says why seams exist. **A vibe-libs seam imports nothing from the channel or `Verbs/`.** It belongs to the class it opens, and no other vibe-libs piece depends on the channel. The file loader's seams and the fake cloud moved first (vibe-libs' `files/FileLoading/AGENTS.md`). The FX fault seam, the meter's two seams, the file handle's, the metadata cache's and loader's, and the waveform cache's and loader's followed (vibe-libs' `audio/FX/AGENTS.md`, `audio/Meter/AGENTS.md`, `audio/Decode/AGENTS.md`, `media/Metadata/AGENTS.md`, and `waveform/WaveformLoading/AGENTS.md`). The mac waveform view's, the equalizer bars', and the Now Playing bridge's were the last (vibe-libs' `waveform/WaveformView/AGENTS.md`, `ui/Controls/AGENTS.md`, and `system/NowPlaying/AGENTS.md`). The fake web server moved with the link client (vibe-libs' `files/ShareLinks/AGENTS.md`). A parser a seam and the channel share lives in vibe-libs' `core/Common`, as `IntegerTokenRules.h` does.

**The three launch flags a test launch passes are read in one place**, `Verbs/DebugCommonVerbs.m`: `--silent`, `--no-audio-hw`, and `--no-now-playing`. No vibe-libs piece reads a flag. Each app delegate pushes the two audio flags into the player's seam before the player exists (`VibeDebugApplyLaunchFlags`, vibe-libs' `AudioPlayer+Debug.h`). Each shell makes no Now Playing controller under `--no-now-playing` or `--no-audio-hw` (`VibeDebugLaunchNoNowPlaying`). `dump_state` and `dump_equalizer` report the two audio flags. The iOS launch probes, `--frame-rate-probe` and `--dataless-diag`, are read in `iOS/DebugiOSEntry.m`.

`Mac/` and `iOS/` hold each platform's table and verbs. Each has its own `Seams/` for the `+Debug` categories over that shell's classes. The open coalescer's and coordinator's seams left `Mac/Seams/` with their classes, for vibe-libs' `system/AppOpening`.

## The standard verbs, from vibe-libs

The verbs that know nothing of Vibe are vibe-libs' `dev/DebugVerbs`, whose doc is their authority. `VibeDebugStandardVerbs(options)` answers the standard table. It holds `dump_build`, `quit`, `work_tally`, `dump_health`, `block_main`, and `block_main_deep` on both platforms. On macOS it adds `dump_view_tree`, `dump_menu`, `click_menu`, `dump_screenshot`, and `raise_window`. On iOS it adds `dump_view_tree`, `dump_screenshot`, `set_clipboard`, `sample_frame_rate`, and `dump_frame_rate`. `VibeDebugInputVerbs(options)` answers the mac's input table: `key`, `key_down`, `key_up`, `click`, `mouse_down`, `mouse_up`, `mouse_move`, `drag`, and `scroll`. Both apps compile the piece through `VibeLibsDebugVerbs`.

The options are blocks over the controller each dispatcher hands a handler. Vibe passes four. `healthExtras` answers `dump_health`'s `ui`, `app`, `pending`, and `materialization` blocks (`VibeDebugHealthExtras`). `chainableVerbs` is the shared table, so `block_main` chains `dump_state`. `targetWindow` is the controller's window. On macOS, `performMenuItem` is the controller's `performMenuItem:`, so a click still proves what a shortcut does. Each dispatcher builds its tables once.

**What stays here reaches the player, the playlist, `AppSettings`, a theme, a fake, or a shell class.** `set_appearance` writes `AppSettings`. `set_window_width` and `measure_resize` size the pitch panel. `quiesce` polls Vibe's pending work, and reads the piece's malloc counter (`VibeDebugMallocBytes`). `gesture_test`, `select_rows`, `set_shortcut`, and `reset_shortcuts` are `Mac/DebugShellInput.m`'s, and call the piece's posting functions. The client's local verbs are `Mac/DebugClientLocalVerbs.m`'s: `scan_bpm`, `scan_key`, `clear_disk_caches`, and `set_analysis`.

## It is in both targets' sources and ships in neither

`project.yml` lists `Vibe/Debug` as an ordinary shared subsystem, so the layout rule needs no exception for it. **Every file is wrapped in `#if DEBUG`**, which a Release build compiles to an empty object.

This is why a shipping header may not carry `#if DEBUG` (root `AGENTS.md`, Vocabulary). The surface a debug build adds to a shipping class is declared here, in a `+Debug` category header (`Mac/Seams/MainPlayerController+Debug.h` and the others). A class that moved to vibe-libs took its seam along, beside it (vibe-libs' `audio/Player`'s `AudioPlayer+Debug.h`, and `media/Metadata`'s `AudioTrackMetadataLoader+Debug.h`). When the methods need only what the class exposes in its header or its `*Internal.h`, they live here too, in `<Class>+Debug.m` (`Mac/Seams/AudioFileConverter+Debug.m`). When they need state private to the class's own file, they stay in that file under `#if DEBUG`, and the header says so (vibe-libs' `EqualizerIndicatorView.m` and `NowPlayingController.m`). Process-wide debug state, such as a fake's hooks, is a file static in the seam's `.m`. The shipping class reaches it through a category method or a function the seam header declares (vibe-libs' `AudioWaveformCache+Debug.mm`, in `waveform/WaveformLoading`). A small hook inside a shipping method stays there under `#if DEBUG`, such as a counter or a hold in the render or decode loop. Three shapes cover what a category cannot add:

- **Debug-only state** becomes a debug-only object the shipping class holds: vibe-libs' `VibeManualRenderPump`, which the player holds.
- **A debug-only field a seam reads** is declared unconditionally in the class's private header (its `*Internal.h`, or its one header), marked "Debug builds only". Release never writes it. `AudioPlayerInternal.h`'s buffering counts and `AudioVoiceBusInternal.h`'s debug fields are examples.
- **A debug-only hook** ships as a plain block pointer with no conditional around it: `MainPlayerControllerInternal.h`'s `undoRedoSettledHandler`, and `AudioFileConverterInternal.h`'s `nextSourceTrashResultingURLFilter`.

**A test target compiles every seam its sources reach.** A seam with its own `<Class>+Debug.m` must be in the test target's sources when the target compiles the class and a file in it imports the seam's header, directly or through another seam. A selector resolves at run time, so the compiler cannot catch an omitted category implementation. `make check-layout` fails on the gap.

**`AudioFileHandle+Debug.h` is the network-mount read-ahead's seam**, so a test plays a local file as if it were on a share. It moved with the handle to vibe-libs' `audio/Decode`, whose `AGENTS.md` states its contract. **TRAP: the rule and the hook are set on a test's thread and read on open and read-ahead threads, so both are read under a lock.** An unlocked read of a block global is a retain racing a release. The seam's statics live in vibe-libs' `files/FileLoading/Transfer/NetworkReadAhead.m` under `#if DEBUG`. The common verb `set_slow_volume` drives the seam in a running app: it forces the rule for every file and installs one hook that throttles, stalls or fails each read. Its state lives in `Verbs/DebugStallVerbs.m` under one `NSCondition`, on which a held read waits. Each set releases every held read.

## The transport, and the two ends of it

A command is a file. The client writes one, the app drains it, and the app writes a reply file back. The transport is vibe-libs' `dev/DebugChannel`: the wire format (`DebugWireFormat`), the drain (`DebugChannel`), and the table's shape and the lookup over it (`DebugCommandDispatch`). Its doc holds the contract and the traps. Both apps compile it through `VibeLibsDebugChannel`. Its files wrap their bodies in `#if DEBUG`, as every file here does. What stays here is each end:

| Piece | Owns |
| --- | --- |
| `Mac/DebugMacEntry.m`, `iOS/DebugiOSEntry.m` | Each platform's executor, which the channel calls. It finds the controller and looks the verb up in the shared table, then the standard table, then on macOS the input table, then its own. It answers the unknown-command reply from the same tables. The mac's also gives its CLI client each verb's wait (`VibeCommandSpecForVerb`). |
| `Mac/DebugClientLocalVerbs.m` | The macOS CLI half, over vibe-libs' client (`dev/DebugChannel/Mac/DebugClient.h`). `main.m` routes `Vibe --debug-cmd …` to `VibeDebugCommandClientMain` **before `NSApplicationMain`**, so the client is the same binary and never launches a second app. It builds the client's options: the channel, the names in its messages, `VIBE_DEBUG_TIMEOUT`, each verb's wait, `dump_screenshot` as the one file verb, and the four local verbs. |

iOS has no client. `debug-ios.sh` writes the command file straight into the simulator container's tmp, a plain host directory. It reads a verb's wait from the tables' source, so a new window needs no second copy.

## A verb is written once unless it cannot be

`Verbs/` holds every verb both platforms can answer. They are written against **`VibeDebugPlayerSurface`** (`DebugPlayerSurface.h`), the smallest protocol that serves them. `VibeTransportCmd` builds a transport or toggle verb that replies with the surface's summary. `MainPlayerController` adopts it on macOS, and `RootViewController` on iOS, since that is the one object that sees the whole iOS app.

The verbs are split by topic. `DebugCommonVerbs.m` holds the state and transport verbs and the shared table. The table adds each topic's verbs after its own. `DebugStallVerbs.m` holds the deliberate stalls off main: `block_player`, `block_render`, `block_decoder`, `hang_open` and `set_slow_volume`. `DebugAudioVerbs.m` holds the meter, decoder, resampler, render-counter, cache, timing, waveform and tempo-scan verbs. The scan's core is `DebugBPMScan.mm`, which the mac's CLI client also runs in its own process. `DebugLoadingVerbs.m` holds the cloud, row-loading, loading-indicator, loading-configuration and link verbs. It also drives the fake cloud and the fake HTTP server. Each platform's dispatcher looks a verb up in the shared table first, so a verb is registered once. **TRAP: a verb in two tables runs from the first one, silently.** So a verb leaves Vibe's tables in the commit that stages it.

What is left per platform is what genuinely differs:

- **`Mac/`**: the entry points and the dispatcher (`DebugMacEntry.{h,m}`), and the command table (`DebugMacVerbs.m`). The table adds four topic tables after its own verbs: `DebugThemeVerbs.m`, `DebugWindowVerbs.m`, `DebugOutputVerbs.m` and `DebugConvertVerbs.m` (with undo and redo). The AppKit-only helpers are `DebugShellInput.m` (direct playlist selection, named gesture probes and shortcut remapping), `DebugSyntheticDrags.m` (the synthetic drop and reorder delegates), `DebugSettingsUI.m` (the structural Settings walker's verbs; its walk from a row to its controls is vibe-libs' seam `SettingsFormViews+Debug.h`, in `ui/SettingsWindow`), `DebugStateDump.m` (`dump_state` and the Open URL window) and `DebugMacConsistency.m` (the mac half of `check_consistency`). `Mac/Seams/` holds the `+Debug` categories over the mac shell's classes, plus `MainPlayerController+DebugPlayerSurface`.
- **`iOS/`**: the entry point and the dispatcher (`DebugiOSEntry.{h,m}`), the command table (`DebugiOSVerbs.m`), the Dropbox verbs it adds after its own (`DebugDropboxVerbs.m`, beside `VibeFakeDropbox`), the verbs that stand in for touches the channel cannot synthesize (`expand_player`, `minimize_player`, `select_tab`, and the favorites, search, route and waveform verbs), and the `+Debug` categories over the iOS shell in `iOS/Seams/`. All of them live here, not beside the classes they extend.

**Gestures are not the channel's job on iOS.** No public API synthesizes a `UITouch` in-process. Taps and drags go through `drive-ios.sh` and the resident `VibeiOSDriver` XCUITest. Its source is vibe-libs' `dev/iOSDriver`, whose doc is its authority. `drive-ios.sh` passes it Vibe's bundle identifier, the relaunch's audio-silencing flags, and the scrubber's identifier for pinches.

## Desktop input boundary

The stress runner permits only reviewed controller and delegate commands, including direct table selection and shell removal. Synthetic file drops and row reorders (`Mac/DebugSyntheticDrags.m`) call shipping delegates without native drag sessions. Raw AppKit events (vibe-libs' input table, `dev/DebugVerbs/Mac/DebugSyntheticInput.m`) can start native window and file drags, and mouse injection activates the app. So they are reserved for explicit gesture tests on an isolated test desktop. The named pitch-fader probes resolve and hit-test fresh geometry before queuing input, and the runner asserts the result. Replay and shrink enforce the same command gate. The workflow is in `vibe-debug` and `vibe-stress`.

## The oracles

These exist for the stress driver, which cannot tell a healthy soak from a leaking one by screenshotting it.

- **`DebugConsistency.{h,m}`**: the checks that hold on both platforms, behind the same surface protocol. Each platform adds its own through `debugCheckPlatform:`. iOS flags row lifts older than 30 seconds. That threshold can also catch a slow multi-folder open. A violation needs investigation against the operation in flight. **TRAP: a check that compares a published or rendered value against the state that produced it can lag a run-loop turn.** Count only a violation that survives a re-check after a short settle, as the stress driver does.
- **The layout probe** (`dump_layout_anchors`, `sample_layout_anchors`) and **the frame probe** (`sample_frame_rate`, `--frame-rate-probe`, vibe-libs' `dev/DebugVerbs/iOS/DebugFrameProbe.{h,m}`) are the iOS shell's oracles for what a screenshot cannot judge: whether the live layout under the card held still, and whether an animation got its frames.
- **`DebugHealth.{h,m}`**: `dump_health`'s UI, app, pending, and materialization blocks (`VibeDebugHealthExtras`), for diffing across a run, and `quiesce`, on both platforms. Each platform gives its UI block, its close and any pending work of its own through the surface. The process block is vibe-libs' `dev/DebugVerbs/DebugProcessHealth.{h,m}`, whose doc holds its descriptor-count TRAP. **TRAP: the mac's view, layer and tracking-area counts read visible windows only.** Closed windows kept for reuse would make one visit to Settings read as a leak. Warm the lazy FX units before taking a leak baseline. Quiesce pending work before comparing memory. Allocator reservations and live allocations are separate readings.
- **`AudioLoadTiming`**: per-phase timings for one waveform decode pass, recorded by the loader and read afterwards, since that pass has no reply path. It is the loader's seam, `AudioWaveformLoader+Debug.h`, in vibe-libs' `waveform/WaveformLoading`. `dump_timing` and `file_cache` read it.
- **The work tally** is a named counting window over the signpost sites. It answers "how much of this work ran at all". It is vibe-libs' `core/Common/VibeWorkTally`, beside the signposts in `VibeMacros.h`, so call sites need no debug header. It compiles only under `VIBE_SIGNPOSTS`, which `project.yml` defines in Debug.

## The simulators of things the app cannot otherwise reach

- **`VibeManualRenderPump`** stands in for the output unit's IO thread, which `--no-audio-hw` never starts. It is vibe-libs' `audio/Player`'s, beside the player it fakes, and that piece's doc is its authority. It calls the production render at real-time pace, so voices are consumed and the timeline advances as against hardware. `VibeAudioTests` drives the same pump with explicit frame pulls and a virtual clock. It lets the whole player run with no audio device, under a sanitizer or on a machine with none.
- **`iOS/VibeFakeDropbox`** stands in for the Dropbox account. A directory on disk answers as the account over the client's own HTTP boundary: an `NSURLProtocol` on sessions the client rebuilds through `useSessionConfiguration:` (`HTTPTransferClientInternal.h`, imported by `DropboxClientInternal.h`). The account is linked as a completed sign-in would be, and the mirror, the browser, search and every open run unchanged. Its serving engine is vibe-libs' `files/HTTP` fake, `VibeFakeHTTPProtocol`. `VibeFakeDropbox.m` holds only the account's routes, its tree, its faults and its log. Downloads arrive in 64 KB pieces over a chosen time or at a chosen rate, a resend continues from its Range, and each file has a rev every answer names. Scripted faults drive each of the client's streaming roads: a stall, a dropped connection, a changed rev, a throttle, an expired token, a failed or slow tail read, a slow tag read, and a server's first-byte latency. **TRAP: an install over a linked fake never links the account again** (the `TRAP:` in `VibeFakeDropbox.m`). A link is an account change. It clears a playlist that reaches into the mirror.
- **`VibeFakeHTTP`** stands in for the web server behind an Open URL link, on both platforms. It lives in vibe-libs' `files/ShareLinks`, beside the link client, and that piece's doc is its authority: what a directory answers, the faults, and iCloud's lookup. Its serving engine is `files/HTTP`'s, which the tests' `HTTPStub` and `VibeFakeDropbox` share. `set_fake_http <directory>` puts it under `LinkStore.shared.client` through `useSessionConfiguration:`, and `set_fake_http off` puts the real sessions back. `fake_http_fault` scripts its faults. `open_url` resolves a link through each shell's own Open URL road (`debugOpenLink:`).
- **`VibeFakeCloud`** stands in for a file provider. Chosen files answer as placeholders, each takes a fixed time to download, and a cancel leaves the file a placeholder. It lives in vibe-libs' `files/FileLoading`, beside the three points it injects at: `PlaceholderFiles`' dataless probe, `CloudFileMaterializer`'s transfer and `DownloadProgressMonitor`'s reporting. That piece's doc is its authority. `Verbs/DebugLoadingVerbs.m` installs it here, and the cloud-loading scenario suite drives it through the channel. **TRAP: its progress seam replaces the monitor's real sources rather than joining them** (`DownloadProgressMonitor+Debug.h`). Under a fake transfer the file on disk is genuinely local, so the allocated-size poll would answer 100% on its first tick.

## Adding a verb

Decide which table it belongs in first. A verb that knows nothing of Vibe belongs in vibe-libs' standard table, `dev/DebugVerbs`, which changes there first. A verb both platforms can answer goes in its topic's file under `Verbs/`, or in `DebugCommonVerbs.m` when no topic fits. If it needs something new from the app, it adds the smallest possible method to `VibeDebugPlayerSurface`. A verb only one platform can answer stays in that platform's table or one of its topic tables, and never reaches the protocol. A new topic file joins its table's concatenation and declares its function beside the table's. The reply is JSON through `DebugWireFormat`. The skill's documentation follows the usage string, not a list kept here.
