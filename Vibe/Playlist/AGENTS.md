# Playlist

`Playlist` (the model) and `PlaylistFile` (the CUE/M3U readers) are shared with iOS and sit at the top level, both tested. **`Mac/` is the `NSTableView` half and has its own `AGENTS.md`**; the iOS target never names that subdirectory, and its list is `Vibe/iOS/LibraryViewController`.

## The model

`Playlist` keeps a track-to-row map **and** a URL-to-rows index. The URL index exists because the same file can sit in the playlist twice: analyzed BPM and key deliveries ask on every track start, and a duplicate row left pointing at a converted-away source would break the moment Delete Original trashes it.

- `replaceAllWithTracks:` replaces the list; `appendTracks:` extends it without touching playback or `currentIndex`. Both take rows the caller minted — a file whole, or a cue sheet's window of one — each a fresh object, since a row's identity is the object. Neither moves an existing row, so both maintain the two indexes incrementally.
- `structureGeneration` changes before a replacement or clear notifies its observer; in-place edits preserve it. Consumers stamp undo registrations with this value. `indexesOfTracks:` resolves captured gesture objects through the identity map, discarding departed objects and deduplicating rows. `forwardTrackAfterRemovingTracksAtIndexes:` predicts only a current-row removal's forward survivor; the shell combines it with ordered playback intent. `advanceFromTrack:toTrack:` adopts a gapless boundary only if both exact objects still name the current row and its successor, then uses the ordinary cursor notification. These decisions are exercised through the real model in `PlaylistTests`.
- `indexesOfTracksWithURL:` reaches every affected row at once; `replaceTracksMatchingTrack:withURL:` is the convert swap's batch landing point (every row still holding the source URL, even after the captured row departs); its per-row `replaceTrackAtIndex:withURL:` mints each replacement and maintains both maps, so a delivery for the departed file cannot stamp a row that no longer holds it.
- **`removeTracksAtIndexes:`, its inverse `insertTracks:atIndexes:` and `moveTracksAtIndexes:toIndexes:` are the mutations that MOVE rows**, so they rebuild both indexes (`rebuildIndexes`) instead of patching them — every entry below an edit names the wrong row otherwise. O(n) is what `NSMutableArray`'s own edit already costs, and an explicit user gesture can afford it; recreating `AudioTrack`s from URLs could not, since it would throw away installed metadata and artwork and defeat every identity check. All three are batch-shaped and a single row is the one-index case, so there is no parallel single-row path to drift. The cursor keeps naming the same object throughout: removal subtracts the removed rows above it — which is also what lands a removed current row on the survivor that slid in, or the clamp's new last row — while insert and move resolve the captured current object through the rebuilt identity map, wherever the edit pushed it. Emptying the list resets it to 0; inserting into an empty list leaves it at 0 naming the first new row. Insert clamps a past-the-end index to the end — the undo of a removal can land after later edits have shortened the list, and it should restore the row as the last one rather than not at all. A move is set-to-set — both sides FINAL row positions, never AppKit insertion slots (`Mac/PlaylistDragRules.h` owns that conversion, once) — and is its own inverse with the sets swapped, which is what the mac shell's reorder undo hands back.
- **The model does not touch the player.** Removing the *current* row through it alone would leave the player sounding a track the playlist no longer contains, so the calling shell owns that transition — on macOS `MainPlayerController`'s removal funnel (`Mac/MainWindow/AGENTS.md`). A move is transport-safe here — the current object survives, so no play funnel is entered — but its successor re-park is still the shell's (`playlistOrderDidChangeHandler`). iOS exposes no remove or reorder UI, and any future one must add its coordinator first rather than calling the model directly.
- Observers get `playlistDidReplaceAllTracks:`, `didAppendTracksAtIndexes:`, `didReplaceTrackAtIndex:`, `didRemoveTracksAtIndexes:`, `didInsertTracksAtIndexes:`, `didMoveTracksFromIndexes:toIndexes:` and `currentIndexDidChangeFromIndex:`. There is **one** observer slot — the iOS shell's ordinary fan-out to several views is `PlaybackController`'s job, while its removal and move methods stay no-ops until iOS has a transport-safe coordinator (`Vibe/iOS/AGENTS.md`).
- **One structural edit sends one event.** Each structural event carries only what the table reconciliation consumes — the removed or landed index set, or a move's sources and destination — and deliberately does *not* also fire `currentIndexDidChangeFromIndex:`: two callbacks for one edit make the mac table reconcile against the same action twice and obscure the ordering.

See `Mac/MainWindow/Convert/AGENTS.md` for why the swap mints a fresh `AudioTrack` rather than reassigning a `url`.

## Playlist files (.cue, .m3u, .m3u8)

`PlaylistFile` turns a playlist file into rows. `NSURLUtil` expands one in place when it is opened at top level. Inside a folder walk an M3U is dropped, since it would double every track the walk already found, but **a CUE sheet stands in for its files**: its rows take its sorted place and the files it names are claimed, so none also loads whole (`NSURLUtil rowsForWalk:`). The sheet resolves against the walk's own listing first (`knownFiles`, folded by `knownFileKeyForPath:` for case and Unicode normalization), so a sheet whose files were listed costs no probe; a sheet naming a missing image adds nothing. An M3U gives file references only — `#EXTINF` is ignored — except for the cue rows Vibe wrote into it (below).

**A CUE sheet reads as rows** (`cueRowsInText:sheetURL:resolvingFile:`, one parser, the resolution injected): one `AudioTrack` per AUDIO TRACK kept, each a window of the FILE its start INDEX sits in, in CD frames (integers, so sample-exact at every common rate), with the sheet's TITLE and PERFORMER. Every file keeps all its audio: its first row starts at frame 0 (hidden audio before track 1 is reachable), a row runs to the next row of its file (a pregap plays at the end of the row before it, as on a CD), the last runs to the file's end, and a FILE none of whose tracks survived plays whole. The drop rules — INDEX 01 beats INDEX 00, a track with neither or starting before its file's last kept start goes, an empty window goes — keep every window playable, which `testCueFuzzedMutationsKeepRowsPlayable` holds under 2000 mutations. Only TITLE and PERFORMER are read: Vibe shows no album, genre or date for any file.

**A FLAC can carry its own sheet** (`cueRowsEmbeddedInFLACAtURL:`), as the foobar2000-style `CUESHEET` tag's text or as the binary CUESHEET block `flac --cuesheet` and EAC write. Both go through the one parser: the text as it is, the block rewritten as the sheet it was made from, its sample offsets rounded to CD frames (exact for a CD rip). The text wins, since only it has titles; an untitled row is named by its number (`AudioTrack.title`). Every FILE line names what was ripped, so the first maps to the FLAC itself and any other is dropped rather than laying windows over the same audio. The reader reads the metadata blocks and nothing else. Whether a file is worth opening at all is `NSURLUtil rowsForFile:`'s decision (`Util/AGENTS.md`), and a sheet beside the file outranks the one inside it.

Each entry resolves through fallback rungs: the named path, its basename beside the playlist (which rescues a Windows-absolute-path entry), then both again under each alternate audio extension (which rescues a rip transcoded after the sheet was written). An entry readable nowhere still yields its primary candidate, so the caller can tell a sandbox denial from a missing file — that distinction is what raises the folder grant (`Mac/Settings/AGENTS.md`). **An opened playlist that lists nothing readable lands as its own row** (`NSURLUtil expandPlaylistFile:`), which fails to open like any file that cannot be, so the header says "Could not open listed files" over its name (`AudioErrorRules.h`) rather than the open vanishing; a sheet met in a folder walk that resolves nothing adds nothing, since the folder's other files speak for themselves.

These files come from other people's software, so two traps are load-bearing rather than defensive.

**TRAP: BOM-less UTF-16 must be decided *before* UTF-8 is tried.** A UTF-16 sheet of ASCII filenames has no byte above 0x7F, so it decodes as UTF-8 *successfully*, with a NUL between every character, and the playlist opens empty; the NUL fallback after UTF-8 only sees files a non-ASCII name made UTF-8 reject. Order: BOM'd UTF-16 → BOM-less UTF-16 signature → UTF-8 → NUL-based UTF-16 fallback → CP1252 → Latin-1. Latin-1 maps every byte, so a non-empty file always decodes: mojibake costs one entry, a nil text all of them.

**TRAP: a name may not reach `NSURL` carrying a NUL or an unpaired surrogate.** Both turn up in truncated and mis-encoded files; `URLByAppendingPathComponent:` and `fileURLWithPath:` answer *nil* for such a component, and a nil candidate raises on the background expansion worker. `StrippedOfUnpathableCharacters` drops them while the name is still a string, and the resolver treats a nil primary as "no URL". A `%00` in a `file://` M3U entry is dropped *before* `NSURL` parses it, because `.path` decodes it to a NUL on older Foundation and keeps it literal on macOS 26.

### Writing one

`m3uTextForTracks:relativeToDirectory:` is the reader's inverse and, through `writeM3UForTracks:relativeToDirectory:toURL:error:` — UTF-8, no BOM, lossy so the write is total, atomic — the only writer: extended M3U, LF, a track under the target directory written relative to it and anything else absolute (no `../` form). Vibe's own reader ignores the `#EXTINF` lines; other players show them. **A cue row is written with two more directives before its path**: VLC's `#EXTVLCOPT:start-time=`/`stop-time=`, so players that honor them play the slice, and `#VIBE-CUE:<track>,<start>,<end>,<title>,<performer>,<sheet URL>` — the window in CD frames, the names percent-encoded so neither holds the comma, the URL last so its own commas need none — which the readers turn back into exactly that row. The line carries everything rather than pointing at the sheet to re-read: the mirror is restored on main at launch, where reading a sheet on a cloud placeholder or a dead mount would hang the launch. A malformed line reads as a plain row, and a line belongs only to the entry after it. **TRAP: every M3U reader trims whitespace, splits at newlines and skips a leading `#`, so a name any of those would mangle goes out as a percent-encoded `file://` URL, which reads back whole.** A backslash in a name does not round-trip in either form: the Windows-separator rule turns it into `/`, that rule's documented trade. `commonDirectoryForTracks:` answers the folder that makes every entry relative. `rowsInM3UData:` is the reader for the app's own absolute output — no resolution rungs, nothing stat'd or read — so the container mirror comes back without a probe or a grant panel. macOS reaches the writer through File > Save Playlist… and the quit-time mirror (`Mac/MainWindow/AGENTS.md`); iOS has no caller yet.

## Where opens come from

`Mac/App/AGENTS.md` owns the open funnel — Launch Services burst coalescing, out-of-order expansion results and supersession. This directory only receives the resulting `loadURLs:selectingIndex:` / `append:`; iOS's own append lands through `PlaybackController.folderSession:didAppendTracks:`.
