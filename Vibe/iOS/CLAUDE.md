# iOS app (VibeiOS target)

The iPhone and iPad app: a single-file player where **the current directory is the playlist**. The user picks a folder (or file) in the system document picker; the folder's audio files, filename-sorted, become the skippable playlist. Dropbox and iCloud work through their Files file-providers in the picker — no provider SDKs; finding a folder is the picker's own search. (An in-app search sheet over the open folder is written but **not shipped** — see `SearchViewController` below.) One screen: the track pager (blurred art + header per page), the full-bleed waveform scrubber, and a Messages-style bottom bar — a glass search field, currently hidden, with the playlist button beside it. Play/pause is the page's center glyph (a screen tap pauses while playing); next and previous are the page swipe, the track sheets, and the lock-screen commands.

This directory is the iOS app shell and nothing else. The target compiles it plus every shared subsystem minus that subsystem's `Mac/` half, per **the directory is the platform boundary** rule in the root `CLAUDE.md`: a path containing `iOS` compiles only here, a path containing `Mac` only into Vibe, a path containing neither into both. So `project.yml` carries no per-file — and no feature-named — excludes, a new file in a shared directory lands in this target automatically and must be AppKit-free or `TARGET_OS_OSX`-guarded, and CI's `build-ios` job enforces that on every push. `make check-layout` enforces the rule itself.

The iOS halves of the shared subsystems are documented where they live: `Audio/iOS/` (`AudioSessionController`, `AudioPlayer+Recovery`) in `Audio/CLAUDE.md`, `WaveformUI/iOS/` (`WaveformScrubberView`) in `WaveformUI/CLAUDE.md`, `Util/iOS/` (`UIView+DarkMode`) in `Util/CLAUDE.md`, and `Debug/iOS/` below.

On iPad the app is a resizable iPadOS 26 window (all four orientations, no `UIRequiresFullScreen`; minimum 320×480 set via `sizeRestrictions` in `VibeiOSSceneDelegate` — the portrait layout's floor). The portrait/landscape layout switch keys off view aspect, so window shape — not device orientation — picks the layout. **Multi-scene stays off, deliberately**: `PlayerViewController` owns the audio engine per-instance, so a second scene would spawn a second engine; the one scene is still freely resizable. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage` — a mid-resize offset rounds to a neighbor page and would otherwise switch tracks.

## The pieces

- **`PlayerViewController`** — the iOS `MainPlayerController`, and split the same way it is: what stays in the class's own file is the coordination — the collaborators it owns, the update funnel, the header and empty states, the transport entry points, and the playlist, folder-session and audio-session delegates. Everything else is a category, each with its contract in its own header:
  - `+PlayerEvents` — every `AudioPlayerDelegate` callback. Two rules govern the file and are stated at its top: **every callback can be stale** and must match the delivered track against the playlist's current one, and **`stop` fires no callback**, so nothing there drives auto-advance.
  - `+Pager` — the collection view's data source and layout, the size-transition re-paging, the per-page waveform bookkeeping, and `commitVisiblePage`. Playback does not switch as pages appear; only the settled page commits.
  - `+Delivery` — where asynchronous results land: metadata, waveform snapshots, and the scrubber's seek. All of them implement the one cross-directory invariant about deliveries racing track changes, which is why they are one file.
  - `+NowPlaying` — the publish and the remote-command routing, which lands on the same transport entry points the screen's own controls use.
  - `+Debug` — the debug channel's extra surface, in `Vibe/Debug/iOS/`.

  **`PlayerViewControllerInternal.h` is the one private surface all of them share** — the class extension with the collaborators, the chrome bindings, the state flags a category touches, and the internal methods. Same reasoning as the mac's: a method a category implements is declared in *that category's header*, never in `PlayerViewController.h` or the internal one, or the compiler cannot check either side. That shared header is the cost of the split, so it is the thing to watch.

  **The screen's display state is resolved in one place**, `PlayerScreenRules.h` — header-only, Foundation-only and tested — rather than re-derived from `_parked`, `_trackStartPending`, `_errorText` and the rest at each site. `screenState` gathers the inputs; `updatePlaybackUI`, `chromeAlpha`, `scrollTick:`, the Now Playing publish and the debug dump all read the result. Its mac twin is `TrackDisplayRules.h`; the two enums are deliberately separate, since this screen has no launch grace and parks tracks the mac has no equivalent of.

  **Four of the mac's features are off here**, each at one place rather than compiled out: no DJ FX (the engine is created with `enableFX:NO` — the FX graph segment is never attached and the mixer wires straight to the output; see `Audio/CLAUDE.md`), no folder art (`AudioTrackArtwork` leaves its resolver handle nil, so a file shows its embedded art alone), no BPM or key analysis (the decode pass's analysis provider is unset, so neither analyzer is built; a track's `bpm` and `key` are whatever its tags carry), and no art thumbnails (`AudioTrackArtwork` decodes, holds and archives none, because the playlist table they exist for has no counterpart here — see `Audio/Metadata/CLAUDE.md`). The settings behind the first three are macOS-only in `AppSettings`, so there is nothing here to read that could disagree; the fourth has no setting at all.

  It owns `Playlist`, both caches and the `PageWaveformCoordinator` over the waveform one, `NowPlayingController`, the session and folder controllers, the 3 Hz `UIUpdateTimer` (foreground-gated; the lock screen extrapolates from the last Now Playing publish), and a `CADisplayLink` that drives the scrolling waveform at display rate while playing in the foreground — paused otherwise, and a seek-in-flight flag holds the seek target on the waveform until `didFinishSeeking:` so the fade-down's stale position never snaps it back. Every cross-directory invariant in the root CLAUDE.md applies unchanged: deliveries matched against the current track, auto-advance only from `didFinishPlaying:` or the gapless `didAutoAdvanceFromTrack:toTrack:` (which moves the cursor without `play:`), prefetch on every start, BPM/key via `AudioTrack.bpm`/`.key`.
- **`FolderSession`** — the picked location's owner: picker presentation, the security scope (held for the whole session — the player, TagLib, and the waveform loader read under it at arbitrary times; released only after a successor is in hand), the bookmark that restores the folder on relaunch (default `bookmarkData`; iOS has no `WithSecurityScope` option and doesn't need it), and the listing via `NSURLUtil audioFilesInDirectory:`. Adoption — bookmark resolution and the listing, both file-provider IPC that can run seconds on a cloud folder — happens on the session's own serial queue, never main; delegate deliveries land on main, in submission order. A single-file pick is a one-track playlist: iOS grants no sibling access from a file grant. A relaunch restore **parks** the remembered track — header, waveform, metadata loaded, nothing playing — and the scene delegate runs exactly one of restore-or-adopt at launch, so a cold "Open in Vibe" never pays for a restore it immediately replaces.
- **`TrackPageCell`** — one full-screen page of the track pager: blurred art + the mac-style header. Two constraint sets swapped on the cell's own aspect in `layoutSubviews`: portrait is the Apple Music-style centered card, landscape is the mac main window transplanted — a small square art card top-left, artist over title beside it, codec line top-right, full-width waveform + time row. The waveform band's numbers live in `TrackPageGeometry.h`, shared with `PlayerViewController`, which mirrors the nominal geometry to place its empty-state line without constraining across the cell boundary. The pager is a paging horizontal `UICollectionView` at the back of `PlayerViewController`'s hierarchy — grab-and-pull to a neighbor commits that track when the scroll settles (Photos semantics; pulling back cancels), with the chrome (waveform, transport, time, bottom bar) overlaid and never scrolling. **A page shows full-size art and nothing standing in for it** — the vinyl placeholder until it arrives, never a thumbnail. iOS keeps no thumbnail at all (`Audio/Metadata/CLAUDE.md`): nothing here draws one, and standing it in only bought a visibly soft card that snapped sharp a moment later, at the price of a second read and decode of the same art. Making the real thing arrive first is the **art window**, in `+Pager`, and its two halves are deliberately separate numbers. **Prefetch** is `kArtPrefetchRadius` pages either side of the current one, and it fetches *metadata first, through the priority lane* — the art dispatch hangs off the metadata object, so behind a playlist-wide scan of a cloud folder a page's art cannot even start until its own tags land. **Retention** is a byte budget, `kArtBudgetBytes`, not a radius: fetching far ahead means reads nobody asked for, while keeping what is already decoded costs only memory, and releasing it means re-reading and re-decoding the instant the user swipes back. Past the budget the pages furthest from the current one are released — distance is the eviction order because in a pager it *is* recency — but never one inside the fetch window, and never one with a live cell, whose image view pins the bitmap anyway, so the release would free nothing while leaving the page one reconfigure from dropping to the placeholder in view. `renderHeaderForTrack:` moves the window; `didLoadMetadata:` re-runs it. The commit path deliberately releases nothing on its own: the departing track is usually the page right beside the arriving one, and dropping its art per commit made every swipe back re-read and re-decode the file. `debug-ios.sh dump_art` reports the window, what is held, and each page's art state, which is the only way to tell "not decoded yet" from "no art at all" — on screen both are the placeholder. **The blurred backdrop is a baked image, not a `UIVisualEffectView`** (`UIImage+Blur`, memoized on the artwork it came from): an effect view's blur is a live backdrop filter that the render server recomputes on every frame anything behind it moves, which during a swipe meant two full-screen blurs per frame — of a picture that never changes. Baking it also collapsed the art view and the effect view above it into one image view.
- **`PageWaveformCoordinator`** — the pager's waveform bookkeeping between `AudioWaveformCache` and the cells: the cache runs one load at a time, and the pipeline owns which page it targets along with that page's URL, the latest snapshot per page for re-hydrating reloaded cells, and the complete set. **Waveform deliveries carry the URL they were loaded for**, so a decode that outlives its retarget is dropped on the value rather than on the cancel having been observed in time — the same cross-directory invariant the mac's `MainPlayerController+Delivery` implements, and the reason `requestIndex:track:` records `_targetURL` beside `_targetIndex`. A page the pipeline already targets is left alone — re-requesting on every cell reload would keep killing the decode — and the snapshot window prunes to a radius around the current page, since distant pages re-load from disk in milliseconds. It passes the cache's URL-tagged BPM/key deliveries through untouched.

  **The scroll hold (`held`) is the pager's frame budget.** A swipe is the one moment the main thread has nothing to spare, and both halves of this object were spending it: a delivery repaints a scrubber, which tears its baked envelope down and restarts a 60 Hz full-view path rebuild — and a decode delivers about ten times a second, so the bake never re-landed and the whole swipe composited the expensive live tree — while a request cancels the ONE load the cache runs, so a swipe across N pages cancelled N decodes and finished none, which is why the stutter was worst on an uncached folder. Held, deliveries are recorded but not forwarded and requests are dropped; `+Pager` sets it on `scrollViewWillBeginDragging:` and clears it in both settle paths, before `commitVisiblePage`, so the page the drag landed on is what asks for a load. The cost is deliberate: a page pulled into view mid-drag shows the snapshot it has, or the loading line, rather than starting a decode nobody has settled on. The same flag pauses the playhead's display link — see `updateScrollLinkState`.
- **`TrackListViewController`** — the playlist button's sheet: Choose Folder row + the directory's tracks, current row marked. Holds `Playlist` weakly; `PlayerViewController` forwards observer changes and metadata deliveries as row reloads (and playlist replacement, so an external open cannot strand an open sheet stale).
- **`SearchViewController`** — **not reachable in the shipping app.** Its only entry point, `PlayerViewController.searchTapped`, hangs off `_searchBarButton`, which is hidden; the bottom bar's geometry is held by a layout guide instead, so unhiding that button is the whole of shipping it. What it is, when it is: the search bar's sheet — a standard `UISearchController` over the open folder's tracks, matching title, artist, and filename, Mail-style — the field is focused on appear and results filter live; the empty query lists everything, so the sheet doubles as a browse list. Selecting a result dismisses and plays. Playlist replacement re-filters it through the same forwarding as the track list.

Persistence lives in `FolderSession`'s own `NSUserDefaults` keys (`VibeiOSFolderBookmark`, `VibeiOSLastTrackFileName`), deliberately not in the shared `AppSettings`.

## Building and verifying

```bash
make build-ios CONFIG=Debug     # exactly what CI's build-ios job runs
```

Use the **`vibe-debug` skill** (its "iOS: the simulator loop" section) to launch, feed, screenshot, and log the app — `launch-ios.sh` boots/installs/relaunches with audio silent by default (the mac's `--no-audio-hw --silent` flags work verbatim; the engine is shared), seeds audio into the container, and the log streams from the host.

**The debug command channel exists on iOS** (debug builds only): `debug-ios.sh <verb>` from the host writes a command file straight into the simulator app's container tmp — a plain host directory, so no CLI client is needed — and the app's directory watcher answers with one JSON object, same file protocol as the mac. The transport is `Vibe/Debug/DebugChannel.m`, shared with the mac verbatim, and so is most of the verb set: `dump_state`, `dump_now_playing`, `play_pause`, `next`, `previous`, `seek`, `open` and `clear_caches` are written once in `Vibe/Debug/DebugCommonVerbs.m` against the `VibeDebugPlayerSurface` protocol, which `PlayerViewController (Debug)` and the mac's `MainPlayerController (Debug)` both adopt. What is left in `Vibe/Debug/iOS/DebugCommands.m` is only what needs UIKit — `dump_view_tree` and `dump_screenshot` — plus the dispatch that tries the shared table first. `PlayerViewController+Debug.{h,m}` both live beside it in `Vibe/Debug/iOS/` — the shipping tree carries no declaration for a tool that does not ship — and the implementation reaches the screen's private state through `PlayerViewControllerInternal.h`, the same production surface the controller's own categories share. The verb list lives in the skill and the channel's own unknown-command reply, deliberately not here. The channel itself cannot inject touches (no public API synthesizes `UITouch`es in-process); **gestures go through the touch driver** — `drive-ios.sh` and the resident `VibeiOSDriver` XCUITest in `Tests/iOSDriver/`, the WebDriverAgent pattern — with tap/press/drag verbs over the same file protocol. The mac's menu/window/FX verbs have no iOS counterparts. Real-pixel screenshots stay `simctl io booted screenshot`; the channel's `dump_screenshot` is the in-process render.

The skill is the canonical home of the whole loop, deliberately not duplicated here, so it cannot drift.

Interruptions, route changes (headphone unplug), background audio past lock, and the lock-screen card need a real device — the simulator exercises none of them faithfully.
