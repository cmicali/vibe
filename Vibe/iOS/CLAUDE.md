# iOS app shell (VibeiOS target)

A single-folder player: **the current directory is the playlist.** The user picks a folder or file in the system document picker; Dropbox and iCloud come through their Files providers, no provider SDKs. Three `UITab`s — Playlist, Favorites, Files — with `UISearchTab`'s circle beside the capsule, a mini player strip in the tab bar's `bottomAccessory`, and the now-playing card presenting up from the strip. Opening anything replaces the playlist, starts playing, selects the Playlist tab and presents the card, so minimizing lands on what was just opened. **Add to Playlist** appends a Files-tab item's or a favorite's tracks without touching playback, the tab or the card; an Add onto nothing is an Open.

This directory is the shell only. The iOS halves of shared subsystems are documented beside them: `Audio/iOS/`, `WaveformUI/iOS/`, `Util/iOS/`. Within this directory, `Player/` (the card: pager, page cell, route control, waveform coordinator), `Search/` (Favorites, Search and the folder stores) and `Settings/` each carry their own `CLAUDE.md`.

A new file in a shared directory joins this target automatically and must be AppKit-free or `TARGET_OS_OSX`-guarded (root `CLAUDE.md`); CI's `build-ios` job catches a leak.

**Layout keys off view aspect, not device orientation.** iPad is a resizable window, all orientations, minimum 320×480 via `sizeRestrictions` in `VibeiOSSceneDelegate`.

**Multi-scene is off.** One `AudioPlayer` per `PlaybackController`, one `PlaybackController` per scene; a second scene would be a second engine. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage`: a mid-resize offset rounds to a neighbor page and would switch tracks.

## PlaybackController — the model

Everything the app plays and nothing that draws it: engine, `Playlist`, metadata cache, audio session, `FolderSession`, Now Playing, the 3 Hz `UIUpdateTimer`, and the display state. The scene delegate owns the one instance; every screen borrows it.

**It broadcasts** (`PlaybackObserver`: synchronous on main, registration order, weak `NSPointerArray`) because three views describe one playback and `Playlist` has one observer slot. **Weak is load-bearing**: an observer is a view or view controller.

**The playlist remove, insert and move observer methods are no-ops.** iOS has no edit UI, and forwarding a model-only edit would not make it safe — removing the current row is a transport operation. An iOS edit UI must first add its own coordinator on the model of `MainPlayerController.removePlaylistTracks:`; calling `Playlist.removeTracksAtIndexes:` directly leaves the player sounding a departed object.

`+PlayerEvents`: every `AudioPlayerDelegate` callback, under the root doc's two rules (every callback can be stale; `stop` fires no callback). `+NowPlaying`: `notifyDidTick` **publishes before it ticks**, so the lock screen never lags the screens.

**On track end is the root guarantee's, enforced at both of its places here**: `successorPrefetchTrack` (nil under Pause, so no splice is armed) feeds the one `prefetchTrack:` site, and `didFinishPlaying:` re-reads the setting before `next`, parking on the finished track exactly as the end of the playlist does. A write to either transition setting ends on `applyTrackTransitionSettings`, which pushes the crossfade and re-parks or drops the successor — the iOS spelling of the mac's `EndOfTrack` and `Crossfade` live effects, and the one thing the Settings screens are handed the model for.

**A scrub on a parked track seeks; it does not play.** Parked, the player holds no file, so `seekToProgress:` opens the file at the scrubbed position, paused, with the duration from metadata. The seek target outranks Loading in the card's progress paths, or the waveform would snap to zero during that open. `didStartPlaying:` clears the in-flight flag; this seek has no `didFinishSeeking:`.

**The metadata sweep waits for the picked track to settle**: `folderSession:didOpenTracks:` schedules it, `didStartPlaying:` and the error path start it, and a two-second fallback covers an open that never lands. The rule underneath is `AudioFileMaterializationCoordinator`'s (root `CLAUDE.md`); this is only the scheduling.

**Display state is resolved once**, in `PlayerScreenRules.h` (header-only, tested from the macOS suite). `screenState` gathers the inputs; the card, the mini strip, Now Playing and the debug dump read the result. Separate from the mac's `TrackDisplayRules.h`: no launch grace here, and parked tracks the mac has no equivalent of.

**Three mac features are off, each at one switch**: no DJ FX (`enableFX:NO`), no folder art (`AudioTrackArtwork`'s resolver handle nil), no BPM/key analysis (no analysis provider installed). Their settings are macOS-only in `AppSettings`.

**The 128px thumbnail is on.** Rows archive compact bytes; decoded pixels live in `AudioTrackArtwork`'s shared bounded LRU (`kEmbeddedThumbnailCacheCount`). An eviction returns the placeholder, decodes once off-main, and refreshes only visible Library, Search and mini-player surfaces. **TRAP: UITableView renders prepared cells before they are "visible" and displays them without re-running `cellForRowAtIndexPath:`** — a delivery in that window repaints nothing, so the Library re-renders each cell in `willDisplayCell:`.

## FolderSession

Owns the picked locations of the current playlist — a **base** folder or file plus any additions: picker presentation, the security scopes, the restore bookmarks (plain `bookmarkData`; iOS has no `WithSecurityScope` option), and the listing via `NSURLUtil audioFilesInDirectory:sortedBy:`. Persistence is its own `NSUserDefaults` keys, not `AppSettings`.

- **Scopes are held as a set** — the base open's and each addition's — for the whole session, since player, TagLib and the waveform loader read under them at arbitrary times, and released only after a successor set is in hand; an append extends the set. A URL may be started twice and each start is balanced by its own stop.
- **Adoption runs off main**: bookmark resolution and listing are provider IPC that can take seconds. Replaces go on a concurrent queue so a new intent is never parked behind an older provider call; appends go on a **serial lane targeting it**, so two Adds land in tap order while a replace overtakes them. Every request carries `openIntentGeneration`: a replace bumps it, an append captures it, and only a result matching the live one delivers or persists. An append also checks the last SETTLED replace, so an Add requested during an open that never landed is dropped rather than added to the wrong playlist; an Add onto a session that has never landed anything is promoted to an Open at request time — including after a failed launch restore, which is why that case plays.
- **Settled is not the same as delivered, and an empty open settles too.** **TRAP:** an open that found no audio leaves the previous playlist standing, so that playlist now answers for the new generation as well and `_landedOpenIntentGeneration` carries forward to it. Without the carry one empty-folder open left every later Add captured at a generation no landing ever matched, and Add was silently dead for the rest of the session. Zero never carries — nothing has landed, so the Add is still promoted to an Open — and an append that found nothing carries nothing, since a bad Add must not make itself the base. Every request ends in `finishOpenIntent:`, the empty ones included; it is the only place the main-confined state moves.
- **One prologue, `beginOpenURLs:appending:restored:fromSearchRoots:`**, serves every entry point (picker, browser, favorite, search hit, inbox copy, restore, Add). It runs on main, does no I/O, and is where `AppSettings.folderOpenSort` is snapshotted and passed to the worker, so an open cannot straddle a Settings change and the walk reads no setting (`Util/CLAUDE.md`). It is also where the main-only stores are asked — `SearchFolderStore.grantCoveringURL:`, then a retained grant, then `FavoritesStore.resolvedRootCoveringURL:`, in that order — and where a hold is taken on each covering scope so an older worker can finish safely.
- **The base is the FIRST contributor, whatever it is**, and it is the playlist's identity: the Playlist tab's title, the star and the base bookmark all name it, and an Add never moves it. A first contributor that is a file is a single-file base — `folderURL` nil, so the title stays "Playlist" and there is no star, because a single file has no identity to bookmark — and every later folder in the same open is an addition. **TRAP: a folder may not claim the base merely because the contributor ahead of it was a file.** A restore delivers base-then-additions, so a single-file base with an appended folder came back as `[file, folder]` and the folder took the base: the base bookmark was rewritten to the addition, the original file demoted, and the next relaunch's union came back reordered as `[folder, file]`. A multi-select replace of a file and a folder therefore keeps the file as the base and the folder as an addition, and — since the open did bring a folder in — it does persist, which the one-file rule below would otherwise refuse.
- **A file grant reaches nothing but the file**, so a single-file pick is a one-track playlist. A folder grant covers the subtree, which `searchRoots` and `openFileFromSearchRoots:` build on: a search hit opens its own directory as the playlist and leaves the grant and bookmark alone — re-pointing the bookmark at a subfolder would shrink next launch's searchable root. **Only a replace of exactly one picked file expands** to its directory, and it does so under any covering root in hand, not only an exactly-equal parent; **an added file is one track, never its directory**.
- **One delivery names each file once**, and a URL that contributed no track is not persisted. Both halves are the same rule: a restore's list can legitimately overlap (an Add the shell deduped away still persisted its bookmark, and a folder can be added beside one of its own files), and the union is delivered as a replace, which does not dedupe — without this the playlist grew a copy of every re-added folder at each relaunch.
- **An append that finds nothing is silent** — no empty-folder event, no delegate call — since a bad Add must not disturb a good playlist.
- **Persistence is a base bookmark plus an ordered addition list**, both rewritten on every landing from what actually contributed, so a dead or emptied addition prunes itself at the next launch with no pruning code. Neither key is touched by a search-hit open, an inbox copy or a one-file open over a folder bookmark; additions made after one of those are session-only, since the persisted base belongs to an earlier playlist.
- **The picker has two modes.** `presentPickerFromViewController:appending:` builds the same picker either way; NO is the empty state's Open, single-selection and replacing, and YES is the Files tab's Add button, multi-selection and appending. The mode is recorded at presentation and read by the picker's delegate — the picker is modal, so only one is ever up.
- **Relaunch parks the remembered track** — header, waveform and metadata loaded, nothing playing, card minimized. The base restores with every addition that still resolves, and the remembered track is looked up over the union, so a track from an added folder parks correctly. **What is remembered is the standardized PATH** (`persistedTrackPath`), because the playlist spans folders once an Add has landed and two albums both holding `01.wav` parked on the wrong one. The match is **two-tier — exact path, then filename** — since a provider can hand the same file back under a different absolute path and the simulator's data-container UUID rotates on reinstall; an exact hit anywhere in the union outranks a filename hit, and the filename tier is also what restores a bare filename left by a build before this one. The defaults key keeps its shipped `VibeiOSLastTrackFileName` spelling for exactly that reason. The scene delegate runs exactly one of restore-or-adopt at launch, so "Open in Vibe" never pays for a restore it replaces.
- **TRAP: acquire before release.** A replace landing installs the successor scope set FIRST and only then stops the previous one, so a failed pick never strands the current playlist unreadable. The `TRAP:` beside `finishOpenIntent:` is the authority.

## RootViewController

The scene's root: a `UITabBarController` child, the mini player in its `bottomAccessory`, the card above both. It alone knows whether the card is up, and owns expand and minimize.

**The tabs are `UITab`s, not view controllers.** `UISearchTab` draws the circle outside the capsule, and `automaticallyActivatesSearch` collapses the bar behind a field and restores the previous tab on cancel. Each tab's view controller comes from a lazy provider; ask `_filesController`, never `UITab.viewController`, whether Files exists — the getter resolves the provider. The search tab's identifier is UIKit's, so `selectedTabIdentifier` matches it by kind.

**A container, not a `UITabBarController` subclass**: the card sits above the tab bar controller's whole view so that view can scale back, and a subclass cannot transform its own view without moving the card.

**The card is built once and never torn down.** Minimize translates it off the bottom. Its pager, art window and waveform snapshots survive, or every expand would re-read and re-decode art; art is not pruned on minimize either — the byte budget bounds it, and pruning costs a placeholder flash.

**TRAP: the card moves by TRANSFORM, never by frame.** Its pages carry `WaveformScrubberView`s, which re-bake their envelope on any bounds change. `dump_state`'s `ui.waveformBaked` checks it.

**TRAP: `shouldAutomaticallyForwardAppearanceMethods` is per-parent.** Turning it off for the card turns it off for the tabs, so both are forwarded by hand; each begin snapshots its exact children and the end consumes that snapshot, because `_expanded` can change between them.

Foreground-inactive is off, not a halfway foreground: the scene delegate's foreground-active bit drives the Library surface and the card's display link. The custom card transition supplies what a presentation would: Reduce Motion settles immediately, the card is the modal accessibility surface while up, and completion moves VoiceOver focus.

## MiniPlayerView

The accessory's content: the 128px thumbnail, title over artist, play/pause and next. Large tap targets, small glyphs (`kGlyphPointSize`); next is `forward.end.fill`, the mac's glyph. `traitCollection.tabAccessoryEnvironment` says when the tab bar has collapsed it inline, where the artist line is dropped. **No playhead bar**: one fits 48pt only by crowding the art and labels.

**TRAP: the row needs a designated give, and the simulator never shows it.** On device the accessory container reports width zero on at least one pass; the row's required content needs 162pt, so UIKit breaks a constraint at random and logs every launch. The art's leading inset is `UILayoutPriorityRequired - 1`. Any new required constraint spanning the row reopens this.

**TRAP: the strip is 48pt, not negotiable.** `UITabAccessory` frames its content at a fixed system height; `intrinsicContentSize` and height constraints are ignored *without a logged conflict*. A taller strip means giving up the accessory, and with it Liquid Glass, inline collapse and the automatic safe-area inset.

## FilesViewController

`UIDocumentBrowserViewController` over every provider, with no navigation controller (it brings its own bar; wrapping stacks two). A pick goes through `PlaybackController.openURLs:openInPlace:`. **It opens folders too**: `UTTypeFolder` leads its content types, so the browser's own Open button hands a directory to `FolderSession`'s open prologue, bit for bit the document picker's path — which is why the Playlist tab has no Open button.

**Add to Playlist has two roads here, and the long-press menu is the working one.** A `UIDocumentBrowserAction` with `UIDocumentBrowserActionAvailabilityMenu` puts it in the long-press context menu of a file *and* of a folder. `allowsPickingMultipleItems` and `…AvailabilityNavigationBar` are set but inert: **iOS 26's browser offers no "Select" mode on iPhone**, so they only widen what an iPad drag selection or a future OS may hand over. **TRAP: a folder row matches `public.directory`, not `public.folder`** — listing `UTTypeFolder` in the action's `supportedContentTypes`, which is what the browser itself filters on, hides the action from every folder while the files still show it, and reads as the action being unsupported on folders altogether. The second road is `additionalLeadingNavigationBarButtonItems`: one `text.badge.plus` button that presents the system picker in its **appending, multi-selection** mode (the empty state's Open picker stays single-selection), because the browser can neither select rows nor run a custom action without them. **TRAP: that button must go on the LEADING side** — the browser draws its own overflow `•••` exactly where it lays a trailing additional item out, so a trailing button renders nowhere and its touches reach the browser's menu instead, which reads as the button simply being absent.

**TRAP: it is the only tab that needs `additionalSafeAreaInsets`, and the clearance must NOT include the accessory's height.** The browser places its own floating capsule against its safe area, which ends at the top of our lowest capsule, so the two collide; a scroll view never shows this. `RootViewController.applyFilesBottomInset` adds the constant `kFilesBarClearance`: UIKit's own 8pt gap plus the browser bar's overhang past its safe area. UIKit's tab-child safe area already spans the accessory, so adding its height leaves a dead band, and one constant lands the same gap with the strip up or down. Re-measure after an iOS update: `dump_view_tree` gives the capsule and accessory anchors, and a screenshot column scan should show three runs 8pt apart.

## LibraryViewController

The Playlist tab: number (replaced on the playing row by the shared `EqualizerIndicatorView`), artwork, title over artist, duration. **Selecting a row plays it and stays here**; expanding the card is the strip's job. Number and duration take the artist line's text style so the secondary columns scale together under Dynamic Type. The folder name goes on `navigationItem.title`, not `self.title`, which is also the tab's title.

**Equalizer activity is actual output plus material visibility** — this doc's half of the root guarantee. Output is `PlaybackController.audioOutputActive`: true through an outgoing fade, false for a Loading request. Visibility is this controller's presentation plus `willDisplayCell:`/`didEndDisplayingCell:` state, plus `RootViewController`'s tab and card exposure — explicit, because the card moves by transform over children that stay "appeared", and kept honest through interactive and interrupted transitions — plus the scene delegate's foreground-active bit. Only then does the playing row start its poller, declaring one `equalizerLevelsWanted:` consumer; stopping balances it. The gate is counted, not boolean, because cell reuse can briefly hold two consumers. Hidden track changes retain one pending scroll index and park there without animation on the next reveal.

**The gutter has three states in precedence: loading, playing, number** (`resolveGutter`). Loading is `CloudTransferRegistry.isTransferringURL:`, a provider transfer really running; it outranks playing because there is no output audio yet. `syncEqualizerActivityForCell:` folds `!loading` into both activity facts so a loading row holds no poller; a registry change re-syncs `visibleCells` in place, never a reload; `didEndDisplayingCell:` and `prepareForReuse` drop `loading`.

`dump_equalizer` is the runtime proof: `renderer.displayTicks` is bounded at 30/s while active and flat after an inactive transition settles. **`--silent` zeroes the tapped signal**, so flat bars under the debug scripts' default launch prove nothing; use `VIBE_AUDIBLE=1`.

The bar carries **the gear, and the star when a folder is open** — absent, not disabled, for a single-file or empty playlist. Title and star both name `FolderSession`'s BASE folder, never an added one: an Add changes neither. `refreshChrome` rebuilds title, star and empty state together. The star fills when the bookmark lands, not on the tap (`Search/CLAUDE.md`), and this screen also redraws on `VibeFavoritesDidChangeNotification`. The empty state's `UIContentUnavailableConfiguration` keeps its own Open action for the first run.

## Building and verifying

The `vibe-debug` skill's "iOS: the simulator loop" section covers launch, feeding audio, screenshots and logs. `RootViewController+Debug` adopts the channel's protocol, composing `PlaybackController+Debug` and `PlayerViewController+Debug` with the shell's own state; all three categories live in `Vibe/Debug/iOS/`. `expand_player`, `minimize_player` and `select_tab` exist because the channel cannot synthesize a touch — gestures go through `drive-ios.sh`. **Interruptions, route changes, background audio past lock and the lock-screen card need a real device.**
