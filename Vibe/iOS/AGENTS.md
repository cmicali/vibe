# iOS app shell (VibeiOS target)

This directory holds the iOS app shell: the app and scene delegates, the tab shell (`RootViewController`), the model (`PlaybackController`), `FolderSession`, the Playlist tab, and the mini player. Its subdirectories hold the Files tab, the now-playing card, Favorites and Search, Settings, and the widget's app side.

**A playlist starts from an opened folder, file or playlist file and can hold additions.** The user picks a folder or file in the app's own browser, the Files tab. Its sources are Dropbox (`Loading/iOS/Dropbox/AGENTS.md`), the app's Documents, and each location granted once through the system folder picker (iCloud Drive, a drive, any other Files provider). There are three `UITab`s, Playlist, Favorites and Files, with `UISearchTab`'s circle beside the capsule. A mini player strip sits in the tab bar's `bottomAccessory`, and the now-playing card presents up from it. Opening anything replaces the playlist, starts playing, selects the Playlist tab and presents the card. A single file played alone keeps its current tab. An active Search tab also keeps the selection. **Add to Playlist** appends tracks without touching playback, the tab or the card. An Add onto nothing is an Open.

This directory is the shell only. The iOS halves of shared subsystems are documented beside them: `Loading/iOS/Dropbox/` (the Dropbox account and its mirror) and `Util/iOS/`. The scrubber is vibe-libs' `waveform/WaveformView`. Here, `Files/` (the Files tab, with its Locations and Recents stores), `Player/` (the card), `Search/` (Favorites, Search and the Favorites store), `Settings/` and `Widget/` (the app side of the Home Screen widget) each have their own `AGENTS.md`.

**Layout keys off view aspect, not device orientation.** On iPad it keys off height too: a short window takes the card's compact layouts (`Player/AGENTS.md`). iPad is a resizable window in all orientations, with a 320×200 minimum through `sizeRestrictions` in `VibeiOSSceneDelegate`. The system can impose a larger minimum.

**Multi-scene is off.** There is one `AudioPlayer` per `PlaybackController` and one `PlaybackController` per scene, so a second scene would be a second engine. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage`. A mid-resize offset rounds to a neighbor page and would switch tracks.

## PlaybackController — the model

It owns everything the app plays and nothing that draws it: the engine, `VibePlaylist`, the metadata cache, the audio session, `FolderSession`, Now Playing, the 3 Hz `UIUpdateTimer` and the display state. The scene delegate owns the one instance, and every screen borrows it.

**It broadcasts** through `PlaybackObserver`: synchronous on main, in registration order, held in a weak `NSPointerArray`. Three views describe one playback, and `VibePlaylist` has one observer slot. **Weak is load-bearing**, since every observer is a view or view controller.

**iOS has exactly one removal: `clearPlaylist`, the whole playlist.** The bar's menu offers it as Clear Playlist. It is the twin of the mac's `closeFile:`. Unloading everything leaves no cursor to strand and no row for the player to be sounding. It stops the player, drops the parked successor and ends the loading open's progress. It then clears the session (scopes, base, additions and the persisted bookmarks and remembered track) **before** the model, whose replace event rebuilds the chrome (the `TRAP:` in `clearPlaylist`). Then it cancels the deferred sweep and the scan. **It settles the launch waiters last of all.** A clear during a launch restore supersedes the restore, so nothing else would settle them. `_launchOpenSettled` is a latch: missed once, every later `performWhenLaunchOpenSettled:` waiter parks, and a widget transport intent then skips a track at some later open. A waiter runs arbitrary work, so it must not see a half-reset controller.

**There are no partial edits.** The remove, insert and move observer methods are no-ops, because there is no row-level edit UI. Removing the current row is a transport operation. A row-level edit UI must add its own funnel on the model of `MainPlayerController.removePlaylistRows:`. Calling `VibePlaylist.removeTracksAtIndexes:` directly leaves the player sounding a departed object.

`+Opening` holds the open and add roads into `FolderSession`, the row being opened (`openingPath`), the restore and the launch settle. It is also the `FolderSessionDelegate`. Every landing arrives there. `+ReplacePrompt` holds the question every screen asks before its tap replaces the playlist, and Open URL's road into it. `+PlayerEvents` holds every `AudioPlayerDelegate` callback. Async callbacks can be stale. `stop` fires no transport or track-end callback. `+NowPlaying` holds `publishNowPlaying`, which `notifyDidTick` calls before it ticks the screens, so the lock screen never lags them. It fills one record with the displayed row's source key, title, artist, one image, and the timing, and pushes it to vibe-libs' `system/NowPlaying`. A debug launch with `--no-now-playing` or `--no-audio-hw` makes no controller (`Debug/AGENTS.md`). The image is `cachedArt`, else `cachedThumbnail`, else `record-bg`, held once so the dirty check sees one object. The system's shuffle and repeat follow the card's Show shuffle and repeat (`iOS/Settings/AGENTS.md`).

**On track end follows the root guarantee.** Every `prefetchTrack:` site parks the playlist's `trackEndSuccessor`, which is nil under Pause. `didFinishPlaying:` calls `advanceAtTrackEnd`, which moves nothing under Pause. It then parks on the finished track, as the end of the playlist does. **A refused splice parks too, and must silence what the player started.** When `advanceFromTrack:toTrack:` no longer accepts the spliced successor (a mode or Pause switched mid-boundary), `didAutoAdvanceFromTrack:toTrack:` runs the track end. If that parks, it reloads the finished track paused over the sounding successor, as the mac does. Every write to a transition setting ends on `applyTrackTransitionSettings`: Pause, the crossfade, and the card's `toggleShuffle` and `cycleRepeatMode`. It pushes the crossfade and both modes, re-parks or drops the successor, publishes the modes to Now Playing and sends `playbackDidChangePlayOrder:`. It is the iOS form of the mac's `EndOfTrack` and `Crossfade` live effects. An open hands its start row to `replaceAllWithTracks:startingAtIndex:` (vibe-libs' `media/PlayQueue/AGENTS.md`).

**TRAP: `prefetchSuccessor` does nothing while the player is stopped.** A stopped player can retain the finished file. Prefetching here can start an unasked download.

**A scrub on a parked track seeks; it does not play.** Parked, the player holds no file, so `seekToProgress:` opens the file at the scrubbed position, paused, with the duration from metadata. `VibePlayerScrubActionFor` (`PlayerScreenRules.h`) decides what a scrub does. The seek target outranks Loading in the card's progress paths, or the waveform would snap to zero during that open. `didStartPlaying:` clears the in-flight flag, since this seek has no `didFinishSeeking:`.

**The metadata sweep waits for the picked track to settle.** `folderSession:didOpenTracks:` schedules it, `didStartPlaying:` and the error path start it, and a two-second fallback covers an open that never lands. **A launch restore starts it at once.** The park opens nothing, so no `didStartPlaying:` is coming. The rule underneath is `AudioFileMaterializationCoordinator`'s (root `AGENTS.md`).

**Display state is resolved once, in `PlayerScreenRules.h`** (header-only, tested from the macOS suite). `screenState` gathers the inputs. The card, the mini strip, Now Playing and the debug dump read the result. It is separate from the mac's `TrackDisplayRules.h`: it has no launch grace, and it has parked tracks. **The slow-open state is separate from it.** `currentOpenSlow` is set before `playbackDidBeginLoading:` is sent. It stays YES until the open settles or fails, and every cursor change, replacement and play clears it. The card's loading shimmer reads it, because `screenState`'s Loading starts at submission and would flash on every fast Next.

**Two mac features are off, each at one switch.** Folder art is off: `AudioTrackArtwork`'s `folderArt` is nil. Key analysis is off: the card's waveform analysis provider never lists the key's observer. **The DJ FX and BPM detection are on.** The player is created with `enableFX:` from the shared setting, and `applyFXSetting` is the setting's live effect. `setFXPadPosition:engaged:` is the one funnel for the card's pad and the debug channel, mapped by `AudioFXMath.h`. The delay taps follow `refreshTempoFeed`: `AudioTrack.bpm` for the current track. It is re-read on every render funnel, on a metadata delivery and on `noteDetectedBPM:forTrack:`. The card forwards that from the waveform decode pass, and it stamps every row sounding that track's window (`VibePlaylist.stampTracksSounding:usingBlock:`).

**The 128px thumbnail is on.** Rows archive compact bytes. Decoded pixels live in `EmbeddedThumbnailCache`, the bounded LRU every `AudioTrackArtwork` shares (`kEmbeddedThumbnailCacheCount`). An eviction returns the placeholder, decodes once off main, and refreshes only the visible Playlist tab, Files browser, Search and mini-player surfaces.

## FolderSession

It owns the picked locations of the current playlist: a **base** folder or file plus any additions. It holds their security scopes, their restore bookmarks (plain `bookmarkData`, since iOS has no `WithSecurityScope` option) and their listing through `FolderWalk entriesInDirectory:sortedBy:`, made into rows by `AudioTrack rowsForEntries:`. A CUE sheet stands in for its files there, as in a mac folder walk. `FolderSession` deduplicates each delivery by standardized path plus a cue row's window. `PlaybackController` removes rows already in the playlist before an Add. Persistence is its own `NSUserDefaults` keys, not `AppSettings`.

`FolderSession.m` holds the prologue, the worker's phases and the landing. `+ExternalOpens` holds the entry points callers reach: open, add, clear and cancel. `+Persistence` holds the launch restore, the remembered track, and minting and resolving bookmarks. The state, the stored keys and the methods each side calls on the other are declared in `FolderSessionInternal.h`.

**A sheet's grant reaches the sheet alone, never the audio beside it.** A `.cue` picked in Choose File… or sent with "Open in Vibe" finds nothing unless a root covers its folder. That open settles empty, then names the sheet through `needsFolderOfSheetAtURL:` (only for a denied folder, never a missing one). `RootViewController` hands it to `CueFolderGrantPrompt` (`Files/`). The prompt asks with the mac's grant wording and presents a folder picker. The sheet then reopens with the picked folder held like a starred folder's root (`FolderSession.h` has the contract). A sheet opened alone where a root covers its folder is its own rows (`entriesForFile:`), resolved against the folder's listing so placeholders count.

- **Scopes are held as a set** (the base open's and each addition's) for the whole session. The player, TagLib and the waveform loader read under them at arbitrary times. A set is released only after a successor set is in hand, and an append extends it. Each start is balanced by its own stop.
- **TRAP: acquire before release.** A replace landing installs the successor scope set first and only then stops the previous one. A failed or superseded pick therefore never strands the current playlist unreadable. The `TRAP:` in `finishOpenIntent:` is the authority.
- **"What may be listed" and "what may be held" are two questions over two lists**, both asked through `rootCoveringPath:in:`. The logical roots (`searchRoots`: the base plus the additions) decide listing and the search-root dedupe. A container folder is never security-scoped, yet a file picked in it must still expand to it. `_scopedURLs` decides what a request takes a hold on. **TRAP: a security scope is started through the URL the system granted, never through a path-equivalent one the app derived.** A search hit leaves the base pointing at a derived parent. Asked for a hold, that URL refuses the start, and nothing is collected. The landing then stops the real grant with no successor, and the playlist goes unreadable mid-play. Minting a bookmark for the star takes its hold from the scoped list for the same reason.
- **Adoption runs off main**, since bookmark resolution and listing are provider IPC that can take seconds. Replaces run on a concurrent queue, so a new intent never waits behind an older provider call. Appends run on a serial lane that targets it, so two Adds with their URLs in hand land in tap order, and a replace overtakes them. Every request carries `openIntentGeneration`. A replace bumps it, an append captures it, and only a result that matches the live one delivers or persists.
- **The worker is `openURLsOnWorkQueue:`, in four phases on the work queue.** `resolveRowsOfOpen:` lists the rows. `adoptHolds:coveringContributorsOfOpen:` keeps each hold that covers a contributor and stops the rest. `mintBookmarksOfOpen:` mints the base and addition bookmarks. `recordRecentsOfOpen:` hands the recents to `RecentsStore` on main. One `FolderSessionOpen`, private to `FolderSession.m`, carries the request and each phase's result to the next. `finishOpenIntent:` then lands it all on main.
- **An append captures the generation when the user asks, not when the caller has a URL.** A caller with asynchronous work first (Favorites, a bookmark to resolve) takes an `addRequestToken` on main and hands it to `addURLs:token:`. An Add judged only on arrival would append to whatever playlist was opened meanwhile. **A replace behind asynchronous work carries its own token**, `PlaybackController.replaceRequestTokenOpening:`, to the `confirmReplacing…` funnel in `PlaybackController+ReplacePrompt`. The funnel drops it when a newer replace, open or clear was asked for meanwhile, so an older tap landing late never replaces the open the user made last. The token is staleness only and reserves no place in the lane. Two Adds therefore land in provider order, not tap order, when a slow resolve is in the way.
- **An Add onto a session that has never landed anything is promoted to an Open**, including after a failed launch restore. An append also checks the last settled replace, so an Add requested during an open that never landed is dropped. **TRAP: only the first such Add promotes.** Each promotion bumps the generation, so two promoted Adds would cancel each other and a selection would vanish. The rest park as waiters. They are replayed through the prologue when the promoted open settles, whichever way it settles: they append if it landed, the first of them promotes if it found nothing, and a user's replace releases them onto its own playlist. **TRAP: a promotion is not a supersession.** The token check in `addURLs:token:` runs before the parking. A token one below the generation a promotion created is still the user's while that promotion is live. A real replace or a clear bumps past it and drops it.
- **An empty open settles too. TRAP:** an open that found no audio leaves the previous playlist standing, so `_landedOpenIntentGeneration` carries forward to the new generation. Without the carry, every later Add is captured at a generation nothing landed, and Add is dead for the session. Zero never carries, so an Add is still promoted. An append that found nothing carries nothing. Every request ends in `finishOpenIntent:`, the only place the main-confined state moves. The promotion's token check and this carry are functions in `FolderSessionRules.h`, tested in `FileSearchRulesTests`.
- **An append that finds nothing leaves the playlist alone**, with no empty-folder event. `folderSession:didAppendTracks:` is still delivered, empty. `PlaybackController` ends every Add with `playback:didSettleAddLanding:` after the append's own events, so whoever asked hears how it landed.
- **One prologue, `beginOpenURLs:appending:expandsFile:grantedFolder:`, serves every entry point**: picker, browser, favorite, search hit and Add. It runs on main and does no I/O. It snapshots `AppSettings.folderOpenSort` for the worker, so the walk reads no setting (`Playlist/AGENTS.md`). It asks the main-only stores, in order: `LocationStore.grantCoveringURL:`, then a retained grant, then `FavoritesStore.resolvedRootCoveringURL:`. It takes a hold on each covering scope so an older worker can finish safely. The launch restore reads the sort itself and enters the work queue directly. An inbox copy skips the worker's expansion, since Documents/Inbox under an open Documents base would expand to the whole Inbox.
- **The base is the first contributor, whatever it is**, and it is the playlist's identity. The Playlist tab's title, the star and the base bookmark all name it, and an Add never moves it. A file base has `folderURL` nil, so the title stays "Playlist" and there is no star. **TRAP: a folder may not claim the base because the contributor ahead of it was a file.** A restore delivers base-then-additions, so a folder behind a file base would rewrite the base bookmark and reorder the union at the next relaunch. A multi-select replace of a file and a folder keeps the file as the base, and it persists.
- **A file grant reaches nothing but the file**, so a single-file pick is a one-track playlist. A folder grant covers the subtree. **Only a replace of exactly one picked file expands** to its directory, under any covering root in hand. An added file is one track, never its directory. **An M3U never expands**: it is its own readable entries (`entriesForFile:`). **The prologue alone decides whether an open becomes the session bookmark.** An open strictly inside a grant only the session holds (a one-off pick) leaves the bookmark alone, since re-pointing it would shrink next launch's reach. Under a Location, a favorite, Documents or the mirror, the open is remembered like any other.
- **The app's own trees are roots every open covers.** Documents and the Dropbox mirror need no grant, so `beginOpenURLs:` adds both to the covering roots. A file opened alone in either expands to its folder with it selected, which is what Play in Folder relies on. This holds at every entry point, so an "Open in Vibe" of a song in Documents opens its folder. Only an inbox copy stays one track.
- **A Dropbox folder nothing has listed yet is listed from Dropbox before an open reads it** (`listFromDropboxIfMirrored:`, on the work queue, bounded so an offline open reads the disk). The mirror holds only what something has listed. A folder already listed is read from disk. A restore can wait up to 20 seconds per unlisted folder.
- **One delivery names each track window once, and a URL that contributed no track is not persisted.** A restore's list can overlap, and the union is delivered as a replace, which does not dedupe. Without this the playlist grew a copy of every re-added folder at each relaunch.
- **Persistence is a base bookmark plus an ordered addition list.** Both are rewritten on every landing from what actually contributed, so a dead or emptied addition prunes itself at the next launch. A search-hit open, an inbox copy and a one-file open over a folder bookmark touch neither key. Additions made after one of those are session-only.
- **A link opened alone is persisted all the same** (`VibeFolderSessionPersistsBase`, `FolderSessionRules.h`). Its file sits under the Links root (`LinkStore`'s `containsURL:`), an app-container directory with no security scope. It opens as a single-file base, never as its directory, which is named by a hash. A relaunch resolves the bookmark and parks on the placeholder, offline too. A mirror file opened alone is not a link and keeps a folder bookmark.
- **A launch restore resolves its bookmarks a bounded few at a time** and merges them in persisted order. The bound is three, the same as `LocationStore`'s (`Files/AGENTS.md`). Delivery still waits for the slowest bookmark, since the walk needs the whole union. The listing and the bookmark minting after it stay serial: the dedupe, the contributor list and the base rule are order-dependent, and the same loop pairs each scope start with its stop.
- **A restore keeps the contributors that still yield tracks.** No resolved bookmarks clears both saved keys. Resolved locations with no tracks also report failure but keep the keys. If the base is gone, the first surviving contributor becomes the base. A successful bookmark mint rewrites the saved keys at landing.
- **Relaunch parks the remembered track**: header, waveform and metadata loaded, nothing playing, card minimized. The remembered track is looked up over the whole union. **What is remembered is the standardized path**, plus a cue row's window (`persistedTrackKey`), since two albums can both hold `01.wav`. **TRAP: the path alone is not enough. The match has two tiers: exact path, then filename** (`VibeFolderSessionRememberedIndex`, `FolderSessionRules.h`). A provider can hand a file back under a different path, and the simulator's container UUID rotates on reinstall. An exact hit anywhere outranks a filename hit. The defaults key keeps its shipped `VibeiOSLastTrackFileName` spelling. The scene delegate runs exactly one of restore or adopt at launch, so "Open in Vibe" never pays for a restore it replaces.
- **The first launch copies the bundled `vibe-theme.mp3` into Documents** (`VibeiOSAppDelegate`, gated on `AppSettings.welcomeTrackSpent`). It is the user's file from then on, and deleting it sticks.
- **Each launch removes the cache stores other builds left**, off main (`VibeiOSAppDelegate`). The rule is shared with the mac (`Audio/AGENTS.md`, Metadata and artwork).
- **A launch prunes links once its open settles** (`VibeiOSSceneDelegate`, `performWhenLaunchOpenSettled:`). It keeps every link the playlist's rows or the recents name (`pruneKeepingTracks:recentURLs:`, `VibeRecentItemURLs`). **TRAP: a recent's URL is built from its recorded folder flag, never by `fileURLWithPath:` alone** (`Files/BrowserRules.h`). That call can stat an unreachable path on main and block launch.

## RootViewController

The scene's root: a `UITabBarController` child, the mini player in its `bottomAccessory`, and the card above both. It alone knows whether the card is up, and it owns expand and minimize. Settings rides the Playlist tab's stack. Leaving that tab pops it (`tabBarController:didSelectTab:previousTab:`).

**The tabs are `UITab`s, not view controllers.** `UISearchTab` draws the circle outside the capsule, and `automaticallyActivatesSearch` collapses the bar behind a field and restores the previous tab on cancel. Each tab's view controller comes from a lazy provider. Ask `_filesController`, never `UITab.viewController`, whether Files exists, since the getter resolves the provider. The search tab's identifier is UIKit's, so `selectedTabIdentifier` matches it by kind.

`+AddedRows` holds the flight of an Add's rows into the Playlist tab (`Files/AGENTS.md`). Its state is declared in `RootViewControllerInternal.h`.

**It is a container, not a `UITabBarController` subclass**, so it can put the card and the backdrop snapshot above the tab bar controller's whole view. A card at rest hides the tabs, or the glass tab bar would keep sampling for nothing.

**The card is built once and never torn down.** Minimize translates it off the bottom. Its pager, art window and waveform snapshots survive, so an expand re-reads and re-decodes nothing. Art is not pruned on minimize either: the byte budget bounds it.

**TRAP: what scales under a moving card is a snapshot of the tabs, never the tabs view.** Scaling the view moves its edges off the screen's, and UIKit removes the safe-area insets and edge margins. The bars and rows then re-lay out, and the screen jumps under the card. A snapshot has no layout to lose (`beginBackdropSnapshot`, taken as the card starts moving and dropped once it rests). **The mini player strip stays installed under the card** (`refreshMiniPlayer`). Removing the accessory shrinks every tab's bottom inset, and a list scrolled to its end is clamped up under the snapshot. `check-layout-stability.sh` on a playlist scrolled to its end is the oracle for both.

**TRAP: the card moves by transform, never by frame.** Its pages carry `WaveformScrubberView`s, which redraw on any bounds change.

**TRAP: `shouldAutomaticallyForwardAppearanceMethods` is per-parent.** Turning it off for the card turns it off for the tabs, so both are forwarded by hand. Each begin snapshots its exact children and the end consumes that snapshot, because `_expanded` can change between them.

Foreground-inactive counts as off: the scene delegate's foreground-active bit drives the Playlist tab's surface and the card's display link. The custom card transition supplies what a presentation would. Reduce Motion settles at once, the card is the modal accessibility surface while up, and completion moves VoiceOver focus.

## MiniPlayerView

The accessory's content: the 128px thumbnail, title over artist, play/pause and next (`forward.end.fill`, the mac's glyph). Targets are large and glyphs small (`kGlyphPointSize`). When `traitCollection.tabAccessoryEnvironment` says the bar collapsed it inline, the artist line is dropped. There is no playhead bar, which fits 48pt only by crowding the art and labels.

**TRAP: the strip is 48pt, not negotiable.** `UITabAccessory` frames its content at a fixed height and ignores `intrinsicContentSize` and height constraints, with no logged conflict. A taller strip means giving up the accessory, and with it Liquid Glass, inline collapse and the automatic safe-area inset.

**TRAP: the row needs a designated give, and the simulator never shows it.** On device the accessory reports width zero on at least one pass. The row's required content needs 162pt, so UIKit breaks a constraint and logs it. The art's leading inset is `UILayoutPriorityRequired - 1`. Any new required constraint across the row reopens this.

## PlaylistViewController

The Playlist tab: number (the shared `EqualizerIndicatorView` on the playing row), artwork, title over artist, duration. Each row is a `PlaylistTrackCell`. **Selecting a row plays it and stays here.** Expanding the card is the strip's job. A track change scrolls the list to the playing row, or leaves that for when it shows. **Under shuffle the list holds still**, since following a jumping play order would lose the user's place on every track. Number and duration take the artist line's text style, so they scale together under Dynamic Type. The folder name goes on `navigationItem.title`, not `self.title`, which is also the tab's title.

**TRAP: UIKit displays a prepared cell without re-running `cellForRowAtIndexPath:`.** A thumbnail or metadata delivery in that window repaints nothing, so the Playlist tab re-renders each cell in `willDisplayCell:`. **TRAP: rendering in place does not re-measure an automatic-dimension row**, so a row whose height moved takes an empty `performBatchUpdates:`.

**Equalizer activity is actual output plus material visibility**, this doc's half of the root guarantee. Output is `PlaybackController.audioOutputActive`: true through an outgoing fade, false for a Loading request. Visibility is this controller's presentation, `willDisplayCell:`/`didEndDisplayingCell:` state, `RootViewController`'s tab and card exposure, and the scene's foreground-active bit. The card exposure is explicit, because the card moves by transform over children that stay "appeared". Only then does the playing row start its poller and declare one `equalizerLevelsWanted:` consumer. The gate is counted, not boolean, because cell reuse can briefly hold two consumers. A hidden track change keeps one pending scroll index and lands there without animation on the next reveal. `dump_equalizer` is the runtime proof: `renderer.displayTicks` is bounded at 30/s while active and flat once inactive.

**The gutter has three states in precedence: loading, playing, number** (`resolveGutter`). Loading is `CloudTransferRegistry`'s `isTransferringURL:`: a provider's, the mirror's or a link's transfer really running, the playing row's included until its download ends. It stays visible during streamed playback. `syncEqualizerActivityForCell:` folds `!loading` into both activity facts, so a loading row holds no poller. A registry change re-syncs `visibleCells` in place, never a reload.

**The gear opens a menu**: Settings, then Clear Playlist alone in a destructive inline group. There is no confirmation, because nothing leaves the disk and reopening rebuilds the playlist. Its accessibility label names the menu, since the button does two things.

**The bar carries the gear, and the star when a folder is open.** The plus that presents the add sheet sits on the leading side, since three trailing items crowd the large title. Star and plus are absent, not disabled: the star for a single-file or empty playlist, the plus for an empty one, whose empty state already offers Open. Title and star name `FolderSession`'s base folder, never an added one. `refreshChrome` rebuilds title, star and empty state together. The star fills when the bookmark lands (`Search/AGENTS.md`), and the screen redraws on `VibeFavoritesDidChangeNotification`. The empty state's Open brings the Files tab forward through `openFilesHandler`, which the shell sets, so this screen knows nothing about tabs.

## Building and verifying

The `vibe-debug` skill's "iOS: the simulator loop" section covers launch, feeding audio, screenshots and logs. `RootViewController+Debug` adopts the channel's protocol and composes `PlaybackController+Debug` and `PlayerViewController+Debug`. All three live in `Vibe/Debug/iOS/Seams/`. `expand_player`, `minimize_player` and `select_tab` exist because the channel cannot synthesize a touch; gestures go through `drive-ios.sh`. **Interruptions, route changes, background audio past lock and the lock-screen card need a real device.**
