# iOS app shell (VibeiOS target)

A single-folder player: **the current directory is the playlist.** The user picks a folder or file in the app's own browser, the Files tab. Its sources are Dropbox (`Dropbox/AGENTS.md`), the app's Documents, and each location granted once through the system folder picker (iCloud Drive, a drive, any other Files provider). There are three `UITab`s, Playlist, Favorites and Files, with `UISearchTab`'s circle beside the capsule. A mini player strip sits in the tab bar's `bottomAccessory`, and the now-playing card presents up from it. Opening anything replaces the playlist, starts playing, selects the Playlist tab and presents the card. The exception is a single file played alone: its tab stays where it was picked. **Add to Playlist** appends tracks without touching playback, the tab or the card. An Add onto nothing is an Open.

This directory is the shell only. The iOS halves of shared subsystems are documented beside them: `Audio/iOS/`, `WaveformUI/iOS/`, `Util/iOS/`. Here, `Player/` (the card), `Search/` (Favorites, Search and the folder stores), `Settings/`, `Dropbox/` and `Widget/` (the app side of the Home Screen widget) each have their own `AGENTS.md`.

**Layout keys off view aspect, not device orientation.** On iPad it keys off height too: a short window takes the card's compact layouts (`Player/AGENTS.md`). iPad is a resizable window in all orientations, with a 320×200 minimum through `sizeRestrictions` in `VibeiOSSceneDelegate`. iPadOS 26 keeps a window at least about 486pt tall, so the system floor is the one that binds.

**Multi-scene is off.** There is one `AudioPlayer` per `PlaybackController` and one `PlaybackController` per scene, so a second scene would be a second engine. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage`. A mid-resize offset rounds to a neighbor page and would switch tracks.

## PlaybackController — the model

It owns everything the app plays and nothing that draws it: the engine, `Playlist`, the metadata cache, the audio session, `FolderSession`, Now Playing, the 3 Hz `UIUpdateTimer` and the display state. The scene delegate owns the one instance, and every screen borrows it.

**It broadcasts** through `PlaybackObserver`: synchronous on main, in registration order, held in a weak `NSPointerArray`. Three views describe one playback, and `Playlist` has one observer slot. **Weak is load-bearing**, since every observer is a view or view controller.

**iOS has exactly one removal: `clearPlaylist`, the whole playlist.** The bar's menu offers it as Clear Playlist. It is the twin of the mac's `closeFile:`. Unloading everything leaves no cursor to strand and no row for the player to be sounding. It stops the player, drops the parked successor and ends the loading open's progress. It then clears the session (scopes, base, additions and the persisted bookmarks and remembered track) **before** the model, whose replace event rebuilds the chrome (the `TRAP:` in `clearPlaylist`). Then it cancels the deferred sweep and the scan. **It settles the launch waiters last of all.** A clear during a launch restore supersedes the restore, so nothing else would settle them. `_launchOpenSettled` is a latch: missed once, every later `performWhenLaunchOpenSettled:` waiter parks, and a widget transport intent then skips a track at some later open. A waiter runs arbitrary work, so it must not see a half-reset controller.

**There are no partial edits.** The remove, insert and move observer methods are no-ops, because there is no row-level edit UI. Removing the current row is a transport operation. A row-level edit UI must add its own funnel on the model of `MainPlayerController.removePlaylistTracks:`. Calling `Playlist.removeTracksAtIndexes:` directly leaves the player sounding a departed object.

`+ReplacePrompt` holds the question every screen asks before its tap replaces the playlist, and Open URL's road into it. `+PlayerEvents` holds every `AudioPlayerDelegate` callback. Every callback can be stale, and `stop` fires none. `+NowPlaying` holds `publishNowPlaying`, which `notifyDidTick` calls before it ticks the screens, so the lock screen never lags them.

**On track end follows the root guarantee.** Every `prefetchTrack:` site parks the playlist's `trackEndSuccessor`, which is nil under Pause. `didFinishPlaying:` calls `advanceAtTrackEnd`, which moves nothing under Pause. It then parks on the finished track, as the end of the playlist does. **A refused splice parks too, and must silence what the player started.** When `advanceFromTrack:toTrack:` no longer accepts the spliced successor (a mode or Pause switched mid-boundary), `didAutoAdvanceFromTrack:toTrack:` runs the track end. If that parks, it reloads the finished track paused over the sounding successor, as the mac does. Every write to a transition setting ends on `applyTrackTransitionSettings`: Pause, the crossfade, and the card's `toggleShuffle` and `cycleRepeatMode`. It pushes the crossfade and both modes, re-parks or drops the successor, publishes the modes to Now Playing and sends `playbackDidChangePlayOrder:`. It is the iOS form of the mac's `EndOfTrack` and `Crossfade` live effects. An open hands its start row to `replaceAllWithTracks:startingAtIndex:` (`Playlist/AGENTS.md`).

**TRAP: `prefetchSuccessor` does nothing while the player is stopped.** A parked track holds no file. Prefetching over a list edit would open one, which on a cloud folder is an unasked download.

**A scrub on a parked track seeks; it does not play.** Parked, the player holds no file, so `seekToProgress:` opens the file at the scrubbed position, paused, with the duration from metadata. The seek target outranks Loading in the card's progress paths, or the waveform would snap to zero during that open. `didStartPlaying:` clears the in-flight flag, since this seek has no `didFinishSeeking:`.

**The metadata sweep waits for the picked track to settle.** `folderSession:didOpenTracks:` schedules it, `didStartPlaying:` and the error path start it, and a two-second fallback covers an open that never lands. **A launch restore starts it at once.** The park opens nothing, so no `didStartPlaying:` is coming. The rule underneath is `AudioFileMaterializationCoordinator`'s (root `AGENTS.md`).

**Display state is resolved once, in `PlayerScreenRules.h`** (header-only, tested from the macOS suite). `screenState` gathers the inputs. The card, the mini strip, Now Playing and the debug dump read the result. It is separate from the mac's `TrackDisplayRules.h`: it has no launch grace, and it has parked tracks. **The slow-open state is separate from it.** `currentOpenSlow` is set before `playbackDidBeginLoading:` is sent. It stays YES until the open settles or fails, and every cursor change, replacement and play clears it. The card's loading shimmer reads it, because `screenState`'s Loading starts at submission and would flash on every fast Next.

**Two mac features are off, each at one switch.** Folder art is off: `AudioTrackArtwork`'s `folderArt` is nil. Key analysis is off: the card's waveform analysis provider never sets `key`. **The DJ FX and BPM detection are on.** The player is created with `enableFX:` from the shared setting, and `applyFXSetting` is the setting's live effect. `setFXPadPosition:engaged:` is the one funnel for the card's pad and the debug channel, mapped by `AudioFXMath.h`. The delay taps follow `refreshTempoFeed`: `AudioTrack.bpm` for the current track. It is re-read on every render funnel, on a metadata delivery and on `noteDetectedBPM:forTrack:`. The card forwards that from the waveform decode pass, and it stamps every row sounding that track's window (`Playlist.stampTracksSounding:usingBlock:`).

**The 128px thumbnail is on.** Rows archive compact bytes. Decoded pixels live in `EmbeddedThumbnailCache`, the bounded LRU every `AudioTrackArtwork` shares (`kEmbeddedThumbnailCacheCount`). An eviction returns the placeholder, decodes once off main, and refreshes only the visible Library, Search and mini-player surfaces.

## FolderSession

It owns the picked locations of the current playlist: a **base** folder or file plus any additions. It holds their security scopes, their restore bookmarks (plain `bookmarkData`, since iOS has no `WithSecurityScope` option) and their listing through `NSURLUtil rowsInDirectory:sortedBy:`. A CUE sheet stands in for its files there, as in a mac folder walk. Dedupe, within one delivery and across an Add, is by standardized path plus a cue row's window. Persistence is its own `NSUserDefaults` keys, not `AppSettings`.

**A sheet's grant reaches the sheet alone, never the audio beside it.** A `.cue` picked in Choose File… or sent with "Open in Vibe" finds nothing unless a root covers its folder. That open settles empty, then names the sheet through `needsFolderOfSheetAtURL:` (only for a denied folder, never a missing one). `RootViewController` asks with the mac's grant wording and presents a folder picker. The sheet then reopens with the picked folder held like a starred folder's root (`FolderSession.h` has the contract). A sheet opened alone where a root covers its folder is its own rows (`rowsForFile:`), resolved against the folder's listing so placeholders count.

- **Scopes are held as a set** (the base open's and each addition's) for the whole session. The player, TagLib and the waveform loader read under them at arbitrary times. A set is released only after a successor set is in hand, and an append extends it. Each start is balanced by its own stop.
- **TRAP: acquire before release.** A replace landing installs the successor scope set first and only then stops the previous one. A failed or superseded pick therefore never strands the current playlist unreadable. The `TRAP:` in `finishOpenIntent:` is the authority.
- **"What may be listed" and "what may be held" are two questions over two lists**, both asked through `rootCoveringPath:in:`. The logical roots (`searchRoots`: the base plus the additions) decide listing and the search-root dedupe. A container folder is never security-scoped, yet a file picked in it must still expand to it. `_scopedURLs` decides what a request takes a hold on. **TRAP: a security scope is started through the URL the system granted, never through a path-equivalent one the app derived.** A search hit leaves the base pointing at a derived parent. Asked for a hold, that URL refuses the start, and nothing is collected. The landing then stops the real grant with no successor, and the playlist goes unreadable mid-play. Minting a bookmark for the star takes its hold from the scoped list for the same reason.
- **Adoption runs off main**, since bookmark resolution and listing are provider IPC that can take seconds. Replaces run on a concurrent queue, so a new intent never waits behind an older provider call. Appends run on a serial lane that targets it, so two Adds with their URLs in hand land in tap order, and a replace overtakes them. Every request carries `openIntentGeneration`. A replace bumps it, an append captures it, and only a result that matches the live one delivers or persists.
- **An append captures the generation when the user asks, not when the caller has a URL.** A caller with asynchronous work first (Favorites, a bookmark to resolve) takes an `addRequestToken` on main and hands it to `addURLs:token:`. An Add judged only on arrival would append to whatever playlist was opened meanwhile. **A replace behind asynchronous work carries its own token**, `PlaybackController.replaceRequestTokenOpening:`, to the `confirmReplacing…` funnel in `PlaybackController+ReplacePrompt`. The funnel drops it when a newer replace, open or clear was asked for meanwhile, so an older tap landing late never replaces the open the user made last. The token is staleness only and reserves no place in the lane. Two Adds therefore land in provider order, not tap order, when a slow resolve is in the way.
- **An Add onto a session that has never landed anything is promoted to an Open**, including after a failed launch restore. An append also checks the last settled replace, so an Add requested during an open that never landed is dropped. **TRAP: only the first such Add promotes.** Each promotion bumps the generation, so two promoted Adds would cancel each other and a selection would vanish. The rest park as waiters. They are replayed through the prologue when the promoted open settles, whichever way it settles: they append if it landed, the first of them promotes if it found nothing, and a user's replace releases them onto its own playlist. **TRAP: a promotion is not a supersession.** The token check in `addURLs:token:` runs before the parking. A token one below the generation a promotion created is still the user's while that promotion is live. A real replace or a clear bumps past it and drops it.
- **An empty open settles too. TRAP:** an open that found no audio leaves the previous playlist standing, so `_landedOpenIntentGeneration` carries forward to the new generation. Without the carry, every later Add is captured at a generation nothing landed, and Add is dead for the session. Zero never carries, so an Add is still promoted. An append that found nothing carries nothing. Every request ends in `finishOpenIntent:`, the only place the main-confined state moves. The promotion's token check and this carry are functions in `Search/FileSearchRules.h`, tested in `FileSearchRulesTests`.
- **An append that finds nothing leaves the playlist alone**, with no empty-folder event. `folderSession:didAppendTracks:` is still delivered, empty. `PlaybackController` ends every Add with `playback:didSettleAddLanding:` after the append's own events, so whoever asked hears how it landed.
- **One prologue, `beginOpenURLs:appending:expandsFile:grantedFolder:`, serves every entry point**: picker, browser, favorite, search hit and Add. It runs on main and does no I/O. It snapshots `AppSettings.folderOpenSort` for the worker, so the walk reads no setting (`Util/AGENTS.md`). It asks the main-only stores, in order: `SearchFolderStore.grantCoveringURL:`, then a retained grant, then `FavoritesStore.resolvedRootCoveringURL:`. It takes a hold on each covering scope so an older worker can finish safely. The launch restore reads the sort itself and enters the work queue directly. An inbox copy skips the worker's expansion, since Documents/Inbox under an open Documents base would expand to the whole Inbox.
- **The base is the first contributor, whatever it is**, and it is the playlist's identity. The Playlist tab's title, the star and the base bookmark all name it, and an Add never moves it. A file base has `folderURL` nil, so the title stays "Playlist" and there is no star. **TRAP: a folder may not claim the base because the contributor ahead of it was a file.** A restore delivers base-then-additions, so a folder behind a file base would rewrite the base bookmark and reorder the union at the next relaunch. A multi-select replace of a file and a folder keeps the file as the base, and it persists.
- **A file grant reaches nothing but the file**, so a single-file pick is a one-track playlist. A folder grant covers the subtree. **Only a replace of exactly one picked file expands** to its directory, under any covering root in hand. An added file is one track, never its directory. **An M3U never expands**: it is its own readable entries (`rowsForFile:`). **The prologue alone decides whether an open becomes the session bookmark.** An open strictly inside a grant only the session holds (a one-off pick) leaves the bookmark alone, since re-pointing it would shrink next launch's reach. Under a Location, a favorite, Documents or the mirror, the open is remembered like any other.
- **The app's own trees are roots every open covers.** Documents and the Dropbox mirror need no grant, so `beginOpenURLs:` adds both to the covering roots. A file opened alone in either expands to its folder with it selected, which is what Play in Folder relies on. This holds at every entry point, so an "Open in Vibe" of a song in Documents opens its folder. Only an inbox copy stays one track.
- **A Dropbox folder nothing has listed yet is listed from Dropbox before an open reads it** (`listFromDropboxIfMirrored:`, on the work queue, bounded so an offline open reads the disk). The mirror holds only what something has listed. A folder already listed is read as it is, so a restore never waits on the network.
- **One delivery names each file once, and a URL that contributed no track is not persisted.** A restore's list can overlap, and the union is delivered as a replace, which does not dedupe. Without this the playlist grew a copy of every re-added folder at each relaunch.
- **Persistence is a base bookmark plus an ordered addition list.** Both are rewritten on every landing from what actually contributed, so a dead or emptied addition prunes itself at the next launch. A search-hit open, an inbox copy and a one-file open over a folder bookmark touch neither key. Additions made after one of those are session-only.
- **A link opened alone is persisted all the same** (`VibeFolderSessionPersistsBase`, `FileSearchRules.h`). Its file sits under the Links root (`LinkStore`'s `containsURL:`), an app-container directory with no security scope. It opens as a single-file base, never as its directory, which is named by a hash. A relaunch resolves the bookmark and parks on the placeholder, offline too. A mirror file opened alone is not a link and keeps a folder bookmark.
- **A launch restore resolves its bookmarks a bounded few at a time** and merges them in persisted order (the bound is `SearchFolderStore`'s, `Search/AGENTS.md`). Delivery still waits for the slowest bookmark, since the walk needs the whole union. The listing and the bookmark minting after it stay serial: the dedupe, the contributor list and the base rule are order-dependent, and the same loop pairs each scope start with its stop.
- **A restore keeps whatever still resolves.** Only a restore where nothing resolves fails, and only that clears the two keys. If the base is gone, the first surviving addition becomes the base by the first-contributor rule, and the landing rewrites both keys.
- **Relaunch parks the remembered track**: header, waveform and metadata loaded, nothing playing, card minimized. The remembered track is looked up over the whole union. **What is remembered is the standardized path**, plus a cue row's window (`persistedTrackKey`), since two albums can both hold `01.wav`. **The match has two tiers: exact path, then filename.** A provider can hand a file back under a different path, and the simulator's container UUID rotates on reinstall. An exact hit anywhere outranks a filename hit. The defaults key keeps its shipped `VibeiOSLastTrackFileName` spelling. The scene delegate runs exactly one of restore or adopt at launch, so "Open in Vibe" never pays for a restore it replaces.
- **The first launch copies the bundled `vibe-theme.mp3` into Documents** (`VibeiOSAppDelegate`, gated on `AppSettings.welcomeTrackLoaded`). It is the user's file from then on, and deleting it sticks.
- **A launch prunes links once its open settles** (`VibeiOSSceneDelegate`, `performWhenLaunchOpenSettled:`). It keeps every link the playlist's rows or the recents name (`pruneKeepingTracks:recentURLs:`, `VibeRecentItemURLs`). **TRAP: a recent's URL is built from its recorded folder flag, never by `fileURLWithPath:` alone** (`FileSearchRules.h`). That call stats the path on main, and a recent on an unreachable SMB share froze the launch for 30 s.

## RootViewController

The scene's root: a `UITabBarController` child, the mini player in its `bottomAccessory`, and the card above both. It alone knows whether the card is up, and it owns expand and minimize. Settings rides the Playlist tab's stack. Leaving that tab pops it (`tabBarController:didSelectTab:previousTab:`).

**The tabs are `UITab`s, not view controllers.** `UISearchTab` draws the circle outside the capsule, and `automaticallyActivatesSearch` collapses the bar behind a field and restores the previous tab on cancel. Each tab's view controller comes from a lazy provider. Ask `_filesController`, never `UITab.viewController`, whether Files exists, since the getter resolves the provider. The search tab's identifier is UIKit's, so `selectedTabIdentifier` matches it by kind.

**It is a container, not a `UITabBarController` subclass**, so it can put the card and the backdrop snapshot above the tab bar controller's whole view. A card at rest hides the tabs, or the glass tab bar would keep sampling for nothing.

**The card is built once and never torn down.** Minimize translates it off the bottom. Its pager, art window and waveform snapshots survive, so an expand re-reads and re-decodes nothing. Art is not pruned on minimize either: the byte budget bounds it.

**TRAP: what scales under a moving card is a snapshot of the tabs, never the tabs view.** Scaling the view moves its edges off the screen's, and UIKit removes the safe-area insets and edge margins. The bars and rows then re-lay out, and the screen jumps under the card. A snapshot has no layout to lose (`beginBackdropSnapshot`, taken as the card starts moving and dropped once it rests). **The mini player strip stays installed under the card** (`refreshMiniPlayer`). Removing the accessory shrinks every tab's bottom inset, and a list scrolled to its end is clamped up under the snapshot. `check-layout-stability.sh` on a playlist scrolled to its end is the oracle for both.

**TRAP: the card moves by transform, never by frame.** Its pages carry `WaveformScrubberView`s, which re-bake on any bounds change.

**TRAP: `shouldAutomaticallyForwardAppearanceMethods` is per-parent.** Turning it off for the card turns it off for the tabs, so both are forwarded by hand. Each begin snapshots its exact children and the end consumes that snapshot, because `_expanded` can change between them.

Foreground-inactive counts as off: the scene delegate's foreground-active bit drives the Library surface and the card's display link. The custom card transition supplies what a presentation would. Reduce Motion settles at once, the card is the modal accessibility surface while up, and completion moves VoiceOver focus.

## MiniPlayerView

The accessory's content: the 128px thumbnail, title over artist, play/pause and next (`forward.end.fill`, the mac's glyph). Targets are large and glyphs small (`kGlyphPointSize`). When `traitCollection.tabAccessoryEnvironment` says the bar collapsed it inline, the artist line is dropped. There is no playhead bar, which fits 48pt only by crowding the art and labels.

**TRAP: the strip is 48pt, not negotiable.** `UITabAccessory` frames its content at a fixed height and ignores `intrinsicContentSize` and height constraints, with no logged conflict. A taller strip means giving up the accessory, and with it Liquid Glass, inline collapse and the automatic safe-area inset.

**TRAP: the row needs a designated give, and the simulator never shows it.** On device the accessory reports width zero on at least one pass. The row's required content needs 162pt, so UIKit breaks a constraint and logs it. The art's leading inset is `UILayoutPriorityRequired - 1`. Any new required constraint across the row reopens this.

## BrowserViewController

The Files tab. It is also the Playlist tab's add sheet (`appending:YES`), where every action appends and closes the sheet; it is titled Add to Playlist at its root. One `UITableViewController` per level sits in a navigation controller. It is not a `UIDocumentBrowserViewController`, whose Open button spins forever under multi-select and whose floating bar collides with the tab bar.

**The root's groups** are Locations (On My iPhone, then Dropbox once linked, then `SearchFolderStore`'s folders), then Recents, then Choose File… and Open URL…, then the paste row while the clipboard holds a link. `VibeBrowserRootRows` (`Search/FileSearchRules.h`, tested from the macOS suite) is the one answer to what a root row is. `VibeBrowserRootLocationIndex` beside it maps a Locations row to its folder in the store. Both read whether Dropbox was linked at the root's last reload, never the live account. The account flips off main before its change is posted. A live read in that gap would open or delete the folder beside the one shown. The root's plus menu holds Add Folder… and, until an account is linked, Connect to Dropbox…. It is built each time it opens. It then follows the account. **A directory lists its folders, then its M3U playlists, then its playable files and CUE sheets**, each in `AppSettings.folderOpenSort`'s order through `NSURLUtil listDirectory:sortedBy:folders:playlists:audio:`. That is the open's own filter and sort, so a song row shown is a row that plays, in the order shown. A playlist is not part of its folder's play: a tap plays it, and its long press has no Play in Folder.

- **A file tap plays that file alone, where it was tapped. A folder tap opens it.** The browser, Search and Recents share this rule. A one-track open presents the card but keeps the tab (`playbackDidOpenNewFolder:`). A folder, a file in its folder, or several picks bring the Playlist tab forward first. The long press has Play in Folder on a file and Play on a folder. Every open is a `PlaybackController` road: `openFileURL:inFolder:` for a tap, `addURLs:` for an Add, and `bookmarkFolderURL:` then `FavoritesStore` for a folder's star.
- **A replace asks first when the playlist was built by hand.** Every replacing tap (the browser's, Recents', Search's and Favorites') goes through `PlaybackController`'s `confirmReplacingPlaylistFrom:openingURLs:inFolder:token:`. `PlaybackController.playlistHasAdditions` is `FolderSession.hasAdditions`, YES once an Add has landed or for a playlist restored with additions. The alert offers Replace, Add Instead and Cancel. Any other playlist is replaced at once.
- **A row says what a tap costs**: the file's size from the listing's stat (a placeholder carries the remote size), `VibeNotDownloadedMark` on a file not downloaded, and the Playlist tab's equalizer on the file now playing (`playbackDidMoveToCurrentTrack:`). That equalizer is held to the root guarantee as the Library's is. The root sets the Files stack's exposure on its bottom browser (`equalizerSurfaceVisible`), each screen adds its own appearance, and the row must be in the viewport (`vibeIsInViewportOfTableView:`). **TRAP: nothing in a screen's initializer may touch the disk.** A screen is made on main as a folder opens, and for a provider's folder a stat or name lookup is IPC that can block.
- **A file's icon is its album art when the metadata cache holds it or its bytes are on the device, else a tile** (`VibeFileTileImage`). Every list row's icon slot (here, Recents, Search and Favorites) is set by `vibeApplyFileIconForName:folder:art:`. Names take two lines and truncate in the middle (`vibeApplyFileNameStyle`). These row pieces live in `FileRow`, not the browser, because every list screen shares them. The art comes from one `AudioTrackMetadataCache` per stack of folders (`stackArtCache`), asked for the rows on screen and a margin when a listing lands and when a scroll settles. **TRAP: a placeholder and a provider's dataless file are never parsed** (`loadArtForVisibleRows`). A parse's cache miss reads the tags from the file: ranged requests or a download for every row. They go to `loadCachedMetadata:`, which reads nothing on a miss. One cache serves the screen on top, and a screen that goes cancels its own scan, never its successor's. A mirrored folder on screen relists on `VibeDropboxDownloadsDidChangeNotification`, so a finished download drops its mark and gains its art.
- **A row being opened spins in its icon slot**, here and in Recents, Search and Favorites (`vibeApplyRowContent:opening:`). `PlaybackController.openingPath` names it from the tap (`replaceRequestTokenOpening:`, before any resolve) until the open lands, finds nothing, is superseded or is given up. `playbackDidChangeOpening:` redraws. A second tap gives it up (`cancelOpening`). A resolve still running is then dropped by the replace funnel, and an open the session holds is cancelled by `FolderSession.cancelOpen`, which settles like an empty open. `kOpeningTimeout` gives up too, with an alert from the root. A caller whose own work ends before the open (a failed resolve, Cancel or Add Instead, a favorite shown in Files) ends it with `endOpeningForReplaceRequest:`.
- **The filter field narrows a listing by name** (`applyFilter`), installed once a listing has a dozen rows. **TRAP: it is always shown, never hidden on scroll.** A collapsing search bar re-lays the bar out on the appearance callbacks the card forwards by hand, and the folder jumped under the card. It is `Stacked`, since iOS 26's integrated placement would put it in the bottom toolbar.
- **Select is multi-select Add.** It is a glyph, and named Select rather than Edit, since nothing is edited. While selecting, the title is the count, Select All takes the back button's place, and a listing or filter change is held. **TRAP: a row swipe sets `isEditing` too.** `isSelecting` excludes it through `_swipingRow`, or the bar flips into multi-select under the swipe.
- **The sort menu is titled "Sort folders by"**, the Settings row's own string, because it writes the one folder-open setting, not this folder's view. The add sheet has no sort menu; its bar carries Close at every level. The bar's items are absent, not disabled, in an empty folder.
- **A Dropbox directory draws from disk at once, then relists** (`DropboxMirror refreshDropboxFolder:`) when it appears, unless this screen listed it within `kRelistInterval`. Pull to refresh relists any directory. A relist that fails says so in a footer over rows already drawn, or in the empty state over none. An unlinked account pops the stack to the root. A sign-in started from the plus menu pushes the account's root when it lands.
- **Open URL… plays a web address** (`presentLinkSheet`, modeled on the mac's window). The sheet has a wrapping field with the URL keyboard, the system's Paste control, a spinner, and Cancel and Open. Open is disabled while the field is blank (`VibeLinkTextIsBlank`), and Return is Open. Open calls `openLinkText:`, which takes a replace token through `PlaybackController`'s `openLinkString:replacingPlaylistFrom:completion:`. `LinkStore` resolves the link off main, and its file opens alone through `confirmReplacing…`. While it resolves, the field and Open are disabled. Cancel or a swipe down cancels the resolve. A failure closes the sheet and shows `link.error.title` with `+[LinkStore messageForError:brief:]`. The completion runs before the replace question, so the sheet closes first and the question goes over `vibeTopmostPresenter`. The browser holds the resolve's cancel block, not `openingPath`, since a link names no file until it resolves. In the add sheet the add token is taken before the resolve and the file goes to `addURLs:token:`. A link never takes the inbox road, which does not persist. `open_url` drives the same method (`Loading/Net/AGENTS.md` has the store).

  **TRAP: the sheet is dismissed by its presenter** (`closeLinkSheetThen:`). Asked of the sheet itself, a dismiss closes only an alert it presents. **TRAP: the system draws its Paste control out of process, blank and ignoring taps, when its content does not fit.** Its height scales with the text size, and it spans the field.
- **The paste row opens a copied link.** It shows only while the clipboard probably holds a web link: `UIPasteboard`'s `detectPatternsForPatterns:` for `ProbableWebURL`, or `hasURLs`. Neither reads the clipboard, so neither raises the paste prompt. The check runs when the root appears, when a scene activates and on `UIPasteboardChangedNotification`, and skips a `changeCount` already checked. A tap hands the clipboard's item providers to `pasteItemProviders:` (`pasteClipboardLink`). Loading one shows iOS's Allow Paste prompt unless the user allowed pasting in the Settings app (`Settings/AGENTS.md`). It opens the first web link (`VibePasteLinkOfItems`) through `openLinkText:`, and text that is no link shows the invalid-link alert. **TRAP: a denied paste still lists its items, with their types.** Only the loads fail (`PBErrorDomain` 13). A paste whose items yielded nothing therefore says nothing. A second tap while it resolves cancels it. **TRAP: the action rows take the dynamic `UIColor.tintColor`**, never `self.view.tintColor`'s value, which is gray while a sheet dims the tint.
- **The system pickers remain for two jobs only.** Add Folder… grants a location (`SearchFolderStore addFolderURL:`, which refuses a covered one with a message), and Choose File… is a one-off multi-select pick. iCloud Drive has no item of its own, because public API cannot point the picker at it. A granted location opens in the browser, and nothing plays. A location is forgotten by the swipe Delete or the long press's Remove Location.
- **The play button plays this folder alone. Its long press plays it with its subfolders** (`openDirectoryWithSubfolders`; Add with Subfolders in the sheet). The walk goes depth first in the listing's order, asks Dropbox for each mirror folder first, and stops at `kMaximumSubfolderTracks` songs or `kMaximumSubfolders` folders and says so. The folders with songs open as one multi-URL open: the first is the base and the rest are additions. In a folder with no song directly inside, the button is its menu alone.
- **Recents is `FolderSession`'s list**: every file and folder opened or added, newest first, at most `kMaximumRecentItems`. **An open that brought more than five things is one entry, the folder they share**, or Play with Subfolders would replace the whole list in one tap. Each entry is recorded where the open lands, with the bookmark the open minted and its folder's display name. A restore records nothing, and Clear Playlist keeps them. The name is recorded, not derived, since the path can outlive the app container it names. `RecentsViewController` lists them. A file plays alone, a folder opens in the browser, and the long press adds Play, Play in Folder, Add to Playlist and Open Folder. **A link (`LinkStore`'s `containsURL:`) has neither folder action**, since its folder is the Links store's, named by a hash. Its second line is the link's host (`LinkStore hostOfLinkFileURL:`, recorded when the open lands). The bar's Clear opens a one-item destructive menu. It is absent while the list is empty, and in the add sheet.
- **An Add's rows fly into the Playlist tab** (`addedRowsHandler`, set by the shell on the root browser). The rows asked for are snapshotted and handed over before the request. `RootViewController` lifts them and flies them to the Playlist tab's item on `playback:didAppendTracksAtIndexes:`. It sets them back down when the settle says nothing landed, or when a superseding open lands empty or is cancelled (`playbackDidCancelOpening:`). There is no timer: every Add ends in `playback:didSettleAddLanding:`, and `check_consistency` reports rows never settled (`liftedRowTimes`). The flight is a UIKit keyframe animation, not a `CAAnimation`, because an iPhone caps an app's own Core Animation at 60 Hz without an Info.plist opt-out. `UITab` has no view, so the target is found by the label the bar draws.
- **Open Folder** (Search and Recents) is `showDirectory:highlighting:` on the root browser. The stack becomes one screen per folder from the covering source, built before the tab switches, and the file it came from is scrolled to and selected for a moment. A folder no persistent root covers (a one-off pick, from Recents) is listed under a scope the bottom screen holds for its lifetime (`_holdsScope`). An open made inside it takes the session's own hold from the recent's bookmark, so the playlist outlives the screen.

## LibraryViewController

The Playlist tab: number (the shared `EqualizerIndicatorView` on the playing row), artwork, title over artist, duration. Each row is a `LibraryTrackCell`. **Selecting a row plays it and stays here.** Expanding the card is the strip's job. A track change scrolls the list to the playing row, or leaves that for when it shows. **Under shuffle the list holds still**, since following a jumping play order would lose the user's place on every track. Number and duration take the artist line's text style, so they scale together under Dynamic Type. The folder name goes on `navigationItem.title`, not `self.title`, which is also the tab's title.

**TRAP: UIKit displays a prepared cell without re-running `cellForRowAtIndexPath:`.** A thumbnail or metadata delivery in that window repaints nothing, so the Library re-renders each cell in `willDisplayCell:`. **TRAP: rendering in place does not re-measure an automatic-dimension row**, so a row whose height moved takes an empty `performBatchUpdates:`.

**Equalizer activity is actual output plus material visibility**, this doc's half of the root guarantee. Output is `PlaybackController.audioOutputActive`: true through an outgoing fade, false for a Loading request. Visibility is this controller's presentation, `willDisplayCell:`/`didEndDisplayingCell:` state, `RootViewController`'s tab and card exposure, and the scene's foreground-active bit. The card exposure is explicit, because the card moves by transform over children that stay "appeared". Only then does the playing row start its poller and declare one `equalizerLevelsWanted:` consumer. The gate is counted, not boolean, because cell reuse can briefly hold two consumers. A hidden track change keeps one pending scroll index and lands there without animation on the next reveal. `dump_equalizer` is the runtime proof: `renderer.displayTicks` is bounded at 30/s while active and flat once inactive.

**The gutter has three states in precedence: loading, playing, number** (`resolveGutter`). Loading is `CloudTransferRegistry`'s `isTransferringURL:`: a provider's, the mirror's or a link's transfer really running, the playing row's included until its download ends. Loading outranks playing because there is no output audio yet. `syncEqualizerActivityForCell:` folds `!loading` into both activity facts, so a loading row holds no poller. A registry change re-syncs `visibleCells` in place, never a reload.

**The gear opens a menu**: Settings, then Clear Playlist alone in a destructive inline group. There is no confirmation, because nothing leaves the disk and reopening rebuilds the playlist. Its accessibility label names the menu, since the button does two things.

**The bar carries the gear, and the star when a folder is open.** The plus that presents the add sheet sits on the leading side, since three trailing items crowd the large title. Star and plus are absent, not disabled: the star for a single-file or empty playlist, the plus for an empty one, whose empty state already offers Open. Title and star name `FolderSession`'s base folder, never an added one. `refreshChrome` rebuilds title, star and empty state together. The star fills when the bookmark lands (`Search/AGENTS.md`), and the screen redraws on `VibeFavoritesDidChangeNotification`. The empty state's Open brings the Files tab forward through `openFilesHandler`, which the shell sets, so this screen knows nothing about tabs.
