# iOS app shell (VibeiOS target)

A single-folder player: **the current directory is the playlist.** The user picks a folder or file in the app's own browser (the Files tab): Dropbox through its HTTP API and a local mirror (`Dropbox/AGENTS.md`), the app's Documents, and each location granted once through the system folder picker — iCloud Drive, a drive, any other Files provider. Three `UITab`s — Playlist, Favorites, Files — with `UISearchTab`'s circle beside the capsule, a mini player strip in the tab bar's `bottomAccessory`, and the now-playing card presenting up from the strip. Opening anything replaces the playlist, starts playing, selects the Playlist tab and presents the card, so minimizing lands on what was just opened. **Add to Playlist** appends a Files-tab item's or a favorite's tracks without touching playback, the tab or the card; an Add onto nothing is an Open.

This directory is the shell only. The iOS halves of shared subsystems are documented beside them: `Audio/iOS/`, `WaveformUI/iOS/`, `Util/iOS/`. Within this directory, `Player/` (the card: pager, page cell, route control, waveform coordinator), `Search/` (Favorites, Search and the folder stores), `Settings/` and `Dropbox/` (the account and its mirror) each carry their own `AGENTS.md`.

A new file in a shared directory joins this target automatically and must be AppKit-free or `TARGET_OS_OSX`-guarded (root `AGENTS.md`); CI's iOS builds catch a leak.

**Layout keys off view aspect, not device orientation** — and on iPad off height too: a short window takes the card's compact layouts (`Player/AGENTS.md`). iPad is a resizable window, all orientations, minimum 320×200 via `sizeRestrictions` in `VibeiOSSceneDelegate` (the card's strip layout's floor); iPadOS 26 itself keeps a window at least about 486pt tall, so the system floor is the one that binds.

**Multi-scene is off.** One `AudioPlayer` per `PlaybackController`, one `PlaybackController` per scene; a second scene would be a second engine. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage`: a mid-resize offset rounds to a neighbor page and would switch tracks.

## PlaybackController — the model

Everything the app plays and nothing that draws it: engine, `Playlist`, metadata cache, audio session, `FolderSession`, Now Playing, the 3 Hz `UIUpdateTimer`, and the display state. The scene delegate owns the one instance; every screen borrows it.

**It broadcasts** (`PlaybackObserver`: synchronous on main, registration order, weak `NSPointerArray`) because three views describe one playback and `Playlist` has one observer slot. **Weak is load-bearing**: an observer is a view or view controller.

**iOS has exactly one playlist mutation, and it is the whole playlist: `clearPlaylist`.** The bar's menu offers it as Clear Playlist. It is the twin of the mac's `closeFile:` and safe for the reason that one is: **unloading everything leaves no surviving cursor to strand and no row for the player to be sounding.** It stops the player (which fires no transport or track-end callback, so nothing auto-advances and the method owns the reset), drops the parked successor, cancels the download monitor, clears the session — scopes, base, additions and the persisted bookmarks with them — **before** the model, whose replace event is what rebuilds the chrome (the `TRAP:` in `clearPlaylist`), then cancels the deferred sweep and the scan.

**There are no partial edits.** The remove, insert and move observer methods are no-ops: there is no row-level edit UI, and forwarding a model-only edit would not make one safe, because removing the *current* row is a transport operation. A row-level edit UI must add its own coordinator on the model of `MainPlayerController.removePlaylistTracks:`; calling `Playlist.removeTracksAtIndexes:` directly leaves the player sounding a departed object. `clearPlaylist` sidesteps that problem by being the whole playlist; it does not solve it.

`+PlayerEvents`: every `AudioPlayerDelegate` callback, under the root doc's two rules (every callback can be stale; `stop` fires no callback). `+NowPlaying`: `publishNowPlaying`, which `notifyDidTick` **calls before it ticks the screens**, so the lock screen never lags them.

**On track end is the root guarantee's, enforced at both of its places here**: `successorPrefetchTrack` (the playlist's `trackEndSuccessor`, nil under Pause, so no successor is queued) feeds every `prefetchTrack:` site (the transition settings, `prefetchSuccessor` and the player-events category), and `didFinishPlaying:` re-reads the setting before `advanceAtTrackEnd`, parking on the finished track exactly as the end of the playlist does. **A refused splice parks too, and must silence what the player started**: when `advanceFromTrack:toTrack:` no longer accepts the successor the player spliced into (a mode or Pause switched mid-boundary), `didAutoAdvanceFromTrack:toTrack:` runs the track end, and if that parks it reloads the finished track paused over the sounding successor, as the mac does — otherwise the card parks on the finished track while the successor plays on. A write to any transition setting — Pause, the crossfade, and the card's shuffle and repeat buttons (`toggleShuffle`, `cycleRepeatMode`) — ends on `applyTrackTransitionSettings`, which pushes the crossfade and both modes, re-parks or drops the successor, publishes the modes to Now Playing and tells observers through `playbackDidChangePlayOrder:` — the iOS spelling of the mac's `EndOfTrack` and `Crossfade` live effects, and what the Settings screens are handed the model for. An open hands its start row to `replaceAllWithTracks:startingAtIndex:` rather than setting the index after (`Playlist/AGENTS.md`).

**A scrub on a parked track seeks; it does not play.** Parked, the player holds no file, so `seekToProgress:` opens the file at the scrubbed position, paused, with the duration from metadata. The seek target outranks Loading in the card's progress paths, or the waveform would snap to zero during that open. `didStartPlaying:` clears the in-flight flag; this seek has no `didFinishSeeking:`.

**The metadata sweep waits for the picked track to settle**: `folderSession:didOpenTracks:` schedules it, `didStartPlaying:` and the error path start it, and a two-second fallback covers an open that never lands. **A launch restore starts it at once**: the park opens nothing, so there is nothing to starve and no `didStartPlaying:` coming — left to the fallback, every row outside the parked track's neighborhood appeared two seconds after launch, all together. The rule underneath is `AudioFileMaterializationCoordinator`'s (root `AGENTS.md`); this is only the scheduling.

**Display state is resolved once**, in `PlayerScreenRules.h` (header-only, tested from the macOS suite). `screenState` gathers the inputs; the card, the mini strip, Now Playing and the debug dump read the result. Separate from the mac's `TrackDisplayRules.h`: no launch grace here, and parked tracks the mac has no equivalent of.

**Two mac features are off, each at one switch**: no folder art (`AudioTrackArtwork`'s resolver handle nil), no key analysis (the card's analysis provider answers `{analyzeBPM, NO}`). Their settings are macOS-only in `AppSettings`. **The DJ FX and BPM detection are on.** The player is created with `enableFX:` from the shared setting and `applyFXSetting` is the write's live effect (the player reconnects its FX segment with the output stopped); `setFXPadPosition:engaged:` is the one funnel the card's pad and the debug channel drive the effects through, mapped by `AudioFXMath.h`. The tempo the delay taps follow is `refreshTempoFeed`'s: `AudioTrack.bpm` for the current track, re-read on every render funnel, on a metadata delivery and on `noteDetectedBPM:forTrack:`, which the card forwards from the waveform decode pass and which stamps every row sounding that track's window (`Playlist.stampTracksSounding:usingBlock:`).

**The 128px thumbnail is on.** Rows archive compact bytes; decoded pixels live in `AudioTrackArtwork`'s shared bounded LRU (`kEmbeddedThumbnailCacheCount`). An eviction returns the placeholder, decodes once off-main, and refreshes only visible Library, Search and mini-player surfaces. **TRAP: UITableView renders prepared cells before they are "visible" and displays them without re-running `cellForRowAtIndexPath:`** — a delivery in that window repaints nothing, so the Library re-renders each cell in `willDisplayCell:`.

## FolderSession

Owns the picked locations of the current playlist — a **base** folder or file plus any additions: the security scopes, the restore bookmarks (plain `bookmarkData`; iOS has no `WithSecurityScope` option), and the listing via `NSURLUtil rowsInDirectory:sortedBy:`, in which a CUE sheet stands in for its files as in a mac folder walk. There is no `.cue` document type: a sheet opened alone carries no grant for the audio beside it, so sheets work inside an opened folder. Dedupe — within one delivery and across an Add — is by standardized path plus a cue row's window, so rows of one image are distinct and a file twice is not. Persistence is its own `NSUserDefaults` keys, not `AppSettings`.

- **Scopes are held as a set** — the base open's and each addition's — for the whole session, since player, TagLib and the waveform loader read under them at arbitrary times, and released only after a successor set is in hand; an append extends the set. A URL may be started twice and each start is balanced by its own stop.
- **"What may be listed" and "what may be held" are two questions over two lists**, both asked through `rootCoveringPath:in:`. The LOGICAL roots (`searchRoots`: the base plus the additions) decide listing and the search-root dedupe, because a container folder is never security-scoped and a file picked inside the open container folder must still expand to it. `_scopedURLs` decides what a request takes a hold on. **TRAP: a security scope is acquired through the URL the system granted, never through a path-equivalent one the app derived.** A search hit leaves the base pointing at a parent derived from the hit; asking the logical roots for the hold picks that derived URL, `startAccessingSecurityScopedResource` refuses it, nothing is collected — and it masks the favorites lookup that would find the real root. The next replace then stops the real grant with no successor and the playlist goes unreadable mid-play. Minting a bookmark for the star takes its hold from the same scoped list, for the same reason.
- **Adoption runs off main**: bookmark resolution and listing are provider IPC that can take seconds. Replaces go on a concurrent queue so a new intent is never parked behind an older provider call; appends go on a **serial lane targeting it**, so two Adds that reach the session with their URLs in hand land in tap order while a replace overtakes them. Every request carries `openIntentGeneration`: a replace bumps it, an append captures it, and only a result matching the live one delivers or persists. **An append captures it when the USER asks, not when the caller finally has a URL** — a caller with its own asynchronous work first (Favorites, resolving a bookmark) takes an `addRequestToken` on main up front and hands it back to `addURLs:token:`, because an Add judged only on arrival captured whatever playlist had been opened meanwhile and appended to that one. **The token is staleness only, and reserves no place in the lane**: an Add that already has its URL can still overtake one waiting on a slow provider, so two Adds land in provider order rather than tap order when a resolve is in the way. Both land; only their relative order gives. Full first-in-first-out would mean parking the serial lane on another screen's provider call or building a pending queue, and neither is worth what it buys. An append also checks the last SETTLED replace, so an Add requested during an open that never landed is dropped rather than added to the wrong playlist; an Add onto a session that has never landed anything is promoted to an Open at request time — including after a failed launch restore, which is why that case plays. **TRAP: only the FIRST such Add promotes.** Promoting every Add made before anything had landed let two Adds onto an empty playlist cancel each other: each became an Open, each bumped the generation, and the second superseded the first, so a selection the user made vanished. That is not the drop rule — a user's explicit replace beating a stale Add is wanted, two Adds beating each other is not. The rest park as **waiters** and are replayed through the prologue when the promoted open settles, **whichever way it settles**: it landed, so they append; it found nothing, so the first of them promotes in its turn; a user's replace beat it, so that replace's own settle releases them onto its playlist. The flag that parks them is set only by a promotion, which is why a failed launch restore still leaves the next Add free to play. **TRAP: a promotion bumps the generation, and that bump must not read as a supersession to the Adds tapped alongside it.** The token check in `addURLs:token:` sits upstream of the parking, so without the exemption a promoted Add drops its own siblings before they can park. A token one below the generation a promotion created is still the user's request while that promotion is the live generation; a real replace or a clear bumps past it and drops them as it should, so the test invalidates itself with no flag to clear. Invisible on local files, where a resolve is a millisecond, and wide open on a cold provider, where it is seconds.
- **Settled is not the same as delivered, and an empty open settles too.** **TRAP:** an open that found no audio leaves the previous playlist standing, so that playlist now answers for the new generation as well and `_landedOpenIntentGeneration` carries forward to it. Without the carry one empty-folder open left every later Add captured at a generation no landing ever matched, and Add was silently dead for the rest of the session. Zero never carries — nothing has landed, so the Add is still promoted to an Open — and an append that found nothing carries nothing, since a bad Add must not make itself the base. Every request ends in `finishOpenIntent:`, the empty ones included; it is the only place the main-confined state moves.
- **One prologue, `beginOpenURLs:appending:fromSearchRoots:`**, serves every entry point (picker, browser, favorite, search hit, Add); the launch restore reads the sort itself and enters the work queue directly, and an inbox copy skips the worker for `finishOpenIntent:`, since Documents/Inbox under an open Documents base would expand to the whole Inbox; its rows are still made on the work queue, since a large FLAC's are read from its header. It runs on main, does no I/O, and is where `AppSettings.folderOpenSort` is snapshotted and passed to the worker, so an open cannot straddle a Settings change and the walk reads no setting (`Util/AGENTS.md`). It is also where the main-only stores are asked — `SearchFolderStore.grantCoveringURL:`, then a retained grant, then `FavoritesStore.resolvedRootCoveringURL:`, in that order — and where a hold is taken on each covering scope so an older worker can finish safely.
- **The base is the FIRST contributor, whatever it is**, and it is the playlist's identity: the Playlist tab's title, the star and the base bookmark all name it, and an Add never moves it. A first contributor that is a file is a single-file base — `folderURL` nil, so the title stays "Playlist" and there is no star, because a single file has no identity to bookmark — and every later folder in the same open is an addition. **TRAP: a folder may not claim the base merely because the contributor ahead of it was a file.** A restore delivers base-then-additions, so a single-file base with an appended folder came back as `[file, folder]` and the folder took the base: the base bookmark was rewritten to the addition, the original file demoted, and the next relaunch's union came back reordered as `[folder, file]`. A multi-select replace of a file and a folder therefore keeps the file as the base and the folder as an addition, and — since the open did bring a folder in — it does persist, which the one-file rule below would otherwise refuse.
- **A file grant reaches nothing but the file**, so a single-file pick is a one-track playlist. A folder grant covers the subtree, which `searchRoots` and `openFileFromSearchRoots:` build on: a search hit opens its own directory as the playlist and leaves the grant and bookmark alone — re-pointing the bookmark at a subfolder would shrink next launch's searchable root. **Only a replace of exactly one picked file expands** to its directory, and it does so under any covering root in hand, not only an exactly-equal parent; **an added file is one track, never its directory**.
- **One delivery names each file once**, and a URL that contributed no track is not persisted. Both halves are the same rule: a restore's list can legitimately overlap (an Add the shell deduped away still persisted its bookmark, and a folder can be added beside one of its own files), and the union is delivered as a replace, which does not dedupe — without this the playlist grew a copy of every re-added folder at each relaunch.
- **An append that finds nothing is silent** — no empty-folder event, no delegate call — since a bad Add must not disturb a good playlist.
- **A launch restore resolves its bookmarks a bounded few at a time and merges them in persisted order.** The bound is `SearchFolderStore`'s, for its reason: one stalled provider must not head-of-line every other bookmark (`Search/AGENTS.md`). A concurrent queue parallelizes nothing inside one block, so resolving the base and each addition in a row cost their sum at every launch. **It does not stop a stalled provider from delaying launch** — the walk needs the whole union, so delivery still waits for the slowest bookmark; bounded concurrency only lets the others make progress meanwhile. **The directory listing and the bookmark minting after it are deliberately still serial**, a partial optimization and stated as one: the dedupe, the contributor list and the first-contributor base rule are order-dependent walks of the one loop that also owns each URL's scope start and its paired stop. Completion order reaches neither playlist order nor contributor ownership.
- **A restore keeps whatever still resolves, and the base is not special.** Only a restore where NOTHING resolves is a failed restore, and only that clears the two keys. A base folder deleted while its additions are still readable restores from those: the first survivor becomes the base by the first-contributor rule, and the landing rewrites both keys from the contributors, which is the same self-healing that prunes a dead addition. Erasing the addition list because the base died threw away folders the user could still play.
- **Persistence is a base bookmark plus an ordered addition list**, both rewritten on every landing from what actually contributed, so a dead or emptied addition prunes itself at the next launch with no pruning code. Neither key is touched by a search-hit open, an inbox copy or a one-file open over a folder bookmark; additions made after one of those are session-only, since the persisted base belongs to an earlier playlist.
- **The app's own trees are roots every open covers**: Documents and the Dropbox mirror need no grant, so `beginOpenURLs:` adds both to the covering roots and a file opened alone in either expands to its folder with it selected — what the browser's file tap relies on. **It reaches every entry point, deliberately**: an "Open in Vibe" of one song in place in Documents opens its folder, as a song in any granted folder does, since the folder is the playlist; only an inbox copy stays one track. The session holds no picker; the browser presents the system ones.
- **Relaunch parks the remembered track** — header, waveform and metadata loaded, nothing playing, card minimized. The base restores with every addition that still resolves, and the remembered track is looked up over the union, so a track from an added folder parks correctly. **What is remembered is the standardized PATH**, plus a cue row's window (`persistedTrackKey`), because the playlist spans folders once an Add has landed and two albums both holding `01.wav` parked on the wrong one. The match is **two-tier — exact path, then filename** — since a provider can hand the same file back under a different absolute path and the simulator's data-container UUID rotates on reinstall; an exact hit anywhere in the union outranks a filename hit, and the filename tier is also what restores a bare filename left by a build before this one. The defaults key keeps its shipped `VibeiOSLastTrackFileName` spelling for exactly that reason. The scene delegate runs exactly one of restore-or-adopt at launch, so "Open in Vibe" never pays for a restore it replaces.
- **TRAP: acquire before release.** A replace landing installs the successor scope set FIRST and only then stops the previous one, so a failed pick never strands the current playlist unreadable. The `TRAP:` beside `finishOpenIntent:` is the authority.

## RootViewController

The scene's root: a `UITabBarController` child, the mini player in its `bottomAccessory`, the card above both. It alone knows whether the card is up, and owns expand and minimize.

**The tabs are `UITab`s, not view controllers.** `UISearchTab` draws the circle outside the capsule, and `automaticallyActivatesSearch` collapses the bar behind a field and restores the previous tab on cancel. Each tab's view controller comes from a lazy provider; ask `_filesController` (the browser's root), never `UITab.viewController`, whether Files exists — the getter resolves the provider. The search tab's identifier is UIKit's, so `selectedTabIdentifier` matches it by kind.

**A container, not a `UITabBarController` subclass**: the card sits above the tab bar controller's whole view so that view can scale back, and a subclass cannot transform its own view without moving the card.

**The card is built once and never torn down.** Minimize translates it off the bottom. Its pager, art window and waveform snapshots survive, or every expand would re-read and re-decode art; art is not pruned on minimize either — the byte budget bounds it, and pruning costs a placeholder flash.

**TRAP: the card moves by TRANSFORM, never by frame.** Its pages carry `WaveformScrubberView`s, which re-bake their envelope on any bounds change. `dump_state`'s `ui.waveformBaked` checks it.

**TRAP: `shouldAutomaticallyForwardAppearanceMethods` is per-parent.** Turning it off for the card turns it off for the tabs, so both are forwarded by hand; each begin snapshots its exact children and the end consumes that snapshot, because `_expanded` can change between them.

Foreground-inactive is off, not a halfway foreground: the scene delegate's foreground-active bit drives the Library surface and the card's display link. The custom card transition supplies what a presentation would: Reduce Motion settles immediately, the card is the modal accessibility surface while up, and completion moves VoiceOver focus.

## MiniPlayerView

The accessory's content: the 128px thumbnail, title over artist, play/pause and next. Large tap targets, small glyphs (`kGlyphPointSize`); next is `forward.end.fill`, the mac's glyph. `traitCollection.tabAccessoryEnvironment` says when the tab bar has collapsed it inline, where the artist line is dropped. **No playhead bar**: one fits 48pt only by crowding the art and labels.

**TRAP: the row needs a designated give, and the simulator never shows it.** On device the accessory container reports width zero on at least one pass; the row's required content needs 162pt, so UIKit breaks a constraint at random and logs every launch. The art's leading inset is `UILayoutPriorityRequired - 1`. Any new required constraint spanning the row reopens this.

**TRAP: the strip is 48pt, not negotiable.** `UITabAccessory` frames its content at a fixed system height; `intrinsicContentSize` and height constraints are ignored *without a logged conflict*. A taller strip means giving up the accessory, and with it Liquid Glass, inline collapse and the automatic safe-area inset.

## BrowserViewController

The Files tab, and the Playlist tab's plus as a sheet (`appending:YES`, every action appends and the sheet closes). One `UITableViewController` per level in a navigation controller: the root lists the sources — Dropbox (or Connect), On My iPhone (Documents), and `SearchFolderStore`'s folders as **Locations** with Add Folder… and Browse Files… — and a directory lists its folders, then its playable files, by name. It replaced a `UIDocumentBrowserViewController`, whose Open button spun forever under multi-select and whose floating bar collided with the tab bar's; neither trap exists now.

- **Every open is a `PlaybackController` road**: a file tap is `openURLs:openInPlace:YES` (it becomes its folder with it selected, because every source is a root an open covers), the bar's play button opens the directory, Add is `addURLs:`, and a folder's star is `bookmarkFolderURL:` then `FavoritesStore`, as before. Edit gives multi-select Add, the road the old picker's multi-select was.
- **A Dropbox directory draws from disk at once, then relists** (`DropboxMirror refreshDropboxFolder:`) when it appears, unless this screen listed it within the last minute (`kRelistInterval`, so going back and forth costs nothing), and always on pull-to-refresh; a placeholder row carries a cloud. An unlinked account pops the stack to the sources.
- **The system pickers remain for two jobs only**: Add Folder… grants a location (`SearchFolderStore addFolderURL:`, which refuses a covered one with a word), and Browse Files… is a one-off multi-select pick from anywhere. The Settings list of search folders is gone; Locations is that list.
- **The bar's items follow the Playlist tab's absent-not-disabled rule**: no Edit in an empty folder, no play in one holding only folders, since a listing is flat.

## LibraryViewController

The Playlist tab: number (replaced on the playing row by the shared `EqualizerIndicatorView`), artwork, title over artist, duration. **Selecting a row plays it and stays here**; expanding the card is the strip's job. A track change scrolls the list to the playing row, or, while hidden, leaves that for when it shows — **except under shuffle, where the list holds still**, since following a play order that jumps across it would yank the user's place on every track. Number and duration take the artist line's text style so the secondary columns scale together under Dynamic Type. The folder name goes on `navigationItem.title`, not `self.title`, which is also the tab's title.

**Equalizer activity is actual output plus material visibility** — this doc's half of the root guarantee. Output is `PlaybackController.audioOutputActive`: true through an outgoing fade, false for a Loading request. Visibility is this controller's presentation plus `willDisplayCell:`/`didEndDisplayingCell:` state, plus `RootViewController`'s tab and card exposure — explicit, because the card moves by transform over children that stay "appeared", and kept honest through interactive and interrupted transitions — plus the scene delegate's foreground-active bit. Only then does the playing row start its poller, declaring one `equalizerLevelsWanted:` consumer; stopping balances it. The gate is counted, not boolean, because cell reuse can briefly hold two consumers. Hidden track changes retain one pending scroll index and park there without animation on the next reveal.

**The gutter has three states in precedence: loading, playing, number** (`resolveGutter`). Loading is `CloudTransferRegistry.isTransferringURL:`, a provider transfer really running; it outranks playing because there is no output audio yet. `syncEqualizerActivityForCell:` folds `!loading` into both activity facts so a loading row holds no poller; a registry change re-syncs `visibleCells` in place, never a reload; `didEndDisplayingCell:` and `prepareForReuse` drop `loading`.

`dump_equalizer` is the runtime proof: `renderer.displayTicks` is bounded at 30/s while active and flat after an inactive transition settles. The meter reads the render's samples before `--silent` zeros them, so the bars are live under the debug scripts' default launch.

**The gear opens a menu, not Settings directly**: Settings, then **Clear Playlist** alone in a destructive inline group at the bottom — the construction the Favorites long-press menu uses, so the app's two menus read alike, and the platform's place for a destructive item. **No confirmation sheet**: nothing leaves the disk, and the playlist is rebuilt by reopening, which is how clearing a queue behaves elsewhere on the platform; the destructive styling carries the warning. Its accessibility label names the menu rather than either item, since the button does two things. A clear also **wipes the persisted bookmarks and the remembered track**, because restoring at the next launch what the user just cleared would be the opposite of what they asked for, and it **releases every scope** — each start balanced by exactly one stop — since nothing reads under them once the playlist is empty. **It also settles the launch waiters, last of all.** A clear during a launch restore supersedes that restore, so none of the delegate methods that would settle them fires, and `_launchOpenSettled` is a **latch**: miss it once and every later `performWhenLaunchOpenSettled:` parks too, all firing together against whatever playlist exists when some later open settles — which a widget transport intent presents as the app skipping a track for no reason. A clear is a settle, for the same reason a restore that found nothing is: there is nothing left to wait for. It goes at the END for the reason the chrome rebuild does — a waiter runs arbitrary work, a widget intent driving transport among it, and must not see a half-reset controller.

The bar carries **the gear, and the star when a folder is open** — absent, not disabled, for a single-file or empty playlist — and, on the **leading** side, **the plus that presents the Files tab's browser as an add sheet**. Leading rather than a third trailing item: three crowd the large title, and the split then reads as what it is — the trailing pair acts on the open folder, the plus acts on the playlist. Adding lives here, not in the Files tab, because a button inside a browser that opens a second browser does not read and because the playlist is what is being added to. **The plus follows the star's absent-not-disabled rule**: with an empty playlist there is nothing to add to, and the empty state's own Open button already owns that moment, so two roads to "find something to play" — the add sheet and the Files tab — never compete on one screen. Title and star both name `FolderSession`'s BASE folder, never an added one: an Add changes neither. `refreshChrome` rebuilds title, star and empty state together. The star fills when the bookmark lands, not on the tap (`Search/AGENTS.md`), and this screen also redraws on `VibeFavoritesDidChangeNotification`. The empty state's `UIContentUnavailableConfiguration` keeps its own Open action for the first run, and it **brings the Files tab forward rather than presenting the add sheet** — the app already has a surface whose job is finding something to play, it is ours (its rows carry Add to Playlist and Add to Vibe Favorites), and it leaves the user somewhere they can keep looking. **This screen knows nothing about tabs**: it calls an `openFilesHandler` the shell sets when it builds the tab, the same direction `equalizerSurfaceVisible` travels, so the library holds no reference back and `selectedTabIdentifier` stays debug-only surface.

## Building and verifying

The `vibe-debug` skill's "iOS: the simulator loop" section covers launch, feeding audio, screenshots and logs. `RootViewController+Debug` adopts the channel's protocol, composing `PlaybackController+Debug` and `PlayerViewController+Debug` with the shell's own state; all three categories live in `Vibe/Debug/iOS/`. `expand_player`, `minimize_player` and `select_tab` exist because the channel cannot synthesize a touch — gestures go through `drive-ios.sh`. **Interruptions, route changes, background audio past lock and the lock-screen card need a real device.**
