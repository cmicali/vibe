# iOS app shell (VibeiOS target)

A single-folder player: **the current directory is the playlist.** The user picks a folder or file in the app's own browser (the Files tab): Dropbox through its HTTP API and a local mirror (`Dropbox/AGENTS.md`), the app's Documents, and each location granted once through the system folder picker — iCloud Drive, a drive, any other Files provider. Three `UITab`s — Playlist, Favorites, Files — with `UISearchTab`'s circle beside the capsule, a mini player strip in the tab bar's `bottomAccessory`, and the now-playing card presenting up from the strip. Opening anything replaces the playlist, starts playing, selects the Playlist tab and presents the card, so minimizing lands on what was just opened — except a single file played alone, whose tab stays where it was picked, so minimizing lands back in the browser. **Add to Playlist** appends a Files-tab item's or a favorite's tracks without touching playback, the tab or the card; an Add onto nothing is an Open.

This directory is the shell only. The iOS halves of shared subsystems are documented beside them: `Audio/iOS/`, `WaveformUI/iOS/`, `Util/iOS/`. Within this directory, `Player/` (the card: pager, page cell, route control, waveform coordinator), `Search/` (Favorites, Search and the folder stores), `Settings/` and `Dropbox/` (the account and its mirror) each carry their own `AGENTS.md`.

A new file in a shared directory joins this target automatically and must be AppKit-free or `TARGET_OS_OSX`-guarded (root `AGENTS.md`); CI's iOS builds catch a leak.

**Layout keys off view aspect, not device orientation** — and on iPad off height too: a short window takes the card's compact layouts (`Player/AGENTS.md`). iPad is a resizable window, all orientations, minimum 320×200 via `sizeRestrictions` in `VibeiOSSceneDelegate` (the card's strip layout's floor); iPadOS 26 itself keeps a window at least about 486pt tall, so the system floor is the one that binds.

**Multi-scene is off.** One `AudioPlayer` per `PlaybackController`, one `PlaybackController` per scene; a second scene would be a second engine. A size transition sets `_windowResizeInFlight`, which holds `commitVisiblePage`: a mid-resize offset rounds to a neighbor page and would switch tracks.

## PlaybackController — the model

Everything the app plays and nothing that draws it: engine, `Playlist`, metadata cache, audio session, `FolderSession`, Now Playing, the 3 Hz `UIUpdateTimer`, and the display state. The scene delegate owns the one instance; every screen borrows it.

**It broadcasts** (`PlaybackObserver`: synchronous on main, registration order, weak `NSPointerArray`) because three views describe one playback and `Playlist` has one observer slot. **Weak is load-bearing**: an observer is a view or view controller.

**iOS has exactly one removal, and it is the whole playlist: `clearPlaylist`.** The bar's menu offers it as Clear Playlist. It is the twin of the mac's `closeFile:` and safe for the reason that one is: **unloading everything leaves no surviving cursor to strand and no row for the player to be sounding.** It stops the player (which fires no transport or track-end callback, so nothing auto-advances and the method owns the reset), drops the parked successor, ends the loading open's progress, clears the session — scopes, base, additions and the persisted bookmarks with them — **before** the model, whose replace event is what rebuilds the chrome (the `TRAP:` in `clearPlaylist`), then cancels the deferred sweep and the scan.

**There are no partial edits.** The remove, insert and move observer methods are no-ops: there is no row-level edit UI, and forwarding a model-only edit would not make one safe, because removing the *current* row is a transport operation. A row-level edit UI must add its own coordinator on the model of `MainPlayerController.removePlaylistTracks:`; calling `Playlist.removeTracksAtIndexes:` directly leaves the player sounding a departed object. `clearPlaylist` sidesteps that problem by being the whole playlist; it does not solve it.

`+PlayerEvents`: every `AudioPlayerDelegate` callback, under the root doc's two rules (every callback can be stale; `stop` fires no callback). `+NowPlaying`: `publishNowPlaying`, which `notifyDidTick` **calls before it ticks the screens**, so the lock screen never lags them.

**On track end is the root guarantee's, enforced at both of its places here**: `successorPrefetchTrack` (the playlist's `trackEndSuccessor`, nil under Pause, so no successor is queued) feeds every `prefetchTrack:` site (the transition settings, `prefetchSuccessor` and the player-events category), and `didFinishPlaying:` re-reads the setting before `advanceAtTrackEnd`, parking on the finished track exactly as the end of the playlist does. **A refused splice parks too, and must silence what the player started**: when `advanceFromTrack:toTrack:` no longer accepts the successor the player spliced into (a mode or Pause switched mid-boundary), `didAutoAdvanceFromTrack:toTrack:` runs the track end, and if that parks it reloads the finished track paused over the sounding successor, as the mac does — otherwise the card parks on the finished track while the successor plays on. A write to any transition setting — Pause, the crossfade, and the card's shuffle and repeat buttons (`toggleShuffle`, `cycleRepeatMode`) — ends on `applyTrackTransitionSettings`, which pushes the crossfade and both modes, re-parks or drops the successor, publishes the modes to Now Playing and tells observers through `playbackDidChangePlayOrder:` — the iOS spelling of the mac's `EndOfTrack` and `Crossfade` live effects, and what the Settings screens are handed the model for. An open hands its start row to `replaceAllWithTracks:startingAtIndex:` rather than setting the index after (`Playlist/AGENTS.md`).

**A scrub on a parked track seeks; it does not play.** Parked, the player holds no file, so `seekToProgress:` opens the file at the scrubbed position, paused, with the duration from metadata. The seek target outranks Loading in the card's progress paths, or the waveform would snap to zero during that open. `didStartPlaying:` clears the in-flight flag; this seek has no `didFinishSeeking:`.

**The metadata sweep waits for the picked track to settle**: `folderSession:didOpenTracks:` schedules it, `didStartPlaying:` and the error path start it, and a two-second fallback covers an open that never lands. **A launch restore starts it at once**: the park opens nothing, so there is nothing to starve and no `didStartPlaying:` coming — left to the fallback, every row outside the parked track's neighborhood appeared two seconds after launch, all together. The rule underneath is `AudioFileMaterializationCoordinator`'s (root `AGENTS.md`); this is only the scheduling.

**Display state is resolved once**, in `PlayerScreenRules.h` (header-only, tested from the macOS suite). `screenState` gathers the inputs; the card, the mini strip, Now Playing and the debug dump read the result. Separate from the mac's `TrackDisplayRules.h`: no launch grace here, and parked tracks the mac has no equivalent of. **The slow-open state is apart from it**: `currentOpenSlow` is YES from `playbackDidBeginLoading:` (set before it is sent) until the open settles or fails, and every cursor change, replacement and play clears it; the card's loading shimmer reads it (`Player/AGENTS.md`), where `screenState`'s Loading, which starts at submission, would flash on every fast Next.

**Two mac features are off, each at one switch**: no folder art (`AudioTrackArtwork`'s resolver handle nil), no key analysis (the card's analysis provider answers `{analyzeBPM, NO}`). Their settings are macOS-only in `AppSettings`. **The DJ FX and BPM detection are on.** The player is created with `enableFX:` from the shared setting and `applyFXSetting` is the write's live effect (the player reconnects its FX segment with the output stopped); `setFXPadPosition:engaged:` is the one funnel the card's pad and the debug channel drive the effects through, mapped by `AudioFXMath.h`. The tempo the delay taps follow is `refreshTempoFeed`'s: `AudioTrack.bpm` for the current track, re-read on every render funnel, on a metadata delivery and on `noteDetectedBPM:forTrack:`, which the card forwards from the waveform decode pass and which stamps every row sounding that track's window (`Playlist.stampTracksSounding:usingBlock:`).

**The 128px thumbnail is on.** Rows archive compact bytes; decoded pixels live in `AudioTrackArtwork`'s shared bounded LRU (`kEmbeddedThumbnailCacheCount`). An eviction returns the placeholder, decodes once off-main, and refreshes only visible Library, Search and mini-player surfaces. **TRAP: UITableView renders prepared cells before they are "visible" and displays them without re-running `cellForRowAtIndexPath:`** — a delivery in that window repaints nothing, so the Library re-renders each cell in `willDisplayCell:`.

## FolderSession

Owns the picked locations of the current playlist — a **base** folder or file plus any additions: the security scopes, the restore bookmarks (plain `bookmarkData`; iOS has no `WithSecurityScope` option), and the listing via `NSURLUtil rowsInDirectory:sortedBy:`, in which a CUE sheet stands in for its files as in a mac folder walk. **A sheet's grant reaches the sheet alone, never the audio beside it**, so a `.cue` picked in Browse Files… or sent with "Open in Vibe" (the target declares the mac's CUE Sheet type) finds nothing unless a root covers its folder. That open settles empty as any does, then names the sheet (`needsFolderOfSheetAtURL:`, only for a denied folder, never a missing one); `RootViewController` asks with the mac's grant wording and presents a folder picker, and the sheet reopens with the picked folder held like a starred folder's root (`FolderSession.h` has the contract). A sheet opened alone from the browser or Recents, where a root covers its folder, is its own rows (`rowsForFile:`, resolved against the folder's listing, so placeholders count), and a sheet that expanded to its folder starts the playlist at its first row. Dedupe — within one delivery and across an Add — is by standardized path plus a cue row's window, so rows of one image are distinct and a file twice is not. Persistence is its own `NSUserDefaults` keys, not `AppSettings`.

- **Scopes are held as a set** — the base open's and each addition's — for the whole session, since player, TagLib and the waveform loader read under them at arbitrary times, and released only after a successor set is in hand; an append extends the set. A URL may be started twice and each start is balanced by its own stop.
- **"What may be listed" and "what may be held" are two questions over two lists**, both asked through `rootCoveringPath:in:`. The LOGICAL roots (`searchRoots`: the base plus the additions) decide listing and the search-root dedupe, because a container folder is never security-scoped and a file picked inside the open container folder must still expand to it. `_scopedURLs` decides what a request takes a hold on. **TRAP: a security scope is acquired through the URL the system granted, never through a path-equivalent one the app derived.** A search hit leaves the base pointing at a parent derived from the hit; asking the logical roots for the hold picks that derived URL, `startAccessingSecurityScopedResource` refuses it, nothing is collected — and it masks the favorites lookup that would find the real root. The next replace then stops the real grant with no successor and the playlist goes unreadable mid-play. Minting a bookmark for the star takes its hold from the same scoped list, for the same reason.
- **Adoption runs off main**: bookmark resolution and listing are provider IPC that can take seconds. Replaces go on a concurrent queue so a new intent is never parked behind an older provider call; appends go on a **serial lane targeting it**, so two Adds that reach the session with their URLs in hand land in tap order while a replace overtakes them. Every request carries `openIntentGeneration`: a replace bumps it, an append captures it, and only a result matching the live one delivers or persists. **An append captures it when the USER asks, not when the caller finally has a URL** — a caller with its own asynchronous work first (Favorites, resolving a bookmark) takes an `addRequestToken` on main up front and hands it back to `addURLs:token:`, because an Add judged only on arrival captured whatever playlist had been opened meanwhile and appended to that one. **A replace behind asynchronous work carries a token of its own to the browser's `confirmReplacing…` funnel, which drops it when a newer replace, open or clear was asked for meanwhile** (`PlaybackController.replaceRequestToken`; not the Add token, which two taps before either resolved shared, so the first to open dropped the one the user chose last) — a favorite's bookmark and Dropbox listing, a search hit's folder, a recent's bookmark, the subfolder walk's listings — or an older tap, landing seconds later, would replace the open the user made last. **The token is staleness only, and reserves no place in the lane**: an Add that already has its URL can still overtake one waiting on a slow provider, so two Adds land in provider order rather than tap order when a resolve is in the way. Both land; only their relative order gives. Full first-in-first-out would mean parking the serial lane on another screen's provider call or building a pending queue, and neither is worth what it buys. An append also checks the last SETTLED replace, so an Add requested during an open that never landed is dropped rather than added to the wrong playlist; an Add onto a session that has never landed anything is promoted to an Open at request time — including after a failed launch restore, which is why that case plays. **TRAP: only the FIRST such Add promotes.** Promoting every Add made before anything had landed let two Adds onto an empty playlist cancel each other: each became an Open, each bumped the generation, and the second superseded the first, so a selection the user made vanished. That is not the drop rule — a user's explicit replace beating a stale Add is wanted, two Adds beating each other is not. The rest park as **waiters** and are replayed through the prologue when the promoted open settles, **whichever way it settles**: it landed, so they append; it found nothing, so the first of them promotes in its turn; a user's replace beat it, so that replace's own settle releases them onto its playlist. The flag that parks them is set only by a promotion, which is why a failed launch restore still leaves the next Add free to play. **TRAP: a promotion bumps the generation, and that bump must not read as a supersession to the Adds tapped alongside it.** The token check in `addURLs:token:` sits upstream of the parking, so without the exemption a promoted Add drops its own siblings before they can park. A token one below the generation a promotion created is still the user's request while that promotion is the live generation; a real replace or a clear bumps past it and drops them as it should, so the test invalidates itself with no flag to clear. Invisible on local files, where a resolve is a millisecond, and wide open on a cold provider, where it is seconds.
- **Settled is not the same as delivered, and an empty open settles too.** **TRAP:** an open that found no audio leaves the previous playlist standing, so that playlist now answers for the new generation as well and `_landedOpenIntentGeneration` carries forward to it. Without the carry one empty-folder open left every later Add captured at a generation no landing ever matched, and Add was silently dead for the rest of the session. Zero never carries — nothing has landed, so the Add is still promoted to an Open — and an append that found nothing carries nothing, since a bad Add must not make itself the base. Every request ends in `finishOpenIntent:`, the empty ones included; it is the only place the main-confined state moves.
- **One prologue, `beginOpenURLs:appending:expandsFile:grantedFolder:`**, serves every entry point (picker, browser, favorite, search hit, Add); the launch restore reads the sort itself and enters the work queue directly, and an inbox copy skips the worker for `finishOpenIntent:`, since Documents/Inbox under an open Documents base would expand to the whole Inbox; its rows are still made on the work queue, since a large FLAC's are read from its header. It runs on main, does no I/O, and is where `AppSettings.folderOpenSort` is snapshotted and passed to the worker, so an open cannot straddle a Settings change and the walk reads no setting (`Util/AGENTS.md`). It is also where the main-only stores are asked — `SearchFolderStore.grantCoveringURL:`, then a retained grant, then `FavoritesStore.resolvedRootCoveringURL:`, in that order — and where a hold is taken on each covering scope so an older worker can finish safely.
- **The base is the FIRST contributor, whatever it is**, and it is the playlist's identity: the Playlist tab's title, the star and the base bookmark all name it, and an Add never moves it. A first contributor that is a file is a single-file base — `folderURL` nil, so the title stays "Playlist" and there is no star, because a single file has no identity to bookmark — and every later folder in the same open is an addition. **TRAP: a folder may not claim the base merely because the contributor ahead of it was a file.** A restore delivers base-then-additions, so a single-file base with an appended folder came back as `[file, folder]` and the folder took the base: the base bookmark was rewritten to the addition, the original file demoted, and the next relaunch's union came back reordered as `[folder, file]`. A multi-select replace of a file and a folder therefore keeps the file as the base and the folder as an addition, and — since the open did bring a folder in — it does persist, which the one-file rule below would otherwise refuse.
- **A file grant reaches nothing but the file**, so a single-file pick is a one-track playlist. A folder grant covers the subtree, which `searchRoots` and `openURL:inFolder:` (a search hit or a recent, alone or in its folder) build on. **The prologue alone decides whether an open becomes the session bookmark**: one strictly inside a grant only the session holds — a one-off pick nothing else persists — leaves it alone, since re-pointing it at a subfolder would shrink next launch's reach to that subfolder; under a Location, a favorite, Documents or the mirror the grant persists by itself, so the open is remembered like any other. **Only a replace of exactly one picked file expands** to its directory, and it does so under any covering root in hand, not only an exactly-equal parent; **an added file is one track, never its directory**. **An M3U never expands**: it is its own readable entries (`rowsForFile:`), since its folder's open leaves it out. In the Dropbox mirror, each folder its entries name is listed first, as an open lists a folder.
- **One delivery names each file once**, and a URL that contributed no track is not persisted. Both halves are the same rule: a restore's list can legitimately overlap (an Add the shell deduped away still persisted its bookmark, and a folder can be added beside one of its own files), and the union is delivered as a replace, which does not dedupe — without this the playlist grew a copy of every re-added folder at each relaunch.
- **An append that finds nothing disturbs nothing, but is not silent**: no empty-folder event, and the playlist is untouched, since a bad Add must not disturb a good playlist — but `folderSession:didAppendTracks:` is still delivered, empty, and `PlaybackController` ends every Add, landed or not, with `playback:didSettleAddLanding:` after the append's own events, so whoever asked (the Files tab's lifted rows) hears how it landed without the playlist's observers reloading for a non-change.
- **A launch restore resolves its bookmarks a bounded few at a time and merges them in persisted order.** The bound is `SearchFolderStore`'s, for its reason: one stalled provider must not head-of-line every other bookmark (`Search/AGENTS.md`). A concurrent queue parallelizes nothing inside one block, so resolving the base and each addition in a row cost their sum at every launch. **It does not stop a stalled provider from delaying launch** — the walk needs the whole union, so delivery still waits for the slowest bookmark; bounded concurrency only lets the others make progress meanwhile. **The directory listing and the bookmark minting after it are deliberately still serial**, a partial optimization and stated as one: the dedupe, the contributor list and the first-contributor base rule are order-dependent walks of the one loop that also owns each URL's scope start and its paired stop. Completion order reaches neither playlist order nor contributor ownership.
- **A restore keeps whatever still resolves, and the base is not special.** Only a restore where NOTHING resolves is a failed restore, and only that clears the two keys. A base folder deleted while its additions are still readable restores from those: the first survivor becomes the base by the first-contributor rule, and the landing rewrites both keys from the contributors, which is the same self-healing that prunes a dead addition. Erasing the addition list because the base died threw away folders the user could still play.
- **Persistence is a base bookmark plus an ordered addition list**, both rewritten on every landing from what actually contributed, so a dead or emptied addition prunes itself at the next launch with no pruning code. Neither key is touched by a search-hit open, an inbox copy or a one-file open over a folder bookmark; additions made after one of those are session-only, since the persisted base belongs to an earlier playlist.
- **A Dropbox folder nothing has listed yet is listed from Dropbox before an open reads it** (`listFromDropboxIfMirrored:`, on the work queue, bounded so an open offline reads the disk): the mirror holds only what something has listed, so a folder played or added from its parent's listing, never browsed into, was empty on disk and the open landed nothing. One already listed — by the browser, a walk, a search hit — is read as it is, so nothing is listed twice and a restore never waits on the network.
- **The app's own trees are roots every open covers**: Documents and the Dropbox mirror need no grant, so `beginOpenURLs:` adds both to the covering roots and a file opened alone in either expands to its folder with it selected — what Play in Folder relies on. **It reaches every entry point, deliberately**: an "Open in Vibe" of one song in place in Documents opens its folder, as a song in any granted folder does, since the folder is the playlist; only an inbox copy stays one track. The session holds no picker: the browser presents the system ones, and the shell the folder picker a sheet's grant needs.
- **Relaunch parks the remembered track** — header, waveform and metadata loaded, nothing playing, card minimized. The base restores with every addition that still resolves, and the remembered track is looked up over the union, so a track from an added folder parks correctly. **What is remembered is the standardized PATH**, plus a cue row's window (`persistedTrackKey`), because the playlist spans folders once an Add has landed and two albums both holding `01.wav` parked on the wrong one. The match is **two-tier — exact path, then filename** — since a provider can hand the same file back under a different absolute path and the simulator's data-container UUID rotates on reinstall; an exact hit anywhere in the union outranks a filename hit, and the filename tier is also what restores a bare filename left by a build before this one. The defaults key keeps its shipped `VibeiOSLastTrackFileName` spelling for exactly that reason. The scene delegate runs exactly one of restore-or-adopt at launch, so "Open in Vibe" never pays for a restore it replaces. **The first launch copies the bundled `vibe-theme.mp3` into Documents** (`VibeiOSAppDelegate`, gated on `AppSettings.welcomeTrackLoaded`), so On My iPhone shows it. It is the user's file from then on, and deleting it sticks, since iOS has no reset.
- **TRAP: acquire before release.** A replace landing installs the successor scope set FIRST and only then stops the previous one, so a failed pick never strands the current playlist unreadable. The `TRAP:` beside `finishOpenIntent:` is the authority.

## RootViewController

The scene's root: a `UITabBarController` child, the mini player in its `bottomAccessory`, the card above both. It alone knows whether the card is up, and owns expand and minimize. Settings rides the Playlist tab's stack, and leaving that tab pops it (`didSelectTab:previousTab:`), so coming back shows the playlist.

**The tabs are `UITab`s, not view controllers.** `UISearchTab` draws the circle outside the capsule, and `automaticallyActivatesSearch` collapses the bar behind a field and restores the previous tab on cancel. Each tab's view controller comes from a lazy provider; ask `_filesController` (the browser's root), never `UITab.viewController`, whether Files exists — the getter resolves the provider. The search tab's identifier is UIKit's, so `selectedTabIdentifier` matches it by kind.

**A container, not a `UITabBarController` subclass**: the card sits above the tab bar controller's whole view, with the backdrop snapshot between them, and a subclass could not put anything of its own above or below its own view. A card at rest hides the tabs; the glass tab bar would otherwise keep sampling for nothing.

**The card is built once and never torn down.** Minimize translates it off the bottom. Its pager, art window and waveform snapshots survive, or every expand would re-read and re-decode art; art is not pruned on minimize either — the byte budget bounds it, and pruning costs a placeholder flash.

**TRAP: what scales under a moving card is a SNAPSHOT of the tabs, never the tabs view.** Scaling the view itself, by its transform or by a sublayer transform above it, moved its edges away from the screen's, and UIKit took away the safe-area insets and the edge layout margins as it did: the navigation bar, the large title, the rows and the tab bar re-laid out and the screen jumped under the card on every expand and dismiss. A snapshot has no layout to lose (`beginBackdropSnapshot`, taken as the card starts moving, dropped once it rests). The tabs are shown under it while the card moves, drawn twice for those frames on purpose: the tab bar comes back with an appearance of its own, which then plays out under the snapshot rather than after the card has landed. **The mini player strip stays installed under the card** (`refreshMiniPlayer`): taking the accessory away on expand shrinks every tab's bottom inset by the strip, a list scrolled to its end is clamped up by that much under the snapshot, and putting it back on dismiss moves nothing, so one card cycle left the last row behind the strip. `check-layout-stability.sh` on a playlist scrolled to its end is the oracle for both.

**TRAP: the card moves by TRANSFORM, never by frame.** Its pages carry `WaveformScrubberView`s, which re-bake their envelope on any bounds change, so a frame animation would bake every page on every frame.

**TRAP: `shouldAutomaticallyForwardAppearanceMethods` is per-parent.** Turning it off for the card turns it off for the tabs, so both are forwarded by hand; each begin snapshots its exact children and the end consumes that snapshot, because `_expanded` can change between them.

Foreground-inactive is off, not a halfway foreground: the scene delegate's foreground-active bit drives the Library surface and the card's display link. The custom card transition supplies what a presentation would: Reduce Motion settles immediately, the card is the modal accessibility surface while up, and completion moves VoiceOver focus.

## MiniPlayerView

The accessory's content: the 128px thumbnail, title over artist, play/pause and next. Large tap targets, small glyphs (`kGlyphPointSize`); next is `forward.end.fill`, the mac's glyph. `traitCollection.tabAccessoryEnvironment` says when the tab bar has collapsed it inline, where the artist line is dropped. **No playhead bar**: one fits 48pt only by crowding the art and labels.

**TRAP: the row needs a designated give, and the simulator never shows it.** On device the accessory container reports width zero on at least one pass; the row's required content needs 162pt, so UIKit breaks a constraint at random and logs every launch. The art's leading inset is `UILayoutPriorityRequired - 1`. Any new required constraint spanning the row reopens this.

**TRAP: the strip is 48pt, not negotiable.** `UITabAccessory` frames its content at a fixed system height; `intrinsicContentSize` and height constraints are ignored *without a logged conflict*. A taller strip means giving up the accessory, and with it Liquid Glass, inline collapse and the automatic safe-area inset.

## BrowserViewController

The Files tab, and the Playlist tab's plus as a sheet (`appending:YES`, every action appends and the sheet closes; it is titled Add to Playlist at its root and prompts it on every pushed level, because it is otherwise the Files tab's twin and there a tap plays). One `UITableViewController` per level in a navigation controller. The root lists the sources — On My iPhone (Documents) and Dropbox once an account is linked — then **Recents**, a group of its own, then **Locations**: `SearchFolderStore`'s folders, then the rows that add one, Connect to Dropbox… (until linked), Add Folder… and Browse Files…. `rootRowsInSection:` is the one answer to what a root row is. A directory lists its folders, then its M3U playlists, then its playable files and CUE sheets, each in `AppSettings.folderOpenSort`'s order through `NSURLUtil`'s own sort, so a folder plays in the order it is shown. A playlist is not part of its folder's play, as a subfolder is not: a tap plays it, its long press has no Play in Folder, and a folder holding playlists but no song has no play button. It is not a `UIDocumentBrowserViewController`: that one's Open button spins forever under multi-select, and its floating bar collides with the tab bar's.

- **A file tap plays that file alone, where it was tapped; a folder tap opens it** — the one rule the browser, Search and Recents share. A one-track, no-folder open presents the card but keeps the tab (`playbackDidOpenNewFolder:`); a folder, a file in its folder, or a pick of several brings the Playlist tab forward first. The long press has Play in Folder (the file's directory as the playlist with it selected), and on a folder, Play. Every open is a `PlaybackController` road: `openFileURL:inFolder:` for a tap, the long press and the bar's play button, `addURLs:` for an Add, and a folder's star is `bookmarkFolderURL:` then `FavoritesStore`.
- **A replace asks first when the playlist was built by hand** (`+confirmReplacingPlaylistOf:from:openingURLs:inFolder:`, the one road every replacing tap takes — the browser's, Recents', Search's and Favorites'): `PlaybackController.playlistHasAdditions` is `FolderSession.hasAdditions`, YES once an Add has landed, or for a playlist restored with addition bookmarks. The alert offers Replace, Add Instead and Cancel; any other playlist is replaced at once, since reopening rebuilds it.
- **A row says what a tap costs**: the file's size from the listing's stat (a placeholder carries the remote size; formatted with the listing, off main), `VibeNotDownloadedMark` on one not downloaded, and on the file now playing the Playlist tab's equalizer as its accessory, its icon kept (`playbackDidMoveToCurrentTrack:`). That equalizer is held to the root guarantee as the Library's is: the root sets the Files stack's exposure on its bottom browser (`equalizerSurfaceVisible`, the Library for its add sheet), each screen adds its own appearance, and the row must be in the viewport (`VibeRowIsInViewport`, the Library's test too). **A file's icon is its album art when its bytes are on the device, else a tile** (`VibeFileTileImage`: a waveform for audio, a note list for a CUE sheet or an M3U; every list row's icon slot — here, Recents, Search and Favorites — is `VibeApplyFileIcon`, and the Playlist tab's rows and the mini player draw the tile in their own art views). The art comes through the app's own pipeline — one `AudioTrackMetadataCache` for a stack of folders (`stackArtCache`: each cache opens a store that lists the whole metadata cache directory), asked for the rows on screen and a margin when a listing lands and when a scroll settles, drawn from `cachedThumbnail` — so a file a playlist has seen answers from the disk cache without being read, and a folder merely browsed is not parsed whole. **TRAP: a placeholder and a provider's dataless file are never asked** (`loadArtForVisibleRows`): a miss reads the tags from the file, which would be ranged requests or a download for every row. The cache serves the screen on top: one that goes cancels its own scan, never its successor's. A mirrored folder on screen relists on `VibeDropboxDownloadsDidChangeNotification`, so a download that lands drops its mark and gains its art without the screen being reopened. Names take two lines and truncate in the middle, here and in Search and Recents (`VibeApplyFileNameStyle`). The listing is `NSURLUtil listDirectory:sortedBy:folders:playlists:audio:`, the same filter the open applies, so a song row shown is a row that plays.
- **A row being opened spins in its icon slot**, here and in Recents, Search and Favorites (`VibeApplyRowContent`): `PlaybackController.openingPath` names it from the tap — `replaceRequestTokenOpening:`, before any resolve — until the open lands, finds nothing, is superseded or is given up, and `playbackDidChangeOpening:` redraws. A second tap on it gives it up (`cancelOpening`: a resolve still running is dropped by the replace funnel, an open the session holds by `FolderSession.cancelOpen`, which settles like an empty open), and so does `kOpeningTimeout`, with an alert from the root. A caller whose own work ends before the open — a failed resolve, Cancel or Add Instead in the replace alert, a favorite shown in Files — ends it with `endOpeningForReplaceRequest:`. A Dropbox search hit has no path to spin until its resolve.
- **The filter field narrows a listing by name** (`applyFilter`, the rows drawn are `_folders`/`_files` over `_allFolders`/`_allFiles`), installed once a listing has a dozen rows. **TRAP: it is always shown, never hidden on scroll.** A search bar that collapses re-lays the bar out on the appearance callbacks the card's expand and dismiss forward by hand, and the folder jumped under the card. `Stacked` under the bar: iOS 26's integrated placement would put it in the bottom toolbar, where the tab bar and the strip are.
- **Select is multi-select Add** — a glyph, since the word beside the other items truncated the folder's name, and "Select" rather than the system's "Edit", since nothing is edited. While selecting the title is the count, Select All takes the back button's place, and a listing or filter change is held (rows are selected by index). **TRAP: a row swipe sets `isEditing` too**; `isSelecting` excludes it through `_swipingRow`, or the bar flips into multi-select under the swipe.
- **The sort menu is titled "Sort folders by", the Settings row's own string**: it writes the one folder-open setting, not this folder's view (Settings › Files and Dropbox shows the same choice). It is absent from the add sheet, whose bar carries Close at every level instead.
- **A Dropbox directory draws from disk at once, then relists** (`DropboxMirror refreshDropboxFolder:`) when it appears, unless this screen listed it within the last minute (`kRelistInterval`, so going back and forth costs nothing). Pull to refresh relists any directory, Dropbox's from Dropbox. A relist that fails over rows already drawn says so in a footer; over none, in the empty state. An unlinked account pops the stack to the sources, and a sign-in started from the Connect row pushes the account's root when it lands.
- **The system pickers remain for two jobs only**: Add Folder… grants a location (`SearchFolderStore addFolderURL:`, which refuses a covered one with a word), and Browse Files… is a one-off multi-select pick from anywhere. A location is forgotten by the system's swipe Delete or the long press's Remove Location.
- **The bar's items follow the Playlist tab's absent-not-disabled rule**: no Select, play or sort in an empty folder.
- **The play button plays this folder alone, and its long press plays it with its subfolders** (`openDirectoryWithSubfolders`; Add with Subfolders in the sheet). A tap never recurses: at the root of a library it would make one playlist of everything. The walk goes depth first in the listing's order, one folder per turn, asking Dropbox for each mirror folder first, since the mirror holds only what something listed; it stops at about 2,000 songs or 500 folders and says so. The folders with songs are opened as ONE multi-URL open, so the first is the base and the rest are additions, each listed flat as any folder is — `FolderSession` learned nothing. In a folder with no song directly inside, a tap has nothing to play and the button is its menu alone.
- **Recents is `FolderSession`'s list**: every file and folder opened or added, newest first, at most 50 — **an open that brought more than five things is one entry, the folder they share** (Play with Subfolders on a library recorded each album and replaced the whole list in one tap) — recorded where the open lands with the bookmark the open minted and the display name of its folder (a restore records nothing; Clear Playlist keeps them). The name is recorded, not derived at draw time: the path can outlive the app container it names. `RecentsViewController`, in the browser's file, lists them: a file plays alone, a folder opens in the browser, and the long press adds Play, Play in Folder, Add to Playlist and Open Folder. The bar's Clear opens a one-item destructive menu, so a stray tap cannot empty the list; it is absent while the list is, and in the add sheet, where the bar carries Close.
- **An Add's rows fly into the Playlist tab** (`addedRowsHandler`, set by the shell on the root browser): an Add changes nothing on the Files tab's own screen, so the rows asked for are snapshotted and handed over before the request. `RootViewController` lifts them, flies them to the Playlist tab's item on `playback:didAppendTracksAtIndexes:`, and sets them back down when the settle says nothing landed — or when an open that superseded the Add lands empty or is cancelled (`playbackDidCancelOpening:`, a tapped spinner or the give-up timeout). No timer: every Add ends in `playback:didSettleAddLanding:`, and `check_consistency` reports rows lifted and never settled (`liftedRowTimes`). The flight is a UIKit keyframe animation, not a `CAAnimation`: an iPhone caps an app's own Core Animation at 60 Hz without an Info.plist opt-out, and it stuttered on a 120 Hz phone. `UITab` has no view, so the target is found by the label the bar draws. Not in the add sheet, which closes onto the playlist.
- **Open Folder** (Search and Recents) is `showDirectory:highlighting:` on the root browser: the stack becomes one screen per folder from the covering source, built before the tab switches so the tab arrives on the folder, with the file it came from scrolled to and selected for a moment once a listing holds it. A folder no persistent root covers — a one-off pick, reached from Recents — is listed under a scope the bottom screen of that stack holds for its lifetime (`_holdsScope`), since the session's hold goes with the playlist; an open made inside it takes the session's own hold from the recent's bookmark (`beginOpenURLs:`'s worker, beside the persisted base), so the playlist outlives the screen.

## LibraryViewController

The Playlist tab: number (replaced on the playing row by the shared `EqualizerIndicatorView`), artwork, title over artist, duration. **Selecting a row plays it and stays here**; expanding the card is the strip's job. A track change scrolls the list to the playing row, or, while hidden, leaves that for when it shows — **except under shuffle, where the list holds still**, since following a play order that jumps across it would yank the user's place on every track. Number and duration take the artist line's text style so the secondary columns scale together under Dynamic Type. The folder name goes on `navigationItem.title`, not `self.title`, which is also the tab's title.

**Equalizer activity is actual output plus material visibility** — this doc's half of the root guarantee. Output is `PlaybackController.audioOutputActive`: true through an outgoing fade, false for a Loading request. Visibility is this controller's presentation plus `willDisplayCell:`/`didEndDisplayingCell:` state, plus `RootViewController`'s tab and card exposure — explicit, because the card moves by transform over children that stay "appeared", and kept honest through interactive and interrupted transitions — plus the scene delegate's foreground-active bit. Only then does the playing row start its poller, declaring one `equalizerLevelsWanted:` consumer; stopping balances it. The gate is counted, not boolean, because cell reuse can briefly hold two consumers. Hidden track changes retain one pending scroll index and park there without animation on the next reveal.

**The gutter has three states in precedence: loading, playing, number** (`resolveGutter`). Loading is `CloudTransferRegistry.isTransferringURL:`, a transfer really running — a provider's or the Dropbox mirror's, the playing row's included, to the download's end; it outranks playing because there is no output audio yet. `PlaybackController` observes the same registry for the card's loading fill and the open deadline (`+PlayerEvents`), so the row and the card never read two monitors. `syncEqualizerActivityForCell:` folds `!loading` into both activity facts so a loading row holds no poller; a registry change re-syncs `visibleCells` in place, never a reload; `didEndDisplayingCell:` and `prepareForReuse` drop `loading`.

`dump_equalizer` is the runtime proof: `renderer.displayTicks` is bounded at 30/s while active and flat after an inactive transition settles. The meter reads the render's samples before `--silent` zeros them, so the bars are live under the debug scripts' default launch.

**The gear opens a menu, not Settings directly**: Settings, then **Clear Playlist** alone in a destructive inline group at the bottom — the construction the Favorites long-press menu uses, so the app's two menus read alike, and the platform's place for a destructive item. **No confirmation sheet**: nothing leaves the disk, and the playlist is rebuilt by reopening, which is how clearing a queue behaves elsewhere on the platform; the destructive styling carries the warning. Its accessibility label names the menu rather than either item, since the button does two things. A clear also **wipes the persisted bookmarks and the remembered track**, because restoring at the next launch what the user just cleared would be the opposite of what they asked for, and it **releases every scope** — each start balanced by exactly one stop — since nothing reads under them once the playlist is empty. **It also settles the launch waiters, last of all.** A clear during a launch restore supersedes that restore, so none of the delegate methods that would settle them fires, and `_launchOpenSettled` is a **latch**: miss it once and every later `performWhenLaunchOpenSettled:` parks too, all firing together against whatever playlist exists when some later open settles — which a widget transport intent presents as the app skipping a track for no reason. A clear is a settle, for the same reason a restore that found nothing is: there is nothing left to wait for. It goes at the END for the reason the chrome rebuild does — a waiter runs arbitrary work, a widget intent driving transport among it, and must not see a half-reset controller.

The bar carries **the gear, and the star when a folder is open** — absent, not disabled, for a single-file or empty playlist — and, on the **leading** side, **the plus that presents the Files tab's browser as an add sheet**. Leading rather than a third trailing item: three crowd the large title, and the split then reads as what it is — the trailing pair acts on the open folder, the plus acts on the playlist. Adding lives here, not in the Files tab, because a button inside a browser that opens a second browser does not read and because the playlist is what is being added to. **The plus follows the star's absent-not-disabled rule**: with an empty playlist there is nothing to add to, and the empty state's own Open button already owns that moment, so two roads to "find something to play" — the add sheet and the Files tab — never compete on one screen. Title and star both name `FolderSession`'s BASE folder, never an added one: an Add changes neither. `refreshChrome` rebuilds title, star and empty state together. The star fills when the bookmark lands, not on the tap (`Search/AGENTS.md`), and this screen also redraws on `VibeFavoritesDidChangeNotification`. The empty state's `UIContentUnavailableConfiguration` keeps its own Open action for the first run, and it **brings the Files tab forward rather than presenting the add sheet** — the app already has a surface whose job is finding something to play, it is ours (its rows carry Add to Playlist and Add to Vibe Favorites), and it leaves the user somewhere they can keep looking. **This screen knows nothing about tabs**: it calls an `openFilesHandler` the shell sets when it builds the tab, the same direction `equalizerSurfaceVisible` travels, so the library holds no reference back and `selectedTabIdentifier` stays debug-only surface.
