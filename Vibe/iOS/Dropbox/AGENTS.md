# Dropbox (iOS)

Dropbox through its HTTP API, not its Files provider: the provider lists a folder only once Dropbox has, so search and browsing came back empty or stalled. No SDK — six endpoints over `NSURLSession`, all Objective-C. The shell is `../AGENTS.md`. The mirror is a remote fetch backend (`System/AGENTS.md`). `VibeiOSAppDelegate` installs it at launch with `installAsRemoteBackend`, beside the Links store.

| File | Owns |
| --- | --- |
| `DropboxClient` | the account: PKCE sign-in in `ASWebAuthenticationSession`, the refresh token in the Keychain, the access token in memory; the JSON call. It subclasses `HTTPTransferClient` (`System/Remote/AGENTS.md`), which runs the streamed download and the ranged read. This class makes their requests and reads Dropbox's answers. The call and both transfers share one failure ladder (`handleFailureStatus:…`: an expired token refreshes once, any other 401 unlinks, a throttle waits and resends) |
| `DropboxMirror` | the account as local files: listing reconciliation, the sidecars, search, and the path mapping. It subclasses `RemotePlaceholderStore` (`System/Remote/AGENTS.md`), which owns the placeholders, the directory index's storage, the fetch that streams, the ranged read, and the download budget. This class names each placeholder's Dropbox `id` and reads Dropbox's answers |
| `DropboxRules.h` | the decisions with no network or disk: PKCE, the wire encodings, entry reading, the version check, the index key. Tested |

Both classes are Foundation-only and compiled into the macOS `VibeTests`, which drive them over a stubbed `NSURLProtocol` and a temp root (`DropboxMirrorTests`). The tail read and the ranged read go through `-[HTTPTransferClient readTarget:…]`. The tests observe it on `DropboxClient`.

## The account

**The app key is `VibeDropboxAppKey` in the generated Info.plist** (`project.yml`), and it is not a secret: PKCE needs none, and the `db-<key>://2/token` redirect is a scheme Dropbox grants every app without registration, so neither the App Console nor Info.plist names it. Scopes: `account_info.read files.metadata.read files.content.read`. The account must be a **Full Dropbox** app; an App folder one sees nothing.

**The App Console app is in development status, not production** (as of October 2026). Dropbox takes a production request only once an app has 50 linked users, so production approval is a Dropbox-side gate and never a release blocker; development status links users up to that count. When linked users approach 50, apply in the App Console.

**The refresh token is one Keychain item, `AfterFirstUnlockThisDeviceOnly`**: a refresh must work under the lock screen while background playback downloads the next track, and a restored backup on another phone signs in again. Before first unlock the item reads as no account — which is why nothing is deleted at launch, only on a real account change.

**TRAP: before first unlock the item reads as locked (`errSecInteractionNotAllowed`), not absent.** The client remembers that and reads again at the next use — `isLinked`, `accountID`, any call — at most once every five seconds, posting the account change when it lands, so a launch before unlock does not run the session signed out.

**TRAP: the default simulator build cannot reach the Keychain.** It is unsigned, so every `SecItem` call answers `-34018` (`errSecMissingEntitlement`): the sign-in works for the session, the refresh token is never saved, and the next launch is signed out. Build with `VIBE_SIGN_SIM=1` to test anything across a relaunch (the vibe-debug skill). A device build is always signed.

**A scope the app lacks answers 400 with plain text, not JSON**, naming the scope; the client logs that body, and a sign-in logs the scopes it was granted. A scope enabled in the App Console reaches only grants made after it — sign in again.

**One refresh is in flight at a time** — the refresh claim: every caller arriving during it is a waiter on that one. `_accountGeneration` moves on every sign-in and sign-out. A refresh or a 401 that belongs to the previous account can then neither restore nor unlink the current one. A Keychain save checks its generation and writes under one Keychain lock that a delete also takes. A sign-out between a save's delete and add left the signed-out account linked at the next launch. A late answer to the account-name call cannot stamp its name and ID on the next account (`refreshAccountNameWithCompletion:`), and the mirror's directory is the ID. A 401 `expired_access_token` refreshes once and retries; any other 401, and a refresh answered 400 (`invalid_grant`: revoked on dropbox.com), unlinks. Unlinking posts `VibeDropboxAccountDidChangeNotification`, on which the mirror prunes every other account's directory and `PlaybackController` clears a playlist reaching into the mirror — whole, as Clear Playlist does, never a row edit. **A cancel settles a transfer at once when no task is in flight for it**, such as one waiting on the refresh. It does not wait for the refresh to come back. That rule and its lock are the base's (`System/Remote/AGENTS.md`). Signing out revokes with a live access token, refreshing an expired one first, so the grant ends on Dropbox's side and not only here.

**The launch warms the account once** (`warmUp`, off main): with an account it refreshes the access token, which lives in memory so a launch's first request always refreshes, and sends each session one `files/download` naming no file, refused at once, for the connection to `content.dropboxapi.com` (a session's connections are its own, and the download and its tail ride different ones). Three small requests a launch; it takes the refresh and two TLS handshakes off the first play (first play after launch measured readable at 1.65 s against 0.9–1.6 s for later ones). Never on a foreground, and nothing before first unlock, when the Keychain reads as no account; a play minutes later finds the connections closed but the token fresh.

## The mirror

`Library/Application Support/Dropbox/<account id>/`, excluded from backup and outside Documents, so the Files app never shows it. **Lazy: a Dropbox folder exists here only once something listed it** — the browser on every visit, a search hit's parent before it opens, and an open itself for a folder nothing has listed yet (`FolderSession.listFromDropboxIfMirrored:`, which asks `hasListedDirectory:`: a folder its parent's listing made carries only its path in its index, one listed itself carries its files). **TRAP: a directory a reconcile deletes takes the cached indexes with it** (`reconcileDirectory:`): kept, a folder that leaves Dropbox and comes back is made empty, its unchanged index skips the xattr write, and it still reads as listed, so its open skips the listing and plays nothing. There is no full sync and no index of the account; search is Dropbox's. **A folder made on the way to a search hit takes the hit's `path_display`**, never `path_lower`, or the browser and the playlist title name it in lowercase.

- **A placeholder is a sparse file of the remote size and `server_modified` with no permissions.** How it is written and installed is the store's (`System/Remote/AGENTS.md`). **Size plus mtime is the version**: Dropbox moves `server_modified` on every upload, and downloaded bytes take the mtime from their own response's `Dropbox-API-Result`, so the next listing sees them as current. A version that differs goes back to a placeholder; a departed entry is deleted.
- **Only playable audio and playlist files (`.cue`, `.m3u`, `.m3u8`) are mirrored**, and the playlists are downloaded with the listing, side by side and off the disk queue, since `rowsForWalk:` reads a sheet while the folder opens and a tap on an M3U reads it at once. **TRAP: one download per sheet** (`_sidecarWaiters`, the claim): two refreshes of one folder — the browser's and a search hit's, or an open's — both find the sheet missing, two downloads share its part file, and the first to finish would rename the other's half-written bytes into place; a refresh that finds the sheet claimed waits on that download.
- **TRAP: a name read back from disk is never sent as a Dropbox path.** A file URL's path comes back decomposed (NFD) whatever was written, while Dropbox keeps names as uploaded, usually composed, so a derived path misses every accented file. Each directory's index (the store's xattr, `System/Remote/AGENTS.md`) holds its own Dropbox path and each file's Dropbox `id`, keyed by `VibeDropboxIndexKey`. A download goes by `id:…`, which also survives a rename (`remoteTargetForURL:error:`). A relisting goes by the directory's recorded path.
- **TRAP: only the last component of a `path_display` is guaranteed its case**, so a component is matched case-insensitively against what is on disk (`VibeDropboxLocalName`) before one is made: two spellings of one folder land in one directory.
- **The fetch streams into a hidden part file**, and the progress poll reads the transfer's own written count. A Dropbox row's loading bar is then a real percentage, which the provider never gave on iOS. The fetch, its stream, and its tail window are the store's (`System/Remote/AGENTS.md`).
- **The part file's rules are `HTTPTransferClient`'s** (`System/Remote/AGENTS.md`): made once, only appended to, resent from its last byte, pinned to its first response's version, and kept when the link ended the transfer. For Dropbox the version is the `Dropbox-API-Result` `rev`, and the size is that header's `size`. A download goes by `id`, which answers whatever version is current, so the pin is what stops two revs splicing into one file. A mismatch fails the transfer with `VibeDropboxErrorFileChanged`. `keepsPartAfterError:` keeps the part for a cancel, which is how a stall lets a stream go, and for a connection lost past the resend bound. The stale sweep takes a kept part after a day. A length other than `size` fails with `VibeDropboxErrorAPI`. **TRAP: the stale-part sweep goes by ctime, never mtime**: the install dates a finished part to its version just before the rename, and a relisting between the two would delete it.
- **A Dropbox stream's tail is read by id, like its download.** A read by id answers whatever rev is current, which is why the store installs the window only when both answers name the same rev (`System/Remote/AGENTS.md`). The tail read starts at the same moment as the download, not after the first response's rev. On a device that brought it 1.0–2.4 s earlier. An MP3 (whose open checks its last 128 bytes), an M4A with its `moov` last, a FLAC with no length, and an AIFF or a WAV with a tag after its audio then open from the head. The AIFF's or the WAV's open reads the header of that tag's chunk. A longer index-last M4A, or a tag larger than its window, waits for its download.
- **Tags are read by range, never by download.** The rule and a streaming file's shortcut are the store's (`System/Remote/AGENTS.md`). The metadata scan parses a placeholder through TagLib reading `files/download` with a `Range` header. That is about three requests and 230–360 KB per file with its artwork, measured on a 954-track folder. Reading a playing file from its stream saves two requests a play, and the tags come no later. Only playing, and the prefetch of what plays next, downloads a whole file — and the scan's read of a format TagLib cannot parse (`PlayableExtensions.tagParsed` excludes w64 and caf), whose CoreAudio facts need the whole file. A row that lost its art rendition reads it by the same rule (`NSURLUtil readsRemotePlaceholderByRange:`), waiting out the user's open as the scan does. One known gap: a FLAC whose STREAMINFO carries no length parses with no duration, since the fallback that measures it opens the file.
- **Past the download budget the oldest downloads go back to placeholders** (the store's eviction, `System/Remote/AGENTS.md`). The budget counts the linked account's directory. The budget is the user's choice, Settings › Files' Maximum Size (`kVibeDropboxDownloadBudgets`, `DropboxRules.h`: 1 to 50 GB, 10 GB by default). Settings saves it under the iOS-owned `VibeDropboxDownloadBudgetKey`, which the shared mirror starts from, then sets `downloadBudget`, which only applies: a smaller one applies at once rather than at the next download, and posts the new total as a download's landing does. Size and mtime are kept, so the cached tags and waveform still match when it comes back, and the card draws an evicted track's cached waveform while it is parked (`Player/AGENTS.md`). A player still reading an evicted file keeps its open descriptor. Settings › Files' Remove Downloads does the same to all of them.

**The simulator needs no account**: `set_fake_dropbox <directory>` (`Debug/VibeFakeDropbox`) puts that directory under the client as the account, over the HTTP boundary the tests stub too. Every case this doc's traps describe is a scripted tree there, and `fake_dropbox_fault` scripts the streaming ones — a dropped connection's resend, a changed rev, a throttle, an expired token, a failed or slow tail read, a stall, a server's first-byte latency — which `vibe-debug`'s `dropbox-streaming.sh` runs as scenarios.

Opens are the shell's ordinary roads: a mirror directory is an app-container URL with no security scope, which `FolderSession` treats as a root every open covers, so a file opened alone becomes its folder with it selected, bookmarks persist, and a relaunch restores from the placeholders offline. `dump_dropbox` reads the account and which playlist tracks are placeholders; the sign-in itself is Dropbox's web sheet, which only a human fills.
