# Dropbox (iOS)

Dropbox through its HTTP API, not its Files provider: the provider lists a folder only once Dropbox has, so search and browsing came back empty or stalled. No SDK — six endpoints over `NSURLSession`, all Objective-C. The shell is `../AGENTS.md`; the materialization backend it plugs into is `System/AGENTS.md`'s remote fetch.

| File | Owns |
| --- | --- |
| `DropboxClient` | the account: PKCE sign-in in `ASWebAuthenticationSession`, the refresh token in the Keychain, the access token in memory; the JSON call, the ranged read and the streamed download, which share one failure ladder (`handleFailureStatus:…`: an expired token refreshes once, any other 401 unlinks, a throttle waits and resends). Downloads stream on a delegate session of their own, so calls and tag reads never queue behind a download's disk writes |
| `DropboxMirror` | the account as local files: listing reconciliation, placeholders, the fetch, search, the download budget |
| `DropboxRules.h` | the decisions with no network or disk: PKCE, the wire encodings, entry reading, the version check, the index key. Tested |

Both classes are Foundation-only and compiled into the macOS `VibeTests`, which drive them over a stubbed `NSURLProtocol` and a temp root (`DropboxMirrorTests`).

## The account

**The app key is `VibeDropboxAppKey` in the generated Info.plist** (`project.yml`), and it is not a secret: PKCE needs none, and the `db-<key>://2/token` redirect is a scheme Dropbox grants every app without registration, so neither the App Console nor Info.plist names it. Scopes: `account_info.read files.metadata.read files.content.read`. The account must be a **Full Dropbox** app; an App folder one sees nothing.

**The refresh token is one Keychain item, `AfterFirstUnlockThisDeviceOnly`**: a refresh must work under the lock screen while background playback downloads the next track, and a restored backup on another phone signs in again. Before first unlock the item reads as no account — which is why nothing is deleted at launch, only on a real account change.

**TRAP: before first unlock the item reads as locked (`errSecInteractionNotAllowed`), not absent.** The client remembers that and reads again at the next use — `isLinked`, `accountID`, any call — at most once every five seconds, posting the account change when it lands, so a launch before unlock does not run the session signed out.

**TRAP: the default simulator build cannot reach the Keychain.** It is unsigned, so every `SecItem` call answers `-34018` (`errSecMissingEntitlement`): the sign-in works for the session, the refresh token is never saved, and the next launch is signed out. Build with `VIBE_SIGN_SIM=1` to test anything across a relaunch (the vibe-debug skill). A device build is always signed.

**A scope the app lacks answers 400 with plain text, not JSON**, naming the scope; the client logs that body, and a sign-in logs the scopes it was granted. A scope enabled in the App Console reaches only grants made after it — sign in again.

**One refresh is in flight at a time** — the refresh claim: every caller arriving during it is a waiter on that one. `_accountGeneration` moves on every sign-in and sign-out, so a refresh or a 401 that belongs to the previous account can neither restore nor unlink the current one, and a late answer to the account-name call cannot stamp its name and ID on the next account (`refreshAccountNameWithCompletion:`; the mirror's directory is the ID). A 401 `expired_access_token` refreshes once and retries; any other 401, and a refresh answered 400 (`invalid_grant`: revoked on dropbox.com), unlinks. Unlinking posts `VibeDropboxAccountDidChangeNotification`, on which the mirror prunes every other account's directory and `PlaybackController` clears a playlist reaching into the mirror — whole, as Clear Playlist does, never a row edit. **A cancel settles a transfer at once when no task is in flight for it** — one waiting on the refresh, or on a retry's delay — never when the refresh comes back (`cancelTransfer:`), so the lane the caller holds is freed now (`System/AGENTS.md`). Signing out revokes with a live access token, refreshing an expired one first, so the grant ends on Dropbox's side and not only here.

**The launch warms the account once** (`warmUp`, off main): with an account it refreshes the access token, which lives in memory so a launch's first request always refreshes, and sends each session one `files/download` naming no file, refused at once, for the connection to `content.dropboxapi.com` (a session's connections are its own, and the download and its tail ride different ones). Three small requests a launch; it takes the refresh and two TLS handshakes off the first play (first play after launch measured readable at 1.65 s against 0.9–1.6 s for later ones). Never on a foreground, and nothing before first unlock, when the Keychain reads as no account; a play minutes later finds the connections closed but the token fresh.

## The mirror

`Library/Application Support/Dropbox/<account id>/`, excluded from backup and outside Documents, so the Files app never shows it. **Lazy: a Dropbox folder exists here only once something listed it** — the browser on every visit, a search hit's parent before it opens, and an open itself for a folder nothing has listed yet (`FolderSession.listFromDropboxIfMirrored:`, which asks `hasListedDirectory:`: a folder its parent's listing made carries only its path in its index, one listed itself carries its files). There is no full sync and no index of the account; search is Dropbox's. **A folder made on the way to a search hit takes the hit's `path_display`**, never `path_lower`, or the browser and the playlist title name it in lowercase.

- **A placeholder is a sparse file of the remote size and `server_modified` with no permissions** (`NSURLUtil`'s remote placeholder): the real stat, and a direct open fails rather than reading zeros. It is written whole and renamed into place, as are downloaded bytes, so no reader ever sees one half made. **Size plus mtime is the version**: Dropbox moves `server_modified` on every upload, and downloaded bytes take the mtime from their own response's `Dropbox-API-Result`, so the next listing sees them as current. A version that differs goes back to a placeholder; a departed entry is deleted.
- **Only playable audio and `.cue` sheets are mirrored**, and the sheets are downloaded with the listing, side by side and off the disk queue, since `rowsForWalk:` reads them while the folder opens. **TRAP: one download per sheet** (`_sidecarWaiters`, the claim): two refreshes of one folder — the browser's and a search hit's, or an open's — both find the sheet missing, two downloads share its part file, and the first to finish would rename the other's half-written bytes into place; a refresh that finds the sheet claimed waits on that download.
- **TRAP: a name read back from disk is never sent as a Dropbox path.** A file URL's path comes back decomposed (NFD) whatever was written, while Dropbox keeps names as uploaded, usually composed, so a derived path misses every accented file. Each directory carries an xattr index — its own Dropbox path and each file's Dropbox `id`, keyed by `VibeDropboxIndexKey` — on the directory, because a placeholder's attributes are as unreadable as its bytes. A download goes by `id:…`, which also survives a rename; a relisting goes by the directory's recorded path. The mirror caches parsed indexes in memory, since a ranged read asks for one per block, and rewrites one only when it changed.
- **TRAP: only the last component of a `path_display` is guaranteed its case**, so a component is matched case-insensitively against what is on disk (`VibeDropboxLocalName`) before one is made: two spellings of one folder land in one directory.
- **The fetch streams into a hidden part file** (`NSURLUtil remotePlaceholderPartURL:`), and the progress poll reads the transfer's own written count (below), so a Dropbox row's loading bar is a real percentage — what the provider never gave on iOS.
- **A part file is made once per transfer, at its first accepted response, and only ever appended to**, so a descriptor opened on it keeps seeing one inode grow. A resend — the failure ladder's refresh or throttle, or a dropped connection, at most two in a row with no byte between — asks for `Range: bytes=<written>-` and appends; a 200 to that is the whole file, its prefix skipped. **TRAP: a download by `id` answers whatever version is current**, so every response's `Dropbox-API-Result` `rev` must equal the first one's, and a first one with none is never resumed: a mismatch fails the transfer with `VibeDropboxErrorFileChanged` and deletes the part. A cancel deletes it too; nothing resumes across launches. **The first response's metadata `size` is the file's length**: a transfer dropped after its last byte is complete rather than resent (`bytes=<size>-` would answer 416), and one ending at any other length fails and deletes the part. **TRAP: the stale-part sweep goes by ctime, never mtime**: the install dates a finished part to its version just before the rename, and a relisting between the two would delete it.
- **A fetch publishes its part file while it writes it** (`availabilityForURL:`, installed as `CloudFileMaterializer`'s streaming lookup, `System/AGENTS.md`): a `CloudFileAvailability` per transfer, keyed by the file's comparable path, made at the first accepted response with that response's size — the version being downloaded, which a re-upload since the listing makes differ from the placeholder's — and kept across every resend. The client's progress callback notes each write after it lands; a response naming no size streams nothing and downloads whole. The fetch's `onReadable` fires once, past `kStreamReadableBytes` (256 KB, an anti-stutter knob: reads wait regardless) and short of the size, so a file that completes first never fires it. **A stream also reads its tail once, beside the download** (`readTailOfPath:…`, sized by `VibeDropboxTailWindowBytes`: 128 KB for every head-and-trailer format, an MP4's a 32nd of the file between 512 KB and 1.5 MB, a two-hour mix's `moov` with headroom, and none for a file at most twice its window): the client's ranged read on the call session, by the same id as the download and at the same moment, so it lands about when the head does instead of a first byte after it (1.0–2.4 s later on a device, when it waited for the first response's rev). It is installed as the availability's tail window, from which the handle reads past the download's edge, so an MP3 (whose open checks its last 128 bytes), an M4A with its `moov` last and a FLAC with no length open from the head; a longer index-last M4A waits for its download. **TRAP: a read by id answers whatever version is current**, so the window is installed only by whichever answer lands second, and only when the ranged answer's `Dropbox-API-Result` names the download's rev and the download's size is the listing's its offset came from; a rev missing on either side drops it (`installTail:…`). Readable does not wait for it. A failed or dropped tail logs one line and leaves the window absent (reads there wait for the download, as before), never the transfer's failure; the finish cancels one still running. Dropped when the download reaches it or finishes. **TRAP: finished after the install, forgotten after the finish**: a reader whose part open missed the rename waits for the finish and then opens the URL, and a failure, whose part the client has already deleted, reaches that same wait as the failure rather than a missing file. The fetch still blocks until complete, and the coordinator opens the handles on readable meanwhile (`Audio/Loading/AGENTS.md`); its cancel, run when nothing reads the stream any more, deletes the part as any cancel does.
- **Tags are read by range, never by download** (`readPlaceholderAtURL:…`, installed as `CloudFileMaterializer.remoteRead`): the metadata scan parses a placeholder through TagLib reading `files/download` with a `Range` header, about three requests and 230–360 KB per file with its artwork, measured on a 954-track folder. **A file streaming now is read from its stream instead** (`streamedBytesOfURL:…`): the playing track's parse starts at the tap, beside the download, so a range in its first MB or its tail window waits up to 3 s for the stream to hold it, and any other range takes the part file's prefix below the bytes noted and asks Dropbox only for the rest: two requests a play fewer, the tags no later. A read past 30 s is given up and the parse fails, to be retried by a later scan. Only playing, and the prefetch of what plays next, downloads a whole file — and the scan's read of a format TagLib cannot parse (`PlayableExtensions.tagParsed` excludes w64 and caf), whose CoreAudio facts need the whole file. A row that lost its art rendition reads it by the same rule (`NSURLUtil readsRemotePlaceholderByRange:`), waiting out the user's open as the scan does. One known gap: a FLAC whose STREAMINFO carries no length parses with no duration, since the fallback that measures it opens the file.
- **Past a 10 GB download budget the oldest downloads go back to placeholders**, oldest first by download time, never the file just fetched. Size and mtime are kept, so the cached tags and waveform still match when it comes back, and the card draws an evicted track's cached waveform while it is parked (`Player/AGENTS.md`). A player still reading an evicted file keeps its open descriptor. Settings › Files' Remove Downloads does the same to all of them.

**The simulator needs no account**: `set_fake_dropbox <directory>` (`Debug/VibeFakeDropbox`) puts that directory under the client as the account, over the HTTP boundary the tests stub too. Every case this doc's traps describe is a scripted tree there, and `fake_dropbox_fault` scripts the streaming ones — a dropped connection's resend, a changed rev, a throttle, an expired token, a failed or slow tail read, a stall, a server's first-byte latency — which `vibe-debug`'s `dropbox-streaming.sh` runs as scenarios.

Opens are the shell's ordinary roads: a mirror directory is an app-container URL with no security scope, which `FolderSession` treats as a root every open covers, so a file opened alone becomes its folder with it selected, bookmarks persist, and a relaunch restores from the placeholders offline. `dump_dropbox` reads the account and which playlist tracks are placeholders; the sign-in itself is Dropbox's web sheet, which only a human fills.
