# Settings window

- `Settings/` holds the Settings window (Vibe > Settings…, ⌘,): `SettingsWindowController`, a toolbar-style `NSTabViewController` in the standard macOS settings-window shape, created lazily by `AppDelegate` and kept alive across closes. ⌘W closes it: File > Close is nil-targeted, and the window controller's own `closeFile:` catches it ahead of the player's.
- **The window title is the title-propagation chain, never set directly**: each pane's `NSViewController.title` names its tab AND, through the tab controller's selected-child propagation and the window's contentViewController title binding, the window. A manually set window title loses to that chain — the propagation clears it to nil on every tab switch.
- One pane per `SettingsPaneViewController` subclass, one file each, on the shared scaffolding in the base class: the pane size (width/height constraints AND `preferredContentSize`; a bare frame yields an arbitrary window size — and the design size is a *minimum*, grown to the form grid's fitting size so a long localization widens the pane instead of clipping) and the top-centered two-column form grid. Panes reload control state in `refreshFromSettings`, which the base runs on every appearance, whenever the window regains key (a system panel returned), and after any menu-bar tracking ends (a menu changed a mirrored setting while the pane stayed visible). The window is deliberately not resizable.
- **The tab-switch resize is animated by exactly one path**, `SettingsTabViewController`'s `didSelectTabViewItem:`, at the app's fixed `kWindowResizeAnimationDuration` through `[window animator] setFrame:` in an explicit `NSAnimationContext` — NOT `setFrame:display:animate:`, whose legacy blocking stepper consumes its duration here without rendering a single intermediate frame. Two AppKit mechanisms each snap the window to the incoming pane's size before the animation can run — turning it into a no-op — and both are disarmed: the panes' size constraints sit at 999, just below required (a required size forces the window there in one layout pass, while at 999 they still define the fitting size and stretch during the animation), and the tab controller swallows `setPreferredContentSize:` (AppKit resizes a window immediately when its `contentViewController`'s preferredContentSize changes). Because nothing else corrects the size anymore, the window controller re-asserts the selected pane's size after the frame autosave restores — the autosaved frame carries a possibly different pane's size.
- Tab titles reuse menu strings where the word is the same (Playback, Appearance, Convert); settings-only strings live in the `settings.*` key family. Each tab item also carries a **stable, unlocalized identifier** (`general`, `playback`, …), which is what the debug channel's `settings_open` selects by.
- **Test this window through the debug channel's settings verbs, never through mouse or key injection**, which post into the main player window: `settings_open`, `dump_settings_ui`, `settings_click` and `settings_close`, implemented in `Debug/DebugSettingsUI.m` and documented in the `vibe-debug` skill. They address a control by the row label or title the pane displays, because the panes are built in code with no view identifiers. Anything a pane gains — a control kind the walker does not know, a name two controls now share — shows up there first, so re-run `dump_settings_ui` after changing a pane's layout.

## Panes

- **General**: the Output popup — mirrors the menu bar's Output menu (same layout, checkmark rule and change action) by using its own `OutputDevicesMenuController` instance as the popup menu's delegate and builder; the controller's device observation refreshes it while open, the pane's own observation plus appear/key refreshes cover it closed — and the default-player button. `DefaultAppRegistration` (here; the type list is `DocumentTypes` in `Common/`) claims every declared audio type one at a time, because each request can raise its own system confirmation panel and a refusal stops the walk. No alert of our own: the system's panel is the whole conversation, and the button reports the result — disabled "Vibe Is the Default Music Player" once it holds them all, refreshed when the window regains key after the system panel. The folder declaration is excluded on purpose: Vibe must never become the default folder handler. The Always-on-top checkbox is `AppSettings.alwaysOnTop`, the same setting as View > Always on Top; the pane writes it and calls `MainPlayerController.applyAlwaysOnTop`, the one place that pushes it to window levels — the player's, and through `AppDelegate.applyAuxiliaryWindowLevels` the About and Settings windows', which must ride at the player's level or the floating player would bury them.
- **Playback**: pitch range (the menu funnels through the same `applyPitchRange`; `AppSettings` is the one place that normalizes — a persisted value that is not exactly 16 reads as 8, so a hand-edited plist cannot reach the fader's divisor), the skip-step presets (`AppSettings.skipBaseBars`: base/2×/4× bars), the crossfade length (`AppSettings.crossfadeMilliseconds`, pushed live to `AudioPlayer.crossfadeMilliseconds`; see `Audio/CLAUDE.md`), the audio-FX toggle (`AppSettings.audioFXEnabled`, default on — off keeps the FX graph segment out of the engine entirely; read once at player init, so the caption under the checkbox says it lands on relaunch; see `Audio/CLAUDE.md`), and the BPM- and key-analysis toggles (`AppSettings.analyzeBPM`, default on, and `.analyzeKey`, default **off** — see `Audio/Analysis/CLAUDE.md` — both read by the waveform loader). How a key is *written* is Appearance's business, not this pane's: this one only decides whether it is detected.
- **Appearance**: appearance (writes the setting, then `setAppearance:` with a non-menu sender applies without rewriting), waveform style (identifiers ride `representedObject`, localized names display-only — the registry re-exposed through `MainPlayerController+Menus`), the Show file info checkbox (`AppSettings.showFileInfo`, default on — off hides the header's codec and BPM/key readouts; the same setting as View > Show File Info, pushed live through `refreshFileInfoDisplay`), the time-display mode (`showRemainingTime` + `refreshTimeDisplay`, the discoverable form of clicking the right time label), and the two key-label choices: notation (`AppSettings.keyNotation`, Camelot or musical, identifiers on `representedObject` like the waveform styles) and `keyColorsEnabled` (default off, the CDJ-style coloring). Both push live through `refreshKeyDisplay`, and both govern *every* key shown including a tagged one, since a tag is parsed to a `VibeMusicalKey` when read and never displayed as written.
- **Convert**: where Convert to FLAC writes (`AppSettings.convertAsksWhereToSave` — the converter skips its silent placement rungs and goes straight to the save panel) and Delete Original After Convert, the same setting as the Convert menu's checkmarked item.
- **Files**: two things a folder grant ties together. First `AppSettings.useFolderArt` (default on), the Album art dropdown at the top — "Load from file only" against "File first, then search folder", the two carrying stable identifiers (`file_only`, `file_then_folder`) on `representedObject` so the choice can be made without touching localized text: a song with no artwork of its own shows a cover image beside it in its folder (`Audio/Metadata/CLAUDE.md`); the pane writes the setting and **must** then call `MainPlayerController.refreshFolderArt` — not merely to redraw: the resolver caches that setting, since it gates every accessor on every cell draw, and that call is the one thing that drops the cache, so a write without it is not observed at all. It is cheap, because nothing per track holds a cover: it drops the decoded images and redraws, and only the folders still on screen are decoded again. What the resolver has *settled* survives, deliberately — the setting decides whether the fallback is consulted, never what a folder holds, and forgetting would demote every walked folder to the lone-file stat probes and their three names. A *grant* change re-resolves too, but only the folders `FolderArtResolver` had declined for want of a grant (`invalidateDirectoriesSettledWithoutGrant` — a grant can unlock a folder but never change a cover already found; see `Audio/Metadata/CLAUDE.md`), and through that controller's own observation of `FolderAccessManagerDidChangeNotification`, not the pane's: the grant that changes that usually arrives from a drop or an open, with this pane never opened. The pane is one two-column form like every other, both rows through the base's grid: the Album art popup against its label, and the whole permissions block — the wrapping secondary-label explain line, the only one in the window, then the folder list and its buttons — stacked in the right column against a "Permissions:" label. The list keeps its fixed width there, which makes this the widest pane in the window rather than the one with the narrowest list. Then the granted-folder list over `FolderAccessManager` (here): every folder the user opens, drags onto the app, or adds through the pane's Add Folder panel is stored as an app-scoped security bookmark (`com.apple.security.files.bookmarks.app-scope` in `Vibe.entitlements`) and re-opened on the next launch, so a grant survives relaunch. Stored rows remain visible immediately, but do not authorize background reads until bookmark restoration has started the security scope. A playlist file is the one open that has to *ask*: opening a .cue/.m3u grants that file alone, not the audio it names, so an unreadable entry raises `requestAccessForPlaylistFolder:` — the same picker and bookmark as Add Folder, serialized on its own gate because powerbox prompts must not stack, and blocking the expansion worker that called it. It lives here, with the other grants, rather than in `NSURLUtil`, which only detects that a grant is needed and reaches this through the handler `AppDelegate` installs at launch: `Vibe/Util` is in the future-shared, no-AppKit source group, and a modal panel in a path utility inverts that. The auto-add hook lives at the single open funnel — `AppDelegate.openURLsWithRestoredAccess:token:`, which every open reaches, the window drop included — and bookmarks only directories, skipping anything under an active grant or under ~/Music, which the `com.apple.security.assets.music.read-write` entitlement covers standing. Restore resolves bookmarks off the main thread (an unreachable mount can block), merges active scopes on main, and holds only opens covered by a still-restoring remembered folder until that specific scope settles; a failed resolve keeps its inactive row so it can be removed. **The row says so, and it costs no I/O to know it**: `grantedFolders` answers `VibeGrantedFolderState` per row — active, restoring, or unavailable — from the resolve the manager already did, and the pane dims an unavailable one and appends "(Unavailable)". Never stat a row to decide that. `viewForTableColumn:` runs on the main thread for every reload, and a dead path's mount can block a stat for an automounter timeout, which is the same reason the icon is the generic one and the drag validation asks the pasteboard. The cost is that a folder deleted *while the app runs* still reads as active, its scope started on an inode nothing can reach; the next launch settles it. Restoration therefore posts its change notification **coalesced to one per run-loop turn**, because it settles one bookmark at a time and each observer does real work — the player invalidates folder art — while the user-driven add and remove post directly, so the pane redraws in the same turn as the click. An unavailable row is also excluded from Add Common Folder's "(Already accessible)" test: it is exactly the folder worth offering to add again. **Every wait for a grant is deadlined at the same two seconds** — the launch drain's and each open's alike. Waiting is an optimization: proceeding without the grant merely risks an unreadable folder, which every open path handles, while waiting forever on a mount that never answers leaves the window in its launch grace with a blank header and no way out. The coverage check that decides whether an open must wait is deliberately case-*insensitive* (`FolderAccessRules.h`), the opposite of `noteOpenedURLs:`'s: these URLs come straight off Launch Services rather than canonicalized, and over-matching only costs a wait that was not needed. The list is multiple-selection, so Remove takes a batch, and Edit > Select All (nil-targeted, `Menu/CLAUDE.md`) reaches it through the responder chain once a row has been clicked. Folders can also be dragged straight onto the list, which is the same `noteOpenedURLs:` funnel — the drag carries the grant the bookmark is made from, and coverage and ~/Music are skipped there as always. What counts as a folder is asked of the *pasteboard*, not the file system (`NSPasteboardURLReadingContentsConformToTypesKey` against `public.folder`): validation runs on the main thread for every mouse move of the drag, and a stat can block on an unreachable mount. A package is a directory but not a `public.folder`, so an app bundle is refused during the drag rather than silently discarded after it, and the drop retargets onto the list as a whole (`setDropRow:-1`) because the rows are in the order grants were added and an insertion point would promise something the store cannot honor. Add Common Folder is a pull-down over the same panel, staged on the home folder, Documents, iCloud Drive or Dropbox with nothing selected, since the sandbox grants nothing the user has not picked: confirming returns the displayed folder. **The real home comes from `getpwuid`** — inside the sandbox `NSHomeDirectory` *and* `NSHomeDirectoryForUser` both answer with the container, which silently made every candidate a path under `…/Containers/…/Data`. The button always opens; each item carries its own state instead, disabled and suffixed "(Not found)" when the folder is not on disk or "(Already accessible)" when a grant already covers it, so the menu says why rather than going quietly dead. **The not-found answers are probed off the main thread**, generation-guarded, and the menu is drawn from what is known now and redrawn when they land: two of the four candidates are file-provider roots — iCloud Drive, and Dropbox under CloudStorage — where a stat blocks for as long as the provider takes, which is the same reason `grantedFolders` costs no I/O. An unprobed path counts as present, so the classic Dropbox location is the one offered until the probe says otherwise. Dropbox is offered at `~/Dropbox`, falling back to `~/Library/CloudStorage/Dropbox` where the file-provider install left no symlink. The pane uses the generic folder content-type icon, so displaying a dead remembered path never asks the mount for a path-specific icon, and refreshes from `FolderAccessManagerDidChangeNotification` on top of the base's refresh contract. Persistence is the manager's own `VibeGrantedFolders` defaults key — bookmark blobs, not settings, so deliberately not `AppSettings`.
- **Advanced**: the Playhead refresh popup (`AppSettings.uiUpdateHzCap`: 3, 30 or 60 Hz, snapped to `kVibeUIUpdateHzCapPresets` on read like the Playback pane's ladders), which caps the playback-UI tick rate that `MainPlayerController` scales to the playhead's on-screen speed — see `MainWindow/CLAUDE.md`; the pane writes it and calls `syncUITimerRate`, the public live-apply hook, since only a track start or a resize would otherwise recompute it. Only a short file can reach the cap, so raising it costs nothing on ordinary songs and 3 Hz is the fixed rate the app ticked at before the rule existed. Then the cache-size readout (both stores summed through each cache's `diskUsageWithCompletion:`, generation-guarded against a stale reply landing after a clear), the Clear Cache button (the same two `invalidateWithCompletion:` calls as the debug channel's `clear_caches`), and the lifetime `AppStats` readouts, with listening time spelled through `Formatters.spelledDurationString:`.

## Driving this window from the debug channel

Verifying a change here against the running app goes through the **`vibe-debug` skill**'s command channel, which covers launching, the reply contract and every other verb. This window needs four of its own, documented here rather than there because they are useless anywhere else.

**Never drive this window with `click`, `drag` or the `key*` verbs.** They all post into the *main player window's* event stream, so at best they miss and at worst they hit the player behind it — and its panes are built in code with no view identifiers, leaving nothing to aim at but coordinates that move with every localization and every pane resize. The four verbs below address it structurally instead: pane by stable identifier, control by the name the pane shows.

```bash
"$V" --debug-cmd settings_open playback                    # by identifier, index or displayed title
"$V" --debug-cmd dump_settings_ui | jq -c '.controls[]|{index,kind,name,state,value}'
"$V" --debug-cmd settings_click "Detect key automatically" on
"$V" --debug-cmd dump_state | jq -e '.settings.analyzeKey' >/dev/null   # assert through the setting, not the pane
"$V" --debug-cmd settings_close
```

`dump_settings_ui` covers the **selected pane only** — switch panes to see another one — and each control carries `kind`, `name`, the row `label` it sits against, `enabled`, a `rect`, and its live value: `state` (on/off/mixed) for a checkbox or radio, `value` + `selected` + `items[]` for a popup, `rows` + `selectedRows` for a list, `value` for a label. `settings_click` replies with that same live value, so the reply alone shows the result.

**Naming.** `settings_click` matches, case-insensitively, a button's own title or the form grid's row label — exactly first, then as a substring, so `"Detect key"` works but `"Detect"` is an error naming both matches. `#3` addresses the dump's index — which is how the **folder list** is reached, since a row label names every control beside it and the Files pane's "Permissions:" therefore names five (its paragraph, the list, and the three buttons, those last three still answering to their own titles). **Quote any name with spaces**: unlike `click_menu`, this verb needs the second token for the value. Popup items match by title *or* by the stable identifier on `represented`, which is how a waveform style, key notation or appearance is chosen without touching localized text: `settings_click Waveform sonic_cirrus`.

What a value means depends on the kind, and the wrong one is an error rather than a silent no-op:

| kind | value | what happens |
| --- | --- | --- |
| `button` | none | `performClick:` |
| `checkbox` | `on`, `off`, `toggle` (default) | the real click path, so `on`/`off` are idempotent — already there replies `action: "unchanged"` |
| `radio` | none, or `on` | same; `off` is refused, since clicking a radio cannot turn one off |
| `popup` | item title, `represented` identifier or `#index` | selects it, then sends the item's own action if it has one (the output devices do), else the button's |
| `pulldown` | same | sends the item's action; `#0` is refused, being the button's title rather than a choice |
| `table` | `2`, `0,3`, `all`, `none` | sets the selection, delegate and all — this is what re-enables Remove |
| `slider` | a number | sets `doubleValue`, then sends the action; the dump carries `value`, `min` and `max` |
| `label` | — | refused: it is a readout, and its text is already in the dump |
| `field` | — | refused: an editable text field has no click path |
| `control` | — | refused: the generic `NSControl` bucket, i.e. a kind the walker does not model yet |

No pane uses a `slider`, a `field` or a bare `control` today. The walker classifies all three anyway, so a pane that gains one is reported honestly rather than skipped — which is the `dump_settings_ui`-first rule above doing its job.

**Traps.**

- **A pane switch animates the window resize** (`kWindowResizeAnimationDuration`, 0.12s), and `settings_open` replies while it is still running — its own `frame` is the mid-flight one, as is any `rect` or screenshot taken in the same breath. `sleep 0.2`, then read `dump_settings_ui`.
- **A sheet blocks everything behind it**, as it does for a real click, so `settings_click` refuses while one is up and `dump_settings_ui` reports it as `sheet`. Only `settings_close` can clear it: it calls `endSheet:` before closing. This matters because **Add Folder and Add Common Folder open a sandbox open panel** that no injection verb can dismiss — powerbox owns it, and the `key*` verbs go to the player.
- Clicking **Set Vibe as Default Music Player** raises a real system confirmation panel, outside the app entirely. Leave it to a human.
- The pane's own `refreshFromSettings` runs on every appearance, so a value changed through the menu bar or the channel shows up in the next `dump_settings_ui` without any nudge.
- Assert the *setting*, through `dump_state.settings`, not just the control: the control moving proves the click landed, the setting proves the action ran.
