# Common/Mac (AppKit side of the store)

**`AppSettings+Mac`** — the macOS half of the store, a category on `AppSettings` (`Common/CLAUDE.md`): every mac-only preference, its identifiers and preset ladders, and the theme store described below. A macOS reader imports `AppSettings+Mac.h` explicitly beside `AppSettings.h`, as it does `AppTheme.h`; the shared `AppSettings.m` reaches this half only through the guarded hooks `AppSettingsInternal.h` declares, and the ivars the half keeps live in that header's class extension because a category cannot declare any.

**`AppTheme`** — one theme, the type the theme system is written in terms of. A theme is a **sparse record** of appearance overrides: a missing field means the default — today's hardcoded look. Records are Foundation/JSON values throughout, colors as `#RRGGBB[AA]`. The record is **flat** — its keys are the accessor names — while a theme **JSON file nests** those fields under the editor's section names, `version` then `name` then `window`/`player`/`info`/`waveform`/`playlist`, each key section-local (`windowCornerRadius` travels as `window.cornerRadius`); `FieldSpecs()` in AppTheme.m is the one schema — one row per field carrying its key, JSON home, default and sanitizer, from which every other table (defaults, known keys, the JSON groups both ways, the color-pair keys) derives — so a field cannot exist without a JSON home or a clamp.

**The built-ins ship as `Resources/Themes/<identifier>.json`** — the filename stem is the stable identifier, the `name` key the English display name, and each file goes through the same `recordFromJSONData:` gate as a user import, so a bundled theme is held to the import's clamps. Adding a built-in is adding a file (the directory is a folder reference in both the app and VibeTests, so no project edit) plus its identifier in `testBuiltInIdentifiers`, the one line of code a theme costs and what keeps a dropped file loud; `testBundledThemesAreValid` is the pull-request gate, and it is load-bearing because the import gate is deliberately tolerant — a typo'd key or bad color is silently dropped, and only the test's sanitizer round-trip makes that loud. Order is `vibe` first, the rest alphabetical by identifier. `vibe.json` must stay field-free — the empty record IS the factory look; that guarantee moved from definitional to **tested** (`testVibeBuiltInIsTheEmptyRecord`), with a hard loader fallback synthesizing the empty record if the file ever goes missing, because `vibe` is the store's snap-back anchor for unknown ids and deleted-active themes. Display names: the JSON's English, overlaid per-language by the hand-managed `ThemeNames` catalog (keyed by identifier) in `AppSettings.displayNameForThemeIdentifier:`. **`defaultArtworkDark`/`defaultArtworkLight`** are the no-artwork placeholder, one per appearance like every color pair — single mode reads and writes the dark slot from either side (`defaultArtworkForDark:`), the light half dormant so a mode flip round-trips. Each value is `""` for the factory record image, `bundled:<name>.<ext>` for a file beside the built-in JSON, or `custom:<sha1>.<ext>` in the container's `Application Support/<bundle id>/ThemeArt` — content-hashed, which is what makes `imageForDefaultArtwork:`'s lifetime cache safe (a changed image is a new key), while bundled art is immutable per build; the record image remains the never-nil fallback for anything missing. `resolvedDefaultArtworkImage` is the pair as ONE image — when the sides differ, a cached dynamic wrapper drawing whichever side the current drawing appearance asks for, the dynamic-color pattern for pixels, so consumers carry no dark flag and an appearance flip re-resolves by itself. A theme naming any default-artwork image exports as a ZIP of `theme.json` plus its image(s) (`archiveDataForRecord:`, the dormant half included); a theme naming none stays plain JSON. **A built-in's `bundled:` image travels too, even though this build ships it** — the archive is the portable form and the build that opens it may not be this one, so exporting only the name would land a built-in on the factory record anywhere else. **Archive entries are named by slot** — `artwork_default_front.<ext>` (dark) and `artwork_default_back.<ext>` (light), with `theme.json` referencing them bare — because where the bytes came from is not the reader's business: a `custom:` content hash and a built-in's `bundled:` resource filename both read as nothing to a person opening the ZIP. Both sides naming one image share its entry, so a single-mode theme ships its bytes once. The prefix is an internal note about where *this build* keeps the image and never travels; `JSONDataForRecord:name:artworkNames:` applies the rename after sanitization, because the sanitizer admits only the prefixed shapes and would drop a bare name. `recordFromJSONOrArchiveData:` takes either form, re-validates and re-hashes each shipped image rather than trusting its name — a reference is read from the raw JSON (the sanitizer has already dropped the bare name), a `custom:`/`bundled:` prefix tolerated for a hand-edited file — and **every archived image lands in the container as `custom:<sha1>`, a built-in's included**, since a slot-named entry says nothing about which build's Resources the bytes started in. A dangling reference in a JSON-only import drops the field. **The file forms are a category, `AppTheme+Archive` — the ZIP codec and the import funnel that takes either form — and `AppThemeInternal.h` is the seam between it and the record**: the two artwork field keys, the bytes a `bundled:`/`custom:` value names (`dataForDefaultArtwork:`, the one read behind the image cache too), the artwork references as WRITTEN in a JSON (`rawDefaultArtworkReferencesInJSONData:`), and the renaming writer above. The ZIP is self-contained: the writer emits stored entries, the reader takes stored and raw-deflate (a hand-made Finder zip), nothing links an archive library. What stays in `AppTheme.m` is the record and nothing else — what each field means, how it is clamped, how it resolves, how it persists as a record and as a theme JSON, and the container files the artwork field names. `technical` and `signal_workshop` are dual-mode exemplars: each spells out both palettes, which is what a `custom` waveform theme forces — an incomplete pair falls back to mono rather than half-applying.

**All sanitization is here, and it is one gate.** `initWithRecord:`, `replaceWithRecord:`, every typed setter, `recordFromJSONData:` and the store's `+sanitizedRecord:` run the same per-field clamps — identifiers snap to their ladders, numbers clamp (radius `[0, kVibeThemeCornerRadiusMax]`, the font sizes to their narrow layout-safe bands), colors must round-trip as hex, bools are numbers only, unknown fields drop (a newer build's export imports as the defaults). So a JSON import, a stored record and a UI edit are held to the same rules by construction. Faces are deliberately **not** validated against installed fonts — `Fonts`' never-nil fallback owns that at resolve time, keeping this class pure and host-lessly testable (`AppThemeTests`).

The **store side lives on `AppSettings`** (three keys, `AppSettings+Mac`): `Appearance.userThemes` (the user themes, flat records plus `id`/`name` — a theme JSON carries the same values nested under the section groups), `Appearance.activeTheme` (the named theme the working state derives from, registered default `vibe`, snapped to `vibe` when it names nothing), and `Appearance.currentTheme` (the persisted **working record**, present only while it diverges from the active theme's own record). `currentTheme` materializes once and is mutated in place; **every field edit funnels through `currentThemeDidChange`** — into the active user theme's record from the same dictionary, so the two cannot drift, or into the divergence key when a read-only built-in is active, which is how a casual toggle (View > Show File Info over the Vibe theme) survives relaunch without dirtying the built-in. Re-applying the theme resets the divergence. The caller then requests the mapped `VibeSettingsLiveEffect`; the store never applies effects.

**Built-in immutability is enforced in the store paths** (`+[AppTheme isBuiltInIdentifier:]` gates every mutation), not by UI disablement alone.

`mode` decides how many color sets a theme has. `dual`, the factory default, keeps a set per appearance — the built-in Vibe theme is dual, its factory look specifying both — and resolves by the appearance the window has. `single` keeps ONE color per field, used in every appearance: the dark-keyed half is the single slot's canonical home, and `colorForBase:dark:`/`setColor:forBase:dark:` force it from either side, so the caller's `forDark:` stops mattering. The light-keyed halves lie dormant under single mode — preserved, never mirrored or consumed — so flipping a theme's mode round-trips both palettes losslessly. The window's own appearance (Auto/Light/Dark) is `AppSettings.windowAppearanceStyle`, not a theme field — but `requiredWindowAppearance` lets a single-mode theme outrank it: the window pins to the dark appearance, the app's native look, so materials and unset defaults stop following the OS and every color the theme sets is literal. nil for dual themes. `AppSettings.windowAppearance` folds the pin in above the stored style and the preview, so the window, the View menu's validation and the Settings toolbar's preview toggle read one answer.

Every color pair is keyed by its exported base name (`kVibeThemeColor*`): `colorForBase:dark:` and `setColor:forBase:dark:` are the slots, the typed `*ColorForDark:` accessors the same slots by name. The four `resolved*Color` accessors are the one home of override-pair-over-semantic-fallback resolution — the label and playlist colors all resolve through them — and `displayColorForBase:dark:` pins any pair to one side for the editor's wells: the override, or what an unset slot draws as, spelled once per pair in `DefaultColorForBase` (the label pairs' semantic fallback resolved under that side, the solid cover, the neutral tint wash, the neutral row fill, Mono's resting levels). It is the only spelling of those constants: the window and playlist covers, the row fills, the editor's wells and the seed a popup writes when it reveals a pair all read it. The pair is captured at call time: an appearance flip re-resolves by itself, a theme change rebuilds whatever holds the color, which is what the `TrackDisplay`/`PlaylistAppearance` effects' guard resets and attribute invalidations are for.

The one-time migration of the pre-theme loose settings (`migrateLooseAppearanceSettingsToTheme`, decided by `+migratedRecordFromLegacyValues:`) runs at `AppSettings` init **before `registerDefaults`** — the ordering is load-bearing, presence checks must not see the registration domain — and consumes the loose keys it migrates, shared-named waveform keys included: that is the Mac store, and iOS is a separate app over a separate one.
