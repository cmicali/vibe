# Common/Mac (AppKit side of the store)

**`AppTheme`** — one theme, the type the theme system is written in terms of. A theme is a **sparse record** of appearance overrides: a missing field means the default — today's hardcoded look. Records are Foundation/JSON values throughout, colors as `#RRGGBB[AA]`. The record is **flat** — its keys are the accessor names — while a theme **JSON file nests** those fields under the editor's section names, `version` then `name` then `window`/`player`/`info`/`waveform`/`playlist`, each key section-local (`windowCornerRadius` travels as `window.cornerRadius`); `ThemeJSONGroups()` in AppTheme.m is the one mapping, asserted at first export to cover every field.

**The built-ins ship as `Resources/Themes/<identifier>.json`** — the filename stem is the stable identifier, the `name` key the English display name, and each file goes through the same `recordFromJSONData:` gate as a user import, so a bundled theme is held to the import's clamps. Adding a built-in is adding a file (the directory is a folder reference in both the app and VibeTests, so no project edit); `testBundledThemesAreValid` is the pull-request gate, and it is load-bearing because the import gate is deliberately tolerant — a typo'd key or bad color is silently dropped, and only the test's sanitizer round-trip makes that loud. Order is `vibe` first, the rest alphabetical by identifier. `vibe.json` must stay field-free — the empty record IS the factory look; that guarantee moved from definitional to **tested** (`testVibeBuiltInIsTheEmptyRecord`), with a hard loader fallback synthesizing the empty record if the file ever goes missing, because `vibe` is the store's snap-back anchor for unknown ids and deleted-active themes. Display names: the JSON's English, overlaid per-language by the hand-managed `ThemeNames` catalog (keyed by identifier) in `AppSettings.displayNameForThemeIdentifier:`. **`defaultArtworkDark`/`defaultArtworkLight`** are the no-artwork placeholder, one per appearance like every color pair — single mode reads and writes the dark slot from either side (`defaultArtworkForDark:`), the light half dormant so a mode flip round-trips. Each value is `""` for the factory record image, `bundled:<name>.<ext>` for a file beside the built-in JSON, or `custom:<sha1>.<ext>` in the container's `Application Support/ThemeArt` — content-hashed, which is what makes `imageForDefaultArtwork:`'s lifetime cache safe (a changed image is a new key), while bundled art is immutable per build; the record image remains the never-nil fallback for anything missing. `resolvedDefaultArtworkImage` is the pair as ONE image — when the sides differ, a cached dynamic wrapper drawing whichever side the current drawing appearance asks for, the dynamic-color pattern for pixels, so consumers carry no dark flag and an appearance flip re-resolves by itself. A custom-art theme exports as a ZIP of `theme.json` plus its image(s) (`archiveDataForRecord:`, the dormant half included); `recordFromJSONOrArchiveData:` takes either form, re-validates and re-hashes each shipped image rather than trusting its name — an archived image reference may be a raw entry basename, `custom:` prefix optional (resolved from the raw JSON, since the sanitizer admits only the stored `custom:<sha1>` shape), and is normalized to the stored form — and drops a dangling reference from a JSON-only import. The ZIP is self-contained in AppTheme.m: the writer emits stored entries, the reader takes stored and raw-deflate (a hand-made Finder zip), nothing links an archive library. `technical` and `signal_workshop` are dual-mode exemplars: each spells out both palettes, which is what a `custom` waveform theme forces — an incomplete pair falls back to mono rather than half-applying.

**All sanitization is here, and it is one gate.** `initWithRecord:`, `replaceWithRecord:`, every typed setter and `recordFromJSONData:` run the same per-field clamps — identifiers snap to their ladders, numbers clamp (radius `[0, kVibeThemeCornerRadiusMax]`, the font sizes to their narrow layout-safe bands), colors must round-trip as hex, bools are numbers only, unknown fields drop (a newer build's export imports as the defaults). So a JSON import, a stored record and a UI edit are held to the same rules by construction. Faces are deliberately **not** validated against installed fonts — `Fonts`' never-nil fallback owns that at resolve time, keeping this class pure and host-lessly testable (`AppThemeTests`).

The **store side lives on `AppSettings`** (three keys, macOS block): `Appearance.userThemes` (the user themes, flat records plus `id`/`name` — a theme JSON carries the same values nested under the section groups), `Appearance.activeTheme` (the named theme the working state derives from, registered default `vibe`, snapped to `vibe` when it names nothing), and `Appearance.currentTheme` (the persisted **working record**, present only while it diverges from the active theme's own record). `currentTheme` materializes once and is mutated in place; **every field edit funnels through `currentThemeDidChange`** — into the active user theme's record from the same dictionary, so the two cannot drift, or into the divergence key when a read-only built-in is active, which is how a casual toggle (View > Show File Info over the Vibe theme) survives relaunch without dirtying the built-in. Re-applying the theme resets the divergence. The caller then requests the mapped `VibeSettingsLiveEffect`; the store never applies effects.

**Built-in immutability is enforced in the store paths** (`+[AppTheme isBuiltInIdentifier:]` gates every mutation), not by UI disablement alone.

`mode` decides how many color sets a theme has. `dual`, the factory default, keeps a set per appearance — the built-in Vibe theme is dual, its factory look specifying both — and resolves by the appearance the window has. `single` keeps ONE color per field, used in every appearance: the dark-keyed half is the single slot's canonical home, and `colorForBase:dark:`/`setColor:forBase:dark:` force it from either side, so the caller's `forDark:` stops mattering. The light-keyed halves lie dormant under single mode — preserved, never mirrored or consumed — so flipping a theme's mode round-trips both palettes losslessly. The window's own appearance (Auto/Light/Dark) is `AppSettings.windowAppearanceStyle`, not a theme field — but `requiredWindowAppearance` lets a single-mode theme outrank it: the window pins to the dark appearance, the app's native look, so materials and unset defaults stop following the OS and every color the theme sets is literal. nil for dual themes.

The four `resolved*Color` accessors are the one home of override-pair-over-semantic-fallback resolution — the label and playlist colors all resolve through them, and the `display*ColorForDark:` accessors beside them pin the same slots to one side for the editor's wells. The pair is captured at call time: an appearance flip re-resolves by itself, a theme change rebuilds whatever holds the color, which is what the `TrackDisplay`/`PlaylistAppearance` effects' guard resets and attribute invalidations are for.

The one-time migration of the pre-theme loose settings (`migrateLooseAppearanceSettingsToTheme`, decided by `+migratedRecordFromLegacyValues:`) runs at `AppSettings` init **before `registerDefaults`** — the ordering is load-bearing, presence checks must not see the registration domain — and consumes the loose keys it migrates, shared-named waveform keys included: that is the Mac store, and iOS is a separate app over a separate one.
