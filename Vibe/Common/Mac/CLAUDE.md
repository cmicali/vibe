# Common/Mac (AppKit side of the store)

**`AppTheme`** — one theme, the type the theme system is written in terms of. A theme is a **sparse record** of appearance overrides: a missing field means the default — today's hardcoded look — which is what makes the built-in `vibe` theme the empty record, definitionally unable to drift from the factory appearance, and `industrial` exactly its four overrides. Records are Foundation/JSON values throughout, colors as `#RRGGBB[AA]`.

**All sanitization is here, and it is one gate.** `initWithRecord:`, `replaceWithRecord:`, every typed setter and `recordFromJSONData:` run the same per-field clamps — identifiers snap to their ladders, numbers clamp (radius `[0, kVibeThemeCornerRadiusMax]`, the font sizes to their narrow layout-safe bands), colors must round-trip as hex, bools are numbers only, unknown fields drop (a newer build's export imports as the defaults). So a JSON import, a stored record and a UI edit are held to the same rules by construction. Faces are deliberately **not** validated against installed fonts — `Fonts`' never-nil fallback owns that at resolve time, keeping this class pure and host-lessly testable (`AppThemeTests`).

The **store side lives on `AppSettings`** (three keys, macOS block): `Appearance.userThemes` (the user themes, flat records plus `id`/`name` — the same shape a theme JSON carries minus the version), `Appearance.activeTheme` (the named theme the working state derives from, registered default `vibe`, snapped to `vibe` when it names nothing), and `Appearance.currentTheme` (the persisted **working record**, present only while it diverges from the active theme's own record). `currentTheme` materializes once and is mutated in place; **every field edit funnels through `currentThemeDidChange`** — into the active user theme's record from the same dictionary, so the two cannot drift, or into the divergence key when a read-only built-in is active, which is how a casual toggle (View > Show File Info over the Vibe theme) survives relaunch without dirtying the built-in. Re-applying the theme resets the divergence. The caller then requests the mapped `VibeSettingsLiveEffect`; the store never applies effects.

**Built-in immutability is enforced in the store paths** (`+[AppTheme isBuiltInIdentifier:]` gates every mutation), not by UI disablement alone.

`appearance` decides whether a theme is dual-mode or single-look: `system` tracks the OS light/dark setting with separate colors per mode, `light`/`dark` pin the main window (`resolvedWindowAppearance` — nil, aqua or darkAqua). The factory default is `dark`, the same pinned-dark window the pre-theme app registered, so the empty record still launches identically. **A pinned theme's color pairs are mirrored** — `mirrorColorPairsIfPinned` runs in the record gate and `setAppearance:`, and the color setters write both halves — so a single-look theme genuinely has one color set: flipping its base carries the colors, and entering single-look adopts what the pinned side showed, absence included (the other half's data is consumed, not archived).

`+dynamicColorWithDark:light:fallback:` is the one home of override-pair-over-semantic-fallback resolution — the label and playlist colors all resolve through it. The pair is captured at call time: an appearance flip re-resolves by itself, a theme change rebuilds whatever holds the color, which is what the `TrackDisplay`/`PlaylistAppearance` effects' guard resets and attribute invalidations are for.

The one-time migration of the pre-theme loose settings (`migrateLooseAppearanceSettingsToTheme`, decided by `+migratedRecordFromLegacyValues:`) runs at `AppSettings` init **before `registerDefaults`** — the ordering is load-bearing, presence checks must not see the registration domain — and consumes the loose keys it migrates, shared-named waveform keys included: that is the Mac store, and iOS is a separate app over a separate one.
